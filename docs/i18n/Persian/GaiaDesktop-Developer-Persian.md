## نگاهی کوتاه به ماژول

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

یک کلاینت برای کتابخانهٔ هسته و نه بیشتر. **هیچ دانشی از GS1** در آن نهفته نیست: هر تعریف AI، قاعدهٔ اعتبارسنجی،
پیام خطا و توضیح بومی‌شده از [`GaiaParser`](../../../../gaia/docs/GaiaParser.md) و
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md) می‌آید. به‌ویژه فهرست AIها هرگز در این ماژول کپی نمی‌شود —
انتخابگر سازنده رجیستری خود هسته را می‌خواند، پس نمی‌تواند AIای پیشنهاد دهد که سازنده آن را رد کند.

**نقاط ورود:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (همان `Application` در JavaFX) و
`tools.pantheum.gaia.desktop.Launcher` (مقدار `Main-Class` در jar بسته‌بندی‌شده).

این ماژول یک برگ است: هیچ چیز به آن وابسته نیست و خودش هم به هیچ ماژول پایین‌دستی دیگری وابسته نیست.

## ساخت و اجرا

- **Java 21** برای اجرا و JDK 21 یا جدیدتر برای ساخت — ماژول با `release=21` کامپایل می‌شود. JavaFX 21 خط LTS متناظر
  است. jar هسته هنوز بایت‌کد Java 11 است و بدون تغییر روی 21 اجرا می‌شود.
- **Maven** روی `PATH`. در این مخزن wrapper وجود ندارد.
- **اول هسته را نصب کنید.** این ماژول `gaia:1.1.0` را از `~/.m2` می‌گیرد؛ jar کهنه یا ناموجود هسته علت معمول
  `package tools.pantheum.gaia does not exist` است.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` تنها آرگومان خط فرمان است و جز `-Dgaia.desktop.home=…` که کل پروفایل را به جای دیگری می‌برد، تنها راه
اثرگذاری بر راه‌اندازی است.

`mvn javafx:run` مسیر توسعه است: افزونه JavaFX را روی **مسیر ماژول** می‌گذارد، پس جعبه‌ابزار به‌صورت ماژول نام‌دار آغاز
می‌شود و `GaiaDesktopApp` را می‌توان مستقیم اجرا کرد. jar بسته‌بندی‌شده چنین کاری نمی‌تواند — همه چیز روی مسیر کلاس است —
و به همین دلیل `Main-Class` آن لایهٔ میانی `Launcher` است. در آن چیدمان، زیرکلاسی از `Application` به‌عنوان
`Main-Class` با پیام *"JavaFX runtime components are missing"* شکست می‌خورد.

همیشه از `clean` استفاده کنید — یک بار، پیش از ساختن مجموعه‌ای از سکوها، چون `target/dist/` را از همهٔ آن‌ها خالی
می‌کند. برای دلیلش [عیب‌یابی ساخت](#عیبیابی-ساخت) را ببینید.

### بسته‌بندی

هر چیز قابل ارسال زیر `target/dist/gaia-desktop-<version>-<platform>/` گرد می‌آید و هیچ چیز دیگری آنجا نیست، تا بتوان پوشه
را یکجا zip یا کپی کرد بی‌آنکه لازم باشد مصنوعات را از میان `classes/`، `maven-status/` و باقی فایل‌های موقت ساخت در
`target/` جدا کرد. `${dist.dir}` آن را یک بار نام‌گذاری می‌کند؛ هر افزونه‌ای که مصنوعی می‌نویسد به آن اشاره می‌کند.

#### یک ساخت برای هر سکو

jarهای JavaFX کد بومی دارند، پس هر توزیع برای یک سکوست که ویژگی `fx.platform` آن را به‌عنوان طبقه‌بند OpenJFX نام
می‌برد: `mac-aarch64`، `mac`، `win`، `linux` یا `linux-aarch64`. پنج پروفایل `fx-*` که بر اساس سیستم‌عامل فعال
می‌شوند، آن را روی سکوی خود ماشین سازنده تنظیم می‌کنند، و این همهٔ چیزی است که `mvn package` یا `mvn javafx:run` ساده
لازم دارد؛ `-Dfx.platform=…` بر آن‌ها مقدم است تا هر سکوی دیگری را از هر ماشینی بسازد — jarهای JavaFX فقط دانلود
هستند. `${dist.dir}` برابر `target/dist/${fx.platform}` است، پس ساخت یک سکو هرگز روی ساخت سکوی دیگر نمی‌نویسد.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

دو جزئیات در pom این کار را ممکن می‌کنند و هر دو به نظر حذف‌شدنی می‌آیند:

- **هر ماژول JavaFX یک وابستگی مستقیم است** — base، graphics، controls، media و web — هر کدام با
  `<classifier>${fx.platform}</classifier>` و یک استثنای `org.openjfx:*`. pomهای OpenJFX jarهای ترایایی خود را بر
  اساس سیستم‌عامل *ماشین سازنده* انتخاب می‌کنند، پس اگر بگذارید graphics یا base به‌صورت ترایایی بیایند، کتابخانه‌های
  بومی Mac در کنار کتابخانه‌های بومی Windows وارد ساخت Windows می‌شوند.
- **ویژگی `fx.platform` است، نه `javafx.platform`.** اگر ویژگی خود OpenJFX را از بیرون تنظیم کنید، pom والدش آن را بر
  حسب خودش بازتعریف می‌کند؛ Maven آن pom را نامعتبر می‌داند و jarهای سکو را بی‌صدا کنار می‌گذارد و ساختی بی‌هیچ
  JavaFX باقی می‌ماند.

هر دو چیدمان یک مسیر را می‌نویسند، `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`، و در هر ساخت دقیقاً
یکی از آن‌ها اجرا می‌شود. `${jar.phase}`، `assembly.skipAssembly` و `mdep.skip` هستند که نمی‌گذارند هر دو آن را از آن
خود کنند.

| | پیش‌فرض | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | حدود 290 KB — فقط کلاس‌ها و منابع همین ماژول | حدود 50 MB — وابستگی‌ها درونش باز شده‌اند |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 jar که یکی‌یکی در `Class-Path` مانیفست نام برده شده‌اند | — |
| آنچه ارسال می‌شود | jar **و** `lib/` کنارش | یک فایل |
| همچنین در `dist/gaia-desktop-<version>-<platform>/` | `run.bat` (win) یا `run.sh` (بقیه) | همان |
| و | `readme.html` و `docs/` (همهٔ سکوها) | همان |

هر توزیع راهنماها را هم دارد: `docs/` با حفظ چیدمانش کپی می‌شود تا پیوندهای میان راهنماها و ترجمه‌ها کار کنند، بجز
ابزارهای ترجمه (`check-i18n.py`، `i18n-manifest.json`)؛ و `readme.html` در ریشه، نمایه‌ای که به هر
کدام پیوند می‌دهد، برگرفته از `src/main/dist/readme.html` که `@VERSION@` در آن با نسخهٔ pom جایگزین می‌شود. هر دو را
گام antrun به نام `pick-launch-script` می‌نویسد که اول `docs/` را پاک می‌کند تا راهنمای حذف‌شده باقی نماند. پیوندهای
readme دستی نوشته شده‌اند — راهنمایی که زیر `docs/` تغییر نام بدهد یا ترجمه‌ای که اضافه شود، در آنجا هم به سطر خودش نیاز
دارد.

`Class-Path` مانیفست و `lib/` دو نیمهٔ یک چیزند: jar برای هر وابستگی زمان اجرا `lib/<artifact>-<version>.jar` را نام
می‌برد و `copy-dependencies` پوشهٔ `lib/` را دقیقاً با همین نام‌ها پر می‌کند. همین است که `java -jar` را به کار
می‌اندازد.

#### برنامه macOS و فایل zip توزیع

یک اجرای antrun، `mac-app-and-zip`، مرحلهٔ `package` را به پایان می‌برد. به همین دلیل افزونهٔ antrun **پس از** افزونه‌های
jar و assembly اعلان شده است — Maven اجراهای یک مرحله را به ترتیب اعلان افزونه‌ها اجرا می‌کند — تا وقتی اجرا می‌شود،
jar در هر دو بسته‌بندی وجود داشته باشد. (اجرای دیگرش، `pick-launch-script`، در `prepare-package` است و تأثیری
نمی‌پذیرد.)

برای `mac` و `mac-aarch64` ابتدا `GAIA Desktop.app` را در پوشهٔ توزیع می‌سازد: `Info.plist` (با جایگزینی `@VERSION@`
با نسخهٔ pom)، راه‌انداز `Contents/MacOS/gaia-desktop` (اجرایی‌شده) و `gaia-desktop.icns`، همه از `src/main/macos/`، سپس
`gaia-desktop.jar` و `lib/` را به `Contents/Java` **منتقل** می‌کند تا بسته مستقل بایستد. `run.sh` وقتی jarی کنارش نباشد
آنجا را می‌گردد. راه‌انداز Java را بر اساس نسخه پیدا می‌کند (`java_home -v 21+`، سپس openjdk از Homebrew — اجرا از
Finder نه `JAVA_HOME` را می‌بیند نه `PATH` را)، اگر چیزی نیابد با `osascript` پنجرهٔ گفتگو نشان می‌دهد، به
`~/.gaia-desktop` می‌رود (`cd`) تا مسیر نسبی `logs/` در logback قابل نوشتن باشد، و `-Xdock:name`/`-Xdock:icon` را
می‌فرستد. macOS فرایند `java` در حال اجرا را به بسته پیوند می‌دهد (شناسهٔ بسته و نماد Dock از آنِ برنامه است)؛ نوار منو
GAIA Desktop را نشان می‌دهد.

سپس برای هر سکو، پوشه را با `<zip>` در Ant زیر پوشه‌ای هم‌نام در `target/dist/gaia-desktop-<version>-<platform>.zip`
فشرده می‌کند: `run.sh` و `Contents/MacOS/**` به‌صورت مجموعه‌فایلی جداگانه با `filemode="755"`، وگرنه پس از باز شدن
قابل اجرا نخواهند بود. فایل zip **پیوست نمی‌شود**: برای انتشارهای GitHub است، و چهار سکو از چهار ساخت می‌آیند که Maven
Central — با یک بارگذاری تغییرناپذیر برای هر نسخه — هرگز نمی‌تواند آن‌ها را یک انتشار بپذیرد.

`project.build.outputTimestamp` روی زمان ساخت تنظیم می‌شود. وگرنه بایگانی‌کننده‌های maven-jar-plugin 3.5 و
maven-assembly-plugin 3.8 تاریخ هر مدخل را 1 فوریهٔ 1980 می‌گذارند.

نماد برنامه را `tools/icon/GaiaIcon.java` می‌کشد (بخشی از ساخت نیست؛ سرآیندش گام‌های `sips`/`iconutil` را دارد).
خروجی‌هایش در مخزن ثبت شده‌اند: `src/main/macos/gaia-desktop.icns` برای بسته، و
`src/main/resources/icons/gaia-desktop-{16..256}.png` که `GaiaDesktopApp` آن‌ها را نماد پنجره قرار می‌دهد (Windows و
Linux؛ macOS نمادهای پنجره را نادیده می‌گیرد).

#### اسکریپت‌های اجرا

`run.sh` و `run.bat` از `src/main/scripts/` می‌آیند و بدون پالایش در `dist/gaia-desktop-<version>-<platform>/` کپی
می‌شوند — `run.sh` پر از بسط‌های پوستهٔ `${...}` است که پالایش Maven ممکن است دلبخواه بازنویسی‌شان کند. سپس یک گام
antrun فقط همانی را نگه می‌دارد که سکو اجرا می‌کند — `run.bat` برای `win` و `run.sh` برای بقیه — و بیت اجرایی را روی
`run.sh` می‌گذارد، چون `copy-resources` آن را منتقل نمی‌کند. تصمیم را از `${fx.platform}` حل‌شده می‌گیرد نه از راه
پروفایل‌ها، چون فعال‌سازی پروفایل نمی‌تواند مقداری را ببیند که پروفایل دیگری تنظیم کرده است: وگرنه ساخت Linuxای که روی
Windows انجام شود اسکریپت میزبان را می‌گرفت.

این اسکریپت‌ها **به مانیفست تکیه نمی‌کنند**. هر کدام مسیر کلاس را خودش می‌سازد: `gaia-desktop.jar` و سپس هر `.jar` در
`lib/`، یکی‌یکی نام‌برده به‌جای سپردن به نویسهٔ عام `lib/*`، تا مسیری که فاصله دارد یک مدخل بماند و شمار افزوده‌ها واقعی
باشد. اجرا با `-cp` دلیل آن است که `tools.pantheum.gaia.desktop.Launcher` را صریح نام می‌برند: `-cp` مقدار `Main-Class`
مانیفست را نمی‌خواند. اما **همچنان** از `Class-Path` آن پیروی می‌کند — jar روی `-cp` jarهایی را که مانیفستش نام برده
همراه می‌آورد که بلافاصله پس از آن جستجو می‌شوند — پس هر jar در `lib/` بارگذاری می‌شود، چه اسکریپت فهرستش کند چه نه، و
کنار گذاشتن یکی از مسیر کلاس اسکریپت آن را بیرون از JVM نگه نمی‌دارد. اسکریپت‌ها با این حال همه را فهرست می‌کنند تا jarی
که مانیفستش کهنه، دستی ویرایش‌شده یا یک مدخل کم دارد هم اجرا شود. همین یک اسکریپت به هر دو بسته‌بندی خدمت می‌کند: jar
`-Pfat` پوشهٔ `lib/`ای برای افزودن ندارد و نیازی هم ندارد، و به همین دلیل `lib/` خالی یک یادداشت است نه خطا.

#### کتابخانه‌های بومی Zebra

ساخت هیچ چیزی از Zebra را ارسال نمی‌کند — نه DLL، نه jar سرویس. در Windows این‌ها از Scanner SDK زبرا که روی ماشین نصب
است می‌آیند: `run.bat` jarهای سرویس `Jpos*.jar` و `bin\` آن را به مسیر کلاس و `bin\` را به `PATH` می‌افزاید، جایی که
`System.loadLibrary` فایل‌های `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` را پیدا می‌کند (مقدار پیش‌فرض
`java.library.path` همان `PATH` است). API ‏JavaPOS و بارگذار پیکربندی‌اش همیشه از `lib\javapos-*.jar` می‌آیند، چه SDK
باشد چه نباشد.

**`run.bat` هرگز jar خود JavaPOS در SDK را اضافه نمی‌کند**، یعنی `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`. زمانی
این کار را می‌کرد و برای پرهیز از دو نسخه از API، `lib\javapos-*.jar` را کنار می‌گذاشت — اما `Class-Path` مانیفست به هر
حال آن‌ها را بار می‌کرد (بالا را ببینید)، پس JVM هر دو را گرفت: کلاس‌های بارگذار 4.x از `lib\`، و در کنارشان
`jpos/res/jpos.properties` و `jcl.xsd` از `javaPOS114.jar`. آن فایل ویژگی‌ها باعث می‌شود
[`JposConfig`](#یکپارچهسازی-اسکنر) کنار بکشد، و آن `jcl.xsd` فقط نسخه‌های JavaPOS تا 1.10 را می‌پذیرد، پس هر مدخل
`jpos.xml` (1.12–1.14) در اعتبارسنجی رد شد، رجیستری خالی ماند و هر اتصال پیش از رسیدن به اسکنر با خطای 109 شکست خورد.
صرف بودن آن jar روی مسیر کلاس برای این کافی است، حتی اگر پشت jarهای `lib\` باشد. jarهای سرویس Zebra بدون تغییر روی
API ‏1.14 از `lib\` اجرا می‌شوند — باز کردن، تصاحب و اسکن به همین شکل با یک اسکنر واقعی تأیید شده‌اند. DLLهایی که دستی
کنار `run.bat` گذاشته شوند هنوز پذیرفته می‌شوند: آنگاه اسکریپت `-Djava.library.path=<dist>;%PATH%` را تنظیم می‌کند و
`PATH` را به انتها می‌افزاید، چون این ویژگی مسیر جستجوی پیش‌فرض را به‌کلی جایگزین می‌کند.

`mvn javafx:run` هیچ‌کدام از این کارها را نمی‌کند، پس تصاحب اسکنر از یک اجرای توسعه در Windows نیاز دارد که jarهای SDK
روی مسیر کلاس و `bin\` آن روی `PATH` با روش دیگری قرار گیرند؛ برای این کار از `dist/` اجرا کنید.

فراتر از مسیر کلاس، این اسکریپت‌ها کارهایی را بر عهده دارند که `java -jar` انجام نمی‌دهد: حل کردن پوشهٔ خودشان تا از هر
پوشهٔ کاری کار کنند، ترجیح `JAVA_HOME` بر `PATH`، و رد کردن JVM پیش از 11 با جمله‌ای که راه‌حل را می‌گوید به‌جای
`UnsupportedClassVersionError`. `GAIA_DESKTOP_OPTS` گزینه‌های JVM را عبور می‌دهد. `run.bat` از `java.exe` استفاده
می‌کند نه `javaw.exe`، تا کنسول باز بماند — Windows تنها سکویی است که اسکنر در آن اجرا می‌شود و وضعیت آن و خطاهای
JavaPOS به آنجا می‌روند.

`run.bat` همچنین Java، JavaFX و سرویس‌های Zebra را از آنچه پیدا می‌کند انتخاب می‌کند — یک `jdk*\` همراه، یک
`javafx-sdk*\lib\` روی مسیر ماژول، Scanner SDK زبرا در `ZEBRA_HOME` — وقتی از JavaFX ‏SDK استفاده می‌کند نسخه‌های
JavaFX در `lib\` را بیرون از مسیر کلاس می‌گذارد، و تجزیه‌گر SAX ‏JDK، پروکسی‌ها و مخزن اعتماد Windows، و
`--enable-native-access` را روی Java 17+ می‌فرستد. جدول آن در بخش
[What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows) در README است. پایان خط‌های CRLF این
فایل را نگه دارید: `cmd.exe` ممکن است در فایل دسته‌ای فقط-LF یک `call :label` را از دست بدهد. `run.sh` هم
`--enable-native-access=ALL-UNNAMED` را می‌فرستد — JavaFX کتابخانه‌های بومی خودش را از `lib/` بار می‌کند و وقتی JavaFX
روی مسیر کلاس است، `ALL-UNNAMED` ماژولی است که آن را پوشش می‌دهد — و مانند `run.bat` تنها وقتی نسخهٔ Java خوانده نشود
نادیده گرفته می‌شود.

هر دو چیدمان کتابخانه‌های بومی JavaFX **یک سکو**، یعنی `${fx.platform}`، را دارند، پس هیچ‌کدام میان سیستم‌عامل‌ها یا
معماری‌ها قابل جابه‌جایی نیست. برای هر هدف یک بار بسازید — [یک ساخت برای هر سکو](#یک-ساخت-برای-هر-سکو) را ببینید.

> **Eclipse.** اجرای `copy-dependencies` یک دستور `<?m2e ignore?>` دارد. m2e پروژهٔ باز فضای کار را به پوشهٔ
> `target/classes` آن حل می‌کند نه به یک jar، و `copy-dependencies` از کپی کردن مصنوع بسته‌بندی‌نشده سر باز می‌زند
> (MDEP-187)، که هر وقت پروژهٔ `gaia` کنار این پروژه باز باشد ساخت خودکار را شکست می‌دهد. نتیجه این است که ساختی که فقط
> در IDE انجام شود پوشهٔ `target/dist/gaia-desktop-<version>-<platform>/lib/` را پر نمی‌کند؛ پیش از استفاده از خود jar،
> `mvn package` را اجرا کنید.

### قیف ورودی

هر ورودی — تایپ‌شده، چسبانده‌شده، بازشده از فایل، اسکن‌شده یا ساخته‌شده — از یک متد،
`MainView.capture(String, ScanSource, String)`، به تجزیه‌گر می‌رسد.

این همان تک تصمیم طراحی است که کل برنامه حول آن ساخته شده. ساخت به گزارش، تاریخچه یا مسیر خروجی جداگانه‌ای نیاز ندارد،
چون پس از قیف، رشتهٔ ساخته‌شده از رشتهٔ اسکن‌شده قابل تمایز نیست. هر چیز تازه‌ای که ورودی تولید می‌کند باید از درون آن
بگذرد نه از کنارش.

### نخ‌ها

| نخ | چه اجرا می‌کند |
|---|---|
| نخ برنامهٔ JavaFX | همهٔ تجزیه، نمایش و رابط کاربری. وقتی جدول‌های AI گرم شدند، تجزیه کمتر از یک میلی‌ثانیه طول می‌کشد، پس نیازی به نخ کارگر نیست |
| `gaia-scanner` | هر فراخوانی به اسکنر — باز کردن، تصاحب، فعال‌سازی، غیرفعال‌سازی، رها کردن، بستن. یک نخ بلندعمر متعلق به `ScannerService`؛ [یکپارچه‌سازی اسکنر](#یکپارچهسازی-اسکنر) را ببینید |
| نخ رویداد JavaPOS | فراخوان‌های برگشتی `ScannerService`. `MainView.FxScannerListener` هر کدام را با `Platform.runLater` منتقل می‌کند |
| پس‌زمینه | انتظار برای `connect()` / `disconnect()` اسکنر (تصاحب ممکن است تا 5 ثانیه طول بکشد)، بازیابی تاریخچهٔ ذخیره‌شده هنگام راه‌اندازی — که گرم‌کردن تجزیه‌گر هم هست — و بررسی به‌روزرسانی (`gaia-update-check`، یک درخواست GitHub، نتیجه با `Platform.runLater` برگردانده می‌شود) |

**هرگز گزینش یک کنترل را از درون رویداد گزینش خودش تغییر ندهید و کنترل را هم از بین نبرید.** سه فروپاشی جداگانه در این
برنامه دقیقاً از همین آمدند: بازنشانی انتخابگر AI درون `clearAndSelect` خود پنجرهٔ بازشو (یک
`IndexOutOfBoundsException` از `ListViewBehavior`)، و بازسازی پنلی که جعبهٔ انتخاب زبان را دارد از درون گرداننده خود
همان جعبه. هر دو اکنون با `Platform.runLater` به تعویق می‌افتند و دلایل در هر دو محل فراخوانی ثبت شده‌اند.

### بازسازی در برابر برچسب‌گذاری دوباره

تغییر زبان، قاب رابط را — منوها، نوار ابزار، پنل گزینه‌ها — از روی فهرست **بازسازی** می‌کند، و این امن است چون هیچ‌کدام
وضعیتی ندارند: `OptionsPane` نمای دوسویه‌ای از `ParseOptions` است، پس مقدارها در مدل زندگی می‌کنند و پنل تازه فوراً
آن‌ها را برمی‌دارد.

کنترل‌هایی که **دادهٔ کاربر** را نگه می‌دارند فیلدند و به‌جای آن در جای خود برچسب تازه می‌گیرند:
`BuilderPane.retext(UiStrings)` سطرهای AI، فیلدهای Digital Link و گزینش را حفظ می‌کند. بازسازی‌اش کار در جریان را دور
می‌ریخت — که یک بار هم چنین کرد.

## توکن {GS}

`TextField` در JavaFX هر نویسهٔ زیر `0x20` را بی‌صدا دور می‌اندازد (`TextInputControl.filterInput`). نه اینکه «عجیب
نمایشش دهد» — حذفش می‌کند. تایپ، چسباندن، `setText` و `insertText` همه متأثرند، پس `setText("01…" + GS + "10LOT")`
نتیجهٔ `"01…10LOT"` را می‌دهد: رشتهٔ عنصری که معنایش بی‌صدا عوض شده، چون AI طول‌متغیر اکنون آنچه را پس از آن آمده می‌بلعد.

`desktop.parse.GsToken` همهٔ پاسخ است. جداکننده در رابط به‌صورت متن لفظی `{GS}` جابه‌جا می‌شود و در مسیر رسیدن به
تجزیه‌گر دوباره `0x1D` می‌شود. این توکن اینجا اختراع نشده — دقیقاً همان شکلی است که `ASCIIRevealerUtils.printable` در
هسته `0x1D` را با آن نشان می‌دهد، پس مقداری که از گزارش کپی شود مستقیم در نوار ورودی چسبانده می‌شود.

یک پالایهٔ `TextFormatter` روی فیلد ورودی هر راهی را که متن ممکن است از آن برسد می‌گیرد — تایپ، ⌘V، منوی زمینه،
کشیدن و رها کردن، `setText` — و به همین دلیل بازنویسی آنجا قرار دارد نه در هر گرداننده.

مسیر اسکنر هرگز از `GsToken` نمی‌گذرد: اسکن‌ها به‌صورت بایت به تجزیه‌گر می‌رسند.

## یکپارچه‌سازی اسکنر

`ScannerService` مالک کنترل `Scanner` در JavaPOS است: باز کردن ← تصاحب ← فعال‌سازی، و پس از هر اسکن رویداد داده را
دوباره مسلح می‌کند. نام‌های منطقی دستگاه از `src/main/resources/jpos.xml` می‌آیند.

**هر فراخوانی دستگاه روی یک نخ، `gaia-scanner`، اجرا می‌شود که تا وقتی سرویس هست زنده است** — هرگز روی نخ FX، و هرگز
روی نخی که پس از فراخوانی پایان می‌یابد. سرویس Zebra از راه JNI و از طریق CoreScanner COM API به اسکنر می‌رسد، و COM
آنچه را راه می‌اندازد به آپارتمان نخ فراخواننده می‌بندد: روی نخی باز کنید که بعد پایان می‌یابد، اسکنر تصاحب می‌شود ولی
خاموش می‌ماند؛ روی نخ دیگری ببندید، آپارتمان اشتباه از حالت آماده خارج می‌شود. بستن روی نخ FX بدترین حالت است، چون
JavaFX آنجا `OleInitialize` را فرا می‌خواند و هدف رها کردن هر پنجره را در برابر آن ثبت می‌کند — یک `CoUninitialize`
روی آن کشیدن و رها کردن را در کل برنامه از کار می‌اندازد. این ویژگی JavaFX روی Windows است، نه یک نسخهٔ خاص JavaFX.
`connect()` و `disconnect()` کار را به آن نخ می‌سپارند و منتظر می‌مانند، پس `MainView` هر دو را از یک نخ پس‌زمینهٔ
کوتاه‌عمر فرا می‌خواند.

دو قاعده نمی‌گذارند دستگاهی بدرفتار اتصال را گیر بیندازد. **برچیدن هرگز زود متوقف نمی‌شود:** `closeQuietly`
غیرفعال‌سازی، رها کردن و بستن را گام‌های جداگانه انجام می‌دهد، فقط وقتی تصاحب برقرار است رها می‌کند و همیشه `close()`
را امتحان می‌کند — پس از تصاحب ناموفق، `release()` خطای «not claimed» می‌دهد، و وقتی گام‌ها یک `try` مشترک داشتند،
همین بستن را جا می‌انداخت و دستگاه را در سرویس Zebra باز می‌گذاشت. **رویداد داده درون `finally` دوباره مسلح می‌شود:**
JavaPOS پس از هر رویداد آن را غیرفعال می‌کند، پس خواندن یا گرداننده‌ای که استثنا پرتاب کند هم باید دوباره مسلح کند،
وگرنه اسکنر تا اتصال دوباره خاموش می‌ماند. `ScannerLifecycleTest` هر دو را در برابر یک `jpos.Scanner` اسکریپت‌شده
می‌آزماید.

**`JposConfig` پیش از نخستین باز کردن، JavaPOS را به `jpos.xml` همراه برنامه هدایت می‌کند.** با jarهای JavaPOS از
Maven (`javapos-config-loader` 4.x) و بدون `jpos/res/jpos.properties` روی مسیر کلاس، در غیر این صورت هر باز کردن با
*"Service does not exist in loaded JCL registry"* (خطای 109) شکست می‌خورد، به سه دلیل جداگانه: مدیر سرویس به
`SimpleRegPopulator` برمی‌گردد که یک `jpos.cfg` سریال‌شده می‌خواند و هرگز `jpos.xml` را نمی‌خواند؛ بارگذار XML فقط در
پوشهٔ کاری دنبال `jpos.xml` می‌گردد نه درون jar؛ و Xerces 2.12.2 در `lib/` ویژگی JAXP ‏`accessExternalDTD` را که بارگذار
تنظیم می‌کند رد می‌کند. `JposConfig` مقدارهای `jpos.config.regPopulatorClass` (`JavaxRegPopulator`)،
`jpos.config.populatorFileURL` (همان `jar:file:…!/jpos.xml` خود jar) و `javax.xml.parsers.SAXParserFactory` (از
JDK) را ویژگی سیستم قرار می‌دهد — هرگز مقداری را که پیش‌تر تنظیم شده دست نمی‌زند، پس
`-Djpos.config.populatorFileURL=file:…` هنوز می‌تواند `jpos.xml` دیگری برگزیند — و وقتی `jpos.properties` روی مسیر کلاس
باشد یا بارگذار 4.x نباشد هیچ چیز تنظیم نمی‌کند. `javaPOS114.jar` در Zebra SDK از همین دست است و رجیستری را به‌کلی خراب
می‌کند، و به همین دلیل `run.bat` آن را بیرون از مسیر کلاس نگه می‌دارد — [کتابخانه‌های بومی Zebra](#کتابخانههای-بومی-zebra)
را ببینید. `JposConfigTest` سرتاسر بررسی می‌کند که رجیستری سپس اسکنرهای فایل را در خود دارد.

**انتخابگر دستگاه از همان رجیستری ساخته می‌شود**، نه اینکه به‌صورت فهرستی در کد نگه داشته شود:
`ScannerService.logicalNames()` مدخل‌های بارشده را روی نخ `gaia-scanner` می‌خواند و آن‌هایی را نگه می‌دارد که دستهٔ
دستگاهشان `Scanner` است — دو مدخل ترازو در `jpos.xml` بیرون می‌مانند — به ترتیب `pickerOrder`: اگر فایل
`ZebraAllScanners` را تعریف کند، آن اول است و بقیه به ترتیب الفبا (رجیستری ترتیب فایل را نگه نمی‌دارد). به فایلی که
آن را ندارد اضافه‌اش نمی‌کنند؛ وقتی هیچ چیز بار نشود فقط پیش‌فرض پیشنهاد می‌شود، پس انتخابگر هرگز خالی نیست. `MainView`
پیش‌فرض را بی‌درنگ نشان می‌دهد و فهرست را از یک نخ پس‌زمینه پر می‌کند و گزینش ذخیره‌شده را نگه می‌دارد. پس اسکنری که به
`jpos.xml` افزوده شود — یا یک فایل کامل که با `-Djpos.config.populatorFileURL` نام برده شود — بی‌هیچ تغییری در کد در
انتخابگر پدیدار می‌شود، و `JposConfigTest` انتخابگر را با خواندنی مستقل از فایل همراه برنامه مقایسه می‌کند. سرویس‌هایی که
این مدخل‌ها نام می‌برند کلاس‌های Zebra هستند (`com.zebra.jpos.service.scanner.*Factory`) که هنوز باید روی مسیر کلاس
باشند — از Scanner SDK از راه `run.bat`، یا jarهای سرویس Zebra که در `lib\` گذاشته شوند.

دادهٔ اسکن به‌صورت **ISO-8859-1** رمزگشایی می‌شود تا هر بایت یک‌به‌یک نگاشت شود و هم پیشوند AIM Code ID و هم هر `0x1D`
سالم بمانند؛ گزارش‌ها با UTF-8 نوشته می‌شوند.

هیچ چیزی در سرویس متنی برای کاربر نمی‌سازد. رویدادها به‌صورت ثابت‌های `ScannerListener.Event` به‌همراه مقدارهای متغیر
بیرون می‌روند و `MainView` عبارت‌ها را از فهرست فراهم می‌کند — وگرنه خط وضعیت در برنامه‌ای که به 35 زبان ترجمه شده
انگلیسی می‌بود. خط‌های گزارش رویداد استثنا هستند و انگلیسی می‌مانند.

### دروازه سکو

`ScannerService.isSupportedPlatform()` یک آزمون `os.name` است و `MainView` پیش از ساختن هر کنترل اسکنر از آن می‌پرسد:
در macOS و Linux نه کلید روشن/خاموش هست، نه انتخابگر دستگاه، نه منوی اسکنر (و بنابراین نه <kbd>⌘K</kbd>)، نه برچسب
وضعیت. این‌ها پنهان نشده‌اند — هرگز ساخته نمی‌شوند.

Zebra سرویس‌های JavaPOS خود را فقط برای Windows عرضه می‌کند و در جای دیگر هیچ چیز زود شکست نمی‌خورد: jarها حل می‌شوند و
کنترل ساخته می‌شود، و سرانجام `open()` است که به خاطر نبود لایهٔ بومی شکست می‌خورد، چند ثانیه و یک پنجرهٔ گفتگو بعد.

این قاعده دربارهٔ *سرویس‌ها*ست نه JavaPOS. فروشنده‌ای که سرویسی چندسکویی عرضه کند اینجا کار خواهد کرد، و گسترش قاعده فقط
تغییری در `supportsJavaPos(String)` است — که سطح بسته است و در برابر رشته‌های `os.name` آزموده شده تا هر دو پاسخ روی هر
ماشینی که ساخت را اجرا کند پوشش داده شوند.

### سیمبولوژی‌ها

`Symbologies` همهٔ **78** نوع دادهٔ اسکن `SCAN_SDT_*` در JavaPOS را به نام‌های نمایشی، و هرجا دو واژگان با هم
بخوانند، به `DataCarrierType` در هسته نگاشت می‌کند. JavaPOS از این دو ریزبین‌تر است — UPC-A را از EAN-13 و Data Matrix
ساده را از GS1 DataMatrix جدا می‌کند، در حالی که AIM یک خانوادهٔ کامل را زیر یک نویسهٔ کد گرد می‌آورد.

نوعی که بیرون از جدول باشد هم نامی قابل استفاده می‌گیرد که با بازتاب روی `ScannerConst` پیدا می‌شود، چون سرویس‌های
فروشندگان واقعاً مقدارهایی بیرون از فهرست مشخصات گزارش می‌کنند. آزمونی روی `ScannerConst` می‌گردد و اگر نوعی اعلان‌شده
بی‌نام باشد شکست می‌خورد — که ثابت‌هایی را هم که JavaPOS آینده بیفزاید می‌گیرد.

برخی نگاشت‌های حامل به‌عمد `UNKNOWN` رها شده‌اند تا حدس زده نشوند: straight 2 of 5 (‏AIM ‏`]R`/`]S` را بر اساس شمار
میله‌های آغاز/پایان جدا می‌کند که JavaPOS گزارش نمی‌کند)، کدهای پستی چهارحالته، و TLC-39.

## بومی‌سازی

برچسب‌ها در یک فایل ویژگی برای هر زبان زیر `src/main/resources/i18n/ui_<CODE>.properties` جای دارند و همان کدهای
فهرست‌های خطای هسته را به کار می‌برند (`EN`، `FR`، `PCM`، …). هر 35 فایل وجود دارند و هر 35 مجموعه‌کلید یکسانی
دارند. فایل‌ها به‌صورت **UTF-8** خوانده می‌شوند، نه ISO-8859-1 که `Properties` فرض می‌کند، پس ترجمه‌ها خوانا ذخیره
می‌شوند نه به‌صورت گریزهای `\uXXXX`.

**بازگشت برای هر کلید است، نه برای هر فایل** — همین است که زبانی نیمه‌ترجمه‌شده را از لحظهٔ رسیدن نخستین کلیدش سودمند
می‌کند. انگلیسی قرارداد است: هر کلید باید آنجا وجود داشته باشد.

| لایه | کلیدها | پوشش |
|---|---|---|
| واژگان مشترک گزارش | 31 | همهٔ 35 زبان |
| قاب رومیزی — منوها، دکمه‌ها، سازنده، گزینه‌ها، خط وضعیت، چیدمان گزارش، وضعیت اسکنر، متن پنجره‌های گفتگو | 114 | همهٔ 35 زبان |

شش اصطلاح از واژگان مشترک (`generated`، `status`، `dlRole`، `interpretations`، `message`، `level`) در گزارش این برنامه
به کار نمی‌روند.
به‌عمد نگه داشته شده‌اند؛ سرآیند فایل همین را می‌گوید.

### آرگومان `--language`

`GaiaDesktopApp.languageOverride()` مقدار `--language=…` را از راه `getParameters().getNamed()` خود JavaFX می‌خواند، با
`Languages.fromArgument` حلش می‌کند — کد فهرست، نام enum یا برچسب BCP 47، بی‌حساسیت به بزرگی و کوچکی حروف — و به
`MainView` می‌سپارد.

**این جایگزینی برای همین اجراست نه برای فایل.** `MainView` زبانی را که بار کرده در `savedLanguage` نگه می‌دارد و *همان*
را بازمی‌نویسد، تا وقتی `languageChosenInSession` بگوید کاربر خودش زبانی برگزیده است؛ آنگاه انتخاب او طبق معمول ماندگار
می‌شود. این جدایی همهٔ طراحی است: یک پروفایل کیوسک یا میان‌بر دمو می‌تواند به اسپانیایی باز شود بی‌آنکه زبانی را که مالک
ماشین فردا با آن باز می‌کند بازنویسی کند، در حالی که انتخاب واقعی در پنل گزینه‌ها همچنان می‌ماند.

مقداری که هیچ فهرستی را نام نبرد، همراه کدهای پذیرفته ثبت و نادیده گرفته می‌شود. نپذیرفتن راه‌اندازی به خاطر یک غلط
تایپی در میان‌بر شکست بدتری می‌بود، و به همین دلیل `Languages.fromArgument` به‌جای پرتاب استثنا `null` برمی‌گرداند.

### افزودن زبان

هیچ تغییری در کد لازم نیست.

1. `ui_<CODE>.properties` را ویرایش کنید — هر زبان از پیش فایلی دارد.
2. مقدارها را ترجمه کنید. جای‌نگهدارهای `{0}` / `{1}` را سر جایشان بگذارید.
3. بسازید. دو آزمون قرارداد را اجرا می‌کنند: یکی وقتی کد کلیدی بخواهد که انگلیسی تعریف نکرده شکست می‌خورد، و دیگری وقتی
   مجموعه‌کلید هر فهرستی از انگلیسی فاصله بگیرد.

آزمون نخست به‌جای بازتاب روی کلاس‌ها، **کد منبع** را برای کلیدهای لفظی می‌کاود، چون کلیدها فقط به‌صورت رشته‌های لفظی در
محل‌های فراخوانی وجود دارند. به همین دلیل پیام تازه باید با کلیدی که مستقیم نوشته شده ساخته شود —
`strings.format("st.scannerError", …)` — نه اینکه از راه یک متغیر جستجو شود، وگرنه آزمون آن را نمی‌بیند.

### آنچه به‌عمد ترجمه نمی‌شود

- نام‌های کوتاه فیلدها که با قلم هم‌عرض کنار مقدارهای خام می‌آیند — `format`، `position`، `length`، `raw` و `part` در
  کارت عنصر، `AI`، `sep`، `pos` و `len` در نوار، و چهار خانه‌ای که جای خطا را نشان می‌دهند (`AI`، `position`، `level`،
  `stage`)، که مقدارهایشان به هر حال نام‌های enum ترجمه‌نشده‌اند؛
- نام نمونه‌ورودی‌ها که سازه‌های GS1 را نام می‌برند، و نام سیمبولوژی‌ها که اسم خاص‌اند؛
- بند چاره‌جویی `GE-C084` — نثر استاندارد که ترجمهٔ نیمه‌کاره‌اش از انگلیسی بدتر است؛
- آخرین سد `ElementBuilder` برای AI ناشناخته، که از رابط کاربری دست‌یافتنی نیست: ویرایشگر خودش AIهای ناشناخته را
  بررسی و از روی فهرست گزارش می‌کند؛
- خط‌های گزارش رویداد.

یک شکاف باقی است: `ScanSource.label()` مقدارهای `manual` / `scanner` / `file` / `built` را برای سطر تاریخچه و سرآیند
گزارش به انگلیسی فراهم می‌کند. بستن آن بیش از یک کلید می‌خواهد — `HistoryCell` هیچ `UiStrings`ای ندارد، و کارخانهٔ
سلول فهرست یک بار نصب می‌شود، پس هنگام تغییر زبان سلول‌ها هم باید تازه شوند.

## قالب‌های وضعیت ذخیره‌شده

دو فایل زیر `~/.gaia-desktop/` که جدا نگه داشته می‌شوند چون با آهنگ‌های متفاوتی تغییر می‌کنند — یک گزارش ثبت خراب یا
دستی ویرایش‌شده نباید به قیمت از دست رفتن تنظیمات کاربر تمام شود. پوشه را با `-Dgaia.desktop.home=…` جایگزین کنید؛
آزمون‌ها هم به همین شکل از پوشهٔ خانگی واقعی دور می‌مانند.

**`options.properties`** — هنگام تغییر یک گزینه و هنگام خروج نوشته می‌شود.

| کلید | معنا |
|---|---|
| `parse.mode`، `parse.language` | عمق خط لوله و زبان پیام‌ها |
| `date.endian`، `date.separator`، `date.month`، `date.year` | نمایش تاریخ |
| `check.skipRequires`، `check.skipExcludes` | گریز از بررسی ساختاری |
| `ui.theme` | `LIGHT` یا `DARK` |
| `ui.optionsPane` | پنل گزینه‌ها باز است؟ |
| `ui.scannerDevice` | آخرین نام منطقی JavaPOS |
| `ui.mode` | `PARSE`، `BUILD` یا `COMBINE` |
| `update.check` | آیا بررسی روزانهٔ به‌روزرسانی اجرا می‌شود (پیش‌فرض `true`) |
| `update.lastCheck` | آخرین بار کی اجرا شد، ISO-8601؛ نبودن یا خوانا نبودنش یعنی وقت بررسی رسیده است |
| `update.skipVersion` | انتشاری که کاربر برایش *رد کردن این نسخه* را برگزید؛ دیگر خودکار پیشنهاد نمی‌شود |

فایل گم‌شده یا آسیب‌دیده هرگز کشنده نیست: هر مقدار جداگانه به پیش‌فرض بازمی‌گردد، پس یک سطر بد فقط همان سطر را از دست
می‌دهد و نه چیز دیگری. در نخستین اجرا، وقتی هیچ فایلی نیست، گزینه‌ها به‌جای پیش‌فرض‌های درونی GAIA، به دست
`SystemDefaults` از تنظیمات منطقه‌ای ماشین مقداردهی می‌شوند — الگوی تاریخ کوتاه زبان محلی ترتیب اجزا، جداکننده و کوتاه
بودن یا نبودن ماه و سال را می‌دهد.

هرگز null به `Properties.setProperty` ندهید: استثنا پرتاب می‌کند، و `persistOptions()` از گرداننده‌های رویداد رابط
کاربری اجرا می‌شود که استثنا از آنجا به نخ FX می‌گریزد. این فروپاشی واقعی‌ای است که این برنامه پیش‌تر داشته است.

**`captures.tsv`** — هنگام تغییر تاریخچه و هنگام خروج نوشته می‌شود. تازه‌ترین در آغاز، حداکثر **500** مدخل.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

فقط آنچه قابل محاسبهٔ دوباره نیست ذخیره می‌شود. `ParseResult` سریال‌سازی **نمی‌شود** — هنگام بارگذاری با تجزیهٔ دوبارهٔ
ورودی از نو به دست می‌آید، پس تاریخچهٔ بازیابی‌شده گزینه‌های *اکنون* برقرار را بازتاب می‌دهد. ورودی‌ها معمولاً FNC1 و
هر چیز دیگری را که اسکنر بیرون می‌دهد دارند، پس فیلد ورودی گریزدار می‌شود (`\\`، `\t`، `\n`، `\r`، و `\xNN` برای هر
چیز دیگری زیر `0x20`) و فایل به‌صورت ISO-8859-1، بایت به بایت، خوانده و نوشته می‌شود.

فایل‌هایی که پیش از ثبت تاریخ نوشته شده‌اند فقط ساعت را دارند؛ هنوز بار می‌شوند، با تاریخ امروز، چون تاریخ واقعی هرگز
نوشته نشده بود.

## آزمون

```bash
(cd gaia-desktop && mvn test)
```

198 آزمون، به‌عمد **بی‌نیاز از جعبه‌ابزار JavaFX**، که آن‌ها را سریع و بی‌نمایشگر نگه می‌دارد. این آزمون‌ها نمایشگر گزارش،
منطق ساخت و جستجوهای AI، تبدیل `{GS}`، پیش‌فرض‌های برگرفته از زبان محلی، هر دو مخزن (از جمله یک رفت‌وبرگشت دارای
`0x1D` و فایل‌هایی که به‌عمد آسیب دیده‌اند)، جدول سیمبولوژی، قاعدهٔ سکوی اسکنر، تکهٔ نسخه، و فهرست‌ها را پوشش می‌دهند.

سه مورد ارزش دانستن دارند، چون از قراردادها دفاع می‌کنند نه از کارکردها:

| آزمون | کی شکست می‌خورد |
|---|---|
| `CatalogueCoverageTest` | کد کلیدی بخواهد که `ui_EN.properties` تعریف نکرده، یا هر یک از 35 فایل از مجموعه‌کلید انگلیسی فاصله بگیرد |
| `SymbologiesTest` | هر ثابت `SCAN_SDT_*` که JavaPOS اعلان کند نام نمایشی نداشته باشد — از جمله ثابتی که ارتقای JavaPOS بیفزاید |
| `ScannerServiceTest` | قاعدهٔ سکو پاسخش را برای Windows یا هر چیز دیگری تغییر دهد |

`UiStrings` در زمان اجرا به‌عمد بخشنده است — کلید ناشناخته به‌جای پرتاب استثنا در میانهٔ چیدمان، خود کلید نمایش داده
می‌شود — و دقیقاً به همین دلیل آزمون فهرست باید وجود داشته باشد.

**پوشش‌داده‌نشده:** هر چیزی که به جعبه‌ابزار زنده نیاز دارد — رفتار تمرکز، کلید تغییر حالت، ویرایش جدول، تغییر زبان، و
هر دو فروپاشی که در [نخ‌ها](#نخها) شرح داده شدند. این‌ها با راندن پنجرهٔ واقعی تأیید شدند، اما پسرفتی در آن‌ها ساخت را
شکست نمی‌دهد. افزودن TestFX یا Monocle این شکاف را می‌بندد.

## محدودیت‌های شناخته‌شده و کارهای باقی‌مانده

- **آزمون رابط کاربری بی‌نمایشگر وجود ندارد.** [آزمون](#آزمون) را ببینید.
- **مصنوعات ویژهٔ سکو.** هر دو بسته‌بندی کتابخانه‌های بومی JavaFX یک سکو را همراه دارند؛ برای هر هدف با `-Dfx.platform`
  یکی بسازید (هر ماشینی می‌تواند همه را بسازد). هیچ‌کدام محیط اجرای Java را همراه ندارد — آن به `jpackage` نیاز دارد که
  فقط برای سیستم‌عاملی که روی آن اجرا می‌شود می‌سازد.
- **ورودی اسکنر فقط در Windows است.** [دروازه سکو](#دروازه-سکو) را ببینید.
- **`ScanSource.label()` بومی‌سازی نشده است.** [آنچه به‌عمد ترجمه نمی‌شود](#آنچه-بهعمد-ترجمه-نمیشود) را ببینید.
- **`UiState.mode` از نوع `String` است** (`"PARSE"` / `"BUILD"`) در حالی که `Theme` کنارش یک enum است، پس آن مقدار لفظی
  در چند جا تکرار می‌شود. یک enum آن‌ها را حذف می‌کرد.
- **هدف Digital Link فقط دامنه و پیشوند مسیر است.** `BuilderDigitalLinkConfig` پارامترهای پرس‌وجوی اضافه و یک قطعه
  (fragment) را هم پشتیبانی می‌کند؛ ویرایشگر آن‌ها را در دسترس نمی‌گذارد.
- **جفت‌های AI ناسازگار (`GE-S006`) در ویرایشگر علامت نمی‌خورند** آن‌طور که AIهای ناشناخته و تکراری علامت می‌خورند —
  ساخت به‌سادگی شکست می‌خورد.
- **فهرست خطای هسته نقل‌قول‌ها را دوبرابر می‌کند** (`value ''09506000134350''`)، که عیناً در شکست‌های ساخت و در گزارش
  دیده می‌شود. به گریز نقل‌قول `MessageFormat` می‌ماند که برگردانده نمی‌شود؛ جای اصلاحش در هسته است.
