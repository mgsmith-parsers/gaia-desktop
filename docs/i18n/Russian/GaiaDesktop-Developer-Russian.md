## Модуль вкратце

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

Клиент основной библиотеки, и не более того. В нём **нет никаких знаний о GS1**: каждое определение AI,
правило проверки, сообщение об ошибке и локализованное описание берутся из
[`GaiaParser`](../../../../gaia/docs/GaiaParser.md) и
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md). В частности, список AI никогда не копируется в этот
модуль — средство выбора в конструкторе читает собственный реестр ядра, поэтому не может предложить AI,
который конструктор отверг бы.

**Точки входа:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX-`Application`) и
`tools.pantheum.gaia.desktop.Launcher` (`Main-Class` упакованного jar).

Модуль — лист: от него ничего не зависит, и сам он не зависит ни от какого другого последующего модуля. Два
класса, с которых он начался, были **скопированы** из `gaia-demo`, а не подключены как зависимость —
`Symbologies` по-прежнему вручную поддерживается в соответствии со своим близнецом оттуда, и в обоих есть
примечание об этом.

## Сборка и запуск

- **Java 21** для запуска и JDK 21 или новее для сборки — модуль компилируется с `release=21`. JavaFX 21 —
  соответствующая линия LTS. Jar ядра по-прежнему содержит байт-код Java 11 и без изменений работает на 21.
- **Maven** в `PATH`. Обёртки (wrapper) в этом репозитории нет.
- **Сначала установленное ядро.** Этот модуль разрешает `gaia:1.1.0` из `~/.m2`; устаревший или
  отсутствующий jar ядра — обычная причина ошибки `package tools.pantheum.gaia does not exist`.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` — единственный аргумент командной строки и, помимо `-Dgaia.desktop.home=…`, переносящего весь
профиль в другое место, единственный способ повлиять на запуск.

`mvn javafx:run` — путь разработки: плагин помещает JavaFX в **module path**, поэтому инструментарий
запускается как именованный модуль, а `GaiaDesktopApp` можно запустить напрямую. Упакованный jar так не
может — всё находится в class path, — поэтому его `Main-Class` — прослойка `Launcher`. Подкласс
`Application` в роли `Main-Class` при такой раскладке падает с *"JavaFX runtime components are missing"*.

Всегда используйте `clean` — один раз, перед сборкой набора платформ, поскольку он очищает `target/dist/`
для всех. Почему — см. [Устранение проблем сборки](#устранение-проблем-сборки).

### Упаковка

Всё поставляемое собирается в `target/dist/gaia-desktop-<version>-<platform>/`, и больше ничего, поэтому
каталог можно упаковать в zip или скопировать целиком, не выбирая артефакты из `target/` рядом с
`classes/`, `maven-status/` и прочими рабочими файлами сборки. `${dist.dir}` называет его один раз; каждый
плагин, записывающий артефакт, указывает на него.

#### Одна сборка на платформу

Jar-файлы JavaFX содержат нативный код, поэтому каждый дистрибутив предназначен для одной платформы,
задаваемой свойством `fx.platform` как классификатор OpenJFX: `mac-aarch64`, `mac`, `win`, `linux` или
`linux-aarch64`. Пять профилей `fx-*`, активируемых по ОС, задают его равным платформе собирающей машины —
этого достаточно для простого `mvn package` или `mvn javafx:run`; `-Dfx.platform=…` имеет над ними
приоритет, чтобы собрать любую другую, с любой машины — jar-файлы JavaFX лишь скачиваются. `${dist.dir}`
равен `target/dist/${fx.platform}`, поэтому сборка одной платформы никогда не перезаписывает другую.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

Это работает благодаря двум деталям pom, и обе выглядят лишними:

- **Каждый модуль JavaFX — прямая зависимость** — base, graphics, controls, media и web, — каждый с
  `<classifier>${fx.platform}</classifier>` и исключением `org.openjfx:*`. Pom-файлы OpenJFX выбирают свои
  транзитивные jar-файлы по ОС *собирающей машины*, поэтому если позволить graphics или base прийти
  транзитивно, нативные библиотеки Mac окажутся в сборке для Windows рядом с библиотеками Windows.
- **Свойство называется `fx.platform`, а не `javafx.platform`.** Если задать его извне, собственное свойство
  OpenJFX переопределяется родительским pom через само себя; Maven отвергает такой pom как некорректный и
  молча отбрасывает платформенные jar-файлы, оставляя сборку вовсе без JavaFX.

Обе раскладки пишут один и тот же путь, `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`, и
за одну сборку выполняется ровно одна из них. `${jar.phase}`, `assembly.skipAssembly` и `mdep.skip` не дают
им обеим претендовать на него.

| | По умолчанию | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — только классы и ресурсы этого модуля | ~50 MB — зависимости распакованы внутрь |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 jar-файлов, поимённо перечисленных в `Class-Path` манифеста | — |
| Поставлять | jar **и** `lib/` рядом с ним | один файл |
| Также в `dist/gaia-desktop-<version>-<platform>/` | `run.bat` (win) или `run.sh` (остальные) | то же |
| И | `readme.html` и `docs/` (каждая платформа) | то же |

Каждый дистрибутив содержит и руководства: `docs/`, скопированный с сохранением структуры, чтобы ссылки
между руководствами и переводами продолжали работать, без инструментов перевода (`check-i18n.py`,
`i18n-manifest.json`, `i18n-plan.md`); и `readme.html` в корне — указатель со ссылками на каждое из них, из
`src/main/dist/readme.html`, где `@VERSION@` заменён версией из pom. Оба записывает шаг antrun
`pick-launch-script`, который сначала удаляет `docs/`, чтобы удалённое руководство не задерживалось. Ссылки
в readme написаны вручную — переименованному руководству или переводу, добавленному в `docs/`, нужна и своя
строка там.

`Class-Path` манифеста и `lib/` — две половины одного целого: jar называет `lib/<artifact>-<version>.jar`
для каждой зависимости времени выполнения, а `copy-dependencies` заполняет `lib/` ровно этими именами.
Именно это заставляет `java -jar` работать.

#### Приложение macOS и zip-архив дистрибутива

Одно выполнение antrun, `mac-app-and-zip`, завершает фазу `package`. Поэтому плагин antrun объявлен
**после** плагинов jar и assembly — Maven выполняет выполнения фазы в порядке объявления плагинов, — так что
jar при любой упаковке уже существует, когда оно запускается. (Другое его выполнение, `pick-launch-script`,
находится в `prepare-package` и не затронуто.)

Для `mac` и `mac-aarch64` оно сначала строит `GAIA Desktop.app` в каталоге дистрибутива: `Info.plist` (с
`@VERSION@`, заменённым версией из pom), запускающий скрипт `Contents/MacOS/gaia-desktop` (сделанный
исполняемым) и `gaia-desktop.icns`, всё из `src/main/macos/`, а затем **перемещает** `gaia-desktop.jar` и
`lib/` в `Contents/Java`, чтобы пакет был самодостаточным. `run.sh` ищет там, когда рядом с ним нет jar.
Запускающий скрипт находит Java по версии (`java_home -v 21+`, затем openjdk из Homebrew — запуски из Finder
не видят ни `JAVA_HOME`, ни `PATH`), показывает диалог через `osascript`, если её нет, делает `cd` в
`~/.gaia-desktop`, чтобы относительный каталог `logs/` у logback был доступен для записи, и передаёт
`-Xdock:name`/`-Xdock:icon`. macOS связывает запущенный `java` с пакетом (его идентификатор пакета и значок
в Dock — от приложения); в строке меню отображается GAIA Desktop.

Затем для каждой платформы оно упаковывает каталог в `target/dist/gaia-desktop-<version>-<platform>.zip` в
папку с тем же именем с помощью `<zip>` из Ant: `run.sh` и `Contents/MacOS/**` идут отдельным набором файлов
с `filemode="755"`, иначе после распаковки они не запустились бы. Zip **не прикрепляется**: он для релизов на
GitHub, а четыре платформы получаются из четырёх сборок, которые Maven Central — одна неизменяемая загрузка
на версию — никогда не смог бы принять как один релиз.

`project.build.outputTimestamp` задаётся временем сборки. Иначе архиваторы в maven-jar-plugin 3.5 и
maven-assembly-plugin 3.8 датируют каждую запись 1 февраля 1980 года.

Значок приложения рисует `tools/icon/GaiaIcon.java` (не входит в сборку; в его заголовке описаны шаги
`sips`/`iconutil`). Его результаты хранятся в репозитории: `src/main/macos/gaia-desktop.icns` для пакета и
`src/main/resources/icons/gaia-desktop-{16..256}.png`, которые `GaiaDesktopApp` устанавливает как значок окна
(Windows и Linux; macOS значки окон игнорирует).

#### Скрипты запуска

`run.sh` и `run.bat` берутся из `src/main/scripts/` и копируются в `dist/gaia-desktop-<version>-<platform>/`
без фильтрации — `run.sh` полон подстановок оболочки `${...}`, которые фильтрация Maven могла бы свободно
переписать. Затем шаг antrun оставляет только тот, который запускает платформа, — `run.bat` для `win`,
`run.sh` для всех остальных — и ставит бит исполнения на `run.sh`, поскольку `copy-resources` его не
сохраняет. Он решает по разрешённому значению `${fx.platform}`, а не через профили, потому что активация
профиля не видит значения, заданного другим профилем: сборка для Linux, сделанная в Windows, иначе получила
бы скрипт хоста.

Они **не полагаются на манифест**. Каждый сам строит class path: `gaia-desktop.jar`, а за ним каждый `.jar`
из `lib/`, перечисленные по одному, а не через подстановочный знак `lib/*`, чтобы путь с пробелами оставался
одной записью, а подсчёт добавленного был настоящим. Запуск с `-cp` — причина, по которой они явно называют
`tools.pantheum.gaia.desktop.Launcher`: `-cp` не читает `Main-Class` из манифеста. Однако его `Class-Path`
он **всё же** учитывает — jar в `-cp` приносит jar-файлы, названные в его манифесте, и они ищутся сразу после
него, — поэтому каждый jar из `lib/` загружается, перечислен он в скрипте или нет, и исключение одного из
class path скрипта не удерживает его вне JVM. Скрипты всё равно их перечисляют, чтобы jar с устаревшим,
отредактированным вручную или неполным манифестом всё же запускался. Один
и тот же скрипт обслуживает обе упаковки: у jar `-Pfat` нет `lib/` для добавления, и он ему не нужен, — по
этой же причине пустой `lib/` — это замечание, а не ошибка.

#### Нативные библиотеки Zebra

Сборка не поставляет ничего от Zebra — ни DLL, ни jar-файлов служб. В Windows они берутся из Scanner SDK от
Zebra, установленного на компьютере: `run.bat` добавляет его jar-файлы служб `Jpos*.jar` и `bin\` в class
path, а `bin\` — в `PATH`, где `System.loadLibrary` находит `CSJPOSScanner.dll` / `CSJPOSScanner64.dll`
(`java.library.path` по умолчанию равен `PATH`). API JavaPOS и его загрузчик конфигурации всегда берутся из
`lib\javapos-*.jar`, с SDK или без него.

**`run.bat` никогда не добавляет собственный jar JavaPOS из SDK**, `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`.
Когда-то он это делал, опуская `lib\javapos-*.jar`, чтобы избежать двух копий API, — но `Class-Path`
манифеста всё равно загружал их (см. выше), так что JVM получала обе: классы загрузчика 4.x из `lib\`, а рядом
`jpos/res/jpos.properties` и `jcl.xsd` из `javaPOS114.jar`. Файл свойств заставляет
[`JposConfig`](#интеграция-сканера) отступить, а этот `jcl.xsd` принимает версии JavaPOS только до 1.10,
поэтому каждая запись в `jpos.xml` (1.12–1.14) не проходила проверку, реестр оставался пустым, и каждое
подключение завершалось ошибкой 109, даже не дойдя до сканера. Для этого достаточно вообще иметь этот jar в
class path, даже позади jar-файлов из `lib\`. Jar-файлы служб Zebra без изменений работают на API 1.14 из
`lib\` — открытие, захват и сканирование так проверены на настоящем сканере. Библиотеки DLL, вручную
положенные рядом с `run.bat`, по-прежнему учитываются: тогда скрипт задаёт
`-Djava.library.path=<dist>;%PATH%`, дописывая `PATH`, потому что это свойство полностью заменяет путь
поиска по умолчанию.

`mvn javafx:run` ничего из этого не делает, поэтому для захвата сканера при запуске из среды разработки в
Windows нужно иными способами поместить jar-файлы SDK в class path, а его `bin\` — в `PATH`; для этого
запускайте из `dist/`.

Помимо class path, они покрывают то, чего не делает `java -jar`: определяют собственный каталог, чтобы
работать из любого рабочего каталога, предпочитают `JAVA_HOME` значению `PATH` и отвергают JVM старше 11
фразой, называющей способ исправления, вместо `UnsupportedClassVersionError`. `GAIA_DESKTOP_OPTS` передаёт
параметры JVM. `run.bat` использует `java.exe`, а не `javaw.exe`, чтобы консоль оставалась открытой —
Windows — единственная платформа, где работает сканер, и его состояние и ошибки JavaPOS выводятся туда.

`run.bat` также выбирает свои Java, JavaFX и службы Zebra по тому, что найдёт, — входящий в комплект `jdk*\`,
`javafx-sdk*\lib\` в module path, Scanner SDK от Zebra в `ZEBRA_HOME`, — исключая из class path копии JavaFX
из `lib\`, когда использует копии из SDK, и передаёт SAX-парсер JDK, прокси и хранилище сертификатов Windows,
а также `--enable-native-access` на Java 17 и новее. Таблица — в разделе README
[What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows). Сохраняйте в файле окончания
строк CRLF: `cmd.exe` может пропустить `call :label` в пакетном файле только с LF. `run.sh` тоже передаёт
`--enable-native-access=ALL-UNNAMED` — JavaFX загружает собственные нативные библиотеки из `lib/`, а при JavaFX
в class path именно `ALL-UNNAMED` — модуль, который это покрывает, — и опускает его, как и `run.bat`, лишь
когда версию Java прочитать не удаётся.

Любая из раскладок содержит нативные библиотеки JavaFX **одной платформы**, `${fx.platform}`, поэтому ни
одна не переносима между ОС или архитектурами. Собирайте по одному разу на целевую платформу — см.
[Одна сборка на платформу](#одна-сборка-на-платформу).

> **Eclipse.** Выполнение `copy-dependencies` содержит инструкцию `<?m2e ignore?>`. m2e разрешает открытый
> проект рабочей области в его папку `target/classes`, а не в jar, а `copy-dependencies` отказывается
> копировать неупакованный артефакт (MDEP-187), из-за чего автоматическая сборка падала бы всякий раз, когда
> проект `gaia` открыт рядом с этим. Как следствие, сборка только в IDE не заполняет
> `target/dist/gaia-desktop-<version>-<platform>/lib/`; выполните `mvn package`, прежде чем использовать
> сам jar.

### Воронка захвата

Любой ввод — набранный, вставленный, открытый из файла, отсканированный или построенный — попадает в
анализатор через один метод, `MainView.capture(String, ScanSource, String)`.

Это единственное проектное решение, вокруг которого построено приложение. Построенной строке не нужен ни
собственный отчёт, ни собственная история, ни собственный путь экспорта, потому что после воронки
построенную строку нельзя отличить от отсканированной. Всё новое, что производит ввод, должно проходить
через неё, а не в обход.

| Поток приложения JavaFX | Весь анализ, отрисовку и интерфейс. Когда таблицы AI прогреты, анализ занимает меньше миллисекунды, поэтому рабочий поток ему не нужен |
| `gaia-scanner` | Каждый вызов сканера — открытие, захват, включение, отключение, освобождение, закрытие. Один долгоживущий поток, принадлежащий `ScannerService`; см. [Интеграция сканера](#интеграция-сканера) |
| Поток событий JavaPOS | Обратные вызовы `ScannerService`. `MainView.FxScannerListener` переносит каждый из них через `Platform.runLater` |
| Фоновый | Ожидание `connect()` / `disconnect()` сканера (захват может занять до 5 с), восстановление сохранённой истории при запуске — что заодно прогревает анализатор — и проверка обновлений (`gaia-update-check`, один запрос к GitHub, результат возвращается через `Platform.runLater`) |

**Никогда не изменяйте выбор элемента управления и не уничтожайте элемент управления изнутри его
собственного события выбора.** Три отдельных сбоя этого приложения возникли именно так: сброс средства
выбора AI внутри собственного `clearAndSelect` всплывающего окна (`IndexOutOfBoundsException` из
`ListViewBehavior`) и перестроение панели, которой принадлежит список выбора языка, из собственного
обработчика этого списка. Оба теперь откладываются через `Platform.runLater`, а причины записаны в обоих
местах вызова.

### Перестроить или переподписать

Смена языка **перестраивает** обрамление из каталога — меню, панель инструментов, панель параметров, — что
безопасно, потому что ничто из этого не хранит состояния: `OptionsPane` — двустороннее представление
`ParseOptions`, так что значения живут в модели, и свежая панель сразу их подхватывает.

Элементы управления, содержащие **данные пользователя**, являются полями и вместо этого переподписываются на
месте: `BuilderPane.retext(UiStrings)` сохраняет строки AI, поля Digital Link и выделение. Перестроение
отбросило бы незавершённую работу — что однажды и случилось.

## Токен {GS}

`TextField` JavaFX молча отбрасывает каждый символ ниже `0x20` (`TextInputControl.filterInput`). Он не
«отображает его странно» — он его удаляет. Это касается ввода, вставки, `setText` и `insertText`, поэтому
`setText("01…" + GS + "10LOT")` даёт `"01…10LOT"`: строку элементов, смысл которой незаметно изменился,
потому что AI переменной длины теперь поглощает то, что шло за ним.

`desktop.parse.GsToken` — это весь ответ. Разделитель проходит через интерфейс как буквальный текст `{GS}` и
по пути к анализатору снова становится `0x1D`. Токен придуман не здесь — ровно так `0x1D` отображает
`ASCIIRevealerUtils.printable` из ядра, поэтому значение, скопированное из отчёта, вставляется обратно в
строку ввода без изменений.

Фильтр `TextFormatter` на поле ввода перехватывает любой путь, которым может прийти текст, — ввод, ⌘V,
контекстное меню, перетаскивание, `setText`, — поэтому преобразование живёт там, а не в каждом обработчике.

Путь сканера никогда не проходит через `GsToken`: сканы доходят до анализатора в виде байтов.

## Интеграция сканера

`ScannerService` владеет элементом управления `Scanner` из JavaPOS: открытие → захват → включение, с
повторным взведением события данных после каждого скана. Логические имена устройств берутся из
`src/main/resources/jpos.xml`.

**Каждый вызов устройства выполняется в одном потоке, `gaia-scanner`, который живёт столько же, сколько
служба**, — никогда в потоке FX и никогда в потоке, который завершается после вызова. Служба Zebra
обращается к сканеру через JNI поверх COM API CoreScanner, а COM привязывает то, что настраивает, к
апартаменту вызывающего потока: откройте в потоке, который затем завершится, — и сканер будет захвачен, но
замолчит; закройте в другом потоке — и будет деинициализирован не тот апартамент. Закрытие в потоке FX —
худший случай, потому что JavaFX вызывает там `OleInitialize` и регистрирует в нём цель перетаскивания
каждого окна — `CoUninitialize` в нём ломает перетаскивание во всём приложении. Это JavaFX в Windows, а не
какая-то конкретная версия JavaFX. `connect()` и `disconnect()` передают работу в этот поток и ждут,
поэтому `MainView` вызывает оба из короткоживущего фонового потока; образец — `JposScannerSession` из
просмотрщика, где сбой перетаскивания был обнаружен впервые.

Два правила не дают неисправному устройству заклинить соединение. **Разборка никогда не прекращается
досрочно:** `closeQuietly` отключает, освобождает и закрывает отдельными шагами, освобождает только при
удерживаемом захвате и всегда пытается выполнить `close()` — после неудачного захвата `release()` выбрасывает
«not claimed», и когда шаги делили один `try`, это пропускало закрытие и оставляло устройство открытым в
службе Zebra. **Событие данных повторно взводится в `finally`:** JavaPOS отключает его после каждого
события, поэтому чтение или обработчик, выбросивший исключение, всё равно должен его взвести, иначе сканер
замолчит до переподключения. `ScannerLifecycleTest` проверяет оба правила на сценарном `jpos.Scanner`.

**`JposConfig` направляет JavaPOS на входящий в комплект `jpos.xml`** перед первым открытием. С jar-файлами
JavaPOS из Maven (`javapos-config-loader` 4.x) и без `jpos/res/jpos.properties` в class path любое открытие
иначе завершается ошибкой *"Service does not exist in loaded JCL registry"* (ошибка 109) по трём отдельным
причинам: диспетчер служб откатывается к `SimpleRegPopulator`, который читает сериализованный `jpos.cfg` и
никогда — `jpos.xml`; загрузчик XML ищет `jpos.xml` только в рабочем каталоге, а не в jar; а Xerces 2.12.2 в
`lib/` отвергает JAXP-свойство `accessExternalDTD`, которое задаёт загрузчик. `JposConfig` задаёт
`jpos.config.regPopulatorClass` (`JavaxRegPopulator`), `jpos.config.populatorFileURL` (собственный
`jar:file:…!/jpos.xml` из jar) и `javax.xml.parsers.SAXParserFactory` (из JDK) как системные свойства —
никогда не уже заданное, так что `-Djpos.config.populatorFileURL=file:…` по-прежнему выбирает другой
`jpos.xml`, — и не задаёт ничего, если в class path есть `jpos.properties` или нет загрузчика 4.x.
`javaPOS114.jar` из Zebra SDK — как раз такой случай и попросту ломает реестр, поэтому `run.bat` держит его
вне class path — см. [Нативные библиотеки Zebra](#нативные-библиотеки-zebra). `JposConfigTest` сквозным
образом проверяет, что реестр затем содержит сканеры из файла.

**Средство выбора устройства генерируется из этого реестра**, а не хранится списком в коде:
`ScannerService.logicalNames()` читает загруженные записи в потоке `gaia-scanner` и оставляет те, у которых
категория устройства — `Scanner` (две записи весов в `jpos.xml` остаются за бортом), в порядке
`pickerOrder`: сначала `ZebraAllScanners`, если файл его определяет, остальные по алфавиту (реестр не
сохраняет порядок файла). Файл без него его не получает; если ничего не загружено, предлагается только
значение по умолчанию, поэтому средство выбора никогда не пусто. `MainView` сразу показывает значение по
умолчанию и дополняет список из фонового потока, сохраняя сохранённый выбор. Так сканер, добавленный в
`jpos.xml`, — или целый файл, указанный через `-Djpos.config.populatorFileURL`, — появляется в средстве
выбора без изменения кода, а `JposConfigTest` сверяет средство выбора с независимым чтением входящего в
комплект файла. Службы, названные в этих записях, — классы Zebra
(`com.zebra.jpos.service.scanner.*Factory`), которые всё равно должны быть в class path — из Scanner SDK
через `run.bat` или как jar-файлы служб Zebra, положенные в `lib\`.

Данные сканирования декодируются как **ISO-8859-1**, чтобы каждый байт отображался 1:1 и сохранились и
префикс AIM Code ID, и каждый `0x1D`; отчёты записываются в UTF-8.

Ничто в службе не составляет текст для пользователя. События выходят как константы `ScannerListener.Event`
плюс меняющиеся значения, а `MainView` подставляет формулировку из каталога — иначе строка состояния была
бы на английском в приложении, переведённом на 35 языков. Исключение — строки журнала, они остаются на
английском.

### Платформенный барьер

`ScannerService.isSupportedPlatform()` — одна проверка `os.name`, и `MainView` обращается к ней, прежде чем
строить любой элемент управления сканером: в macOS и Linux нет ни переключателя, ни средства выбора
устройства, ни меню «Сканер» (а значит, и <kbd>⌘K</kbd>), ни надписи состояния. Они не скрыты — они никогда
не создаются.

Zebra поставляет свои службы JavaPOS только для Windows, а в других системах ничто не падает рано: jar-файлы
разрешаются, элемент управления создаётся, и лишь `open()` в итоге падает из-за отсутствующего нативного
слоя — несколько секунд и один диалог спустя.

Правило касается *служб*, а не JavaPOS. Поставщик, выпустивший бы кроссплатформенную службу, работал бы
здесь, и расширение правила — это изменение только в `supportsJavaPos(String)`, методе с видимостью в
пределах пакета, который тестируется на строках `os.name`, так что оба ответа проверены на любой машине,
где идёт сборка.

### Символики

`Symbologies` сопоставляет все **78** типов данных сканирования JavaPOS `SCAN_SDT_*` с отображаемыми именами,
а также с `DataCarrierType` ядра там, где два словаря совпадают. JavaPOS — более детальный из двух: он
различает UPC-A и EAN-13, а также простой Data Matrix и GS1 DataMatrix, тогда как AIM объединяет целое
семейство под одним символом кода.

Тип вне таблицы всё равно получает пригодное имя, найденное отражением по `ScannerConst`, потому что службы
поставщиков действительно сообщают значения вне списка спецификации. Тест обходит `ScannerConst` и падает,
если у какого-либо объявленного типа нет имени, — это заодно ловит константы, которые добавит будущая
версия JavaPOS.

Некоторые сопоставления носителей намеренно оставлены `UNKNOWN`, а не угаданы: простой 2 из 5 (AIM
различает `]R`/`]S` по числу стартовых/стоповых штрихов, о которых JavaPOS не сообщает), почтовые коды с
четырьмя состояниями и TLC-39.

## Локализация

Надписи хранятся в одном файле свойств на язык в `src/main/resources/i18n/ui_<CODE>.properties`, с теми же
кодами, что и каталоги ошибок ядра (`EN`, `FR`, `PCM`, …). Существуют все 35, и у всех 35 одинаковый набор
ключей. Файлы читаются как **UTF-8**, а не как ISO-8859-1, которую предполагает `Properties`, чтобы переводы
хранились в читаемом виде, а не как экранированные последовательности `\uXXXX`.

**Откат выполняется по ключу, а не по файлу** — благодаря этому частично переведённый язык полезен с того
момента, как появляется его первый ключ. Английский — это контракт: каждый ключ должен существовать в нём.

| Слой | Ключи | Охват |
|---|---|---|
| Общая лексика отчёта, перенесённая из `GaiaHtmlReport` в `gaia-demo` | 31 | все 35 языков |
| Обрамление приложения — меню, кнопки, конструктор, параметры, строка состояния, макет отчёта, состояние сканера, тексты диалогов | 114 | все 35 языков |

Шесть общих терминов (`generated`, `status`, `dlRole`, `interpretations`, `message`, `level`) отчётом этого
приложения не используются. Они сохранены, чтобы общий блок оставался точной копией лексики демо; об этом
сказано в заголовке файла.

### Аргумент `--language`

`GaiaDesktopApp.languageOverride()` читает `--language=…` через собственный `getParameters().getNamed()`
JavaFX, разрешает его с помощью `Languages.fromArgument` — код каталога, имя перечисления или тег BCP 47, без
учёта регистра — и передаёт в `MainView`.

**Переопределение действует на запуск, а не на файл.** `MainView` хранит загруженный язык в `savedLanguage`
и записывает обратно *его*, пока `languageChosenInSession` не покажет, что пользователь сам выбрал язык;
тогда его выбор сохраняется как обычно. В этом разделении и состоит весь замысел: профиль киоска или
демонстрационный ярлык может открыться на испанском, не переписывая то, с чем завтра откроется у владельца
компьютера, а настоящий выбор, сделанный на панели параметров, по-прежнему сохраняется.

Значение, не указывающее ни на один каталог, записывается в журнал вместе с допустимыми кодами и
игнорируется. Отказ запускаться из-за опечатки в ярлыке был бы худшим сбоем, и по той же причине
`Languages.fromArgument` возвращает `null`, а не выбрасывает исключение.

### Добавление языка

Изменения кода не требуются.

1. Отредактируйте `ui_<CODE>.properties` — у каждого языка уже есть файл.
2. Переведите значения. Оставьте на месте заполнители `{0}` / `{1}`.
3. Соберите. Два теста следят за контрактом: один падает, если код запрашивает ключ, которого нет в
   английском, другой — если набор ключей какого-либо каталога расходится с английским.

Первый тест ищет литералы ключей в **исходниках**, а не применяет отражение к классам, потому что ключи
существуют только как строковые литералы в местах вызова. Поэтому новое сообщение нужно строить с ключом,
записанным прямо в вызове, — `strings.format("st.scannerError", …)`, — а не искать через переменную, иначе
тест его не увидит.

### Что намеренно не переводится

- краткие имена полей моноширинным шрифтом рядом с необработанными значениями — `format`, `position`,
  `length`, `raw` и `part` карточки элемента, `AI`, `sep`, `pos` и `len` ленты и четыре ячейки,
  указывающие место ошибки (`AI`, `position`, `level`, `stage`), значения которых в любом случае —
  непереведённые имена перечислений;
- имена примеров ввода, обозначающие конструкции GS1, и названия символик, являющиеся именами
  собственными;
- абзац с рекомендацией по исправлению для `GE-C084` — нормативный текст, где перевод наполовину хуже
  английского;
- защитная проверка `ElementBuilder` на неизвестные AI, недостижимая из интерфейса: редактор сам проверяет
  неизвестные AI и сообщает о них из каталога;
- строки журнала.

Остаётся один пробел: `ScanSource.label()` выдаёт `manual` / `scanner` / `file` / `built` на английском в
строку истории и в шапку отчёта. Чтобы его закрыть, нужно больше, чем ключ: у `HistoryCell` нет
`UiStrings`, а фабрика ячеек списка устанавливается один раз, так что при смене языка пришлось бы обновлять
и ячейки.

## Форматы сохранённого состояния

Два файла в `~/.gaia-desktop/`, хранящиеся отдельно, потому что меняются в разном ритме: повреждённый или
отредактированный вручную журнал захватов не должен стоить пользователю его настроек. Каталог можно
переопределить через `-Dgaia.desktop.home=…` — так тесты держатся вне настоящего домашнего каталога.

**`options.properties`** — записывается при изменении параметра и при выходе.

| Ключ | Значение |
|---|---|
| `parse.mode`, `parse.language` | Глубина конвейера и язык сообщений |
| `date.endian`, `date.separator`, `date.month`, `date.year` | Отображение дат |
| `check.skipRequires`, `check.skipExcludes` | Исключения из структурных проверок |
| `ui.theme` | `LIGHT` или `DARK` |
| `ui.optionsPane` | Панель открыта? |
| `ui.scannerDevice` | Последнее логическое имя JavaPOS |
| `ui.mode` | `PARSE`, `BUILD` или `COMBINE` |
| `update.check` | Выполняется ли ежедневная проверка обновлений (по умолчанию `true`) |
| `update.lastCheck` | Когда она выполнялась последний раз, ISO-8601; отсутствие или нечитаемое значение означает, что проверка нужна |
| `update.skipVersion` | Релиз, для которого пользователь выбрал *Пропустить эту версию*; автоматически больше не предлагается |

Отсутствующий или повреждённый файл никогда не фатален: каждое значение откатывается отдельно, поэтому одна
плохая строка стоит только этой строки. При первом запуске, когда файла нет вовсе, параметры заполняются
`SystemDefaults` из региональных настроек компьютера, а не из встроенных значений GAIA по умолчанию:
короткий шаблон даты для языкового стандарта даёт порядок компонентов, разделитель и то, сокращаются ли
месяц и год.

Никогда не передавайте `Properties.setProperty` значение null: он выбрасывает исключение, а
`persistOptions()` выполняется из обработчиков событий интерфейса, где исключение уходит в поток FX. Это
настоящий сбой, который у этого приложения уже был.

**`captures.tsv`** — записывается при изменении истории и при выходе. Новейшие первыми, не более **500**
записей.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

Хранится только то, что нельзя вычислить заново. `ParseResult` **не** сериализуется — он восстанавливается
повторным анализом ввода при загрузке, поэтому восстановленная история отражает параметры, действующие
*сейчас*. Ввод обычно содержит FNC1 и всё, что ещё выдаёт сканер, поэтому поле ввода экранируется (`\\`,
`\t`, `\n`, `\r` и `\xNN` для всего прочего ниже `0x20`), а файл читается и записывается как ISO-8859-1,
байт в байт.

Файлы, записанные до того, как стала сохраняться дата, содержат только время; они по-прежнему загружаются,
с сегодняшней датой, потому что настоящая дата так и не была записана.

## Тестирование

```bash
(cd gaia-desktop && mvn test)
```

96 тестов, намеренно **не зависящих от инструментария JavaFX**, что делает их быстрыми и не требующими
дисплея. Они покрывают генератор отчёта, логику построения и поиск AI, преобразование `{GS}`, значения по
умолчанию, выведенные из языкового стандарта, оба хранилища (включая прохождение туда и обратно с `0x1D` и
намеренно повреждённые файлы), таблицу символик, платформенное правило сканера, заглушку версии и каталоги.

Три стоит знать, потому что они защищают контракты, а не функции:

| Тест | Падает, когда |
|---|---|
| `CatalogueCoverageTest` | Код запрашивает ключ, которого нет в `ui_EN.properties`, или какой-либо из 35 файлов расходится с английским набором ключей |
| `SymbologiesTest` | У какой-либо объявленной в JavaPOS константы `SCAN_SDT_*` нет отображаемого имени — включая ту, что добавит обновление JavaPOS |
| `ScannerServiceTest` | Платформенное правило меняет ответ для Windows или для чего-либо ещё |

`UiStrings` намеренно снисходителен во время выполнения — неизвестный ключ отображается как сам ключ, а не
выбрасывает исключение посреди раскладки, — и именно поэтому тест каталога обязан существовать.

**Не покрыто:** всё, что требует работающего инструментария, — поведение фокуса, переключение режима,
редактирование таблиц, смена языка и оба сбоя, описанные в разделе [Потоки](#потоки). Это проверено
управлением настоящим окном, но регрессия в них не провалила бы сборку. Добавление TestFX или Monocle закрыло
бы этот пробел.

## Устранение проблем сборки

| Симптом | Причина и решение |
|---|---|
| `package tools.pantheum.gaia does not exist` | Ядро не установлено. `(cd gaia && mvn install -DskipTests)` |
| *"JavaFX runtime components are missing"* | `Main-Class` jar-файла должна быть `Launcher`, а не `GaiaDesktopApp` |
| *"Unsupported JavaFX configuration: classes were loaded from unnamed module"* при запуске | Ожидаемо и безвредно — JavaFX отмечает, что находится в class path. Именно поэтому существует `Launcher` |
| Jar не запускается, `NoClassDefFoundError` | Jar по умолчанию содержит только классы этого модуля; рядом должен лежать `dist/lib/`. Используйте `-Pfat`, чтобы получить один самодостаточный файл |
| `Artifact has not been packaged yet … MDEP-187` в Eclipse | Разрешение рабочей области в m2e. См. примечание в разделе [Упаковка](#упаковка) |
| В сборке появляются дубликаты файлов `… 2.properties` | Проект лежит в папке, синхронизируемой с iCloud, и синхронизация посреди сборки создала конфликтующие копии. Всегда `mvn clean package`; лучше исключите `target/` из синхронизации |
| Пункт меню показывает ключ вроде `act.hri` | Этого ключа нет в `ui_EN.properties`. Сборка должна была это поймать — см. [Тестирование](#тестирование) |

## Известные ограничения и открытые задачи

- **Нет тестов интерфейса без дисплея.** См. [Тестирование](#тестирование).
- **Платформенно-зависимые артефакты.** Обе упаковки содержат нативные библиотеки JavaFX одной платформы;
  собирайте по одной на целевую платформу с `-Dfx.platform` (любая машина может собрать все). Ни одна не
  содержит среды выполнения Java — для этого нужен `jpackage`, который собирает только для той ОС, на которой
  работает.
- **Ввод со сканера только в Windows.** См. [Платформенный барьер](#платформенный-барьер).
- **`ScanSource.label()` не локализован.** См. [Что намеренно не
  переводится](#что-намеренно-не-переводится).
- **`UiState.mode` — это `String`** (`"PARSE"` / `"BUILD"`), тогда как `Theme` рядом — перечисление, поэтому
  литерал встречается в нескольких местах. Перечисление избавило бы от них.
- **Цель Digital Link — только домен и префикс пути.** `BuilderDigitalLinkConfig` поддерживает также
  дополнительные параметры запроса и фрагмент; редактор их не предоставляет.
- **Взаимоисключающие пары AI (`GE-S006`) не помечаются в редакторе** так, как неизвестные и повторяющиеся
  AI, — построение просто завершается ошибкой.
- **Каталог ошибок ядра удваивает кавычки** (`value ''09506000134350''`), что дословно появляется в ошибках
  построения и в отчёте. Похоже на экранирование кавычек в `MessageFormat`, которое не снимается; исправление
  относится к ядру.
