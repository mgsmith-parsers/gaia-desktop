## మాడ్యూల్ ఒక్క చూపులో

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

ఇది కోర్ లైబ్రరీకి ఒక క్లయింట్ మాత్రమే, అంతకు మించి ఏమీ కాదు. ఇందులో **ఎలాంటి GS1 జ్ఞానమూ పొందుపరచలేదు**: ప్రతి
AI నిర్వచనం, ధ్రువీకరణ నియమం, దోష సందేశం మరియు స్థానికీకరించిన వివరణ [`GaiaParser`](../../../../gaia/docs/GaiaParser.md)
మరియు [`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md) నుంచే వస్తాయి. ముఖ్యంగా, AI జాబితాను ఈ మాడ్యూల్‌లోకి ఎప్పుడూ
కాపీ చేయరు — బిల్డర్ పికర్ కోర్ యొక్క సొంత రిజిస్ట్రీని చదువుతుంది, కాబట్టి బిల్డర్ తిరస్కరించే AI ని అది అందించలేదు.

**ప్రవేశ బిందువులు:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX `Application`) మరియు
`tools.pantheum.gaia.desktop.Launcher` (ప్యాకేజ్ చేసిన jar యొక్క `Main-Class`).

ఈ మాడ్యూల్ ఒక ఆకు (leaf): దేనికీ ఇది అవసరం కాదు, ఇది కూడా ఏ ఇతర దిగువ మాడ్యూల్‌పైనా ఆధారపడదు.

## బిల్డ్ చేయడం మరియు నడపడం

- నడపడానికి **Java 21**, బిల్డ్ చేయడానికి JDK 21 లేదా కొత్తది — మాడ్యూల్ `release=21` తో కంపైల్ అవుతుంది. JavaFX 21
  దానికి సరిపోయే LTS వరుస. కోర్ jar ఇప్పటికీ Java 11 బైట్‌కోడ్, 21 పై మార్పు లేకుండా నడుస్తుంది.
- `PATH` పై **Maven**. ఈ రిపోజిటరీలో wrapper లేదు.
- **ముందుగా కోర్‌ను ఇన్‌స్టాల్ చేయండి.** ఈ మాడ్యూల్ `gaia:1.1.0` ను `~/.m2` నుంచి తీసుకుంటుంది; పాత లేదా లేని కోర్ jar
  సాధారణంగా `package tools.pantheum.gaia does not exist` కి కారణం.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` ఒక్కటే కమాండ్-లైన్ ఆర్గ్యుమెంట్, మరియు మొత్తం ప్రొఫైల్‌ను వేరే చోటికి మళ్లించే `-Dgaia.desktop.home=…`
తప్ప, ప్రారంభాన్ని ప్రభావితం చేసే ఏకైక మార్గం.

`mvn javafx:run` అభివృద్ధి మార్గం: ప్లగిన్ JavaFX ను **మాడ్యూల్ పాత్** పై ఉంచుతుంది, కాబట్టి టూల్‌కిట్ పేరున్న మాడ్యూల్‌గా
ప్రారంభమవుతుంది, `GaiaDesktopApp` ను నేరుగా లాంచ్ చేయవచ్చు. ప్యాకేజ్ చేసిన jar అలా చేయలేదు — అందులో అంతా క్లాస్ పాత్‌పై
ఉంటుంది — అందుకే దాని `Main-Class` అనేది `Launcher` షిమ్. ఆ అమరికలో `Main-Class` గా `Application` ఉపక్లాస్ ఉంటే
*"JavaFX runtime components are missing"* తో విఫలమవుతుంది.

ఎప్పుడూ `clean` వాడండి — వేదికల సమూహాన్ని బిల్డ్ చేసే ముందు ఒక్కసారి, ఎందుకంటే అది `target/dist/` నుంచి అన్నింటినీ
ఖాళీ చేస్తుంది. కారణం కోసం [బిల్డ్ సమస్యల పరిష్కారం](#బిల్డ్-సమస్యల-పరిష్కారం) చూడండి.

### ప్యాకేజింగ్

పంపదగినదంతా `target/dist/gaia-desktop-<version>-<platform>/` కింద సేకరించబడుతుంది, ఇంకేమీ కాదు, కాబట్టి `target/` లో
`classes/`, `maven-status/` మరియు బిల్డ్ యొక్క మిగతా తాత్కాలిక ఫైళ్ల పక్కన ఉన్న ఆర్టిఫ్యాక్ట్‌లను ఏరకుండానే ఆ
డైరెక్టరీని ఒక సెట్‌గా zip లేదా కాపీ చేయవచ్చు. `${dist.dir}` దానికి ఒక్కచోటే పేరు పెడుతుంది; ఆర్టిఫ్యాక్ట్ రాసే ప్రతి
ప్లగిన్ దానినే సూచిస్తుంది.

#### ప్రతి వేదికకు ఒక బిల్డ్

JavaFX jar లు నేటివ్ కోడ్‌ను మోస్తాయి, కాబట్టి ప్రతి పంపిణీ ఒకే వేదిక కోసం, దాని పేరును `fx.platform` ప్రాపర్టీ OpenJFX
క్లాసిఫైయర్‌గా ఇస్తుంది: `mac-aarch64`, `mac`, `win`, `linux` లేదా `linux-aarch64`. OS ను బట్టి సక్రియమయ్యే ఐదు
`fx-*` ప్రొఫైల్‌లు దాన్ని బిల్డ్ చేస్తున్న యంత్రం యొక్క సొంత వేదికకు సెట్ చేస్తాయి, సాధారణ `mvn package` లేదా
`mvn javafx:run` కి కావలసింది అంతే; `-Dfx.platform=…` వాటిని అధిగమించి ఏ యంత్రం నుంచైనా ఏ ఇతర వేదికనైనా బిల్డ్ చేస్తుంది
— JavaFX jar లు కేవలం డౌన్‌లోడ్‌లు. `${dist.dir}` అంటే `target/dist/${fx.platform}`, కాబట్టి ఒక వేదిక బిల్డ్ మరొకదాని
బిల్డ్‌ను ఎప్పుడూ తిరగరాయదు.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

రెండు pom వివరాలు దీన్ని పని చేయిస్తాయి, రెండూ తీసివేయదగినవిగా కనిపిస్తాయి:

- **ప్రతి JavaFX మాడ్యూల్ ప్రత్యక్ష ఆధారం** — base, graphics, controls, media మరియు web — ఒక్కొక్కటీ
  `<classifier>${fx.platform}</classifier>` మరియు ఒక `org.openjfx:*` మినహాయింపుతో. OpenJFX pom లు తమ పరోక్ష
  (transitive) jar లను *బిల్డ్ చేస్తున్న యంత్రం* యొక్క OS ను బట్టి ఎంచుకుంటాయి, కాబట్టి graphics లేదా base ను పరోక్షంగా
  రానిస్తే Windows బిల్డ్‌లో Windows నేటివ్‌ల పక్కన Mac నేటివ్‌లు కూడా చేరుతాయి.
- **ప్రాపర్టీ `fx.platform`, `javafx.platform` కాదు.** బయటి నుంచి సెట్ చేస్తే OpenJFX సొంత ప్రాపర్టీని దాని పేరెంట్ pom
  తనతోనే మళ్లీ నిర్వచిస్తుంది; Maven ఆ pom ను చెల్లనిదిగా తిరస్కరించి వేదిక jar లను నిశ్శబ్దంగా వదిలేస్తుంది, JavaFX
  అసలే లేని బిల్డ్ మిగులుతుంది.

రెండు అమరికలూ ఒకే పాత్‌ను రాస్తాయి, `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`, ప్రతి బిల్డ్‌లో
వాటిలో సరిగ్గా ఒకటే నడుస్తుంది. `${jar.phase}`, `assembly.skipAssembly` మరియు `mdep.skip` రెండూ దాన్ని క్లెయిమ్
చేయకుండా ఆపుతాయి.

| | డిఫాల్ట్ | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — ఈ మాడ్యూల్ క్లాసులు మరియు వనరులు మాత్రమే | ~50 MB — ఆధారాలు దానిలోకి విప్పబడ్డాయి |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 jar లు, మానిఫెస్ట్ `Class-Path` లో ఒక్కొక్కటిగా పేర్కొన్నవి | — |
| పంపేది | jar **మరియు** దాని పక్కన `lib/` | ఒకే ఫైల్ |
| `dist/gaia-desktop-<version>-<platform>/` లో ఇంకా | `run.bat` (win) లేదా `run.sh` (ఇతరాలు) | అదే |
| మరియు | `readme.html` మరియు `docs/` (ప్రతి వేదిక) | అదే |

ప్రతి పంపిణీ మార్గదర్శినులను కూడా మోస్తుంది: `docs/` దాని అమరికతో కాపీ అవుతుంది, కాబట్టి మార్గదర్శినులు మరియు అనువాదాల
మధ్య లింకులు పని చేస్తూనే ఉంటాయి, అనువాద సాధనాలు (`check-i18n.py`, `i18n-manifest.json`) మినహా; మరియు
రూట్ వద్ద `readme.html`, ప్రతి దానికి లింక్ చేసే సూచిక, `src/main/dist/readme.html` నుంచి, అందులో `@VERSION@` pom
వెర్షన్‌తో మార్చబడుతుంది. రెండింటినీ `pick-launch-script` antrun దశ రాస్తుంది, తీసేసిన మార్గదర్శిని మిగిలిపోకుండా అది
ముందుగా `docs/` ను తొలగిస్తుంది. readme లింకులు చేతితో రాసినవి — `docs/` కింద మార్గదర్శిని పేరు మార్చినా లేదా అనువాదం
జోడించినా అక్కడ కూడా దాని వరుస కావాలి.

మానిఫెస్ట్ `Class-Path` మరియు `lib/` ఒకే విషయానికి రెండు సగాలు: jar ప్రతి రన్‌టైమ్ ఆధారానికి
`lib/<artifact>-<version>.jar` అని పేర్కొంటుంది, `copy-dependencies` సరిగ్గా ఆ పేర్లతో `lib/` ను నింపుతుంది. అదే
`java -jar` పని చేసేలా చేస్తుంది.

#### macOS యాప్ మరియు పంపిణీ zip

ఒక antrun అమలు, `mac-app-and-zip`, `package` దశను ముగిస్తుంది. ఆ కారణంగానే antrun ప్లగిన్‌ను jar మరియు assembly
ప్లగిన్‌ల **తర్వాత** ప్రకటించారు — Maven ఒక దశలోని అమలులను ప్లగిన్ ప్రకటన క్రమంలో నడుపుతుంది — కాబట్టి అది నడిచేటప్పుడు
jar, ఏ ప్యాకేజింగ్‌లోనైనా, ఇప్పటికే ఉంటుంది. (దాని మరో అమలు, `pick-launch-script`, `prepare-package` లో ఉంది, దానిపై
ప్రభావం ఉండదు.)

`mac` మరియు `mac-aarch64` కోసం అది ముందుగా పంపిణీ డైరెక్టరీలో `GAIA Desktop.app` ను నిర్మిస్తుంది: `Info.plist`
(`@VERSION@` ను pom వెర్షన్‌తో మార్చి), లాంచర్ `Contents/MacOS/gaia-desktop` (అమలు చేయదగినదిగా చేసి) మరియు
`gaia-desktop.icns`, అన్నీ `src/main/macos/` నుంచి, తర్వాత `gaia-desktop.jar` మరియు `lib/` ను `Contents/Java` లోకి
**తరలిస్తుంది**, కాబట్టి బండిల్ స్వతంత్రంగా నిలుస్తుంది. పక్కన jar లేనప్పుడు `run.sh` అక్కడ చూస్తుంది. లాంచర్ వెర్షన్‌ను బట్టి
Java ను వెతుకుతుంది (`java_home -v 21+`, తర్వాత Homebrew openjdk — Finder నుంచి లాంచ్ చేస్తే `JAVA_HOME` లేదా `PATH`
కనిపించవు), ఏదీ దొరకకపోతే `osascript` ద్వారా డైలాగ్ చూపుతుంది, logback యొక్క సాపేక్ష `logs/` రాయదగినదిగా ఉండేలా
`~/.gaia-desktop` కి `cd` చేస్తుంది, మరియు `-Xdock:name`/`-Xdock:icon` ను పంపుతుంది. macOS నడుస్తున్న `java` ను
బండిల్‌తో అనుబంధిస్తుంది (దాని bundle id మరియు Dock ఐకాన్ యాప్‌వే); మెనూ బార్‌లో GAIA Desktop కనిపిస్తుంది.

తర్వాత, ప్రతి వేదిక కోసం, అది Ant యొక్క `<zip>` తో డైరెక్టరీని అదే పేరున్న ఫోల్డర్ కింద
`target/dist/gaia-desktop-<version>-<platform>.zip` గా zip చేస్తుంది: `run.sh` మరియు `Contents/MacOS/**` ను
`filemode="755"` తో వేరే ఫైల్ సెట్‌గా, లేకపోతే unzip చేశాక అవి నడవవు. zip **జతచేయబడదు**: అది GitHub విడుదలల కోసం,
నాలుగు వేదికలు నాలుగు బిల్డ్‌ల నుంచి వస్తాయి, వాటిని Maven Central — ప్రతి వెర్షన్‌కు మార్చలేని ఒకే అప్‌లోడ్ — ఎప్పటికీ
ఒక విడుదలగా తీసుకోలేదు.

`project.build.outputTimestamp` ను బిల్డ్ సమయానికి సెట్ చేస్తారు. లేకపోతే maven-jar-plugin 3.5 మరియు
maven-assembly-plugin 3.8 లోని ఆర్కైవర్లు ప్రతి ఎంట్రీకి 1 ఫిబ్రవరి 1980 తేదీ వేస్తాయి.

యాప్ ఐకాన్‌ను `tools/icon/GaiaIcon.java` గీస్తుంది (ఇది బిల్డ్‌లో భాగం కాదు; దాని హెడర్‌లో `sips`/`iconutil` దశలు
ఉన్నాయి). దాని అవుట్‌పుట్‌లు రిపోజిటరీలో చెక్-ఇన్ చేయబడ్డాయి: బండిల్ కోసం `src/main/macos/gaia-desktop.icns`, మరియు
`src/main/resources/icons/gaia-desktop-{16..256}.png`, వీటిని `GaiaDesktopApp` విండో ఐకాన్‌గా సెట్ చేస్తుంది
(Windows మరియు Linux; macOS విండో ఐకాన్‌లను పట్టించుకోదు).

#### ప్రారంభ స్క్రిప్టులు

`run.sh` మరియు `run.bat` `src/main/scripts/` నుంచి వస్తాయి, ఫిల్టర్ లేకుండా `dist/gaia-desktop-<version>-<platform>/`
లోకి కాపీ అవుతాయి — `run.sh` నిండా `${...}` షెల్ విస్తరణలు ఉంటాయి, వాటిని Maven ఫిల్టరింగ్ ఇష్టం వచ్చినట్లు
తిరగరాయవచ్చు. తర్వాత ఒక antrun దశ వేదిక నడిపేదాన్ని మాత్రమే ఉంచుతుంది — `win` కి `run.bat`, మిగతా అన్నింటికీ `run.sh`
— మరియు `run.sh` పై అమలు బిట్‌ను సెట్ చేస్తుంది, ఎందుకంటే `copy-resources` దాన్ని మోయదు. అది ప్రొఫైల్‌ల ద్వారా కాకుండా
నిర్ధారించిన `${fx.platform}` నుంచి నిర్ణయిస్తుంది, ఎందుకంటే ప్రొఫైల్ సక్రియం మరో ప్రొఫైల్ సెట్ చేసిన విలువను చూడలేదు:
లేకపోతే Windows పై చేసిన Linux బిల్డ్‌కు హోస్ట్ స్క్రిప్ట్ వచ్చేది.

అవి **మానిఫెస్ట్‌పై ఆధారపడవు**. ఒక్కొక్కటీ క్లాస్ పాత్‌ను తానే నిర్మిస్తుంది, `gaia-desktop.jar` తర్వాత `lib/` లోని ప్రతి
`.jar`, `lib/*` వైల్డ్‌కార్డ్‌కు వదలకుండా ఒక్కొక్కటిగా పేర్కొని, కాబట్టి ఖాళీలున్న పాత్ ఒకే ఎంట్రీగా ఉంటుంది, జోడించిన
వాటి లెక్క నిజమైనది. `-cp` తో లాంచ్ చేయడమే అవి `tools.pantheum.gaia.desktop.Launcher` ను స్పష్టంగా పేర్కొనడానికి కారణం:
`-cp` మానిఫెస్ట్ `Main-Class` ను చదవదు. అయినా అది దాని `Class-Path` ను **ఇప్పటికీ** అనుసరిస్తుంది — `-cp` పై ఉన్న jar
తన మానిఫెస్ట్ పేర్కొన్న jar లను తెస్తుంది, అవి దాని తర్వాత వెంటనే వెతకబడతాయి — కాబట్టి స్క్రిప్ట్ జాబితాలో పెట్టినా
పెట్టకపోయినా ప్రతి `lib/` jar లోడ్ అవుతుంది, స్క్రిప్ట్ క్లాస్ పాత్ నుంచి ఒకదాన్ని తీసేసినా అది JVM బయట ఉండదు. అయినా
స్క్రిప్టులు అన్నింటినీ జాబితాలో పెడతాయి, కాబట్టి మానిఫెస్ట్ పాతదైనా, చేతితో మార్చినదైనా లేదా ఒక ఎంట్రీ తక్కువైనా ఆ jar
ప్రారంభమవుతుంది. ఒకే స్క్రిప్ట్ రెండు ప్యాకేజింగ్‌లకూ పని చేస్తుంది: `-Pfat` jar కి జోడించడానికి `lib/` లేదు, అవసరమూ
లేదు, అందుకే ఖాళీ `lib/` ఒక గమనిక మాత్రమే, దోషం కాదు.

#### Zebra స్థానిక లైబ్రరీలు

బిల్డ్ Zebra కి చెందినదేదీ పంపదు — DLL లు లేవు, సర్వీస్ jar లు లేవు. Windows పై అవి యంత్రంలో ఇన్‌స్టాల్ చేసిన Zebra
Scanner SDK నుంచి వస్తాయి: `run.bat` దాని `Jpos*.jar` సర్వీస్ jar లు మరియు `bin\` ను క్లాస్ పాత్‌కు, `bin\` ను `PATH` కు
జోడిస్తుంది, అక్కడ `System.loadLibrary` `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` ను కనుగొంటుంది
(`java.library.path` డిఫాల్ట్ `PATH`). JavaPOS API మరియు దాని కాన్ఫిగరేషన్ లోడర్ ఎల్లప్పుడూ `lib\javapos-*.jar`
నుంచే వస్తాయి, SDK ఉన్నా లేకపోయినా.

**`run.bat` SDK యొక్క సొంత JavaPOS jar ను ఎప్పుడూ జోడించదు**, `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`. ఒకప్పుడు
జోడించేది, API రెండు కాపీలు రాకుండా `lib\javapos-*.jar` ను వదిలేసేది — కానీ మానిఫెస్ట్ `Class-Path` వాటిని ఎలాగూ లోడ్
చేసింది (పైన చూడండి), కాబట్టి JVM కి రెండూ వచ్చాయి: `lib\` నుంచి 4.x లోడర్ క్లాసులు, వాటి పక్కన `javaPOS114.jar` యొక్క
`jpos/res/jpos.properties` మరియు `jcl.xsd`. ఆ ప్రాపర్టీస్ ఫైల్ [`JposConfig`](#స్కానర్-అనుసంధానం) ను పక్కకు
తప్పుకునేలా చేస్తుంది, ఆ `jcl.xsd` 1.10 వరకు ఉన్న JavaPOS వెర్షన్‌లను మాత్రమే అంగీకరిస్తుంది, కాబట్టి `jpos.xml` లోని
ప్రతి ఎంట్రీ (1.12–1.14) ధ్రువీకరణలో విఫలమైంది, రిజిస్ట్రీ ఖాళీగా ఉండిపోయింది, స్కానర్‌ను చేరకముందే ప్రతి కనెక్ట్ దోషం 109
తో విఫలమైంది. దానికి ఆ jar క్లాస్ పాత్‌పై ఉండటమే చాలు, `lib\` jar ల వెనుక ఉన్నా సరే. Zebra సర్వీస్ jar లు `lib\` లోని
1.14 API పై మార్పు లేకుండా నడుస్తాయి — open, claim మరియు స్కాన్ ఆ విధంగానే నిజమైన స్కానర్‌పై ధ్రువీకరించబడ్డాయి.
`run.bat` పక్కన చేతితో ఉంచిన DLL లు ఇప్పటికీ గౌరవించబడతాయి: అప్పుడు స్క్రిప్ట్ `-Djava.library.path=<dist>;%PATH%` ను
సెట్ చేస్తుంది, `PATH` ను చివరన జోడిస్తూ, ఎందుకంటే ఈ ప్రాపర్టీ డిఫాల్ట్ శోధన పాత్‌ను పూర్తిగా భర్తీ చేస్తుంది.

`mvn javafx:run` వీటిలో ఏదీ చేయదు, కాబట్టి Windows పై అభివృద్ధి రన్ నుంచి స్కానర్‌ను claim చేయడానికి SDK jar లను క్లాస్
పాత్‌పై మరియు దాని `bin\` ను `PATH` పై వేరే మార్గాల్లో ఉంచాలి; దాని కోసం `dist/` నుంచి నడపండి.

క్లాస్ పాత్‌తో పాటు అవి `java -jar` చేయనివి కూడా చూసుకుంటాయి: ఏ పని డైరెక్టరీ నుంచైనా పని చేసేలా తమ సొంత డైరెక్టరీని
నిర్ధారించడం, `PATH` కంటే `JAVA_HOME` కి ప్రాధాన్యం ఇవ్వడం, మరియు 11 కి ముందటి JVM ను `UnsupportedClassVersionError`
బదులు పరిష్కారాన్ని చెప్పే వాక్యంతో తిరస్కరించడం. `GAIA_DESKTOP_OPTS` JVM ఎంపికలను ముందుకు పంపుతుంది. `run.bat`
`javaw.exe` కాకుండా `java.exe` వాడుతుంది, కాబట్టి కన్సోల్ తెరిచే ఉంటుంది — స్కానర్ నడిచే ఏకైక వేదిక Windows, దాని స్థితి
మరియు JavaPOS దోషాలు అక్కడికే వెళ్తాయి.

`run.bat` తనకు దొరికిన వాటి నుంచి Java, JavaFX మరియు Zebra సర్వీసులను కూడా ఎంచుకుంటుంది — బండిల్ చేసిన `jdk*\`,
మాడ్యూల్ పాత్‌పై `javafx-sdk*\lib\`, `ZEBRA_HOME` వద్ద Zebra Scanner SDK — SDK యొక్క JavaFX వాడేటప్పుడు `lib\` లోని
JavaFX కాపీలను క్లాస్ పాత్ బయట ఉంచుతుంది, మరియు JDK యొక్క SAX పార్సర్, Windows ప్రాక్సీలు మరియు ట్రస్ట్ స్టోర్, Java 17+
పై `--enable-native-access` ను పంపుతుంది. README లోని [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows)
లో పట్టిక ఉంది. ఫైల్ యొక్క CRLF లైన్ ముగింపులను ఉంచండి: LF మాత్రమే ఉన్న బ్యాచ్ ఫైల్‌లో `cmd.exe` ఒక `call :label` ను
తప్పిపోవచ్చు. `run.sh` కూడా `--enable-native-access=ALL-UNNAMED` ను పంపుతుంది — JavaFX తన సొంత నేటివ్‌లను `lib/` నుంచి
లోడ్ చేస్తుంది, JavaFX క్లాస్ పాత్‌పై ఉన్నప్పుడు దాన్ని కవర్ చేసే మాడ్యూల్ `ALL-UNNAMED` — `run.bat` లో లాగానే, Java
వెర్షన్ చదవలేనప్పుడు మాత్రమే వదిలేయబడుతుంది.

రెండు అమరికలూ **ఒకే వేదిక** యొక్క, `${fx.platform}` యొక్క, JavaFX నేటివ్‌లను మోస్తాయి, కాబట్టి ఏదీ OS లేదా ఆర్కిటెక్చర్
దాటి పోర్టబుల్ కాదు. ప్రతి లక్ష్యానికి ఒకసారి బిల్డ్ చేయండి — [ప్రతి వేదికకు ఒక బిల్డ్](#ప్రతి-వేదికకు-ఒక-బిల్డ్) చూడండి.

> **Eclipse.** `copy-dependencies` అమలులో ఒక `<?m2e ignore?>` సూచన ఉంది. m2e తెరిచి ఉన్న వర్క్‌స్పేస్ ప్రాజెక్ట్‌ను jar
> కు బదులు దాని `target/classes` ఫోల్డర్‌కు నిర్ధారిస్తుంది, `copy-dependencies` ప్యాకేజ్ చేయని ఆర్టిఫ్యాక్ట్‌ను కాపీ
> చేయడానికి నిరాకరిస్తుంది (MDEP-187), దీనివల్ల `gaia` ప్రాజెక్ట్ దీని పక్కన తెరిచి ఉన్నప్పుడల్లా ఆటో-బిల్డ్ విఫలమవుతుంది.
> ఫలితంగా, IDE లో మాత్రమే చేసిన బిల్డ్ `target/dist/gaia-desktop-<version>-<platform>/lib/` ను నింపదు; jar ను స్వయంగా
> వాడే ముందు `mvn package` నడపండి.

### ప్రవేశ గరాటు

ప్రతి ఇన్‌పుట్ — టైప్ చేసినది, అతికించినది, ఫైల్ నుంచి తెరిచినది, స్కాన్ చేసినది లేదా నిర్మించినది — ఒకే మెథడ్ ద్వారా,
`MainView.capture(String, ScanSource, String)`, పార్సర్‌ను చేరుతుంది.

యాప్ దేని చుట్టూ నిర్మించబడిందో ఆ ఏకైక డిజైన్ నిర్ణయం ఇదే. నిర్మాణానికి సొంత నివేదిక, సొంత చరిత్ర లేదా సొంత ఎగుమతి మార్గం
అవసరం లేదు, ఎందుకంటే గరాటు తర్వాత నిర్మించిన స్ట్రింగ్‌ను స్కాన్ చేసిన దాని నుంచి వేరు చేయలేం. ఇన్‌పుట్‌ను ఉత్పత్తి చేసే
కొత్తదేదైనా దాని పక్కగా కాకుండా దాని గుండానే వెళ్లాలి.

### థ్రెడింగ్

| థ్రెడ్ | ఏమి నడుపుతుంది |
|---|---|
| JavaFX అప్లికేషన్ థ్రెడ్ | అన్ని పార్సింగ్, రెండరింగ్ మరియు UI. AI పట్టికలు వేడెక్కాక పార్సింగ్ ఒక మిల్లీసెకను కంటే తక్కువ, కాబట్టి వర్కర్ అవసరం లేదు |
| `gaia-scanner` | స్కానర్‌లోకి ప్రతి కాల్ — open, claim, enable, disable, release, close. `ScannerService` స్వంతమైన దీర్ఘకాల థ్రెడ్ ఒకటి; [స్కానర్ అనుసంధానం](#స్కానర్-అనుసంధానం) చూడండి |
| JavaPOS ఈవెంట్ థ్రెడ్ | `ScannerService` కాల్‌బ్యాక్‌లు. `MainView.FxScannerListener` ప్రతి దాన్నీ `Platform.runLater` తో అవతలికి చేరుస్తుంది |
| నేపథ్యం | స్కానర్ `connect()` / `disconnect()` కోసం వేచి ఉండటం (claim కు 5 సెకన్ల వరకు పట్టవచ్చు), ప్రారంభంలో సేవ్ చేసిన చరిత్రను పునరుద్ధరించడం — ఇది పార్సర్‌ను వేడెక్కించే పని కూడా చేస్తుంది — మరియు అప్‌డేట్ తనిఖీ (`gaia-update-check`, ఒక GitHub అభ్యర్థన, ఫలితం `Platform.runLater` తో తిరిగి పంపబడుతుంది) |

**ఒక నియంత్రణ యొక్క ఎంపికను దాని సొంత ఎంపిక ఈవెంట్ లోపలి నుంచి ఎప్పుడూ మార్చవద్దు, ఆ నియంత్రణను నాశనం చేయవద్దు.** ఈ
యాప్‌లో మూడు వేర్వేరు క్రాష్‌లు సరిగ్గా దీని వల్లే వచ్చాయి: పాప్అప్ సొంత `clearAndSelect` లోపల AI పికర్‌ను రీసెట్ చేయడం
(`ListViewBehavior` నుంచి వచ్చిన `IndexOutOfBoundsException`), మరియు భాషా కాంబోను కలిగి ఉన్న ప్యానెల్‌ను ఆ కాంబో సొంత
హ్యాండ్లర్ లోపలి నుంచి పునర్నిర్మించడం. రెండూ ఇప్పుడు `Platform.runLater` తో వాయిదా వేయబడ్డాయి, కారణాలు రెండు కాల్
స్థానాల్లోనూ నమోదై ఉన్నాయి.

### పునర్నిర్మాణం మరియు తిరిగి లేబుల్ చేయడం

భాష మార్పు చట్రాన్ని — మెనూలు, టూల్‌బార్, ఎంపికల ప్యానెల్ — కేటలాగ్ నుంచి **పునర్నిర్మిస్తుంది**, ఇది సురక్షితం ఎందుకంటే
వాటిలో దేనికీ స్థితి ఉండదు: `OptionsPane` అనేది `ParseOptions` యొక్క రెండు-వైపుల దృశ్యం, కాబట్టి విలువలు మోడల్‌లో
ఉంటాయి, కొత్త ప్యానెల్ వాటిని వెంటనే తిరిగి తీసుకుంటుంది.

**వినియోగదారు డేటా** ను పట్టుకున్న నియంత్రణలు ఫీల్డ్‌లు, వాటిని బదులుగా అక్కడికక్కడే తిరిగి లేబుల్ చేస్తారు:
`BuilderPane.retext(UiStrings)` AI వరుసలు, Digital Link ఫీల్డ్‌లు మరియు ఎంపికను ఉంచుతుంది. దాన్ని పునర్నిర్మిస్తే జరుగుతున్న
పని పోతుంది — ఒకప్పుడు అలాగే జరిగింది కూడా.

## {GS} టోకెన్

JavaFX `TextField` `0x20` కంటే తక్కువ ఉన్న ప్రతి అక్షరాన్ని నిశ్శబ్దంగా వదిలేస్తుంది (`TextInputControl.filterInput`).
"వింతగా చూపిస్తుంది" కాదు — తొలగిస్తుంది. టైప్ చేయడం, అతికించడం, `setText` మరియు `insertText` అన్నీ ప్రభావితమవుతాయి,
కాబట్టి `setText("01…" + GS + "10LOT")` నుంచి `"01…10LOT"` వస్తుంది: అర్థం నిశ్శబ్దంగా మారిన ఎలిమెంట్ స్ట్రింగ్,
ఎందుకంటే మారే-పొడవు AI ఇప్పుడు తన తర్వాత వచ్చినదాన్ని మింగేస్తుంది.

`desktop.parse.GsToken` పూర్తి సమాధానం. విభాజకం UI గుండా అక్షరశః టెక్స్ట్ `{GS}` గా ప్రయాణించి, పార్సర్‌కు వెళ్లే దారిలో
మళ్లీ `0x1D` అవుతుంది. ఈ టోకెన్ ఇక్కడ కనిపెట్టింది కాదు — కోర్ యొక్క `ASCIIRevealerUtils.printable` `0x1D` ను సరిగ్గా
ఇలాగే చూపిస్తుంది, కాబట్టి నివేదిక నుంచి కాపీ చేసిన విలువను నేరుగా ఇన్‌పుట్ బార్‌లోకి తిరిగి అతికించవచ్చు.

ఇన్‌పుట్ ఫీల్డ్‌పై ఉన్న `TextFormatter` ఫిల్టర్ టెక్స్ట్ రాగల ప్రతి మార్గాన్నీ పట్టుకుంటుంది — టైప్ చేయడం, ⌘V, సందర్భ మెనూ,
లాగి వదలడం, `setText` — అందుకే తిరగరాత ప్రతి హ్యాండ్లర్‌లో కాకుండా అక్కడే ఉంటుంది.

స్కానర్ మార్గం ఎప్పుడూ `GsToken` గుండా వెళ్లదు: స్కాన్‌లు పార్సర్‌ను బైట్‌లుగా చేరుతాయి.

## స్కానర్ అనుసంధానం

`ScannerService` JavaPOS `Scanner` నియంత్రణకు యజమాని: open → claim → enable, ప్రతి స్కాన్ తర్వాత డేటా ఈవెంట్‌ను మళ్లీ
సక్రియం చేస్తూ. తార్కిక పరికర పేర్లు `src/main/resources/jpos.xml` నుంచి వస్తాయి.

**ప్రతి పరికర కాల్ ఒకే థ్రెడ్‌పై, `gaia-scanner` పై, నడుస్తుంది, అది సర్వీస్ ఉన్నంత కాలం ఉంటుంది** — ఎప్పుడూ FX థ్రెడ్‌పై
కాదు, కాల్ తర్వాత ముగిసే థ్రెడ్‌పై ఎప్పుడూ కాదు. Zebra సర్వీస్ CoreScanner COM API ద్వారా JNI తో స్కానర్‌ను చేరుతుంది,
COM తాను ఏర్పాటు చేసిన దాన్ని కాల్ చేసిన థ్రెడ్ యొక్క అపార్ట్‌మెంట్‌కు కట్టేస్తుంది: తర్వాత ముగిసే థ్రెడ్‌పై open చేస్తే
స్కానర్ claim అవుతుంది కానీ మౌనంగా ఉంటుంది; వేరే థ్రెడ్‌పై close చేస్తే తప్పు అపార్ట్‌మెంట్ అన్‌ఇనిషియలైజ్ అవుతుంది. FX
థ్రెడ్‌పై close చేయడం అత్యంత చెడ్డ సందర్భం, ఎందుకంటే JavaFX అక్కడ `OleInitialize` ను కాల్ చేసి ప్రతి విండో డ్రాప్
లక్ష్యాన్ని దానికి వ్యతిరేకంగా నమోదు చేస్తుంది — దానిపై ఒక `CoUninitialize` మొత్తం యాప్‌లో లాగి వదలడాన్ని చంపేస్తుంది.
ఇది Windows పై JavaFX విషయం, ఏ ఒక్క JavaFX వెర్షన్‌దీ కాదు. `connect()` మరియు `disconnect()` ఆ థ్రెడ్‌కు పనిని అప్పగించి
వేచి ఉంటాయి, కాబట్టి `MainView` రెండింటినీ స్వల్పకాల నేపథ్య థ్రెడ్ నుంచి కాల్ చేస్తుంది.

రెండు నియమాలు తప్పుగా ప్రవర్తించే పరికరం కనెక్షన్‌ను అడ్డుకోకుండా ఆపుతాయి. **మూసివేత ఎప్పుడూ ముందుగానే ఆగదు:**
`closeQuietly` disable, release మరియు close ను వేర్వేరు దశలుగా చేస్తుంది, claim పట్టుకుని ఉన్నప్పుడే release చేస్తుంది,
ఎల్లప్పుడూ `close()` ను ప్రయత్నిస్తుంది — విఫలమైన claim తర్వాత `release()` "not claimed" ను విసురుతుంది, దశలు ఒకే `try`
ను పంచుకున్నప్పుడు అది close ను దాటవేసి పరికరాన్ని Zebra సర్వీస్‌లో తెరిచి వదిలేసేది. **డేటా ఈవెంట్‌ను `finally` లో మళ్లీ
సక్రియం చేస్తారు:** JavaPOS ప్రతి ఈవెంట్ తర్వాత దాన్ని నిష్క్రియం చేస్తుంది, కాబట్టి మినహాయింపు విసిరే రీడ్ లేదా హ్యాండ్లర్
కూడా మళ్లీ సక్రియం చేయాలి, లేకపోతే తిరిగి కనెక్ట్ అయ్యే వరకు స్కానర్ మౌనంగా ఉంటుంది. `ScannerLifecycleTest` రెండింటినీ
స్క్రిప్ట్ చేసిన `jpos.Scanner` పై పరీక్షిస్తుంది.

**`JposConfig` మొదటి open కి ముందు JavaPOS ను బండిల్ చేసిన `jpos.xml` వైపు చూపిస్తుంది.** Maven JavaPOS jar లతో
(`javapos-config-loader` 4.x) మరియు క్లాస్ పాత్‌పై `jpos/res/jpos.properties` లేనప్పుడు, లేకపోతే ప్రతి open
*"Service does not exist in loaded JCL registry"* (దోషం 109) తో విఫలమవుతుంది, మూడు వేర్వేరు కారణాల వల్ల: సర్వీస్
మేనేజర్ `SimpleRegPopulator` కి వెనక్కి వెళ్తుంది, అది సీరియలైజ్ చేసిన `jpos.cfg` ను చదువుతుంది, `jpos.xml` ను ఎప్పుడూ
కాదు; XML లోడర్ `jpos.xml` ను పని డైరెక్టరీలో మాత్రమే వెతుకుతుంది, jar లోపల కాదు; మరియు `lib/` లోని Xerces 2.12.2
లోడర్ సెట్ చేసే JAXP `accessExternalDTD` ప్రాపర్టీని తిరస్కరిస్తుంది. `JposConfig` `jpos.config.regPopulatorClass`
(`JavaxRegPopulator`), `jpos.config.populatorFileURL` (jar సొంత `jar:file:…!/jpos.xml`) మరియు
`javax.xml.parsers.SAXParserFactory` (JDK ది) ను సిస్టమ్ ప్రాపర్టీలుగా సెట్ చేస్తుంది — ఇప్పటికే సెట్ చేసినదాన్ని ఎప్పుడూ
కాదు, కాబట్టి `-Djpos.config.populatorFileURL=file:…` ఇప్పటికీ వేరే `jpos.xml` ను ఎంచుకోగలదు — మరియు క్లాస్ పాత్‌పై
`jpos.properties` ఉన్నప్పుడు లేదా 4.x లోడర్ లేనప్పుడు ఏదీ సెట్ చేయదు. Zebra SDK యొక్క `javaPOS114.jar` అలాంటి సందర్భమే,
అది రిజిస్ట్రీని పూర్తిగా విరగ్గొడుతుంది, అందుకే `run.bat` దాన్ని క్లాస్ పాత్ బయట ఉంచుతుంది —
[Zebra స్థానిక లైబ్రరీలు](#zebra-స్థానిక-లైబ్రరీలు) చూడండి. `JposConfigTest` ఆ తర్వాత రిజిస్ట్రీలో ఫైల్ స్కానర్‌లు ఉన్నాయని
మొదటి నుంచి చివరి వరకు తనిఖీ చేస్తుంది.

**పరికర పికర్ ఆ రిజిస్ట్రీ నుంచే రూపొందించబడుతుంది**, కోడ్‌లో జాబితాగా ఉంచబడదు: `ScannerService.logicalNames()`
`gaia-scanner` థ్రెడ్‌పై లోడ్ అయిన ఎంట్రీలను చదివి, పరికర వర్గం `Scanner` అయినవాటిని ఉంచుతుంది — `jpos.xml` లోని రెండు
తూనిక ఎంట్రీలు బయటే ఉంటాయి — `pickerOrder` క్రమంలో: ఫైల్ దాన్ని నిర్వచిస్తే `ZebraAllScanners` మొదట, మిగతావి అక్షర
క్రమంలో (రిజిస్ట్రీ ఫైల్ క్రమాన్ని ఉంచదు). అది లేని ఫైల్‌కు అది ఇవ్వబడదు; ఏదీ లోడ్ కాకపోతే డిఫాల్ట్ ఒక్కటే అందించబడుతుంది,
కాబట్టి పికర్ ఎప్పుడూ ఖాళీగా ఉండదు. `MainView` డిఫాల్ట్‌ను వెంటనే చూపి, సేవ్ చేసిన ఎంపికను ఉంచుతూ నేపథ్య థ్రెడ్ నుంచి
జాబితాను నింపుతుంది. కాబట్టి `jpos.xml` కి జోడించిన స్కానర్ — లేదా `-Djpos.config.populatorFileURL` తో పేర్కొన్న పూర్తి
ఫైల్ — కోడ్ మార్పు లేకుండానే పికర్‌లో కనిపిస్తుంది, `JposConfigTest` పికర్‌ను బండిల్ చేసిన ఫైల్ యొక్క స్వతంత్ర పఠనంతో
పోల్చి తనిఖీ చేస్తుంది. ఆ ఎంట్రీలు పేర్కొనే సర్వీసులు Zebra క్లాసులు (`com.zebra.jpos.service.scanner.*Factory`), అవి
ఇప్పటికీ క్లాస్ పాత్‌పై ఉండాలి — `run.bat` ద్వారా Scanner SDK నుంచి, లేదా `lib\` లో వేసిన Zebra సర్వీస్ jar ల నుంచి.

స్కాన్ డేటా **ISO-8859-1** గా డీకోడ్ అవుతుంది, కాబట్టి ప్రతి బైట్ 1:1 గా మ్యాప్ అవుతుంది, AIM Code ID ఉపసర్గ మరియు ప్రతి
`0x1D` రెండూ నిలిచి ఉంటాయి; నివేదికలు UTF-8 గా రాయబడతాయి.

సర్వీస్‌లోని ఏదీ వినియోగదారు కోసం టెక్స్ట్ కూర్చదు. ఈవెంట్‌లు `ScannerListener.Event` స్థిరాంకాలు మరియు మారే విలువలుగా
బయటకు వెళ్తాయి, `MainView` కేటలాగ్ నుంచి పదాలను అందిస్తుంది — లేకపోతే 35 విధాలుగా అనువదించిన అనువర్తనంలో స్థితి
లైన్ ఆంగ్లంలో ఉండేది. లాగ్ లైన్‌లు మినహాయింపు, అవి ఆంగ్లంలోనే ఉంటాయి.

### వేదిక ద్వారం

`ScannerService.isSupportedPlatform()` ఒక `os.name` పరీక్ష, `MainView` ఏ స్కానర్ నియంత్రణనైనా నిర్మించే ముందు దాన్ని
అడుగుతుంది: macOS మరియు Linux పై టోగుల్ లేదు, పరికర పికర్ లేదు, స్కానర్ మెనూ లేదు (కాబట్టి <kbd>⌘K</kbd> కూడా లేదు),
స్థితి లేబుల్ లేదు. అవి దాచబడలేదు — అవి ఎప్పుడూ నిర్మించబడవు.

Zebra తన JavaPOS సర్వీసులను Windows కోసం మాత్రమే పంపుతుంది, ఇతర చోట్ల ఏదీ ముందుగా విఫలం కాదు: jar లు నిర్ధారించబడతాయి,
నియంత్రణ నిర్మించబడుతుంది, చివరికి నేటివ్ పొర లేనందున విఫలమయ్యేది `open()`, కొన్ని సెకన్లు మరియు ఒక డైలాగ్ తర్వాత.

ఈ నియమం *సర్వీసుల* గురించి, JavaPOS గురించి కాదు. క్రాస్-ప్లాట్‌ఫామ్ సర్వీస్ పంపే విక్రేత ఇక్కడ పని చేస్తారు, నియమాన్ని
విస్తరించడం అంటే `supportsJavaPos(String)` లో మాత్రమే మార్పు — అది package-private, `os.name` స్ట్రింగ్‌లకు వ్యతిరేకంగా
పరీక్షించబడింది, కాబట్టి బిల్డ్ నడిపే ఏ యంత్రంపైనైనా రెండు సమాధానాలూ కవర్ అవుతాయి.

### సింబాలజీలు

`Symbologies` అన్ని **78** JavaPOS `SCAN_SDT_*` స్కాన్-డేటా రకాలను ప్రదర్శన పేర్లకు, మరియు రెండు పదజాలాలు సరిపోయే చోట
కోర్ యొక్క `DataCarrierType` కు మ్యాప్ చేస్తుంది. రెండింటిలో JavaPOS సూక్ష్మమైనది — అది UPC-A ను EAN-13 నుంచి, సాధారణ
Data Matrix ను GS1 DataMatrix నుంచి వేరు చేస్తుంది, AIM మాత్రం ఒక కుటుంబం మొత్తాన్ని ఒకే కోడ్ అక్షరం కింద సమూహం
చేస్తుంది.

పట్టిక బయట ఉన్న రకానికి కూడా వాడదగిన పేరు వస్తుంది, అది `ScannerConst` పై రిఫ్లెక్షన్ ద్వారా కనుగొనబడుతుంది, ఎందుకంటే
విక్రేత సర్వీసులు నిజంగానే స్పెసిఫికేషన్ జాబితా బయటి విలువలను నివేదిస్తాయి. ఒక పరీక్ష `ScannerConst` గుండా నడిచి, ప్రకటించిన
ఏ రకానికైనా పేరు లేకపోతే విఫలమవుతుంది — భవిష్యత్ JavaPOS జోడించే స్థిరాంకాలను కూడా ఇది పట్టుకుంటుంది.

కొన్ని క్యారియర్ మ్యాపింగ్‌లు ఊహించకుండా ఉద్దేశపూర్వకంగా `UNKNOWN` గా వదిలేశారు: straight 2 of 5 (AIM `]R`/`]S` ను
start/stop బార్ల సంఖ్యను బట్టి వేరు చేస్తుంది, దాన్ని JavaPOS నివేదించదు), నాలుగు-స్థితుల తపాలా కోడ్‌లు, మరియు TLC-39.

## స్థానికీకరణ

లేబుల్‌లు ప్రతి భాషకు ఒక ప్రాపర్టీస్ ఫైల్‌లో `src/main/resources/i18n/ui_<CODE>.properties` కింద ఉంటాయి, కోర్ దోష
కేటలాగ్‌ల లాగానే అదే కోడ్‌లను వాడుతూ (`EN`, `FR`, `PCM`, …). మొత్తం 35 ఉన్నాయి, మొత్తం 35 ఒకే కీ సమితిని కలిగి
ఉన్నాయి. ఫైళ్లు **UTF-8** గా చదవబడతాయి, `Properties` ఊహించే ISO-8859-1 గా కాదు, కాబట్టి అనువాదాలు `\uXXXX`
ఎస్కేప్‌లుగా కాకుండా చదవగలిగే రూపంలో నిల్వ అవుతాయి.

**ఫాల్‌బ్యాక్ ప్రతి కీకి, ప్రతి ఫైల్‌కు కాదు** — పాక్షికంగా అనువదించిన భాష దాని మొదటి కీ చేరిన క్షణం నుంచే ఉపయోగపడేలా
చేసేది ఇదే. ఆంగ్లమే ఒప్పందం: ప్రతి కీ అక్కడ ఉండాలి.

| పొర | కీలు | వ్యాప్తి |
|---|---|---|
| పంచుకున్న నివేదిక పదజాలం | 31 | మొత్తం 35 భాషలు |
| డెస్క్‌టాప్ చట్రం — మెనూలు, బటన్లు, బిల్డర్, ఎంపికలు, స్థితి లైన్, నివేదిక అమరిక, స్కానర్ స్థితి, డైలాగ్ పాఠ్యాలు | 114 | మొత్తం 35 భాషలు |

పంచుకున్న పదాలలో ఆరు (`generated`, `status`, `dlRole`, `interpretations`, `message`, `level`) ఈ యాప్ నివేదికలో
వాడబడవు.
వాటిని ఉద్దేశపూర్వకంగా ఉంచారు; ఫైల్ హెడర్ ఆ విషయం చెబుతుంది.

### `--language` ఆర్గ్యుమెంట్

`GaiaDesktopApp.languageOverride()` JavaFX సొంత `getParameters().getNamed()` ద్వారా `--language=…` ను చదివి,
`Languages.fromArgument` తో దాన్ని నిర్ధారిస్తుంది — కేటలాగ్ కోడ్, enum పేరు, లేదా BCP 47 ట్యాగ్, పెద్ద-చిన్న అక్షరాల
భేదం లేకుండా — మరియు `MainView` కి అప్పగిస్తుంది.

**ఈ ఓవర్‌రైడ్ రన్ కోసం, ఫైల్ కోసం కాదు.** `MainView` తాను లోడ్ చేసిన భాషను `savedLanguage` లో ఉంచి, *దాన్నే* తిరిగి
రాస్తుంది, `languageChosenInSession` వినియోగదారు స్వయంగా భాషను ఎంచుకున్నారని చెప్పే వరకు; అప్పుడు వారి ఎంపిక మామూలుగా
నిలుస్తుంది. ఆ విభజనే మొత్తం డిజైన్: కియోస్క్ ప్రొఫైల్ లేదా డెమో షార్ట్‌కట్ యంత్ర యజమాని రేపు తెరిచే భాషను మార్చకుండానే
స్పానిష్‌లో తెరవగలదు, అదే సమయంలో ఎంపికల ప్యానెల్‌లో చేసిన నిజమైన ఎంపిక నిలిచి ఉంటుంది.

ఏ కేటలాగ్‌నూ సూచించని విలువ ఆమోదించిన కోడ్‌లతో పాటు లాగ్ చేయబడి విస్మరించబడుతుంది. షార్ట్‌కట్‌లోని ఒక అక్షర దోషం కారణంగా
ప్రారంభించడానికి నిరాకరించడం మరింత చెడ్డ వైఫల్యం అవుతుంది, అదే కారణంతో `Languages.fromArgument` మినహాయింపు విసరకుండా
`null` ను తిరిగి ఇస్తుంది.

### భాషను జోడించడం

కోడ్ మార్పు అవసరం లేదు.

1. `ui_<CODE>.properties` ను సవరించండి — ప్రతి భాషకూ ఇప్పటికే ఫైల్ ఉంది.
2. విలువలను అనువదించండి. `{0}` / `{1}` ప్లేస్‌హోల్డర్‌లను అలాగే వదలండి.
3. బిల్డ్ చేయండి. రెండు పరీక్షలు ఒప్పందాన్ని అమలు చేస్తాయి: కోడ్ ఆంగ్లం నిర్వచించని కీని అడిగితే ఒకటి విఫలమవుతుంది, ఏ
   కేటలాగ్ కీ సమితి అయినా ఆంగ్లం నుంచి తప్పుకుంటే మరొకటి విఫలమవుతుంది.

మొదటి పరీక్ష క్లాసులపై రిఫ్లెక్షన్ చేయకుండా **సోర్స్ కోడ్** లో కీ లిటరల్‌ల కోసం స్కాన్ చేస్తుంది, ఎందుకంటే కీలు కాల్
స్థానాల్లో స్ట్రింగ్ లిటరల్‌లుగా మాత్రమే ఉంటాయి. అందుకే కొత్త సందేశాన్ని వేరియబుల్ ద్వారా వెతకకుండా కీని నేరుగా రాసి
నిర్మించాలి — `strings.format("st.scannerError", …)` — లేకపోతే పరీక్ష దాన్ని చూడలేదు.

### ఉద్దేశపూర్వకంగా అనువదించనివి

- ముడి విలువల పక్కన మోనోస్పేస్‌లో చూపే సంక్షిప్త ఫీల్డ్ పేర్లు — ఎలిమెంట్ కార్డ్ యొక్క `format`, `position`, `length`,
  `raw` మరియు `part`, టేప్ యొక్క `AI`, `sep`, `pos` మరియు `len`, మరియు దోషం స్థానాన్ని చూపే నాలుగు సెల్‌లు (`AI`,
  `position`, `level`, `stage`), వీటి విలువలు ఎలాగూ అనువదించని enum పేర్లే;
- GS1 నిర్మాణాలకు పేరు పెట్టే నమూనా-ఇన్‌పుట్ పేర్లు, మరియు సరైన నామవాచకాలైన సింబాలజీ పేర్లు;
- `GE-C084` పరిష్కార పేరా — సగం అనువాదం ఆంగ్లం కంటే చెడ్డదైన ప్రమాణాల గద్యం;
- `ElementBuilder` యొక్క తెలియని-AI చివరి రక్షణ, ఇది UI నుంచి చేరలేనిది: ఎడిటర్ తెలియని AI లను తానే తనిఖీ చేసి వాటిని
  కేటలాగ్ నుంచి నివేదిస్తుంది;
- లాగ్ లైన్‌లు.

ఒక లోటు మిగిలి ఉంది: `ScanSource.label()` చరిత్ర వరుసకు మరియు నివేదిక శీర్షికకు `manual` / `scanner` / `file` /
`built` ను ఆంగ్లంలో అందిస్తుంది. దాన్ని మూసివేయడానికి ఒక కీ కంటే ఎక్కువ కావాలి — `HistoryCell` కి `UiStrings` లేదు,
జాబితా సెల్ ఫ్యాక్టరీ ఒక్కసారే ఇన్‌స్టాల్ అవుతుంది, కాబట్టి భాష మారినప్పుడు సెల్‌లను కూడా రిఫ్రెష్ చేయాల్సి ఉంటుంది.

## నిల్వ చేసిన స్థితి ఫార్మాట్లు

`~/.gaia-desktop/` కింద రెండు ఫైళ్లు, అవి వేర్వేరు వేగాలతో మారతాయి కాబట్టి వేరుగా ఉంచారు — పాడైన లేదా చేతితో సవరించిన
క్యాప్చర్ లాగ్ వినియోగదారు సెట్టింగ్‌లను పోగొట్టకూడదు. డైరెక్టరీని `-Dgaia.desktop.home=…` తో మార్చండి, దీని వల్లే
పరీక్షలు నిజమైన హోమ్ డైరెక్టరీకి దూరంగా ఉంటాయి.

**`options.properties`** — ఒక ఎంపిక మారినప్పుడు, మరియు నిష్క్రమించేటప్పుడు రాయబడుతుంది.

| కీ | అర్థం |
|---|---|
| `parse.mode`, `parse.language` | పైప్‌లైన్ లోతు మరియు సందేశ భాష |
| `date.endian`, `date.separator`, `date.month`, `date.year` | తేదీ ప్రదర్శన |
| `check.skipRequires`, `check.skipExcludes` | నిర్మాణ తనిఖీ నుంచి మినహాయింపులు |
| `ui.theme` | `LIGHT` లేదా `DARK` |
| `ui.optionsPane` | ఎంపికల ప్యానెల్ తెరిచి ఉందా? |
| `ui.scannerDevice` | చివరి JavaPOS తార్కిక పేరు |
| `ui.mode` | `PARSE`, `BUILD` లేదా `COMBINE` |
| `update.check` | రోజువారీ అప్‌డేట్ తనిఖీ నడుస్తుందా (డిఫాల్ట్ `true`) |
| `update.lastCheck` | అది చివరిసారి ఎప్పుడు నడిచింది, ISO-8601; లేకపోతే లేదా చదవలేకపోతే తనిఖీ రావలసి ఉంది |
| `update.skipVersion` | వినియోగదారు *ఈ వెర్షన్‌ను దాటవేయి* ఎంచుకున్న విడుదల; మళ్లీ స్వయంచాలకంగా అందించబడదు |

లేని లేదా పాడైన ఫైల్ ఎప్పుడూ ప్రాణాంతకం కాదు: ప్రతి విలువ విడిగా ఫాల్‌బ్యాక్ అవుతుంది, కాబట్టి ఒక చెడ్డ లైన్ ఆ లైన్‌ను
మాత్రమే కోల్పోయేలా చేస్తుంది, ఇంకేమీ కాదు. మొదటి లాంచ్‌లో, ఫైల్ అసలే లేనప్పుడు, ఎంపికలు GAIA అంతర్నిర్మిత డిఫాల్ట్‌ల
నుంచి కాకుండా `SystemDefaults` ద్వారా యంత్రం యొక్క ప్రాంతీయ సెట్టింగ్‌ల నుంచి నింపబడతాయి — లొకేల్ యొక్క చిన్న తేదీ నమూనా
భాగాల క్రమాన్ని, విభాజకాన్ని, మరియు నెల, సంవత్సరం సంక్షిప్తమా కాదా అనేదాన్ని ఇస్తుంది.

`Properties.setProperty` కి ఎప్పుడూ null ఇవ్వకండి: అది మినహాయింపు విసురుతుంది, `persistOptions()` UI ఈవెంట్
హ్యాండ్లర్ల నుంచి నడుస్తుంది, అక్కడ మినహాయింపు FX థ్రెడ్‌పైకి తప్పించుకుంటుంది. ఇది ఈ యాప్‌కు ఇప్పటికే జరిగిన నిజమైన
క్రాష్.

**`captures.tsv`** — చరిత్ర మారినప్పుడు, మరియు నిష్క్రమించేటప్పుడు రాయబడుతుంది. కొత్తది ముందు, గరిష్టంగా **500**
ఎంట్రీలు.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

తిరిగి లెక్కించలేనిది మాత్రమే నిల్వ అవుతుంది. `ParseResult` సీరియలైజ్ **చేయబడదు** — లోడ్ చేసేటప్పుడు ఇన్‌పుట్‌ను మళ్లీ
పార్స్ చేయడం ద్వారా అది తిరిగి పొందబడుతుంది, కాబట్టి పునరుద్ధరించిన చరిత్ర *ఇప్పుడు* అమలులో ఉన్న ఎంపికలను ప్రతిబింబిస్తుంది.
ఇన్‌పుట్‌లలో తరచుగా FNC1 మరియు స్కానర్ వెలువరించే ఇంకేదైనా ఉంటుంది, కాబట్టి ఇన్‌పుట్ ఫీల్డ్ ఎస్కేప్ చేయబడుతుంది (`\\`,
`\t`, `\n`, `\r`, మరియు `0x20` కంటే తక్కువ మిగతా అన్నింటికీ `\xNN`), ఫైల్ ISO-8859-1 గా, బైట్ వారీగా, చదవబడుతుంది
మరియు రాయబడుతుంది.

తేదీని నమోదు చేయడం మొదలుపెట్టక ముందు రాసిన ఫైళ్లలో గడియార సమయం మాత్రమే ఉంటుంది; అవి ఇప్పటికీ లోడ్ అవుతాయి, ఈరోజు
తేదీతో, ఎందుకంటే నిజమైన తేదీ ఎప్పుడూ రాయబడలేదు.

(cd gaia-desktop && mvn test)

198 పరీక్షలు, ఉద్దేశపూర్వకంగా **JavaFX టూల్‌కిట్ లేకుండా**, ఇది వాటిని వేగంగా, హెడ్‌లెస్‌గా ఉంచుతుంది. అవి నివేదిక
రెండరర్, నిర్మాణ తర్కం మరియు AI శోధనలు, `{GS}` మార్పిడి, లొకేల్ నుంచి వచ్చిన డిఫాల్ట్‌లు, రెండు స్టోర్‌లు (`0x1D` ఉన్న
రౌండ్ ట్రిప్ మరియు ఉద్దేశపూర్వకంగా పాడుచేసిన ఫైళ్లతో సహా), సింబాలజీ పట్టిక, స్కానర్ వేదిక నియమం, వెర్షన్ స్టబ్, మరియు
కేటలాగ్‌లను కవర్ చేస్తాయి.

మూడు తెలుసుకోదగినవి, ఎందుకంటే అవి ఫంక్షన్‌లను కాకుండా ఒప్పందాలను రక్షిస్తాయి:

| పరీక్ష | ఎప్పుడు విఫలమవుతుంది |

| `CatalogueCoverageTest` | `ui_EN.properties` నిర్వచించని కీని కోడ్ అడిగినప్పుడు, లేదా 35 ఫైళ్లలో ఏదైనా ఆంగ్ల కీ సమితి నుంచి తప్పుకున్నప్పుడు |
| `SymbologiesTest` | JavaPOS ప్రకటించిన ఏ `SCAN_SDT_*` స్థిరాంకానికైనా ప్రదర్శన పేరు లేనప్పుడు — JavaPOS అప్‌గ్రేడ్ జోడించిన దానితో సహా |

`UiStrings` రన్‌టైమ్‌లో ఉద్దేశపూర్వకంగా క్షమించేది — తెలియని కీ అమరిక మధ్యలో మినహాయింపు విసరకుండా కీ గానే కనిపిస్తుంది —
అందుకే సరిగ్గా కేటలాగ్ పరీక్ష ఉండాలి.

**కవర్ కానివి:** లైవ్ టూల్‌కిట్ అవసరమైనవి ఏవైనా — ఫోకస్ ప్రవర్తన, మోడ్ టోగుల్, పట్టిక సవరణ, భాష మార్పు, మరియు
[థ్రెడింగ్](#థ్రెడింగ్) కింద వివరించిన రెండు క్రాష్‌లు. వీటిని నిజమైన విండోను నడిపి ధ్రువీకరించారు, కానీ వాటిలో రిగ్రెషన్ వస్తే
బిల్డ్ విఫలం కాదు. TestFX లేదా Monocle జోడిస్తే ఆ లోటు మూసుకుపోతుంది.

## తెలిసిన పరిమితులు మరియు మిగిలిన పని

- **హెడ్‌లెస్ UI పరీక్షలు లేవు.** [పరీక్షలు](#పరీక్షలు) చూడండి.
- **వేదిక-నిర్దిష్ట ఆర్టిఫ్యాక్ట్‌లు.** రెండు ప్యాకేజింగ్‌లూ ఒక వేదిక యొక్క JavaFX నేటివ్‌లను బండిల్ చేస్తాయి; ప్రతి లక్ష్యానికి
  `-Dfx.platform` తో ఒకటి బిల్డ్ చేయండి (ఏ యంత్రమైనా అన్నింటినీ బిల్డ్ చేయగలదు). ఏదీ Java రన్‌టైమ్‌ను బండిల్ చేయదు — దానికి
  `jpackage` కావాలి, అది తాను నడిచే OS కోసం మాత్రమే బిల్డ్ చేస్తుంది.
- **స్కానర్ ఇన్‌పుట్ Windows పై మాత్రమే.** [వేదిక ద్వారం](#వేదిక-ద్వారం) చూడండి.
- **`ScanSource.label()` స్థానికీకరించబడలేదు.** [ఉద్దేశపూర్వకంగా అనువదించనివి](#ఉద్దేశపూర్వకంగా-అనువదించనివి) చూడండి.
- **`UiState.mode` ఒక `String`** (`"PARSE"` / `"BUILD"`), దాని పక్కన ఉన్న `Theme` మాత్రం enum, కాబట్టి ఆ లిటరల్ చాలా
  చోట్ల కనిపిస్తుంది. enum వాటిని తొలగిస్తుంది.
- **Digital Link లక్ష్యం డొమైన్ మరియు పాత్ ఉపసర్గ మాత్రమే.** `BuilderDigitalLinkConfig` అదనపు క్వెరీ పారామితులు మరియు
  ఒక ఫ్రాగ్మెంట్‌కు కూడా మద్దతిస్తుంది; ఎడిటర్ వాటిని చూపదు.
- **పరస్పరం మినహాయించే AI జతలు (`GE-S006`) ఎడిటర్‌లో గుర్తించబడవు**, తెలియని మరియు నకిలీ AI లు గుర్తించబడే విధంగా —
  నిర్మాణం నేరుగా విఫలమవుతుంది.
- **కోర్ దోష కేటలాగ్ కొటేషన్ గుర్తులను రెట్టింపు చేస్తుంది** (`value ''09506000134350''`), ఇది నిర్మాణ వైఫల్యాల్లో మరియు
  నివేదికలో యథాతథంగా కనిపిస్తుంది. ఇది అన్-ఎస్కేప్ కాని `MessageFormat` కొటేషన్-ఎస్కేపింగ్ లాగా కనిపిస్తుంది; సవరణ కోర్‌లో
  జరగాలి.
