## ماڈیول ایک نظر میں

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

یہ کور لائبریری کا ایک کلائنٹ ہے، اس سے زیادہ کچھ نہیں۔ اس میں **GS1 کا کوئی علم شامل نہیں**: ہر AI تعریف، توثیق کا قاعدہ،
خرابی کا پیغام اور مقامی بنائی گئی وضاحت [`GaiaParser`](../../../../gaia/docs/GaiaParser.md) اور
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md) سے آتی ہے۔ خاص طور پر، AI کی فہرست کبھی اس ماڈیول میں کاپی
نہیں کی جاتی — بلڈر کا پِکر کور کی اپنی رجسٹری پڑھتا ہے، اس لیے وہ ایسا AI پیش نہیں کر سکتا جسے بلڈر رد کر دے۔

**داخلے کے مقامات:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX `Application`) اور
`tools.pantheum.gaia.desktop.Launcher` (پیک شدہ jar کی `Main-Class`)۔

یہ ماڈیول ایک پتا (leaf) ہے: کوئی چیز اس پر منحصر نہیں، اور یہ کسی دوسرے ڈاؤن اسٹریم ماڈیول پر منحصر نہیں۔

## بلڈ اور چلانا

- چلانے کے لیے **Java 21**، اور بلڈ کے لیے JDK 21 یا نیا — ماڈیول `release=21` کے ساتھ کمپائل ہوتا ہے۔ JavaFX 21
  اس سے مطابقت رکھنے والی LTS لائن ہے۔ کور jar اب بھی Java 11 بائٹ کوڈ ہے اور 21 پر بغیر تبدیلی کے چلتا ہے۔
- `PATH` پر **Maven**۔ اس ریپوزیٹری میں کوئی wrapper نہیں ہے۔
- **پہلے کور انسٹال کریں۔** یہ ماڈیول `gaia:1.1.0` کو `~/.m2` سے حاصل کرتا ہے؛ پرانا یا غیر موجود کور jar ہی
  عموماً `package tools.pantheum.gaia does not exist` کی وجہ ہوتا ہے۔

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` واحد کمانڈ لائن آرگیومنٹ ہے، اور `-Dgaia.desktop.home=…` کے سوا، جو پوری پروفائل کو کہیں اور لے جاتا ہے،
اسٹارٹ اپ پر اثر ڈالنے کا واحد طریقہ ہے۔

`mvn javafx:run` ڈویلپمنٹ کا راستہ ہے: پلگ اِن JavaFX کو **ماڈیول پاتھ** پر رکھتا ہے، اس لیے ٹول کٹ ایک نامزد ماڈیول کے
طور پر شروع ہوتی ہے اور `GaiaDesktopApp` کو براہ راست لانچ کیا جا سکتا ہے۔ پیک شدہ jar ایسا نہیں کر سکتا — اس میں سب کچھ
کلاس پاتھ پر ہوتا ہے — اسی لیے اس کی `Main-Class` `Launcher` شِم ہے۔ اس ترتیب میں `Main-Class` کے طور پر `Application`
کی ذیلی کلاس *"JavaFX runtime components are missing"* کے ساتھ ناکام ہو جاتی ہے۔

ہمیشہ `clean` استعمال کریں — پلیٹ فارمز کا ایک مجموعہ بلڈ کرنے سے پہلے ایک بار، کیونکہ یہ `target/dist/` کو ان سب
سے خالی کر دیتا ہے۔ وجہ کے لیے [بلڈ کے مسائل کا حل](#بلڈ-کے-مسائل-کا-حل) دیکھیں۔

### پیکجنگ

بھیجنے کے قابل ہر چیز `target/dist/gaia-desktop-<version>-<platform>/` کے نیچے جمع کی جاتی ہے اور اس کے سوا کچھ
نہیں، تاکہ اس ڈائریکٹری کو ایک سیٹ کے طور پر zip یا کاپی کیا جا سکے، `target/` میں `classes/`، `maven-status/` اور
بلڈ کی باقی عارضی فائلوں کے ساتھ پڑے آرٹیفیکٹ چھانٹے بغیر۔ `${dist.dir}` اس کا نام ایک ہی جگہ رکھتا ہے؛ آرٹیفیکٹ
لکھنے والا ہر پلگ اِن اسی کی طرف اشارہ کرتا ہے۔

#### ہر پلیٹ فارم کے لیے ایک بلڈ

JavaFX jar نیٹو کوڈ رکھتے ہیں، اس لیے ہر تقسیم ایک پلیٹ فارم کے لیے ہوتی ہے، جس کا نام `fx.platform` پراپرٹی
OpenJFX کلاسیفائر کے طور پر رکھتی ہے: `mac-aarch64`، `mac`، `win`، `linux` یا `linux-aarch64`۔ OS کے مطابق فعال
ہونے والی پانچ `fx-*` پروفائلیں اسے بلڈ کرنے والی مشین کے اپنے پلیٹ فارم پر سیٹ کرتی ہیں، اور عام `mvn package` یا
`mvn javafx:run` کو بس یہی چاہیے؛ `-Dfx.platform=…` ان پر فوقیت لے کر کسی بھی مشین سے کوئی بھی دوسرا پلیٹ فارم بلڈ
کرتا ہے — JavaFX jar محض ڈاؤن لوڈ ہیں۔ `${dist.dir}` دراصل `target/dist/${fx.platform}` ہے، اس لیے ایک پلیٹ فارم کا
بلڈ کبھی دوسرے کے بلڈ کو اوور رائٹ نہیں کرتا۔

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

pom کی دو تفصیلات اسے ممکن بناتی ہیں، اور دونوں ہٹانے کے قابل لگتی ہیں:

- **ہر JavaFX ماڈیول براہ راست انحصار ہے** — base، graphics، controls، media اور web — ہر ایک
  `<classifier>${fx.platform}</classifier>` اور ایک `org.openjfx:*` اخراج کے ساتھ۔ OpenJFX کے pom اپنے متعدی
  (transitive) jar *بلڈ کرنے والی مشین* کے OS کے مطابق چنتے ہیں، اس لیے graphics یا base کو متعدی طور پر آنے دینے سے
  Windows بلڈ میں Windows والوں کے ساتھ Mac کی نیٹو لائبریریاں بھی آ جاتی ہیں۔
- **پراپرٹی `fx.platform` ہے، `javafx.platform` نہیں۔** باہر سے سیٹ کرنے پر OpenJFX کی اپنی پراپرٹی کو اس کا پیرنٹ
  pom خود اسی کے حوالے سے دوبارہ متعین کر دیتا ہے؛ Maven اس pom کو غلط قرار دے کر رد کر دیتا ہے اور خاموشی سے
  پلیٹ فارم jar ہٹا دیتا ہے، اور ایسا بلڈ رہ جاتا ہے جس میں JavaFX ہے ہی نہیں۔

دونوں ترتیبیں ایک ہی پاتھ لکھتی ہیں، `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`، اور ہر بلڈ میں
ان میں سے ٹھیک ایک چلتی ہے۔ `${jar.phase}`، `assembly.skipAssembly` اور `mdep.skip` ہی انہیں دونوں کے اس پر دعویٰ
کرنے سے روکتے ہیں۔

| | ڈیفالٹ | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — صرف اس ماڈیول کی کلاسیں اور وسائل | ~50 MB — انحصارات اس کے اندر کھول کر رکھے گئے |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 jar، مینی فیسٹ `Class-Path` میں ایک ایک کر کے نامزد | — |
| بھیجیں | jar **اور** اس کے ساتھ `lib/` | ایک فائل |
| `dist/gaia-desktop-<version>-<platform>/` میں یہ بھی | `run.bat` (win) یا `run.sh` (باقی) | وہی |
| اور | `readme.html` اور `docs/` (ہر پلیٹ فارم) | وہی |

ہر تقسیم میں گائیڈز بھی ہوتی ہیں: `docs/` اپنی ترتیب کے ساتھ کاپی کیا جاتا ہے، تاکہ گائیڈز اور تراجم کے درمیان روابط
کام کرتے رہیں، ترجمے کے ٹولز (`check-i18n.py`، `i18n-manifest.json`) کے سوا؛ اور روٹ پر
`readme.html`، جو ہر ایک سے ربط دینے والا اشاریہ ہے، `src/main/dist/readme.html` سے، جس میں `@VERSION@` کو pom ورژن
سے بدلا جاتا ہے۔ دونوں کو `pick-launch-script` antrun مرحلہ لکھتا ہے، جو پہلے `docs/` کو حذف کرتا ہے تاکہ ہٹائی گئی گائیڈ
پیچھے نہ رہ جائے۔ readme کے روابط ہاتھ سے لکھے گئے ہیں — `docs/` کے نیچے کسی گائیڈ کا نام بدلنے یا ترجمہ شامل کرنے پر
وہاں بھی اس کی قطار درکار ہے۔

مینی فیسٹ `Class-Path` اور `lib/` ایک ہی چیز کے دو آدھے حصے ہیں: jar ہر رن ٹائم انحصار کے لیے
`lib/<artifact>-<version>.jar` کا نام لیتا ہے، اور `copy-dependencies` `lib/` کو ٹھیک انہی ناموں سے بھرتا ہے۔ یہی
`java -jar` کو کام کرنے کے قابل بناتا ہے۔

#### macOS ایپ اور تقسیم کی zip

ایک antrun ایگزیکیوشن، `mac-app-and-zip`، `package` مرحلے کو ختم کرتا ہے۔ اسی وجہ سے antrun پلگ اِن کو jar اور
assembly پلگ اِنز کے **بعد** ڈکلیئر کیا گیا ہے — Maven کسی مرحلے کے ایگزیکیوشن پلگ اِن ڈکلیئریشن کی ترتیب سے چلاتا ہے —
تاکہ جب یہ چلے تو jar، کسی بھی پیکجنگ میں، موجود ہو۔ (اس کا دوسرا ایگزیکیوشن، `pick-launch-script`، `prepare-package`
میں ہے اور متاثر نہیں ہوتا۔)

`mac` اور `mac-aarch64` کے لیے یہ پہلے تقسیم کی ڈائریکٹری میں `GAIA Desktop.app` بناتا ہے: `Info.plist` (جس میں
`@VERSION@` کو pom ورژن سے بدلا جاتا ہے)، لانچر `Contents/MacOS/gaia-desktop` (قابل عمل بنایا گیا) اور
`gaia-desktop.icns`، سب `src/main/macos/` سے، پھر `gaia-desktop.jar` اور `lib/` کو `Contents/Java` میں **منتقل** کرتا
ہے، تاکہ بنڈل خود کفیل رہے۔ جب ساتھ میں کوئی jar نہ ہو تو `run.sh` وہاں دیکھتا ہے۔ لانچر ورژن کے لحاظ سے Java ڈھونڈتا ہے
(`java_home -v 21+`، پھر Homebrew کا openjdk — Finder سے لانچ کرنے پر `JAVA_HOME` یا `PATH` نظر نہیں آتے)، کچھ نہ
ملے تو `osascript` کے ذریعے ڈائیلاگ دکھاتا ہے، `~/.gaia-desktop` میں `cd` کرتا ہے تاکہ logback کا نسبتی `logs/` قابل
تحریر ہو، اور `-Xdock:name`/`-Xdock:icon` پاس کرتا ہے۔ macOS چلتے ہوئے `java` کو بنڈل سے منسلک کرتا ہے (اس کی bundle
id اور Dock آئیکن ایپ کے ہوتے ہیں)؛ مینو بار میں GAIA Desktop دکھائی دیتا ہے۔

پھر، ہر پلیٹ فارم کے لیے، یہ Ant کے `<zip>` سے ڈائریکٹری کو اسی نام کے فولڈر کے نیچے
`target/dist/gaia-desktop-<version>-<platform>.zip` میں zip کرتا ہے: `run.sh` اور `Contents/MacOS/**` کو
`filemode="755"` کے ساتھ الگ فائل سیٹ کے طور پر، ورنہ unzip ہونے پر وہ چلنے کے قابل نہ رہتیں۔ zip **منسلک نہیں کی
جاتی**: یہ GitHub ریلیز کے لیے ہے، اور چاروں پلیٹ فارم چار بلڈز سے آتے ہیں، جنہیں Maven Central — فی ورژن ایک ناقابل
تبدیل اپ لوڈ — کبھی ایک ریلیز کے طور پر قبول نہیں کر سکتا۔

`project.build.outputTimestamp` کو بلڈ کے وقت پر سیٹ کیا جاتا ہے۔ ورنہ maven-jar-plugin 3.5 اور
maven-assembly-plugin 3.8 کے آرکائیورز ہر اندراج کی تاریخ 1 فروری 1980 رکھ دیتے ہیں۔

ایپ آئیکن `tools/icon/GaiaIcon.java` بناتا ہے (یہ بلڈ کا حصہ نہیں؛ اس کے ہیڈر میں `sips`/`iconutil` کے مراحل ہیں)۔ اس
کے آؤٹ پٹ ریپوزیٹری میں چیک اِن ہیں: بنڈل کے لیے `src/main/macos/gaia-desktop.icns`، اور
`src/main/resources/icons/gaia-desktop-{16..256}.png`، جنہیں `GaiaDesktopApp` ونڈو آئیکن کے طور پر سیٹ کرتا ہے
(Windows اور Linux؛ macOS ونڈو آئیکن کو نظر انداز کرتا ہے)۔

#### لانچ اسکرپٹس

`run.sh` اور `run.bat` `src/main/scripts/` سے آتے ہیں، اور بغیر فلٹر کیے `dist/gaia-desktop-<version>-<platform>/`
میں کاپی ہوتے ہیں — `run.sh` میں `${...}` شیل ایکسپینشنز بھری ہیں جنہیں Maven فلٹرنگ من مانے طریقے سے بدل سکتی ہے۔
پھر ایک antrun مرحلہ صرف وہی رکھتا ہے جسے پلیٹ فارم چلاتا ہے — `win` کے لیے `run.bat`، باقی سب کے لیے `run.sh` — اور
`run.sh` پر ایگزیکیوٹ بِٹ سیٹ کرتا ہے، کیونکہ `copy-resources` اسے ساتھ نہیں لاتا۔ یہ پروفائلز کے بجائے حل شدہ
`${fx.platform}` سے فیصلہ کرتا ہے، کیونکہ پروفائل کی فعالیت وہ قدر نہیں دیکھ سکتی جو کسی دوسری پروفائل نے سیٹ کی ہو: ورنہ
Windows پر بنایا گیا Linux بلڈ میزبان کا اسکرپٹ پا لیتا۔

یہ **مینی فیسٹ پر انحصار نہیں کرتے**۔ ہر ایک خود کلاس پاتھ بناتا ہے، `gaia-desktop.jar` اور اس کے بعد `lib/` کا ہر
`.jar`، `lib/*` وائلڈ کارڈ پر چھوڑنے کے بجائے ایک ایک کر کے نامزد، تاکہ اسپیس والا پاتھ ایک ہی اندراج رہے اور شامل
کیے گئے کی گنتی حقیقی ہو۔ `-cp` سے لانچ کرنا ہی وجہ ہے کہ یہ `tools.pantheum.gaia.desktop.Launcher` کو واضح طور پر
نامزد کرتے ہیں: `-cp` مینی فیسٹ کی `Main-Class` نہیں پڑھتا۔ لیکن یہ اس کے `Class-Path` کی **پھر بھی** پیروی کرتا ہے —
`-cp` پر موجود jar اپنے مینی فیسٹ میں نامزد jar ساتھ لاتا ہے، جنہیں اس کے فوراً بعد تلاش کیا جاتا ہے — اس لیے ہر `lib/`
jar لوڈ ہوتا ہے چاہے اسکرپٹ اسے فہرست میں رکھے یا نہیں، اور اسکرپٹ کے کلاس پاتھ سے کسی کو چھوڑ دینا اسے JVM سے باہر
نہیں رکھتا۔ اسکرپٹس پھر بھی سب کو فہرست میں رکھتے ہیں، تاکہ جس jar کا مینی فیسٹ پرانا، ہاتھ سے ترمیم شدہ یا ایک اندراج
کم ہو، وہ بھی شروع ہو جائے۔ ایک ہی اسکرپٹ دونوں پیکجنگز کے کام آتا ہے: `-Pfat` jar کے پاس شامل کرنے کو کوئی `lib/` نہیں
اور اسے ضرورت بھی نہیں، یہی وجہ ہے کہ خالی `lib/` ایک نوٹ ہے، خرابی نہیں۔

#### Zebra نیٹو لائبریریاں

بلڈ Zebra کی کوئی چیز ساتھ نہیں بھیجتا — نہ DLL، نہ سروس jar۔ Windows پر یہ مشین پر انسٹال Zebra کے Scanner SDK سے
آتے ہیں: `run.bat` اس کے `Jpos*.jar` سروس jar اور `bin\` کو کلاس پاتھ میں اور `bin\` کو `PATH` میں شامل کرتا ہے، جہاں
`System.loadLibrary` `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` کو ڈھونڈ لیتا ہے (`java.library.path` کا ڈیفالٹ
`PATH` ہے)۔ JavaPOS API اور اس کا کنفیگریشن لوڈر ہمیشہ `lib\javapos-*.jar` سے آتے ہیں، SDK ہو یا نہ ہو۔

**`run.bat` کبھی SDK کا اپنا JavaPOS jar شامل نہیں کرتا**، یعنی `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`۔ پہلے
یہ ایسا کرتا تھا، API کی دو نقلوں سے بچنے کے لیے `lib\javapos-*.jar` کو چھوڑ کر — لیکن مینی فیسٹ `Class-Path` نے انہیں
پھر بھی لوڈ کر لیا (اوپر دیکھیں)، اس لیے JVM کو دونوں مل گئے: `lib\` سے 4.x لوڈر کلاسیں، اور ان کے ساتھ
`javaPOS114.jar` کی `jpos/res/jpos.properties` اور `jcl.xsd`۔ پراپرٹیز فائل [`JposConfig`](#اسکینر-انضمام) کو پیچھے
ہٹا دیتی ہے، اور وہ `jcl.xsd` صرف 1.10 تک کے JavaPOS ورژن قبول کرتی ہے، اس لیے `jpos.xml` کا ہر اندراج (1.12–1.14)
توثیق میں ناکام ہوا، رجسٹری خالی رہی، اور اسکینر تک پہنچنے سے پہلے ہی ہر کنکشن خرابی 109 کے ساتھ ناکام ہوا۔ اس کے لیے اس
jar کا کلاس پاتھ پر ہونا ہی کافی ہے، چاہے وہ `lib\` کے jar کے پیچھے ہی کیوں نہ ہو۔ Zebra کے سروس jar `lib\` کے 1.14
API پر بغیر تبدیلی کے چلتے ہیں — open، claim اور اسکین کو اسی طرح ایک اصلی اسکینر پر جانچا گیا ہے۔ `run.bat` کے ساتھ
ہاتھ سے رکھے گئے DLL اب بھی تسلیم کیے جاتے ہیں: تب اسکرپٹ `-Djava.library.path=<dist>;%PATH%` سیٹ کرتا ہے، `PATH` کو
آخر میں جوڑتے ہوئے کیونکہ یہ پراپرٹی ڈیفالٹ تلاش کے پاتھ کو مکمل طور پر بدل دیتی ہے۔

`mvn javafx:run` ان میں سے کچھ نہیں کرتا، اس لیے Windows پر ڈویلپمنٹ رن سے اسکینر claim کرنے کے لیے SDK کے jar کو
کلاس پاتھ پر اور اس کے `bin\` کو `PATH` پر کسی اور طریقے سے رکھنا ہوگا؛ اس کے لیے `dist/` سے چلائیں۔

کلاس پاتھ کے علاوہ یہ وہ کام بھی سنبھالتے ہیں جو `java -jar` نہیں کرتا: اپنی ڈائریکٹری کو حل کرنا تاکہ کسی بھی ورکنگ
ڈائریکٹری سے کام کریں، `PATH` کے بجائے `JAVA_HOME` کو ترجیح دینا، اور 11 سے پہلے کے JVM کو
`UnsupportedClassVersionError` کے بجائے حل بتانے والے جملے کے ساتھ رد کرنا۔ `GAIA_DESKTOP_OPTS` JVM اختیارات آگے
پہنچاتا ہے۔ `run.bat` `javaw.exe` نہیں، `java.exe` استعمال کرتا ہے، تاکہ کنسول کھلا رہے — Windows ہی واحد پلیٹ فارم
ہے جہاں اسکینر چلتا ہے، اور اس کی حالت اور JavaPOS خرابیاں وہیں جاتی ہیں۔

`run.bat` جو کچھ پاتا ہے اس کی بنیاد پر Java، JavaFX اور Zebra سروسز بھی چنتا ہے — بنڈل شدہ `jdk*\`، ماڈیول پاتھ پر
`javafx-sdk*\lib\`، `ZEBRA_HOME` پر Zebra کا Scanner SDK — SDK والا JavaFX استعمال کرتے وقت `lib\` کی JavaFX نقلوں کو
کلاس پاتھ سے باہر رکھتا ہے، اور JDK کا SAX پارسر، Windows پراکسی اور ٹرسٹ اسٹور، اور Java 17+ پر
`--enable-native-access` پاس کرتا ہے۔ README کے [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows)
میں جدول ہے۔ فائل کے CRLF لائن اختتام برقرار رکھیں: صرف LF والی بیچ فائل میں `cmd.exe` کسی `call :label` کو چھوڑ
سکتا ہے۔ `run.sh` بھی `--enable-native-access=ALL-UNNAMED` پاس کرتا ہے — JavaFX اپنی نیٹو لائبریریاں `lib/` سے لوڈ
کرتا ہے، اور JavaFX کے کلاس پاتھ پر ہونے پر `ALL-UNNAMED` ہی وہ ماڈیول ہے جو اسے احاطہ کرتا ہے — جسے، `run.bat` کی
طرح، صرف اسی وقت چھوڑا جاتا ہے جب Java ورژن پڑھا نہ جا سکے۔

دونوں ترتیبیں **ایک پلیٹ فارم** کی، یعنی `${fx.platform}` کی، JavaFX نیٹو لائبریریاں رکھتی ہیں، اس لیے کوئی بھی OS یا
آرکیٹیکچر کے پار منتقل کرنے کے قابل نہیں۔ ہر ہدف کے لیے ایک بار بلڈ کریں — [ہر پلیٹ فارم کے لیے ایک
بلڈ](#ہر-پلیٹ-فارم-کے-لیے-ایک-بلڈ) دیکھیں۔

> **Eclipse۔** `copy-dependencies` ایگزیکیوشن میں ایک `<?m2e ignore?>` ہدایت ہے۔ m2e کھلے ورک اسپیس پروجیکٹ کو jar کے
> بجائے اس کے `target/classes` فولڈر سے حل کرتا ہے، اور `copy-dependencies` غیر پیک شدہ آرٹیفیکٹ کو کاپی کرنے سے انکار
> کرتا ہے (MDEP-187)، جس سے جب بھی `gaia` پروجیکٹ اس کے ساتھ کھلا ہو، آٹو بلڈ ناکام ہو جاتا۔ نتیجہ یہ ہے کہ صرف IDE
> والا بلڈ `target/dist/gaia-desktop-<version>-<platform>/lib/` کو نہیں بھرتا؛ jar کو خود استعمال کرنے سے پہلے
> `mvn package` چلائیں۔

### ان پٹ کی قیف

ہر ان پٹ — ٹائپ کیا گیا، چسپاں کیا گیا، فائل سے کھولا گیا، اسکین کیا گیا یا تشکیل دیا گیا — ایک ہی میتھڈ،
`MainView.capture(String, ScanSource, String)`، کے ذریعے پارسر تک پہنچتا ہے۔

یہی وہ واحد ڈیزائن فیصلہ ہے جس کے گرد ایپ بنی ہے۔ تشکیل کو نہ اپنی رپورٹ چاہیے، نہ اپنی تاریخ، نہ اپنا ایکسپورٹ راستہ،
کیونکہ قیف سے گزرنے کے بعد تشکیل دی گئی اسٹرنگ اسکین کی گئی اسٹرنگ سے الگ پہچانی نہیں جا سکتی۔ ان پٹ پیدا کرنے والی
کوئی بھی نئی چیز اس کے برابر سے نہیں، اسی میں سے گزرنی چاہیے۔

## {GS} ٹوکن

JavaFX `TextField` `0x20` سے نیچے کے ہر حرف کو خاموشی سے ضائع کر دیتا ہے (`TextInputControl.filterInput`)۔ "عجیب انداز
میں دکھاتا ہے" نہیں — مٹا دیتا ہے۔ ٹائپ کرنا، چسپاں کرنا، `setText` اور `insertText` سب متاثر ہیں، اس لیے
`setText("01…" + GS + "10LOT")` سے `"01…10LOT"` ملتا ہے: ایک ایلیمنٹ اسٹرنگ جس کا مطلب خاموشی سے بدل گیا ہے، کیونکہ
متغیر لمبائی والا AI اب اپنے بعد آنے والے حصے کو نگل لیتا ہے۔

`desktop.parse.GsToken` ہی پورا جواب ہے۔ جداکار UI میں لفظی متن `{GS}` کے طور پر چلتا ہے اور پارسر تک جاتے ہوئے دوبارہ
`0x1D` بن جاتا ہے۔ یہ ٹوکن یہاں ایجاد نہیں ہوا — یہ ٹھیک وہی ہے جس صورت میں کور کا `ASCIIRevealerUtils.printable`
`0x1D` کو دکھاتا ہے، اس لیے رپورٹ سے کاپی کی گئی قدر سیدھی ان پٹ بار میں واپس چسپاں کی جا سکتی ہے۔

ان پٹ فیلڈ پر ایک `TextFormatter` فلٹر ہر اس راستے کو پکڑتا ہے جس سے متن آ سکتا ہے — ٹائپ کرنا، ⌘V، سیاقی مینو، گھسیٹ کر
چھوڑنا، `setText` — اسی لیے یہ تبدیلی ہر ہینڈلر میں نہیں، وہیں رہتی ہے۔

اسکینر کا راستہ کبھی `GsToken` سے نہیں گزرتا: اسکین پارسر تک بائٹس کے طور پر پہنچتے ہیں۔

## اسکینر انضمام

`ScannerService` JavaPOS کے `Scanner` کنٹرول کا مالک ہے: open ← claim ← enable، ہر اسکین کے بعد ڈیٹا ایونٹ کو دوبارہ
فعال کرتے ہوئے۔ منطقی ڈیوائس نام `src/main/resources/jpos.xml` سے آتے ہیں۔

**ہر ڈیوائس کال ایک ہی تھریڈ، `gaia-scanner`، پر چلتی ہے، جو سروس جتنی دیر زندہ رہتا ہے** — کبھی FX تھریڈ پر نہیں، اور
کبھی ایسے تھریڈ پر نہیں جو کال کے بعد ختم ہو جائے۔ Zebra کی سروس CoreScanner COM API کے ذریعے JNI سے اسکینر تک پہنچتی
ہے، اور COM جو کچھ سیٹ کرتا ہے اسے کال کرنے والے تھریڈ کے اپارٹمنٹ سے باندھ دیتا ہے: کسی ایسے تھریڈ پر open کریں جو بعد
میں ختم ہو جائے، تو اسکینر claim تو ہوتا ہے مگر خاموش رہتا ہے؛ کسی دوسرے تھریڈ پر close کریں، تو غلط اپارٹمنٹ ان
انیشیلائز ہوتا ہے۔ FX تھریڈ پر close کرنا بدترین صورت ہے، کیونکہ JavaFX وہاں `OleInitialize` کال کرتا ہے اور ہر ونڈو
کا ڈراپ ہدف اسی کے مقابل رجسٹر کرتا ہے — اس پر ایک `CoUninitialize` پوری ایپ میں گھسیٹ کر چھوڑنا ختم کر دیتا ہے۔ یہ
Windows پر JavaFX کا معاملہ ہے، کسی ایک JavaFX ورژن کا نہیں۔ `connect()` اور `disconnect()` اس تھریڈ کو کام سونپ کر
انتظار کرتے ہیں، اس لیے `MainView` دونوں کو ایک قلیل العمر پس منظر تھریڈ سے کال کرتا ہے۔

دو قواعد گڑبڑ کرنے والی ڈیوائس کو کنکشن جام کرنے سے روکتے ہیں۔ **بند کرنے کا عمل کبھی جلدی نہیں رکتا:** `closeQuietly`
disable، release اور close کو الگ الگ مراحل میں کرتا ہے، release صرف تب کرتا ہے جب claim پکڑا ہوا ہو، اور ہمیشہ
`close()` کی کوشش کرتا ہے — ناکام claim کے بعد `release()` "not claimed" پھینکتا ہے، اور جب مراحل ایک ہی `try` بانٹتے
تھے تو اس سے close چھوٹ جاتا تھا اور ڈیوائس Zebra کی سروس میں کھلی رہ جاتی تھی۔ **ڈیٹا ایونٹ کو `finally` میں دوبارہ
فعال کیا جاتا ہے:** JavaPOS ہر ایونٹ کے بعد اسے غیر فعال کر دیتا ہے، اس لیے استثنا پھینکنے والے ریڈ یا ہینڈلر کو بھی
دوبارہ فعال کرنا ہی ہوگا، ورنہ اسکینر دوبارہ کنکٹ ہونے تک خاموش رہے گا۔ `ScannerLifecycleTest` دونوں کو ایک اسکرپٹ شدہ
`jpos.Scanner` کے مقابل چلاتا ہے۔

**`JposConfig` پہلے open سے پہلے JavaPOS کو بنڈل شدہ `jpos.xml` کی طرف اشارہ کرتا ہے۔** Maven کے JavaPOS jar
(`javapos-config-loader` 4.x) اور کلاس پاتھ پر کوئی `jpos/res/jpos.properties` نہ ہونے کی صورت میں، ورنہ ہر open
*"Service does not exist in loaded JCL registry"* (خرابی 109) کے ساتھ ناکام ہوتا ہے، تین الگ وجوہات سے: سروس مینیجر
`SimpleRegPopulator` پر لوٹ جاتا ہے، جو سیریلائز شدہ `jpos.cfg` پڑھتا ہے اور کبھی `jpos.xml` نہیں؛ XML لوڈر `jpos.xml`
کو صرف ورکنگ ڈائریکٹری میں تلاش کرتا ہے، jar کے اندر نہیں؛ اور `lib/` میں Xerces 2.12.2 لوڈر کی سیٹ کی ہوئی JAXP
`accessExternalDTD` پراپرٹی کو رد کرتا ہے۔ `JposConfig` `jpos.config.regPopulatorClass` (`JavaxRegPopulator`)،
`jpos.config.populatorFileURL` (jar کا اپنا `jar:file:…!/jpos.xml`) اور `javax.xml.parsers.SAXParserFactory` (JDK کا)
کو سسٹم پراپرٹیز کے طور پر سیٹ کرتا ہے — کبھی پہلے سے سیٹ کسی کو نہیں، اس لیے `-Djpos.config.populatorFileURL=file:…`
اب بھی کوئی دوسرا `jpos.xml` چن سکتا ہے — اور جب کلاس پاتھ پر `jpos.properties` ہو یا 4.x لوڈر نہ ہو، تو کچھ بھی سیٹ نہیں
کرتا۔ Zebra SDK کا `javaPOS114.jar` ایسی ہی صورت ہے اور رجسٹری کو مکمل طور پر توڑ دیتا ہے، اسی لیے `run.bat` اسے کلاس
پاتھ سے باہر رکھتا ہے — [Zebra نیٹو لائبریریاں](#zebra-نیٹو-لائبریریاں) دیکھیں۔ `JposConfigTest` شروع سے آخر تک جانچتا
ہے کہ رجسٹری میں پھر فائل کے اسکینر موجود ہوتے ہیں۔

**ڈیوائس پِکر اسی رجسٹری سے بنتا ہے**، کوڈ میں فہرست کے طور پر نہیں رکھا جاتا: `ScannerService.logicalNames()`
`gaia-scanner` تھریڈ پر لوڈ شدہ اندراجات پڑھتا ہے اور انہیں رکھتا ہے جن کی ڈیوائس کیٹیگری `Scanner` ہے — `jpos.xml`
کے دو ترازو اندراجات باہر رہتے ہیں — `pickerOrder` ترتیب میں: فائل میں متعین ہو تو `ZebraAllScanners` پہلے، باقی حروف
تہجی کی ترتیب میں (رجسٹری فائل کی ترتیب نہیں رکھتی)۔ جس فائل میں یہ نہیں، اسے یہ دیا نہیں جاتا؛ کچھ بھی لوڈ نہ ہو تو صرف
ڈیفالٹ پیش کیا جاتا ہے، اس لیے پِکر کبھی خالی نہیں ہوتا۔ `MainView` ڈیفالٹ کو فوراً دکھاتا ہے اور محفوظ انتخاب کو برقرار
رکھتے ہوئے ایک پس منظر تھریڈ سے فہرست بھرتا ہے۔ اس لیے `jpos.xml` میں شامل کیا گیا اسکینر — یا
`-Djpos.config.populatorFileURL` سے نامزد پوری فائل — کسی کوڈ تبدیلی کے بغیر پِکر میں نظر آتا ہے، اور `JposConfigTest`
پِکر کو بنڈل شدہ فائل کی ایک آزاد قرأت کے مقابل جانچتا ہے۔ ان اندراجات میں نامزد سروسز Zebra کی کلاسیں ہیں
(`com.zebra.jpos.service.scanner.*Factory`)، جنہیں اب بھی کلاس پاتھ پر ہونا چاہیے — `run.bat` کے ذریعے Scanner SDK
سے، یا `lib\` میں ڈالے گئے Zebra کے سروس jar سے۔

اسکین ڈیٹا کو **ISO-8859-1** کے طور پر ڈی کوڈ کیا جاتا ہے تاکہ ہر بائٹ 1:1 میپ ہو اور AIM Code ID سابقہ اور ہر `0x1D`
دونوں محفوظ رہیں؛ رپورٹیں UTF-8 میں لکھی جاتی ہیں۔

سروس میں کوئی چیز صارف کے لیے متن نہیں بناتی۔ ایونٹس `ScannerListener.Event` مستقلات اور بدلنے والی قدروں کے طور پر باہر
جاتے ہیں، اور `MainView` کیٹلاگ سے الفاظ فراہم کرتا ہے — ورنہ 35 طریقوں سے ترجمہ شدہ ایپلیکیشن میں حالت کی لائن انگریزی
میں ہوتی۔ لاگ لائنیں استثنا ہیں اور انگریزی میں رہتی ہیں۔

### پلیٹ فارم گیٹ

`ScannerService.isSupportedPlatform()` ایک `os.name` جانچ ہے، اور `MainView` کوئی بھی اسکینر کنٹرول بنانے سے پہلے اس سے
پوچھتا ہے: macOS اور Linux پر نہ ٹوگل ہے، نہ ڈیوائس پِکر، نہ اسکینر مینو (اور اس لیے نہ <kbd>⌘K</kbd>)، نہ حالت کا لیبل۔
یہ چھپائے نہیں گئے — یہ کبھی بنائے ہی نہیں جاتے۔

Zebra اپنی JavaPOS سروسز صرف Windows کے لیے بھیجتا ہے، اور کہیں اور کچھ بھی جلدی ناکام نہیں ہوتا: jar حل ہو جاتے ہیں
اور کنٹرول بن جاتا ہے، اور آخر میں `open()` ہی غیر موجود نیٹو پرت کی وجہ سے ناکام ہوتا ہے، کئی سیکنڈ اور ایک ڈائیلاگ کے
بعد۔

یہ قاعدہ *سروسز* کے بارے میں ہے، JavaPOS کے بارے میں نہیں۔ کراس پلیٹ فارم سروس بھیجنے والا فروخت کنندہ یہاں کام کرے
گا، اور قاعدے کو وسیع کرنا صرف `supportsJavaPos(String)` میں تبدیلی ہے — جو package-private ہے اور `os.name`
اسٹرنگز کے مقابل ٹیسٹ شدہ ہے تاکہ بلڈ چلانے والی کسی بھی مشین پر دونوں جواب احاطے میں آئیں۔

### سمبولوجیز

`Symbologies` تمام **78** JavaPOS `SCAN_SDT_*` اسکین ڈیٹا اقسام کو ڈسپلے ناموں سے، اور جہاں دونوں ذخیرۂ الفاظ ملتے ہیں
وہاں کور کے `DataCarrierType` سے میپ کرتا ہے۔ دونوں میں JavaPOS زیادہ باریک ہے — یہ UPC-A کو EAN-13 سے، اور سادہ
Data Matrix کو GS1 DataMatrix سے الگ کرتا ہے، جہاں AIM پورے خاندان کو ایک کوڈ حرف کے تحت جمع کرتا ہے۔

جدول سے باہر کی قسم کو بھی قابل استعمال نام ملتا ہے، جو `ScannerConst` پر ریفلیکشن سے ڈھونڈا جاتا ہے، کیونکہ فروخت
کنندگان کی سروسز واقعی تفصیلات کی فہرست سے باہر کی قدریں رپورٹ کرتی ہیں۔ ایک ٹیسٹ `ScannerConst` پر چلتا ہے اور ناکام
ہوتا ہے اگر کسی اعلان شدہ قسم کا نام نہ ہو — جو مستقبل کے JavaPOS کے شامل کردہ مستقلات کو بھی پکڑ لیتا ہے۔

کچھ کیریئر میپنگز اندازہ لگانے کے بجائے جان بوجھ کر `UNKNOWN` چھوڑی گئی ہیں: straight 2 of 5 (AIM `]R`/`]S` کو
start/stop بار کی گنتی سے الگ کرتا ہے، جسے JavaPOS رپورٹ نہیں کرتا)، چار حالتوں والے ڈاک کوڈ، اور TLC-39۔

## لوکلائزیشن

لیبل فی زبان ایک پراپرٹیز فائل میں `src/main/resources/i18n/ui_<CODE>.properties` کے نیچے رہتے ہیں، کور کی خرابی
کیٹلاگز والے ہی کوڈ استعمال کرتے ہوئے (`EN`، `FR`، `PCM`، …)۔ تمام 35 موجود ہیں اور تمام 35 میں یکساں کلیدی مجموعہ
ہے۔ فائلیں **UTF-8** کے طور پر پڑھی جاتی ہیں، نہ کہ اس ISO-8859-1 کے طور پر جو `Properties` فرض کرتا ہے، اس لیے تراجم
`\uXXXX` ایسکیپس کے بجائے قابل مطالعہ صورت میں محفوظ ہوتے ہیں۔

**فال بیک فی کلید ہے، فی فائل نہیں** — یہی وہ چیز ہے جو جزوی طور پر ترجمہ شدہ زبان کو اس کی پہلی کلید آتے ہی مفید بنا
دیتی ہے۔ انگریزی معاہدہ ہے: ہر کلید وہاں موجود ہونی چاہیے۔

| پرت | کلیدیں | احاطہ |
|---|---|---|
| مشترکہ رپورٹ ذخیرۂ الفاظ | 31 | تمام 35 زبانیں |
| ڈیسک ٹاپ ڈھانچہ — مینو، بٹن، بلڈر، اختیارات، حالت کی لائن، رپورٹ کی ترتیب، اسکینر کی حالت، ڈائیلاگ کا متن | 114 | تمام 35 زبانیں |

مشترکہ اصطلاحات میں سے چھ (`generated`، `status`، `dlRole`، `interpretations`، `message`، `level`) اس ایپ کی رپورٹ میں
استعمال نہیں ہوتیں۔
انہیں جان بوجھ کر رکھا گیا ہے؛ فائل کا ہیڈر یہ بتاتا ہے۔

### `--language` آرگیومنٹ

`GaiaDesktopApp.languageOverride()` JavaFX کے اپنے `getParameters().getNamed()` کے ذریعے `--language=…` پڑھتا ہے، اسے
`Languages.fromArgument` سے حل کرتا ہے — کیٹلاگ کوڈ، enum نام، یا BCP 47 ٹیگ، بڑے چھوٹے حروف سے قطع نظر — اور
`MainView` کے حوالے کرتا ہے۔

**یہ اوور رائیڈ رن کے لیے ہے، فائل کے لیے نہیں۔** `MainView` جو زبان لوڈ کرتا ہے اسے `savedLanguage` میں رکھتا ہے اور
*وہی* واپس لکھتا ہے، جب تک `languageChosenInSession` یہ نہ بتائے کہ صارف نے خود کوئی زبان چنی ہے؛ تب ان کا انتخاب معمول
کے مطابق محفوظ ہوتا ہے۔ یہی تقسیم پورا ڈیزائن ہے: کیوسک پروفائل یا ڈیمو شارٹ کٹ مشین کے مالک کی کل کھلنے والی زبان کو
بدلے بغیر ہسپانوی میں کھل سکتا ہے، جبکہ اختیارات کے پینل میں کیا گیا حقیقی انتخاب پھر بھی برقرار رہتا ہے۔

کسی بھی کیٹلاگ کا نام نہ لینے والی قدر قبول شدہ کوڈز کے ساتھ لاگ کی جاتی ہے اور نظر انداز کر دی جاتی ہے۔ شارٹ کٹ میں
ایک ٹائپو کی وجہ سے شروع ہونے سے انکار کرنا بدتر ناکامی ہوتی، اور اسی وجہ سے `Languages.fromArgument` استثنا پھینکنے کے
بجائے `null` لوٹاتا ہے۔

### زبان شامل کرنا

کسی کوڈ تبدیلی کی ضرورت نہیں۔

1. `ui_<CODE>.properties` میں ترمیم کریں — ہر زبان کی فائل پہلے سے موجود ہے۔
2. قدروں کا ترجمہ کریں۔ `{0}` / `{1}` پلیس ہولڈرز اپنی جگہ رہنے دیں۔
3. بلڈ کریں۔ دو ٹیسٹ معاہدہ نافذ کرتے ہیں: ایک ناکام ہوتا ہے اگر کوڈ ایسی کلید مانگے جسے انگریزی متعین نہیں کرتی،
   دوسرا اگر کسی کیٹلاگ کا کلیدی مجموعہ انگریزی سے ہٹ جائے۔

پہلا ٹیسٹ کلاسوں پر ریفلیکشن کے بجائے **سورس کوڈ** میں کلیدی لٹرلز تلاش کرتا ہے، کیونکہ کلیدیں صرف کال کی جگہوں پر
اسٹرنگ لٹرلز کے طور پر موجود ہیں۔ اسی لیے نیا پیغام کلید کو براہ راست لکھ کر بنانا چاہیے —
`strings.format("st.scannerError", …)` — کسی ویری ایبل کے ذریعے تلاش کر کے نہیں، ورنہ ٹیسٹ اسے دیکھ نہیں پائے گا۔

### جو جان بوجھ کر ترجمہ نہیں کیا جاتا

- خام قدروں کے ساتھ مونو اسپیس میں دکھائے جانے والے مختصر فیلڈ نام — ایلیمنٹ کارڈ کے `format`، `position`، `length`،
  `raw` اور `part`، ٹیپ کے `AI`، `sep`، `pos` اور `len`، اور خرابی کا مقام بتانے والے چار خانے (`AI`، `position`،
  `level`، `stage`)، جن کی قدریں ویسے بھی غیر ترجمہ شدہ enum نام ہیں؛
- نمونہ ان پٹ کے نام، جو GS1 ساختوں کے نام ہیں، اور سمبولوجی کے نام، جو اسمائے معرفہ ہیں؛
- `GE-C084` کا اصلاحی پیراگراف — معیاری نثر، جہاں آدھا ادھورا ترجمہ انگریزی سے بدتر ہے؛
- `ElementBuilder` کا نامعلوم AI کا آخری دفاع، جو UI سے قابل رسائی نہیں: ایڈیٹر نامعلوم AI خود جانچتا ہے اور کیٹلاگ سے
  ان کی رپورٹ کرتا ہے؛
- لاگ لائنیں۔

ایک کمی باقی ہے: `ScanSource.label()` تاریخ کی قطار اور رپورٹ کے سرنامے کو `manual` / `scanner` / `file` / `built`
انگریزی میں دیتا ہے۔ اسے دور کرنے کے لیے ایک کلید سے زیادہ درکار ہے — `HistoryCell` کے پاس `UiStrings` نہیں، اور فہرست
کی سیل فیکٹری ایک بار انسٹال ہوتی ہے، اس لیے زبان بدلنے پر سیلز کو بھی تازہ کرنا ہوگا۔

## محفوظ حالت کے فارمیٹ

`~/.gaia-desktop/` کے نیچے دو فائلیں، الگ رکھی گئی ہیں کیونکہ یہ مختلف رفتار سے بدلتی ہیں — خراب یا ہاتھ سے ترمیم شدہ
کیپچر لاگ کی قیمت صارف کو اپنی ترتیبات سے نہیں چکانی چاہیے۔ ڈائریکٹری کو `-Dgaia.desktop.home=…` سے بدلیں، جس سے ٹیسٹ
اصل ہوم ڈائریکٹری سے دور رہتے ہیں۔

**`options.properties`** — کوئی اختیار بدلنے پر، اور باہر نکلتے وقت لکھی جاتی ہے۔

|---|---|

| `update.check` | روزانہ اپ ڈیٹ جانچ چلتی ہے یا نہیں (ڈیفالٹ `true`) |
| `update.lastCheck` | یہ آخری بار کب چلی، ISO-8601؛ غیر موجود یا ناقابل مطالعہ ہونے کا مطلب ہے کہ جانچ واجب ہے |
| `update.skipVersion` | وہ ریلیز جس کے لیے صارف نے *یہ ورژن چھوڑ دیں* چنا؛ خود بخود دوبارہ پیش نہیں کی جاتی |

غیر موجود یا خراب فائل کبھی مہلک نہیں ہوتی: ہر قدر الگ الگ فال بیک کرتی ہے، اس لیے ایک خراب لائن کی قیمت صرف وہی لائن
ہے۔ پہلی بار لانچ کرنے پر، کسی فائل کے بغیر، اختیارات GAIA کے اندرونی ڈیفالٹس کے بجائے `SystemDefaults` کے ذریعے مشین کی
علاقائی ترتیبات سے بھرے جاتے ہیں — لوکیل کا مختصر تاریخ پیٹرن اجزاء کی ترتیب، جداکار، اور یہ کہ مہینہ اور سال مختصر ہیں یا
نہیں، دیتا ہے۔

`Properties.setProperty` کو کبھی null نہ دیں: یہ استثنا پھینکتا ہے، اور `persistOptions()` UI ایونٹ ہینڈلرز سے چلتا ہے
جہاں استثنا FX تھریڈ پر نکل جاتا ہے۔ یہ ایک حقیقی کریش ہے جو اس ایپ میں پہلے ہو چکا ہے۔

**`captures.tsv`** — تاریخ بدلنے پر، اور باہر نکلتے وقت لکھی جاتی ہے۔ نیا ترین پہلے، زیادہ سے زیادہ **500** اندراجات۔

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

صرف وہی محفوظ کیا جاتا ہے جس کا دوبارہ حساب نہیں ہو سکتا۔ `ParseResult` سیریلائز **نہیں** کیا جاتا — لوڈ ہونے پر ان پٹ کو
دوبارہ پارس کر کے اسے پھر سے اخذ کیا جاتا ہے، اس لیے بحال شدہ تاریخ *اب* نافذ اختیارات کی عکاسی کرتی ہے۔ ان پٹ میں
معمول کے مطابق FNC1 اور اسکینر کا خارج کیا گیا کچھ بھی اور ہوتا ہے، اس لیے ان پٹ فیلڈ ایسکیپ کیا جاتا ہے (`\\`، `\t`،
`\n`، `\r`، اور `0x20` سے نیچے باقی ہر چیز کے لیے `\xNN`) اور فائل ISO-8859-1 کے طور پر، بائٹ بہ بائٹ، پڑھی اور لکھی
جاتی ہے۔

تاریخ درج ہونے سے پہلے لکھی گئی فائلوں میں صرف گھڑی کا وقت ہوتا ہے؛ یہ پھر بھی لوڈ ہوتی ہیں، آج کی تاریخ کے ساتھ،
کیونکہ اصل تاریخ کبھی لکھی ہی نہیں گئی تھی۔

## ٹیسٹنگ

```bash
(cd gaia-desktop && mvn test)
```

198 ٹیسٹ، جان بوجھ کر **JavaFX ٹول کٹ سے آزاد**، جو انہیں تیز اور ہیڈلیس رکھتا ہے۔ یہ رپورٹ رینڈرر، تشکیل کی منطق اور AI
کی تلاش، `{GS}` تبدیلی، لوکیل سے اخذ کردہ ڈیفالٹس، دونوں اسٹورز (بشمول `0x1D` والا راؤنڈ ٹرپ اور جان بوجھ کر خراب کی گئی
فائلیں)، سمبولوجی جدول، اسکینر پلیٹ فارم قاعدہ، ورژن اسٹب، اور کیٹلاگز کا احاطہ کرتے ہیں۔

تین جاننے کے قابل ہیں کیونکہ یہ فنکشنز کے بجائے معاہدوں کی حفاظت کرتے ہیں:

| ٹیسٹ | کب ناکام ہوتا ہے |
|---|---|
| `CatalogueCoverageTest` | کوڈ ایسی کلید مانگتا ہے جسے `ui_EN.properties` متعین نہیں کرتی، یا 35 میں سے کوئی فائل انگریزی کلیدی مجموعے سے ہٹ جاتی ہے |
| `SymbologiesTest` | JavaPOS کے اعلان کردہ کسی `SCAN_SDT_*` مستقل کا کوئی ڈسپلے نام نہیں — JavaPOS اپ گریڈ سے شامل ہونے والا بھی |
| `ScannerServiceTest` | پلیٹ فارم قاعدہ Windows یا کسی اور کے لیے اپنا جواب بدل دیتا ہے |

`UiStrings` رن ٹائم پر جان بوجھ کر درگزر کرنے والا ہے — نامعلوم کلید ترتیب کے بیچ استثنا پھینکنے کے بجائے خود کلید کے طور
پر دکھائی دیتی ہے — ٹھیک یہی وجہ ہے کہ کیٹلاگ ٹیسٹ کا ہونا ضروری ہے۔

**احاطے میں نہیں:** لائیو ٹول کٹ کی ضرورت والی کوئی بھی چیز — فوکس کا رویہ، موڈ ٹوگل، جدول میں ترمیم، زبان کی تبدیلی،
اور [تھریڈنگ](#تھریڈنگ) میں بیان کردہ دونوں کریش۔ انہیں اصلی ونڈو چلا کر جانچا گیا تھا، لیکن ان میں رجعت سے بلڈ ناکام نہیں
ہوگا۔ TestFX یا Monocle شامل کرنے سے یہ کمی دور ہو جائے گی۔

## معلوم حدود اور باقی کام

- **کوئی ہیڈلیس UI ٹیسٹ نہیں۔** [ٹیسٹنگ](#ٹیسٹنگ) دیکھیں۔
- **پلیٹ فارم مخصوص آرٹیفیکٹ۔** دونوں پیکجنگز ایک پلیٹ فارم کی JavaFX نیٹو لائبریریاں بنڈل کرتی ہیں؛ ہر ہدف کے لیے
  `-Dfx.platform` سے ایک بنائیں (کوئی بھی مشین سب بنا سکتی ہے)۔ کوئی بھی Java رن ٹائم بنڈل نہیں کرتی — اس کے لیے
  `jpackage` چاہیے، جو صرف اسی OS کے لیے بناتا ہے جس پر وہ چلتا ہے۔
- **اسکینر ان پٹ صرف Windows پر ہے۔** [پلیٹ فارم گیٹ](#پلیٹ-فارم-گیٹ) دیکھیں۔
- **`ScanSource.label()` مقامی نہیں بنایا گیا۔** [جو جان بوجھ کر ترجمہ نہیں کیا
  جاتا](#جو-جان-بوجھ-کر-ترجمہ-نہیں-کیا-جاتا) دیکھیں۔
- **`UiState.mode` ایک `String` ہے** (`"PARSE"` / `"BUILD"`) جبکہ اس کے ساتھ `Theme` ایک enum ہے، اس لیے یہ لٹرل کئی
  جگہوں پر آتا ہے۔ ایک enum انہیں ختم کر دے گا۔
- **Digital Link ہدف صرف ڈومین اور پاتھ سابقہ ہے۔** `BuilderDigitalLinkConfig` اضافی کوئری پیرامیٹرز اور ایک فریگمنٹ کو
  بھی سپورٹ کرتا ہے؛ ایڈیٹر انہیں ظاہر نہیں کرتا۔
- **باہم خارج AI جوڑے (`GE-S006`) ایڈیٹر میں اس طرح نشان زد نہیں ہوتے** جیسے نامعلوم اور ڈپلیکیٹ AI ہوتے ہیں — تشکیل بس
  ناکام ہو جاتی ہے۔
- **کور کی خرابی کیٹلاگ اقتباس کے نشانات دوگنے کر دیتی ہے** (`value ''09506000134350''`)، جو تشکیل کی ناکامیوں اور رپورٹ
  میں جوں کا توں نظر آتا ہے۔ یہ `MessageFormat` کی اقتباس ایسکیپنگ لگتی ہے جسے اَن ایسکیپ نہیں کیا جا رہا؛ اس کا حل کور
  میں ہونا چاہیے۔
