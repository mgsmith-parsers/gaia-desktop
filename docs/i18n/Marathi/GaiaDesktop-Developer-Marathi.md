## मॉड्यूल एका दृष्टिक्षेपात

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

हे कोअर लायब्ररीचे एक क्लायंट आहे, त्यापेक्षा जास्त काही नाही. त्यात **GS1 चे कोणतेही ज्ञान अंतर्भूत नाही**: प्रत्येक
AI व्याख्या, पडताळणी नियम, त्रुटी संदेश आणि स्थानिकीकृत वर्णन [`GaiaParser`](../../../../gaia/docs/GaiaParser.md)
आणि [`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md) मधून येते. विशेषतः, AI यादी या मॉड्यूलमध्ये कधीही कॉपी केली
जात नाही — बिल्डरचा पिकर कोअरची स्वतःची रजिस्ट्री वाचतो, त्यामुळे बिल्डर नाकारेल असा AI तो देऊ शकत नाही.

**प्रवेश बिंदू:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX `Application`) आणि
`tools.pantheum.gaia.desktop.Launcher` (पॅकेज केलेल्या jar चा `Main-Class`).

हे मॉड्यूल एक पान (leaf) आहे: कोणतीही गोष्ट त्यावर अवलंबून नाही, आणि ते इतर कोणत्याही डाउनस्ट्रीम मॉड्यूलवर अवलंबून
नाही.

## बिल्ड आणि चालवणे

- चालवण्यासाठी **Java 21**, आणि बिल्ड करण्यासाठी JDK 21 किंवा नवीन — मॉड्यूल `release=21` ने कंपाइल होते. JavaFX 21
  ही त्याला जुळणारी LTS मालिका आहे. कोअर jar अजूनही Java 11 बाइटकोड आहे आणि 21 वर बदलाशिवाय चालतो.
- `PATH` वर **Maven**. या रिपॉझिटरीमध्ये wrapper नाही.
- **आधी कोअर इन्स्टॉल करा.** हे मॉड्यूल `gaia:1.1.0` हे `~/.m2` मधून घेते; जुना किंवा नसलेला कोअर jar हेच
  `package tools.pantheum.gaia does not exist` चे नेहमीचे कारण असते.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` हा एकमेव कमांड-लाइन आर्ग्युमेंट आहे, आणि संपूर्ण प्रोफाइल दुसरीकडे नेणाऱ्या `-Dgaia.desktop.home=…`
व्यतिरिक्त स्टार्ट-अपवर परिणाम करण्याचा एकमेव मार्ग आहे.

`mvn javafx:run` हा विकासाचा मार्ग आहे: प्लगिन JavaFX ला **मॉड्यूल पाथ** वर ठेवतो, त्यामुळे टूलकिट नाव असलेले मॉड्यूल
म्हणून सुरू होते आणि `GaiaDesktopApp` थेट लाँच करता येतो. पॅकेज केलेला jar तसे करू शकत नाही — त्यात सर्व काही क्लास
पाथवर असते — म्हणूनच त्याचा `Main-Class` हा `Launcher` शिम आहे. त्या मांडणीत `Main-Class` म्हणून `Application` चा
सबक्लास *"JavaFX runtime components are missing"* सह अयशस्वी होतो.

नेहमी `clean` वापरा — प्लॅटफॉर्मचा संच बिल्ड करण्यापूर्वी एकदा, कारण तो `target/dist/` मधून ते सर्व रिकामे करतो. कारण
जाणून घेण्यासाठी [बिल्डमधील समस्यांचे निवारण](#बिल्डमधील-समस्यांचे-निवारण) पाहा.

### पॅकेजिंग

पाठवण्याजोगे सर्व काही `target/dist/gaia-desktop-<version>-<platform>/` खाली एकत्र केले जाते आणि दुसरे काहीही नाही,
त्यामुळे `target/` मधल्या `classes/`, `maven-status/` आणि बिल्डच्या उरलेल्या तात्पुरत्या फाइल्सच्या शेजारून आर्टिफॅक्ट्स
न निवडता ती डिरेक्टरी एक संच म्हणून zip किंवा कॉपी करता येते. `${dist.dir}` तिला एकाच ठिकाणी नाव देतो; आर्टिफॅक्ट
लिहिणारा प्रत्येक प्लगिन तिच्याकडेच निर्देश करतो.

#### प्रत्येक प्लॅटफॉर्मसाठी एक बिल्ड

JavaFX jar नेटिव्ह कोड बाळगतात, त्यामुळे प्रत्येक वितरण एकाच प्लॅटफॉर्मसाठी असते, ज्याचे नाव `fx.platform` प्रॉपर्टी
OpenJFX क्लासिफायर म्हणून देते: `mac-aarch64`, `mac`, `win`, `linux` किंवा `linux-aarch64`. OS नुसार सक्रिय होणारी
पाच `fx-*` प्रोफाइल्स तिला बिल्ड करणाऱ्या मशीनच्या स्वतःच्या प्लॅटफॉर्मवर सेट करतात, आणि साध्या `mvn package` किंवा
`mvn javafx:run` ला एवढेच हवे असते; `-Dfx.platform=…` त्यांना मागे टाकून कोणत्याही मशीनवरून इतर कोणताही प्लॅटफॉर्म बिल्ड
करतो — JavaFX jar फक्त डाउनलोड आहेत. `${dist.dir}` म्हणजे `target/dist/${fx.platform}`, त्यामुळे एका प्लॅटफॉर्मचा बिल्ड
दुसऱ्याच्या बिल्डवर कधीही अधिलेखन करत नाही.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

pom मधील दोन तपशील हे शक्य करतात, आणि दोन्ही काढून टाकण्याजोगे वाटतात:

- **प्रत्येक JavaFX मॉड्यूल थेट अवलंबित्व आहे** — base, graphics, controls, media आणि web — प्रत्येकासोबत
  `<classifier>${fx.platform}</classifier>` आणि एक `org.openjfx:*` वगळणी. OpenJFX चे pom त्यांचे संक्रामक
  (transitive) jar *बिल्ड करणाऱ्या मशीनच्या* OS वरून निवडतात, त्यामुळे graphics किंवा base संक्रामकपणे येऊ दिल्यास
  Windows बिल्डमध्ये Windows च्या नेटिव्हशेजारी Mac चे नेटिव्ह देखील येतात.
- **प्रॉपर्टी `fx.platform` आहे, `javafx.platform` नाही.** बाहेरून सेट केल्यास OpenJFX ची स्वतःची प्रॉपर्टी तिचा पॅरेंट pom
  स्वतःच्याच संदर्भात पुन्हा परिभाषित करतो; Maven तो pom अवैध म्हणून नाकारतो आणि शांतपणे प्लॅटफॉर्म jar वगळतो, आणि
  ज्यात JavaFX च नाही असा बिल्ड उरतो.

दोन्ही मांडण्या एकच पाथ लिहितात, `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`, आणि प्रत्येक बिल्डमध्ये
त्यापैकी नेमकी एक चालते. `${jar.phase}`, `assembly.skipAssembly` आणि `mdep.skip` हेच दोघांना त्यावर दावा करण्यापासून
रोखतात.

| | डीफॉल्ट | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — फक्त या मॉड्यूलचे क्लासेस आणि संसाधने | ~50 MB — अवलंबित्वे त्यात उघडून ठेवलेली |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 16 jar, मॅनिफेस्ट `Class-Path` मध्ये एकेक करून नाव दिलेले | — |
| पाठवा | jar **आणि** त्याच्या शेजारी `lib/` | एक फाइल |
| `dist/gaia-desktop-<version>-<platform>/` मध्ये हेही | `run.bat` (win) किंवा `run.sh` (इतर) | तसेच |
| आणि | `readme.html` आणि `docs/` (प्रत्येक प्लॅटफॉर्म) | तसेच |

प्रत्येक वितरणात मार्गदर्शिकाही असतात: `docs/` त्याच्या मांडणीसह कॉपी केले जाते, जेणेकरून मार्गदर्शिका आणि भाषांतरांमधील
दुवे चालू राहतात, भाषांतराची साधने (`check-i18n.py`, `i18n-manifest.json`) वगळून; आणि रूटवर
`readme.html`, जो प्रत्येकाशी जोडणारा निर्देशांक आहे, `src/main/dist/readme.html` मधून, ज्यात `@VERSION@` pom
आवृत्तीने बदलले जाते. दोन्ही `pick-launch-script` antrun पायरी लिहिते, जी आधी `docs/` हटवते जेणेकरून काढलेली
मार्गदर्शिका मागे राहू नये. readme मधील दुवे हाताने लिहिलेले आहेत — `docs/` खाली एखाद्या मार्गदर्शिकेचे नाव बदलल्यास
किंवा भाषांतर जोडल्यास तिथेही त्याची ओळ हवी.

मॅनिफेस्ट `Class-Path` आणि `lib/` एकाच गोष्टीचे दोन अर्धे भाग आहेत: jar प्रत्येक रनटाइम अवलंबित्वासाठी
`lib/<artifact>-<version>.jar` नाव देतो, आणि `copy-dependencies` नेमक्या त्याच नावांनी `lib/` भरतो. यामुळेच
`java -jar` चालतो.

#### macOS ॲप आणि वितरण zip

एक antrun अंमलबजावणी, `mac-app-and-zip`, `package` टप्पा संपवते. त्याच कारणाने antrun प्लगिन jar आणि assembly
प्लगिन्सच्या **नंतर** घोषित केला आहे — Maven एका टप्प्यातील अंमलबजावण्या प्लगिन घोषणेच्या क्रमाने चालवतो — त्यामुळे ती
चालते तेव्हा jar, कोणत्याही पॅकेजिंगमध्ये, आधीच अस्तित्वात असतो. (तिची दुसरी अंमलबजावणी, `pick-launch-script`,
`prepare-package` मध्ये आहे आणि तिच्यावर परिणाम होत नाही.)

`mac` आणि `mac-aarch64` साठी ती आधी वितरण डिरेक्टरीत `GAIA Desktop.app` बांधते: `Info.plist` (ज्यात `@VERSION@`
pom आवृत्तीने बदलले जाते), लाँचर `Contents/MacOS/gaia-desktop` (कार्यान्वित करण्यायोग्य केलेला) आणि
`gaia-desktop.icns`, सर्व `src/main/macos/` मधून, नंतर `gaia-desktop.jar` आणि `lib/` ला `Contents/Java` मध्ये
**हलवते**, जेणेकरून बंडल स्वतंत्रपणे उभे राहते. शेजारी jar नसताना `run.sh` तिथे शोधतो. लाँचर आवृत्तीनुसार Java शोधतो
(`java_home -v 21+`, नंतर Homebrew चे openjdk — Finder मधून लाँच केल्यावर `JAVA_HOME` किंवा `PATH` दिसत नाही), काही न
सापडल्यास `osascript` द्वारे संवाद दाखवतो, `~/.gaia-desktop` मध्ये `cd` करतो जेणेकरून logback चे सापेक्ष `logs/`
लिहिण्याजोगे असते, आणि `-Xdock:name`/`-Xdock:icon` पास करतो. macOS चालू असलेल्या `java` ला बंडलशी जोडतो (त्याचा bundle
id आणि Dock आयकन ॲपचे असतात); मेनू बारमध्ये GAIA Desktop दिसते.

नंतर, प्रत्येक प्लॅटफॉर्मसाठी, ती Ant च्या `<zip>` ने डिरेक्टरी त्याच नावाच्या फोल्डरखाली
`target/dist/gaia-desktop-<version>-<platform>.zip` मध्ये zip करते: `run.sh` आणि `Contents/MacOS/**` हे
`filemode="755"` सह वेगळा फाइल संच म्हणून, नाहीतर unzip केल्यावर ते चालवता येणार नाहीत. zip **जोडला जात नाही**: तो GitHub
रिलीझसाठी आहे, आणि चार प्लॅटफॉर्म चार बिल्डमधून येतात, जे Maven Central — प्रत्येक आवृत्तीसाठी एक न बदलणारे अपलोड —
कधीही एक रिलीझ म्हणून स्वीकारू शकत नाही.

`project.build.outputTimestamp` बिल्डच्या वेळेवर सेट केला जातो. नाहीतर maven-jar-plugin 3.5 आणि
maven-assembly-plugin 3.8 मधील आर्काइव्हर्स प्रत्येक नोंदीला 1 फेब्रुवारी 1980 ही तारीख देतात.

ॲप आयकन `tools/icon/GaiaIcon.java` काढतो (तो बिल्डचा भाग नाही; त्याच्या हेडरमध्ये `sips`/`iconutil` च्या पायऱ्या
आहेत). त्याची आउटपुट्स रिपॉझिटरीत चेक-इन केलेली आहेत: बंडलसाठी `src/main/macos/gaia-desktop.icns`, आणि
`src/main/resources/icons/gaia-desktop-{16..256}.png`, जे `GaiaDesktopApp` विंडो आयकन म्हणून सेट करतो (Windows आणि
Linux; macOS विंडो आयकनकडे दुर्लक्ष करते).

#### लाँच स्क्रिप्ट

`run.sh` आणि `run.bat` हे `src/main/scripts/` मधून येतात, आणि फिल्टर न करता `dist/gaia-desktop-<version>-<platform>/`
मध्ये कॉपी केले जातात — `run.sh` मध्ये `${...}` शेल विस्तार भरलेले आहेत जे Maven फिल्टरिंग मनमानीपणे बदलू शकते. नंतर
एक antrun पायरी फक्त तोच ठेवते जो प्लॅटफॉर्म चालवतो — `win` साठी `run.bat`, बाकी सर्वांसाठी `run.sh` — आणि `run.sh`
वर कार्यान्वयन बिट सेट करते, कारण `copy-resources` तो सोबत नेत नाही. ती प्रोफाइल्सऐवजी निश्चित झालेल्या
`${fx.platform}` वरून ठरवते, कारण प्रोफाइल सक्रियता दुसऱ्या प्रोफाइलने सेट केलेले मूल्य पाहू शकत नाही: नाहीतर Windows वर
केलेल्या Linux बिल्डला होस्टची स्क्रिप्ट मिळाली असती.

त्या **मॅनिफेस्टवर अवलंबून नाहीत**. प्रत्येक स्वतःच क्लास पाथ तयार करते, `gaia-desktop.jar` आणि त्यानंतर `lib/` मधील
प्रत्येक `.jar`, `lib/*` वाइल्डकार्डवर न सोडता एकेक करून नाव देऊन, जेणेकरून स्पेस असलेला पाथ एकच नोंद राहतो आणि जोडलेल्यांची
गणना खरी असते. `-cp` ने लाँच करणे हेच कारण आहे की त्या `tools.pantheum.gaia.desktop.Launcher` स्पष्टपणे नमूद करतात:
`-cp` मॅनिफेस्टचा `Main-Class` वाचत नाही. तरीही तो त्याच्या `Class-Path` चे **पालन करतो** — `-cp` वरील jar त्याच्या
मॅनिफेस्टमध्ये नाव दिलेले jar सोबत आणतो, जे त्याच्या लगेच नंतर शोधले जातात — त्यामुळे स्क्रिप्टने यादीत ठेवले असो वा नसो,
प्रत्येक `lib/` jar लोड होतो, आणि स्क्रिप्टच्या क्लास पाथमधून एखादा वगळल्याने तो JVM बाहेर राहत नाही. तरीही स्क्रिप्ट सर्व
यादीत ठेवतात, जेणेकरून ज्याचा मॅनिफेस्ट जुना, हाताने संपादित केलेला किंवा एक नोंद कमी आहे असा jar देखील सुरू होतो. एकच
स्क्रिप्ट दोन्ही पॅकेजिंगसाठी काम करते: `-Pfat` jar कडे जोडण्यासाठी कोणताही `lib/` नाही आणि त्याची गरजही नाही, म्हणूनच
रिकामा `lib/` ही एक सूचना आहे, त्रुटी नाही.

#### Zebra नेटिव्ह लायब्ररी

बिल्ड Zebra चे काहीही पाठवत नाही — ना DLL, ना सर्व्हिस jar. Windows वर ते मशीनवर इन्स्टॉल केलेल्या Zebra च्या Scanner
SDK मधून येतात: `run.bat` त्याचे `Jpos*.jar` सर्व्हिस jar आणि `bin\` क्लास पाथमध्ये आणि `bin\` हे `PATH` मध्ये जोडतो,
जिथे `System.loadLibrary` ला `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` सापडतात (`java.library.path` चे डीफॉल्ट
`PATH` आहे). JavaPOS API आणि त्याचा कॉन्फिगरेशन लोडर नेहमी `lib\javapos-*.jar` मधून येतात, SDK असो वा नसो.

**`run.bat` कधीही SDK चा स्वतःचा JavaPOS jar जोडत नाही**, `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`. पूर्वी तो
जोडत असे, API च्या दोन प्रती टाळण्यासाठी `lib\javapos-*.jar` वगळून — पण मॅनिफेस्ट `Class-Path` ने ते तरीही लोड केले
(वर पाहा), त्यामुळे JVM ला दोन्ही मिळाले: `lib\` मधील 4.x लोडर क्लासेस, आणि त्यांच्या शेजारी `javaPOS114.jar` चे
`jpos/res/jpos.properties` आणि `jcl.xsd`. प्रॉपर्टीज फाइल [`JposConfig`](#स्कॅनर-एकत्रीकरण) ला बाजूला व्हायला लावते,
आणि तो `jcl.xsd` फक्त 1.10 पर्यंतच्या JavaPOS आवृत्त्या स्वीकारतो, त्यामुळे `jpos.xml` मधील प्रत्येक नोंद (1.12–1.14)
पडताळणीत अयशस्वी झाली, रजिस्ट्री रिकामी राहिली, आणि स्कॅनरपर्यंत पोहोचण्याआधीच प्रत्येक कनेक्ट त्रुटी 109 सह अयशस्वी झाला.
त्यासाठी तो jar क्लास पाथवर असणे पुरेसे आहे, अगदी `lib\` च्या jar च्या मागे असला तरी. Zebra चे सर्व्हिस jar `lib\` मधील
1.14 API वर बदलाशिवाय चालतात — open, claim आणि स्कॅन याच प्रकारे खऱ्या स्कॅनरवर तपासले गेले आहेत. `run.bat` शेजारी
हाताने ठेवलेले DLL अजूनही मान्य केले जातात: तेव्हा स्क्रिप्ट `-Djava.library.path=<dist>;%PATH%` सेट करते, `PATH` शेवटी
जोडून, कारण ही प्रॉपर्टी डीफॉल्ट शोध पाथ पूर्णपणे बदलते.

`mvn javafx:run` यापैकी काहीच करत नाही, त्यामुळे Windows वर विकास रनमधून स्कॅनर claim करण्यासाठी SDK चे jar क्लास पाथवर
आणि त्याचा `bin\` हा `PATH` वर इतर मार्गांनी ठेवावा लागेल; त्यासाठी `dist/` मधून चालवा.

क्लास पाथच्या पलीकडे त्या `java -jar` जे करत नाही ते सांभाळतात: स्वतःची डिरेक्टरी निश्चित करणे जेणेकरून त्या कोणत्याही
कार्य डिरेक्टरीमधून चालतात, `PATH` ऐवजी `JAVA_HOME` ला प्राधान्य देणे, आणि 11 पूर्वीचा JVM
`UnsupportedClassVersionError` ऐवजी उपाय सांगणाऱ्या वाक्याने नाकारणे. `GAIA_DESKTOP_OPTS` JVM पर्याय पुढे पाठवतो.
`run.bat` हा `javaw.exe` नव्हे तर `java.exe` वापरतो, जेणेकरून कन्सोल उघडा राहतो — Windows हा एकमेव प्लॅटफॉर्म आहे जिथे
स्कॅनर चालतो, आणि त्याची स्थिती आणि JavaPOS त्रुटी तिथेच जातात.

`run.bat` जे सापडेल त्यावरून Java, JavaFX आणि Zebra सर्व्हिसेसही निवडतो — बंडल केलेला `jdk*\`, मॉड्यूल पाथवर
`javafx-sdk*\lib\`, `ZEBRA_HOME` येथे Zebra चा Scanner SDK — SDK चे JavaFX वापरताना `lib\` मधील JavaFX प्रती क्लास
पाथबाहेर ठेवतो, आणि JDK चा SAX पार्सर, Windows प्रॉक्सी आणि ट्रस्ट स्टोअर, आणि Java 17+ वर `--enable-native-access`
पास करतो. README मधील [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows) मध्ये तक्ता आहे.
फाइलचे CRLF ओळ-शेवट जपा: फक्त LF असलेल्या बॅच फाइलमध्ये `cmd.exe` एखादा `call :label` चुकवू शकतो. `run.sh` देखील
`--enable-native-access=ALL-UNNAMED` पास करतो — JavaFX त्याचे स्वतःचे नेटिव्ह `lib/` मधून लोड करतो, आणि JavaFX क्लास
पाथवर असताना `ALL-UNNAMED` हेच त्याला व्यापणारे मॉड्यूल आहे — `run.bat` प्रमाणेच, फक्त Java आवृत्ती वाचता येत नसेल तेव्हाच
वगळले जाते.

दोन्ही मांडण्या **एका प्लॅटफॉर्मचे**, `${fx.platform}` चे, JavaFX नेटिव्ह बाळगतात, त्यामुळे कोणतीही OS किंवा आर्किटेक्चर
ओलांडून नेता येत नाही. प्रत्येक लक्ष्यासाठी एकदा बिल्ड करा — [प्रत्येक प्लॅटफॉर्मसाठी एक
बिल्ड](#प्रत्येक-प्लॅटफॉर्मसाठी-एक-बिल्ड) पाहा.

> **Eclipse.** `copy-dependencies` अंमलबजावणीत एक `<?m2e ignore?>` सूचना आहे. m2e उघड्या वर्कस्पेस प्रोजेक्टला jar ऐवजी
> त्याच्या `target/classes` फोल्डरमध्ये निश्चित करतो, आणि `copy-dependencies` पॅकेज न केलेला आर्टिफॅक्ट कॉपी करण्यास
> नकार देतो (MDEP-187), ज्यामुळे `gaia` प्रोजेक्ट याच्या शेजारी उघडा असताना ऑटो-बिल्ड अयशस्वी होईल. परिणाम असा की फक्त
> IDE मधील बिल्ड `target/dist/gaia-desktop-<version>-<platform>/lib/` भरत नाही; jar स्वतः वापरण्यापूर्वी `mvn package`
> चालवा.

हाच तो एकमेव डिझाइन निर्णय आहे ज्याभोवती ॲप उभे आहे. निर्मितीला स्वतःचा अहवाल, स्वतःचा इतिहास किंवा स्वतःचा निर्यात मार्ग

### पुनर्बांधणी विरुद्ध पुनर्लेबलिंग

`BuilderPane.retext(UiStrings)` AI ओळी, Digital Link फील्ड्स आणि निवड टिकवून ठेवतो. ते पुन्हा बांधल्यास चालू असलेले काम
हरवेल — जसे एकदा झालेही होते.

## {GS} टोकन

JavaFX `TextField` हा `0x20` खालील प्रत्येक अक्षर शांतपणे टाकून देतो (`TextInputControl.filterInput`). "विचित्रपणे
दाखवतो" नव्हे — काढून टाकतो. टाइप करणे, पेस्ट करणे, `setText` आणि `insertText` सर्व प्रभावित होतात, त्यामुळे
`setText("01…" + GS + "10LOT")` मधून `"01…10LOT"` मिळते: एक एलिमेंट स्ट्रिंग जिचा अर्थ शांतपणे बदलला आहे, कारण बदलत्या
लांबीचा AI आता त्याच्या नंतर आलेले गिळून टाकतो.

`desktop.parse.GsToken` हेच संपूर्ण उत्तर आहे. विभाजक UI मधून शब्दशः मजकूर `{GS}` म्हणून प्रवास करतो आणि पार्सरकडे
जाताना पुन्हा `0x1D` बनतो. हा टोकन इथे शोधलेला नाही — कोअरचा `ASCIIRevealerUtils.printable` `0x1D` नेमका याच रूपात
दाखवतो, त्यामुळे अहवालातून कॉपी केलेले मूल्य थेट इनपुट बारमध्ये परत पेस्ट करता येते.

इनपुट फील्डवरील एक `TextFormatter` फिल्टर मजकूर येऊ शकणारा प्रत्येक मार्ग पकडतो — टाइप करणे, ⌘V, संदर्भ मेनू, ओढून
सोडणे, `setText` — म्हणूनच हे पुनर्लेखन प्रत्येक हँडलरमध्ये नव्हे, तिथेच असते.

स्कॅनरचा मार्ग कधीही `GsToken` मधून जात नाही: स्कॅन पार्सरपर्यंत बाइट्स म्हणून पोहोचतात.

## स्कॅनर एकत्रीकरण

`ScannerService` हा JavaPOS च्या `Scanner` नियंत्रणाचा मालक आहे: open → claim → enable, प्रत्येक स्कॅननंतर डेटा इव्हेंट
पुन्हा सक्रिय करत. तार्किक डिव्हाइस नावे `src/main/resources/jpos.xml` मधून येतात.

**प्रत्येक डिव्हाइस कॉल एकाच थ्रेडवर, `gaia-scanner` वर, चालतो, जो सर्व्हिस जिवंत असेपर्यंत जिवंत राहतो** — कधीही FX
थ्रेडवर नाही, आणि कॉलनंतर संपणाऱ्या थ्रेडवर कधीही नाही. Zebra ची सर्व्हिस CoreScanner COM API मार्फत JNI द्वारे
स्कॅनरपर्यंत पोहोचते, आणि COM जे सेट करतो ते कॉल करणाऱ्या थ्रेडच्या अपार्टमेंटशी बांधतो: नंतर संपणाऱ्या थ्रेडवर open
करा, तर स्कॅनर claim होतो पण गप्प राहतो; दुसऱ्या थ्रेडवर close करा, तर चुकीचे अपार्टमेंट अनइनिशियलाइज होते. FX थ्रेडवर
close करणे हे सर्वात वाईट प्रकरण आहे, कारण JavaFX तिथे `OleInitialize` कॉल करतो आणि प्रत्येक विंडोचे ड्रॉप लक्ष्य
त्याच्याविरुद्ध नोंदवतो — त्यावर एक `CoUninitialize` संपूर्ण ॲपमधील ओढून सोडणे बंद पाडतो. हे Windows वरील JavaFX चे आहे,
कोणत्याही एका JavaFX आवृत्तीचे नाही. `connect()` आणि `disconnect()` त्या थ्रेडकडे काम सोपवून वाट पाहतात, त्यामुळे
`MainView` दोघांनाही एका अल्पायुषी पार्श्वभूमी थ्रेडमधून कॉल करतो.

दोन नियम बिघडलेल्या डिव्हाइसला कनेक्शन अडकवण्यापासून रोखतात. **बंद करण्याची प्रक्रिया कधीही लवकर थांबत नाही:**
`closeQuietly` disable, release आणि close वेगवेगळ्या पायऱ्यांमध्ये करतो, claim धरलेला असेल तेव्हाच release करतो, आणि
नेहमी `close()` चा प्रयत्न करतो — अयशस्वी claim नंतर `release()` "not claimed" फेकतो, आणि पायऱ्या एकच `try` वाटून घेत
तेव्हा त्यामुळे close वगळला जायचा आणि डिव्हाइस Zebra च्या सर्व्हिसमध्ये उघडा राहायचा. **डेटा इव्हेंट `finally` मध्ये पुन्हा
सक्रिय केला जातो:** JavaPOS प्रत्येक इव्हेंटनंतर तो निष्क्रिय करतो, त्यामुळे अपवाद फेकणाऱ्या रीड किंवा हँडलरनेही पुन्हा
सक्रिय करायलाच हवे, नाहीतर पुन्हा कनेक्ट होईपर्यंत स्कॅनर गप्प राहतो. `ScannerLifecycleTest` दोन्ही नियम एका स्क्रिप्ट
केलेल्या `jpos.Scanner` विरुद्ध चालवतो.

**`JposConfig` पहिल्या open आधी JavaPOS ला बंडल केलेल्या `jpos.xml` कडे निर्देशित करतो.** Maven च्या JavaPOS jar
(`javapos-config-loader` 4.x) सह आणि क्लास पाथवर कोणताही `jpos/res/jpos.properties` नसताना, अन्यथा प्रत्येक open
*"Service does not exist in loaded JCL registry"* (त्रुटी 109) सह अयशस्वी होतो, तीन वेगळ्या कारणांनी: सर्व्हिस मॅनेजर
`SimpleRegPopulator` वर परत जातो, जो क्रमबद्ध `jpos.cfg` वाचतो आणि कधीही `jpos.xml` नाही; XML लोडर `jpos.xml` फक्त
कार्य डिरेक्टरीत शोधतो, jar च्या आत नाही; आणि `lib/` मधील Xerces 2.12.2 लोडरने सेट केलेली JAXP `accessExternalDTD`
प्रॉपर्टी नाकारतो. `JposConfig` हा `jpos.config.regPopulatorClass` (`JavaxRegPopulator`),
`jpos.config.populatorFileURL` (jar चे स्वतःचे `jar:file:…!/jpos.xml`) आणि `javax.xml.parsers.SAXParserFactory`
(JDK चे) सिस्टम प्रॉपर्टीज म्हणून सेट करतो — आधीच सेट केलेली कधीही नाही, त्यामुळे
`-Djpos.config.populatorFileURL=file:…` अजूनही दुसरा `jpos.xml` निवडू शकतो — आणि क्लास पाथवर `jpos.properties`
असताना किंवा 4.x लोडर नसताना काहीच सेट करत नाही. Zebra SDK चा `javaPOS114.jar` असेच एक प्रकरण आहे आणि रजिस्ट्री पूर्णपणे
मोडतो, म्हणूनच `run.bat` त्याला क्लास पाथबाहेर ठेवतो — [Zebra नेटिव्ह लायब्ररी](#zebra-नेटिव्ह-लायब्ररी) पाहा.
`JposConfigTest` सुरुवातीपासून शेवटपर्यंत तपासतो की त्यानंतर रजिस्ट्रीत फाइलमधील स्कॅनर असतात.

**डिव्हाइस पिकर त्याच रजिस्ट्रीमधून तयार होतो**, कोडमध्ये यादी म्हणून ठेवला जात नाही: `ScannerService.logicalNames()`
`gaia-scanner` थ्रेडवर लोड झालेल्या नोंदी वाचतो आणि ज्यांची डिव्हाइस श्रेणी `Scanner` आहे त्या ठेवतो — `jpos.xml` मधील
वजनकाट्याच्या दोन नोंदी बाहेर राहतात — `pickerOrder` क्रमाने: फाइलने परिभाषित केला असल्यास `ZebraAllScanners` पहिला,
बाकी वर्णक्रमाने (रजिस्ट्री फाइलचा क्रम ठेवत नाही). ज्या फाइलमध्ये तो नाही तिला तो दिला जात नाही; काहीच लोड न झाल्यास फक्त
डीफॉल्ट दिला जातो, त्यामुळे पिकर कधीही रिकामा नसतो. `MainView` डीफॉल्ट लगेच दाखवतो आणि जतन केलेली निवड टिकवून एका
पार्श्वभूमी थ्रेडमधून यादी भरतो. त्यामुळे `jpos.xml` मध्ये जोडलेला स्कॅनर — किंवा `-Djpos.config.populatorFileURL` ने
नाव दिलेली संपूर्ण फाइल — कोणताही कोड बदल न करता पिकरमध्ये दिसतो, आणि `JposConfigTest` पिकरला बंडल केलेल्या फाइलच्या
स्वतंत्र वाचनाशी जुळवून तपासतो. त्या नोंदी ज्या सर्व्हिसेसची नावे देतात त्या Zebra चे क्लासेस आहेत
(`com.zebra.jpos.service.scanner.*Factory`), जे अजूनही क्लास पाथवर असायलाच हवेत — `run.bat` द्वारे Scanner SDK मधून,
किंवा `lib\` मध्ये टाकलेल्या Zebra च्या सर्व्हिस jar मधून.

स्कॅन डेटा **ISO-8859-1** म्हणून डीकोड केला जातो जेणेकरून प्रत्येक बाइट 1:1 मॅप होतो आणि AIM Code ID उपसर्ग आणि प्रत्येक
`0x1D` दोन्ही टिकतात; अहवाल UTF-8 मध्ये लिहिले जातात.

सर्व्हिसमधील काहीही वापरकर्त्यासाठी मजकूर रचत नाही. इव्हेंट्स `ScannerListener.Event` स्थिरांक आणि बदलणारी मूल्ये म्हणून
बाहेर जातात, आणि `MainView` कॅटलॉगमधून शब्दरचना पुरवतो — नाहीतर 35 प्रकारे भाषांतरित अनुप्रयोगात स्थिती ओळ इंग्रजीत
राहिली असती. लॉग ओळी अपवाद आहेत आणि इंग्रजीतच राहतात.

### प्लॅटफॉर्म गेट

`ScannerService.isSupportedPlatform()` ही एक `os.name` चाचणी आहे, आणि `MainView` कोणतेही स्कॅनर नियंत्रण बांधण्याआधी
तिला विचारतो: macOS आणि Linux वर ना टॉगल, ना डिव्हाइस पिकर, ना स्कॅनर मेनू (आणि म्हणून ना <kbd>⌘K</kbd>), ना स्थिती
लेबल. ते लपवलेले नाहीत — ते कधीच तयार केले जात नाहीत.

Zebra आपल्या JavaPOS सर्व्हिसेस फक्त Windows साठी पाठवते, आणि इतरत्र काहीही लवकर अयशस्वी होत नाही: jar निश्चित होतात
आणि नियंत्रण तयार होते, आणि शेवटी नसलेल्या नेटिव्ह स्तरामुळे `open()` च अयशस्वी होतो, काही सेकंदांनी आणि एका संवादानंतर.

हा नियम *सर्व्हिसेस* बद्दल आहे, JavaPOS बद्दल नाही. क्रॉस-प्लॅटफॉर्म सर्व्हिस पाठवणारा विक्रेता इथे चालेल, आणि नियम
विस्तारणे म्हणजे फक्त `supportsJavaPos(String)` मधील बदल — जो package-private आहे आणि `os.name` स्ट्रिंग्सविरुद्ध
तपासलेला आहे जेणेकरून बिल्ड चालवणाऱ्या कोणत्याही मशीनवर दोन्ही उत्तरे व्यापली जातात.

### सिम्बॉलॉजी

`Symbologies` सर्व **78** JavaPOS `SCAN_SDT_*` स्कॅन-डेटा प्रकारांना प्रदर्शन नावांशी, आणि जिथे दोन्ही शब्दसंग्रह जुळतात
तिथे कोअरच्या `DataCarrierType` शी मॅप करतो. दोघांपैकी JavaPOS अधिक सूक्ष्म आहे — तो UPC-A ला EAN-13 पासून, आणि साध्या
Data Matrix ला GS1 DataMatrix पासून वेगळे करतो, जिथे AIM संपूर्ण कुटुंबाला एका कोड अक्षराखाली एकत्र करतो.

तक्त्याबाहेरील प्रकारालाही वापरण्याजोगे नाव मिळते, जे `ScannerConst` वर रिफ्लेक्शनद्वारे शोधले जाते, कारण विक्रेत्यांच्या
सर्व्हिसेस खरोखरच विनिर्देश यादीबाहेरील मूल्ये कळवतात. एक चाचणी `ScannerConst` मधून फिरते आणि कोणत्याही घोषित प्रकाराला नाव
नसल्यास अयशस्वी होते — जे भविष्यातील JavaPOS ने जोडलेले स्थिरांकही पकडते.

काही कॅरिअर मॅपिंग्स अंदाज लावण्याऐवजी जाणूनबुजून `UNKNOWN` ठेवली आहेत: straight 2 of 5 (AIM `]R`/`]S` ला start/stop
बारच्या संख्येवरून वेगळे करतो, जे JavaPOS कळवत नाही), चार-स्थितीचे टपाल कोड, आणि TLC-39.

## स्थानिकीकरण

लेबले प्रत्येक भाषेसाठी एका प्रॉपर्टीज फाइलमध्ये `src/main/resources/i18n/ui_<CODE>.properties` खाली राहतात, कोअरच्या
त्रुटी कॅटलॉग्ससारखेच कोड वापरून (`EN`, `FR`, `PCM`, …). सर्व 35 अस्तित्वात आहेत आणि सर्व 35 मध्ये एकसारखा की-संच
आहे. फाइल्स **UTF-8** म्हणून वाचल्या जातात, `Properties` गृहीत धरतो त्या ISO-8859-1 म्हणून नाही, त्यामुळे भाषांतरे
`\uXXXX` एस्केपऐवजी वाचता येण्याजोग्या स्वरूपात साठवली जातात.

**फॉलबॅक प्रत्येक कीनुसार आहे, प्रत्येक फाइलनुसार नाही** — यामुळेच अंशतः भाषांतरित भाषा तिची पहिली की येताक्षणी उपयुक्त
ठरते. इंग्रजी हा करार आहे: प्रत्येक की तिथे असायलाच हवी.

| स्तर | की | व्याप्ती |
|---|---|---|
| सामायिक अहवाल शब्दसंग्रह | 31 | सर्व 35 भाषा |
| डेस्कटॉप चौकट — मेनू, बटणे, बिल्डर, पर्याय, स्थिती ओळ, अहवाल मांडणी, स्कॅनर स्थिती, संवादांचा मजकूर | 114 | सर्व 35 भाषा |

सामायिक संज्ञांपैकी सहा (`generated`, `status`, `dlRole`, `interpretations`, `message`, `level`) या ॲपच्या अहवालात
वापरल्या जात नाहीत.
त्या जाणूनबुजून ठेवल्या आहेत; फाइल हेडर तसे सांगतो.

### `--language` आर्ग्युमेंट

`GaiaDesktopApp.languageOverride()` हा JavaFX च्या स्वतःच्या `getParameters().getNamed()` द्वारे `--language=…` वाचतो,
`Languages.fromArgument` ने तो निश्चित करतो — कॅटलॉग कोड, enum नाव, किंवा BCP 47 टॅग, केस-असंवेदनशील — आणि `MainView`
कडे सोपवतो.

**हे अधिलेखन रनसाठी आहे, फाइलसाठी नाही.** `MainView` लोड केलेली भाषा `savedLanguage` मध्ये ठेवतो आणि *तीच* परत लिहितो,
जोपर्यंत `languageChosenInSession` सांगत नाही की वापरकर्त्याने स्वतः भाषा निवडली आहे; तेव्हा त्यांची निवड नेहमीप्रमाणे जतन
होते. हीच विभागणी संपूर्ण डिझाइन आहे: किऑस्क प्रोफाइल किंवा डेमो शॉर्टकट मशीनचा मालक उद्या कोणत्या भाषेत उघडेल ते न बदलता
स्पॅनिशमध्ये उघडू शकतो, तर पर्याय पॅनेलमध्ये केलेली खरी निवड तरीही टिकते.

कोणत्याही कॅटलॉगचे नाव न देणारे मूल्य स्वीकारलेल्या कोडसह लॉग केले जाते आणि दुर्लक्षित केले जाते. शॉर्टकटमधील एका टायपोमुळे
सुरू होण्यास नकार देणे हे अधिक वाईट अपयश ठरले असते, आणि याच कारणाने `Languages.fromArgument` अपवाद फेकण्याऐवजी `null`
परत करतो.

### भाषा जोडणे

कोणताही कोड बदल आवश्यक नाही.

1. `ui_<CODE>.properties` संपादित करा — प्रत्येक भाषेची फाइल आधीच आहे.
2. मूल्यांचे भाषांतर करा. `{0}` / `{1}` प्लेसहोल्डर जागीच ठेवा.
3. बिल्ड करा. दोन चाचण्या करार लागू करतात: एक अयशस्वी होते जर कोडने इंग्रजीत परिभाषित नसलेली की मागितली, दुसरी जर
   कोणत्याही कॅटलॉगचा की-संच इंग्रजीपासून भरकटला.

पहिली चाचणी क्लासेसवर रिफ्लेक्शन करण्याऐवजी **सोर्स कोड** मध्ये की लिटरल शोधते, कारण की फक्त कॉल स्थानांवर स्ट्रिंग
लिटरल म्हणूनच अस्तित्वात असतात. म्हणूनच नवा संदेश की थेट लिहून बांधायला हवा — `strings.format("st.scannerError", …)` —
व्हेरिएबलद्वारे शोधून नाही, नाहीतर चाचणीला तो दिसणार नाही.

### जाणूनबुजून भाषांतरित न केलेल्या गोष्टी

- कच्च्या मूल्यांशेजारी मोनोस्पेसमध्ये दाखवलेली संक्षिप्त फील्ड नावे — एलिमेंट कार्डचे `format`, `position`, `length`,
  `raw` आणि `part`, टेपचे `AI`, `sep`, `pos` आणि `len`, आणि त्रुटीचे स्थान दाखवणारे चार सेल (`AI`, `position`,
  `level`, `stage`), ज्यांची मूल्ये तशीही भाषांतरित न केलेली enum नावे आहेत;
- नमुना-इनपुटची नावे, जी GS1 रचनांची नावे आहेत, आणि सिम्बॉलॉजीची नावे, जी विशेषनामे आहेत;
- `GE-C084` चा उपाय परिच्छेद — मानकांचे गद्य, जिथे अर्धवट भाषांतर इंग्रजीपेक्षा वाईट आहे;
- `ElementBuilder` चा अज्ञात-AI साठीचा शेवटचा बचाव, जो UI मधून पोहोचता येत नाही: संपादक अज्ञात AI स्वतः तपासतो आणि
  कॅटलॉगमधून त्यांची माहिती देतो;
- लॉग ओळी.

एक उणीव उरली आहे: `ScanSource.label()` इतिहास ओळीला आणि अहवालाच्या शीर्षभागाला `manual` / `scanner` / `file` /
`built` इंग्रजीत पुरवतो. ती भरून काढण्यासाठी एका कीपेक्षा जास्त लागते — `HistoryCell` कडे `UiStrings` नाही, आणि यादीची
सेल फॅक्टरी एकदाच इन्स्टॉल होते, त्यामुळे भाषा बदलल्यावर सेल्सही रिफ्रेश करावे लागतील.

## साठवलेल्या स्थितीचे स्वरूप

`~/.gaia-desktop/` खाली दोन फाइल्स, वेगळ्या ठेवल्या आहेत कारण त्या वेगवेगळ्या गतीने बदलतात — दूषित किंवा हाताने संपादित
कॅप्चर लॉगची किंमत वापरकर्त्याला आपल्या सेटिंग्जने मोजावी लागू नये. डिरेक्टरी `-Dgaia.desktop.home=…` ने बदला, यामुळेच
चाचण्या खऱ्या होम डिरेक्टरीपासून दूर राहतात.

**`options.properties`** — एखादा पर्याय बदलल्यावर, आणि बाहेर पडताना लिहिली जाते.

| की | अर्थ |
|---|---|
| `parse.mode`, `parse.language` | पाइपलाइनची खोली आणि संदेशाची भाषा |
| `date.endian`, `date.separator`, `date.month`, `date.year` | तारीख प्रदर्शन |
| `check.skipRequires`, `check.skipExcludes` | संरचनात्मक तपासणीतून सूट |
| `ui.theme` | `LIGHT` किंवा `DARK` |
| `ui.optionsPane` | पर्याय पॅनेल उघडे आहे? |
| `ui.scannerDevice` | शेवटचे JavaPOS तार्किक नाव |
| `ui.mode` | `PARSE`, `BUILD` किंवा `COMBINE` |
| `update.check` | दैनिक अपडेट तपासणी चालते की नाही (डीफॉल्ट `true`) |
| `update.lastCheck` | ती शेवटची कधी चालली, ISO-8601; नसल्यास किंवा वाचता न आल्यास तपासणी बाकी आहे |
| `update.skipVersion` | ज्या रिलीझसाठी वापरकर्त्याने *ही आवृत्ती वगळा* निवडले; आपोआप पुन्हा दिले जात नाही |

नसलेली किंवा खराब फाइल कधीही घातक नसते: प्रत्येक मूल्य स्वतंत्रपणे फॉलबॅक करते, त्यामुळे एका वाईट ओळीची किंमत फक्त तीच ओळ
आहे. पहिल्या लाँचच्या वेळी, कोणतीही फाइल नसताना, पर्याय GAIA च्या अंगभूत डीफॉल्टऐवजी `SystemDefaults` द्वारे मशीनच्या
प्रादेशिक सेटिंग्जमधून भरले जातात — लोकेलचा लहान तारीख नमुना घटकांचा क्रम, विभाजक, आणि महिना व वर्ष संक्षिप्त आहेत की
नाही हे देतो.

`Properties.setProperty` ला कधीही null देऊ नका: तो अपवाद फेकतो, आणि `persistOptions()` UI इव्हेंट हँडलर्समधून चालतो
जिथे अपवाद FX थ्रेडवर निसटतो. हा या ॲपमध्ये आधीच घडलेला खरा क्रॅश आहे.

**`captures.tsv`** — इतिहास बदलल्यावर, आणि बाहेर पडताना लिहिली जाते. सर्वात नवे आधी, कमाल **500** नोंदी.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

फक्त जे पुन्हा मोजता येत नाही तेच साठवले जाते. `ParseResult` क्रमबद्ध केला **जात नाही** — लोड करताना इनपुट पुन्हा पार्स
करून तो पुन्हा मिळवला जातो, त्यामुळे पुनर्संचयित इतिहास *आत्ता* लागू असलेले पर्याय दर्शवतो. इनपुटमध्ये नेहमीच FNC1 आणि
स्कॅनर जे काही बाहेर टाकतो ते असते, त्यामुळे इनपुट फील्ड एस्केप केले जाते (`\\`, `\t`, `\n`, `\r`, आणि `0x20` खालील
इतर सर्वांसाठी `\xNN`) आणि फाइल ISO-8859-1 म्हणून, बाइट-दर-बाइट, वाचली व लिहिली जाते.

तारीख नोंदवणे सुरू होण्याआधी लिहिलेल्या फाइल्समध्ये फक्त घड्याळाची वेळ असते; त्या तरीही लोड होतात, आजच्या तारखेसह, कारण
खरी तारीख कधीच लिहिली गेली नव्हती.

## चाचणी

```bash
(cd gaia-desktop && mvn test)
```

198 चाचण्या, जाणूनबुजून **JavaFX टूलकिटपासून मुक्त**, ज्यामुळे त्या जलद आणि हेडलेस राहतात. त्या अहवाल रेंडरर, निर्मिती
तर्क आणि AI शोध, `{GS}` रूपांतरण, लोकेलवरून मिळवलेले डीफॉल्ट, दोन्ही स्टोअर्स (`0x1D` असलेली राउंड ट्रिप आणि जाणूनबुजून
खराब केलेल्या फाइल्ससह), सिम्बॉलॉजी तक्ता, स्कॅनर प्लॅटफॉर्म नियम, आवृत्ती स्टब, आणि कॅटलॉग्स व्यापतात.

तीन जाणून घेण्याजोग्या आहेत कारण त्या फंक्शन्सऐवजी करारांचे रक्षण करतात:

| चाचणी | केव्हा अयशस्वी होते |
|---|---|
| `CatalogueCoverageTest` | कोडने `ui_EN.properties` मध्ये परिभाषित नसलेली की मागितली, किंवा 35 पैकी कोणतीही फाइल इंग्रजी की-संचापासून भरकटली |
| `SymbologiesTest` | JavaPOS ने घोषित केलेल्या कोणत्याही `SCAN_SDT_*` स्थिरांकाला प्रदर्शन नाव नाही — JavaPOS अपग्रेडने जोडलेल्यासह |
| `ScannerServiceTest` | प्लॅटफॉर्म नियम Windows साठी किंवा इतर कशासाठीही उत्तर बदलतो |

`UiStrings` रनटाइमला जाणूनबुजून क्षमाशील आहे — अज्ञात की मांडणीच्या मध्येच अपवाद फेकण्याऐवजी स्वतः की म्हणून दिसते — म्हणूनच
नेमकी कॅटलॉग चाचणी असणे आवश्यक आहे.

**व्याप्तीबाहेर:** जिवंत टूलकिट लागणारे काहीही — फोकस वर्तन, मोड टॉगल, तक्ता संपादन, भाषा बदल, आणि
[थ्रेडिंग](#थ्रेडिंग) खाली वर्णन केलेले दोन्ही क्रॅश. ते खरी विंडो चालवून तपासले गेले, पण त्यांच्यात रिग्रेशन झाल्यास बिल्ड
अयशस्वी होणार नाही. TestFX किंवा Monocle जोडल्यास ही उणीव भरून निघेल.

## ज्ञात मर्यादा आणि उरलेले काम

- **कोणत्याही हेडलेस UI चाचण्या नाहीत.** [चाचणी](#चाचणी) पाहा.
- **प्लॅटफॉर्म-विशिष्ट आर्टिफॅक्ट्स.** दोन्ही पॅकेजिंग्स एका प्लॅटफॉर्मचे JavaFX नेटिव्ह बंडल करतात; प्रत्येक लक्ष्यासाठी
  `-Dfx.platform` ने एक बिल्ड करा (कोणतेही मशीन ते सर्व बिल्ड करू शकते). कोणतेही Java रनटाइम बंडल करत नाही — त्यासाठी
  `jpackage` लागतो, जो फक्त तो ज्या OS वर चालतो त्यासाठीच बिल्ड करतो.
- **स्कॅनर इनपुट फक्त Windows वर आहे.** [प्लॅटफॉर्म गेट](#प्लॅटफॉर्म-गेट) पाहा.
- **`ScanSource.label()` स्थानिकीकृत नाही.** [जाणूनबुजून भाषांतरित न केलेल्या
  गोष्टी](#जाणूनबुजून-भाषांतरित-न-केलेल्या-गोष्टी) पाहा.
- **`UiState.mode` हा `String` आहे** (`"PARSE"` / `"BUILD"`) तर त्याच्या शेजारचा `Theme` हा enum आहे, त्यामुळे ते
  लिटरल अनेक ठिकाणी येते. एक enum ते काढून टाकेल.
- **Digital Link लक्ष्य फक्त डोमेन आणि पाथ उपसर्ग आहे.** `BuilderDigitalLinkConfig` अतिरिक्त क्वेरी पॅरामीटर्स आणि एक
  फ्रॅगमेंटही समर्थित करतो; संपादक ते उघड करत नाही.
- **परस्पर-वर्जित AI जोड्या (`GE-S006`) संपादकात तशा चिन्हांकित होत नाहीत** जशा अज्ञात आणि डुप्लिकेट AI होतात —
  निर्मिती सरळ अयशस्वी होते.
- **कोअरचा त्रुटी कॅटलॉग अवतरण चिन्हे दुप्पट करतो** (`value ''09506000134350''`), जे निर्मिती अपयशांत आणि अहवालात जसेच्या
  तसे दिसते. हे `MessageFormat` चे अवतरण-एस्केपिंग असल्यासारखे दिसते जे अन-एस्केप होत नाही; त्याचा सुधार कोअरमध्ये व्हायला
  हवा.
