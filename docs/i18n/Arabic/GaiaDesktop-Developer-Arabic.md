## نظرة سريعة على الوحدة

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

عميل للمكتبة الأساسية لا أكثر. لا تتضمن الوحدة **أي معرفة بـ GS1**: فكل تعريف لـ AI، وكل قاعدة تحقق،
وكل رسالة خطأ، وكل وصف مترجم يأتي من [`GaiaParser`](../../../../gaia/docs/GaiaParser.md) و
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md). وعلى وجه الخصوص لا تُنسخ قائمة AI أبدًا إلى هذه
الوحدة — فمنتقي المُنشئ يقرأ سجل النواة نفسه، ولذلك لا يمكنه أن يعرض AI سيرفضه المُنشئ.

**نقاط الدخول:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (فئة `Application` في JavaFX) و
`tools.pantheum.gaia.desktop.Launcher` (قيمة `Main-Class` في ملف jar المحزّم).

الوحدة ورقة طرفية: لا شيء يعتمد عليها، ولا تعتمد هي على أي وحدة لاحقة أخرى.

## البناء والتشغيل

- **Java 21** للتشغيل، وJDK 21 أو أحدث للبناء — تُترجَم الوحدة باستخدام `release=21`. وJavaFX 21 هو خط
  LTS المقابل. لا يزال ملف jar الخاص بالنواة بشيفرة Java 11 البايتية، ويعمل على 21 دون تغيير.
- **Maven** على `PATH`. لا يوجد wrapper في هذا المستودع.
- **ثبّت النواة أولًا.** تجلب هذه الوحدة `gaia:1.1.0` من `~/.m2`؛ وملف jar قديم أو مفقود للنواة هو السبب
  المعتاد للخطأ `package tools.pantheum.gaia does not exist`.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` هو الوسيط الوحيد في سطر الأوامر، والطريقة الوحيدة للتأثير في بدء التشغيل غير
`-Dgaia.desktop.home=…` الذي يوجّه الملف الشخصي بكامله إلى مكان آخر.

`mvn javafx:run` هو مسار التطوير: تضع الإضافة JavaFX على **مسار الوحدات**، فتبدأ مجموعة الأدوات بوصفها
وحدة مسمّاة ويمكن تشغيل `GaiaDesktopApp` مباشرة. أما ملف jar المحزّم فلا يستطيع ذلك — فكل شيء فيه على
مسار الفئات — ولهذا تكون قيمة `Main-Class` فيه هي الوسيط `Launcher`. وإذا وُضعت فئة فرعية من `Application`
في `Main-Class` ضمن هذا التخطيط فإنها تفشل بالرسالة *"JavaFX runtime components are missing"*.

استخدم `clean` دائمًا — مرة واحدة قبل بناء مجموعة من المنصات، لأنه يفرغ `target/dist/` منها جميعًا.
انظر [استكشاف أخطاء البناء وإصلاحها](#استكشاف-أخطاء-البناء-وإصلاحها) لمعرفة السبب.

### التحزيم

كل ما يُشحن يُجمع تحت `target/dist/gaia-desktop-<version>-<platform>/` ولا شيء غيره، حتى يمكن ضغط المجلد
أو نسخه كمجموعة واحدة دون انتقاء المخرجات من `target/` إلى جانب `classes/` و`maven-status/` وبقية
الملفات المؤقتة للبناء. يسمّيه `${dist.dir}` مرة واحدة، وكل إضافة تكتب مخرَجًا تشير إليه.

#### بناء لكل منصة

تحمل ملفات jar الخاصة بـ JavaFX شيفرة أصلية، ولذلك تكون كل حزمة توزيع لمنصة واحدة، يسمّيها الخاصية
`fx.platform` بوصفها مصنِّف OpenJFX: `mac-aarch64` أو `mac` أو `win` أو `linux` أو `linux-aarch64`.
تضبطها خمسة ملفات تعريف `fx-*` تُفعَّل حسب نظام التشغيل على منصة الجهاز الذي يبني، وهذا كل ما يحتاجه
`mvn package` أو `mvn javafx:run` العاديان؛ ويتقدم عليها `-Dfx.platform=…` لبناء أي منصة أخرى من أي جهاز —
فملفات jar الخاصة بـ JavaFX مجرد تنزيلات. قيمة `${dist.dir}` هي `target/dist/${fx.platform}`، ولذلك لا
يكتب بناء منصة فوق بناء منصة أخرى أبدًا.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

تفصيلتان في ملف pom تجعلان ذلك ممكنًا، وكلتاهما تبدو قابلة للحذف:

- **كل وحدة من وحدات JavaFX تبعية مباشرة** — base وgraphics وcontrols وmedia وweb — كل منها مع
  `<classifier>${fx.platform}</classifier>` واستبعاد `org.openjfx:*`. فملفات pom الخاصة بـ OpenJFX تختار
  ملفات jar المتعدية حسب نظام تشغيل *الجهاز الذي يبني*، فإذا تُركت graphics أو base لتصل بشكل متعدٍّ
  دخلت المكتبات الأصلية لنظام Mac في بناء Windows إلى جانب مكتبات Windows.
- **الخاصية هي `fx.platform` وليست `javafx.platform`.** إذا ضُبطت خاصية OpenJFX نفسها من الخارج، أعاد
  ملف pom الأب تعريفها بدلالة نفسها؛ فيرفض Maven ملف pom ذاك لأنه غير صالح ويُسقط ملفات jar الخاصة
  بالمنصة بصمت، تاركًا بناءً لا JavaFX فيه.

يكتب التخطيطان المسار نفسه، `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`، ويعمل واحد منهما فقط في
كل بناء. و`${jar.phase}` و`assembly.skipAssembly` و`mdep.skip` هي ما يمنعهما من المطالبة به معًا.

| | الافتراضي | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | نحو 290 KB — فئات هذه الوحدة ومواردها فقط | نحو 50 MB — التبعيات مفكوكة داخله |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 16 ملف jar، مسمّاة واحدًا واحدًا في `Class-Path` في البيان | — |
| ما يُشحن | ملف jar **و** `lib/` بجانبه | ملف واحد |
| وفي `dist/gaia-desktop-<version>-<platform>/` أيضًا | `run.bat` (win) أو `run.sh` (غيرها) | الشيء نفسه |
| و | `readme.html` و`docs/` (كل المنصات) | الشيء نفسه |

تحمل كل حزمة توزيع الأدلة أيضًا: `docs/` منسوخًا مع الحفاظ على تخطيطه، حتى تبقى الروابط بين الأدلة
والترجمات صالحة، باستثناء أدوات الترجمة (`check-i18n.py` و`i18n-manifest.json`)؛ و
`readme.html` في الجذر، وهو فهرس يربط بكل منها، مأخوذ من `src/main/dist/readme.html` مع استبدال
`@VERSION@` بإصدار pom. يكتبهما معًا خطوة antrun المسماة `pick-launch-script`، التي تحذف `docs/` أولًا
حتى لا يبقى دليل أُزيل. روابط ملف readme مكتوبة يدويًا — فالدليل الذي يُعاد تسميته أو الترجمة التي
تُضاف تحت `docs/` يحتاج إلى سطره هناك أيضًا.

`Class-Path` في البيان و`lib/` نصفان لشيء واحد: يسمّي ملف jar المسار `lib/<artifact>-<version>.jar` لكل
تبعية وقت تشغيل، ويملأ `copy-dependencies` المجلد `lib/` بهذه الأسماء بالضبط. وهذا ما يجعل `java -jar`
يعمل.

#### تطبيق macOS وملف zip للتوزيع

تنهي عملية تنفيذ antrun واحدة، `mac-app-and-zip`، المرحلة `package`. ولهذا السبب أُعلنت إضافة antrun
**بعد** إضافتي jar وassembly — إذ يشغّل Maven عمليات التنفيذ في المرحلة الواحدة بترتيب إعلان الإضافات —
فيكون ملف jar موجودًا، في أي من التحزيمين، حين تعمل. (أما عملية التنفيذ الأخرى، `pick-launch-script`،
ففي `prepare-package` ولا تتأثر.)

بالنسبة إلى `mac` و`mac-aarch64` تبني أولًا `GAIA Desktop.app` في مجلد التوزيع: `Info.plist` (مع استبدال
`@VERSION@` بإصدار pom)، والمشغّل `Contents/MacOS/gaia-desktop` (بعد جعله قابلًا للتنفيذ)، و
`gaia-desktop.icns`، وكلها من `src/main/macos/`، ثم **تنقل** `gaia-desktop.jar` و`lib/` إلى
`Contents/Java`، فتصبح الحزمة قائمة بذاتها. يبحث `run.sh` هناك حين لا يجد ملف jar بجانبه. يجد المشغّل
Java حسب الإصدار (`java_home -v 21+`، ثم openjdk من Homebrew — فالتشغيل من Finder لا يرى `JAVA_HOME`
ولا `PATH`)، ويعرض مربع حوار عبر `osascript` حين لا يجد شيئًا، وينفّذ `cd` إلى `~/.gaia-desktop` ليكون
المسار النسبي `logs/` الخاص بـ logback قابلًا للكتابة، ويمرّر `-Xdock:name`/`-Xdock:icon`. يربط macOS
عملية `java` الجارية بالحزمة (فيكون معرّف الحزمة وأيقونة Dock للتطبيق)؛ ويظهر في شريط القوائم GAIA
Desktop.

ثم، لكل منصة، تضغط المجلد إلى `target/dist/gaia-desktop-<version>-<platform>.zip` تحت مجلد بالاسم نفسه،
باستخدام `<zip>` من Ant: `run.sh` و`Contents/MacOS/**` كمجموعة ملفات منفصلة مع `filemode="755"`، وإلا
لما أمكن تشغيلهما بعد فك الضغط. ملف zip **لا يُرفق**: فهو لإصدارات GitHub، والمنصات الأربع تأتي من أربع
عمليات بناء، ولا يمكن لـ Maven Central — برفع واحد غير قابل للتغيير لكل إصدار — أن يقبلها إصدارًا واحدًا.

تُضبط `project.build.outputTimestamp` على وقت البناء. وإلا فإن أدوات الأرشفة في maven-jar-plugin 3.5
وmaven-assembly-plugin 3.8 تؤرّخ كل مدخل بتاريخ 1 فبراير 1980.

يرسم أيقونة التطبيق `tools/icon/GaiaIcon.java` (وهو ليس جزءًا من البناء؛ وفي ترويسته خطوات
`sips`/`iconutil`). ومخرجاته محفوظة في المستودع: `src/main/macos/gaia-desktop.icns` للحزمة، و
`src/main/resources/icons/gaia-desktop-{16..256}.png` التي يضبطها `GaiaDesktopApp` أيقونةً للنافذة
(Windows وLinux؛ أما macOS فيتجاهل أيقونات النوافذ).

#### سكربتات التشغيل

يأتي `run.sh` و`run.bat` من `src/main/scripts/`، ويُنسخان إلى `dist/gaia-desktop-<version>-<platform>/` دون ترشيح —
فـ `run.sh` مليء بتوسيعات الصدفة `${...}` التي قد يعيد ترشيح Maven كتابتها كما يشاء. ثم تُبقي خطوة antrun
على السكربت الذي تشغّله المنصة فقط — `run.bat` لـ `win`، و`run.sh` لكل ما سواها — وتضبط بت التنفيذ على
`run.sh`، لأن `copy-resources` لا يحمله. وهي تقرر بناءً على قيمة `${fx.platform}` المحسومة لا من خلال ملفات
التعريف، لأن تفعيل ملف تعريف لا يرى قيمة ضبطها ملف تعريف آخر: وإلا لحصل بناء Linux مصنوع على Windows على
سكربت المضيف.

إنهما **لا يعتمدان على البيان**. كل منهما يبني مسار الفئات بنفسه: `gaia-desktop.jar` يليه كل ملف `.jar`
في `lib/`، مسمّى واحدًا واحدًا بدلًا من تركه للنمط الشامل `lib/*`، حتى يبقى المسار الذي يحتوي مسافات
مدخلًا واحدًا ويكون عدد ما أُضيف حقيقيًا. والتشغيل باستخدام `-cp` هو سبب تسميتهما
`tools.pantheum.gaia.desktop.Launcher` صراحة: فـ `-cp` لا يقرأ `Main-Class` في البيان. لكنه **لا يزال**
يتبع `Class-Path` الخاص به — فملف jar على `-cp` يجلب ملفات jar التي يسمّيها بيانه، ويُبحث فيها مباشرة
بعده — ولذلك يُحمَّل كل ملف jar في `lib/` سواء أدرجه السكربت أم لا، وحذف أحدها من مسار فئات السكربت لا
يُبقيه خارج JVM. ومع ذلك يدرجها السكربتان جميعًا، حتى يبدأ ملف jar الذي بيانه قديم أو معدّل يدويًا أو
ينقصه مدخل. يخدم السكربت نفسه كلا التحزيمين: فملف jar الخاص بـ `-Pfat` ليس له `lib/` يضيفه ولا يحتاج
إليه، وهذا أيضًا سبب كون `lib/` الفارغ ملاحظةً لا خطأً.

#### مكتبات Zebra الأصلية

لا يشحن البناء شيئًا من Zebra — لا ملفات DLL ولا ملفات jar للخدمات. ففي Windows تأتي من Scanner SDK
الخاص بـ Zebra المثبّت على الجهاز: يضيف `run.bat` ملفات jar للخدمات `Jpos*.jar` و`bin\` إلى مسار الفئات
و`bin\` إلى `PATH`، حيث يجد `System.loadLibrary` الملف `CSJPOSScanner.dll` / `CSJPOSScanner64.dll`
(فالقيمة الافتراضية لـ `java.library.path` هي `PATH`). أما واجهة JavaPOS البرمجية ومحمّل إعداداتها
فيأتيان دائمًا من `lib\javapos-*.jar`، بوجود SDK أو بدونه.

**`run.bat` لا يضيف أبدًا ملف jar الخاص بـ JavaPOS في SDK نفسه**، أي
`External\JavaPOS-1.14.0-Dist\javaPOS114.jar`. كان يفعل ذلك من قبل، تاركًا `lib\javapos-*.jar` لتجنب
نسختين من الواجهة البرمجية — لكن `Class-Path` في البيان حمّلهما على أي حال (انظر أعلاه)، فحصلت JVM على
كليهما: فئات المحمّل 4.x من `lib\`، ومعها `jpos/res/jpos.properties` و`jcl.xsd` من `javaPOS114.jar`. ملف
الخصائص يجعل [`JposConfig`](#تكامل-الماسح) يتنحّى، وملف `jcl.xsd` ذاك لا يقبل إصدارات JavaPOS إلا حتى
1.10، فأخفق كل مدخل في `jpos.xml` (1.12–1.14) في التحقق، وبقي السجل فارغًا، وفشل كل اتصال بالخطأ 109
قبل الوصول إلى الماسح أصلًا. ووجود ملف jar ذاك على مسار الفئات يكفي لذلك، حتى لو كان بعد ملفات jar في
`lib\`. تعمل ملفات jar الخاصة بخدمات Zebra دون تغيير على واجهة 1.14 من `lib\` — فقد تُحقق من الفتح
والحجز والمسح على ماسح حقيقي بهذه الطريقة. ولا تزال ملفات DLL الموضوعة يدويًا بجانب `run.bat` محترمة:
يضبط السكربت حينها `-Djava.library.path=<dist>;%PATH%`، مُلحقًا `PATH` لأن الخاصية تستبدل مسار البحث
الافتراضي استبدالًا تامًا.

`mvn javafx:run` لا يفعل شيئًا من هذا، ولذلك يحتاج حجز الماسح من تشغيل تطويري على Windows إلى وضع ملفات
jar الخاصة بـ SDK على مسار الفئات و`bin\` الخاص به على `PATH` بوسائل أخرى؛ شغّل من `dist/` لذلك.

وفضلًا عن مسار الفئات يتوليان ما لا يفعله `java -jar`: حلّ مجلدهما الخاص حتى يعملا من أي مجلد عمل،
وتفضيل `JAVA_HOME` على `PATH`، ورفض JVM أقدم من 11 بجملة تذكر العلاج بدلًا من
`UnsupportedClassVersionError`. يمرّر `GAIA_DESKTOP_OPTS` خيارات JVM. يستخدم `run.bat` الملف `java.exe`
لا `javaw.exe`، فتبقى وحدة التحكم مفتوحة — فـ Windows هو المنصة الوحيدة التي يعمل فيها الماسح، وإليها
تذهب حالته وأخطاء JavaPOS.

ويختار `run.bat` أيضًا Java وJavaFX وخدمات Zebra مما يجده — `jdk*\` مرفقًا، و`javafx-sdk*\lib\` على
مسار الوحدات، وScanner SDK الخاص بـ Zebra في `ZEBRA_HOME` — تاركًا نسخ JavaFX في `lib\` خارج مسار الفئات
حين يستخدم نسخة SDK، ويمرّر محلل SAX الخاص بـ JDK، ووكلاء Windows ومخزن الثقة، و`--enable-native-access`
على Java 17 وما بعده. ويحتوي قسم [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows)
في README على الجدول. حافظ على نهايات الأسطر CRLF في الملف: فقد يفوّت `cmd.exe` استدعاء `call :label` في
ملف دفعي بنهايات LF فقط. ويمرّر `run.sh` كذلك `--enable-native-access=ALL-UNNAMED` — فـ JavaFX يحمّل
مكتباته الأصلية من `lib/`، ومع وجود JavaFX على مسار الفئات تكون `ALL-UNNAMED` هي الوحدة التي تشمله —
ولا يُتخطى ذلك، كما في `run.bat`، إلا حين يتعذر قراءة إصدار Java.

يحمل كل من التخطيطين مكتبات JavaFX الأصلية **لمنصة واحدة**، `${fx.platform}`، ولذلك لا يمكن نقل أي
منهما بين أنظمة التشغيل أو المعماريات. ابنِ مرة لكل هدف — انظر [بناء لكل منصة](#بناء-لكل-منصة).

> **Eclipse.** تحمل عملية تنفيذ `copy-dependencies` التعليمة `<?m2e ignore?>`. يحلّ m2e مشروع مساحة العمل
> المفتوح إلى مجلده `target/classes` بدلًا من ملف jar، ويرفض `copy-dependencies` نسخ مخرَج غير محزّم
> (MDEP-187)، مما يُفشل البناء التلقائي كلما كان مشروع `gaia` مفتوحًا بجانب هذا المشروع. والنتيجة أن
> البناء داخل IDE وحده لا يملأ `target/dist/gaia-desktop-<version>-<platform>/lib/`؛ شغّل `mvn package` قبل
> استخدام ملف jar نفسه.

### قمع الإدخال

كل إدخال — مكتوب، أو ملصق، أو مفتوح من ملف، أو ممسوح، أو مُنشأ — يصل إلى المحلل عبر دالة واحدة،
`MainView.capture(String, ScanSource, String)`.

هذا هو قرار التصميم الوحيد الذي بُني التطبيق حوله. فالإنشاء لا يحتاج إلى تقرير خاص به، ولا إلى سجل خاص
به، ولا إلى مسار تصدير خاص به، لأن السلسلة المُنشأة بعد القمع لا يمكن تمييزها من السلسلة الممسوحة. وكل
جديد ينتج إدخالًا ينبغي أن يمر عبره لا أن يلتف حوله.

### الخيوط

| الخيط | ما يشغّله |
|---|---|
| خيط تطبيق JavaFX | كل التحليل والعرض وواجهة المستخدم. يستغرق التحليل أقل من جزء من الألف من الثانية بعد تسخين جداول AI، فلا يحتاج إلى خيط عامل |

| الخلفية | انتظار `connect()` / `disconnect()` للماسح (قد يستغرق الحجز حتى 5 ثوانٍ)، واستعادة السجل المحفوظ عند بدء التشغيل — وهو ما يعمل أيضًا على تسخين المحلل — وفحص التحديثات (`gaia-update-check`، طلب واحد إلى GitHub، وتُعاد النتيجة عبر `Platform.runLater`) |

التطبيق جاءت من ذلك بالضبط: إعادة ضبط منتقي AI داخل `clearAndSelect` الخاص بالنافذة المنبثقة نفسها
(استثناء `IndexOutOfBoundsException` صادر من `ListViewBehavior`)، وإعادة بناء اللوحة التي تملك قائمة
اللغات المنسدلة من داخل معالج تلك القائمة نفسها. كلاهما الآن مؤجَّل باستخدام `Platform.runLater`،
والأسباب مدوّنة في موضعي الاستدعاء كليهما.

### إعادة البناء مقابل إعادة التسمية

تغيير اللغة **يعيد بناء** إطار الواجهة من الفهرس — القوائم وشريط الأدوات ولوحة الخيارات — وهذا آمن لأن
شيئًا منها لا يملك حالة: فـ `OptionsPane` عرض ثنائي الاتجاه لـ `ParseOptions`، فتعيش القيم في النموذج
وتلتقطها اللوحة الجديدة مباشرة.

أما عناصر التحكم التي تحمل **بيانات المستخدم** فهي حقول، وتُعاد تسميتها في مكانها بدلًا من ذلك:
`BuilderPane.retext(UiStrings)` يحتفظ بصفوف AI وحقول Digital Link والتحديد. وإعادة بنائها ستتجاهل العمل
الجاري — وقد فعلت ذلك مرة.

## رمز {GS}

يتجاهل `TextField` في JavaFX بصمت كل حرف أقل من `0x20` (`TextInputControl.filterInput`). ليس "يعرضه بشكل
غريب" — بل يحذفه. الكتابة واللصق و`setText` و`insertText` كلها متأثرة، فيعطي
`setText("01…" + GS + "10LOT")` النتيجة `"01…10LOT"`: سلسلة عناصر تغيّر معناها بهدوء، لأن AI ذا الطول
المتغير يبتلع الآن ما يليه.

`desktop.parse.GsToken` هو الحل كله. ينتقل الفاصل عبر الواجهة بوصفه النص الحرفي `{GS}` ويصبح `0x1D` من
جديد في طريقه إلى المحلل. والرمز ليس مخترعًا هنا — بل هو بالضبط ما يعرض به `ASCIIRevealerUtils.printable`
في النواة الحرف `0x1D`، ولذلك تُلصق القيمة المنسوخة من تقرير مباشرة في شريط الإدخال.

يلتقط مرشح `TextFormatter` على حقل الإدخال كل طريق يمكن أن يصل منه النص — الكتابة، و⌘V، وقائمة السياق،
والسحب والإفلات، و`setText` — ولهذا تعيش إعادة الكتابة هناك لا في كل معالج.

مسار الماسح لا يمر أبدًا عبر `GsToken`: فالمسحات تصل إلى المحلل بايتات.

## تكامل الماسح

يملك `ScannerService` عنصر التحكم `Scanner` الخاص بـ JavaPOS: فتح ← حجز ← تمكين، مع إعادة تفعيل حدث
البيانات بعد كل مسح. تأتي أسماء الأجهزة المنطقية من `src/main/resources/jpos.xml`.

**كل استدعاء للجهاز يعمل على خيط واحد، `gaia-scanner`، يعيش ما عاشت الخدمة** — لا على خيط FX أبدًا، ولا
على خيط ينتهي بعد الاستدعاء. تصل خدمة Zebra إلى الماسح عبر JNI من خلال واجهة CoreScanner COM، وCOM يربط
ما يُعدّه بشقة (apartment) الخيط المستدعي: افتح على خيط ينتهي بعد ذلك، فيُحجز الماسح لكنه يبقى صامتًا؛
وأغلق على خيط آخر، فتُلغى تهيئة الشقة الخطأ. والإغلاق على خيط FX هو أسوأ الحالات، لأن JavaFX يستدعي
`OleInitialize` هناك ويسجل هدف الإفلات لكل نافذة بناءً عليه — واستدعاء `CoUninitialize` عليه يقتل السحب
والإفلات في التطبيق كله. هذا هو JavaFX على Windows، لا إصدار بعينه من JavaFX. يرسل `connect()`
و`disconnect()` العمل إلى ذلك الخيط وينتظران، ولذلك يستدعيهما `MainView` من خيط خلفي قصير العمر.

قاعدتان تمنعان جهازًا مضطربًا من تعطيل الاتصال. **التفكيك لا يتوقف مبكرًا أبدًا:** يعطّل `closeQuietly`
ويحرّر ويغلق في خطوات منفصلة، ولا يحرّر إلا حين يكون الحجز قائمًا، ويحاول دائمًا `close()` — فبعد فشل
الحجز يرمي `release()` استثناء "غير محجوز"، وحين كانت الخطوات تتشارك `try` واحدًا كان ذلك يتخطى الإغلاق
ويترك الجهاز مفتوحًا في خدمة Zebra. **يُعاد تفعيل حدث البيانات في `finally`:** يعطّله JavaPOS بعد كل حدث،
فيجب أن يُعاد تفعيله حتى لو رمت القراءة أو المعالج استثناءً، وإلا صمت الماسح حتى إعادة الاتصال. ويختبر
`ScannerLifecycleTest` القاعدتين كلتيهما مقابل `jpos.Scanner` مبرمج مسبقًا.

**يوجّه `JposConfig` مكتبة JavaPOS إلى ملف `jpos.xml` المرفق** قبل أول فتح. فمع ملفات jar الخاصة بـ JavaPOS
من Maven (`javapos-config-loader` 4.x) ودون `jpos/res/jpos.properties` على مسار الفئات، يفشل كل فتح
بخلاف ذلك بالرسالة *"Service does not exist in loaded JCL registry"* (الخطأ 109)، لثلاثة أسباب منفصلة:
يعود مدير الخدمات إلى `SimpleRegPopulator`، الذي يقرأ `jpos.cfg` مسلسَلًا ولا يقرأ `jpos.xml` أبدًا؛ ويبحث
محمّل XML عن `jpos.xml` في مجلد العمل فقط، لا داخل ملف jar؛ ويرفض Xerces 2.12.2 الموجود في `lib/` خاصية
JAXP `accessExternalDTD` التي يضبطها المحمّل. يضبط `JposConfig` كلًا من `jpos.config.regPopulatorClass`
(`JavaxRegPopulator`) و`jpos.config.populatorFileURL` (`jar:file:…!/jpos.xml` الخاص بملف jar نفسه) و
`javax.xml.parsers.SAXParserFactory` (الخاص بـ JDK) خصائصَ نظام — دون أن يمس أبدًا ما ضُبط من قبل، فيظل
`-Djpos.config.populatorFileURL=file:…` قادرًا على اختيار `jpos.xml` آخر — ولا يضبط شيئًا حين يكون
`jpos.properties` على مسار الفئات أو حين لا يكون المحمّل 4.x موجودًا. ملف `javaPOS114.jar` الخاص بـ SDK من
Zebra حالة من هذا النوع، وهو يكسر السجل تمامًا، ولهذا يُبقيه `run.bat` خارج مسار الفئات — انظر
[مكتبات Zebra الأصلية](#مكتبات-zebra-الأصلية). ويتحقق `JposConfigTest` من البداية إلى النهاية من أن السجل
يحتوي بعدها على ماسحات الملف.

**يُولَّد منتقي الأجهزة من ذلك السجل**، ولا يُحفظ قائمةً في الشيفرة: يقرأ `ScannerService.logicalNames()`
المدخلات المحمّلة على خيط `gaia-scanner` ويُبقي ما كانت فئة جهازه `Scanner` — فيبقى مدخلا الميزان في
`jpos.xml` خارجًا — بترتيب `pickerOrder`: `ZebraAllScanners` أولًا إن عرّفه الملف، والباقي أبجديًا (فالسجل
لا يحتفظ بترتيب الملف). والملف الذي لا يعرّفه لا يُضاف إليه؛ وحين لا يُحمَّل شيء يُعرض الافتراضي وحده،
فلا يكون المنتقي فارغًا أبدًا. يعرض `MainView` الافتراضي فورًا ويملأ القائمة من خيط خلفي، محتفظًا
بالاختيار المحفوظ. وهكذا يظهر الماسح المضاف إلى `jpos.xml` — أو ملف كامل يُسمّى عبر
`-Djpos.config.populatorFileURL` — في المنتقي دون أي تغيير في الشيفرة، ويتحقق `JposConfigTest` من المنتقي
مقابل قراءة مستقلة للملف المرفق. والخدمات التي تسمّيها تلك المدخلات هي فئات Zebra
(`com.zebra.jpos.service.scanner.*Factory`)، التي لا يزال يجب أن تكون على مسار الفئات — من Scanner SDK عبر
`run.bat`، أو ملفات jar لخدمات Zebra موضوعة في `lib\`.

تُفك شيفرة بيانات المسح بترميز **ISO-8859-1** حتى يقابل كل بايت حرفًا واحدًا بالضبط، فتبقى بادئة AIM
Code ID وكل `0x1D` سليمة؛ وتُكتب التقارير بترميز UTF-8.

لا شيء في الخدمة يصوغ نصًا للمستخدم. تخرج الأحداث بوصفها ثوابت `ScannerListener.Event` مع القيم التي
تتغير، ويوفّر `MainView` الصياغة من الفهرس — وإلا لكان سطر الحالة بالإنجليزية في تطبيق مترجم إلى 35 لغة.
أسطر السجل هي الاستثناء وتبقى بالإنجليزية.

### بوابة المنصة

`ScannerService.isSupportedPlatform()` اختبار واحد لـ `os.name`، ويسأله `MainView` قبل بناء أي عنصر تحكم
للماسح: ففي macOS وLinux لا يوجد مفتاح تبديل، ولا منتقي أجهزة، ولا قائمة الماسح (وبالتالي لا
<kbd>⌘K</kbd>)، ولا تسمية حالة. إنها ليست مخفية — بل لا تُنشأ أبدًا.

تشحن Zebra خدمات JavaPOS الخاصة بها لـ Windows فقط، ولا شيء يفشل مبكرًا في غيره: تُحلّ ملفات jar ويُنشأ
عنصر التحكم، ثم يكون `open()` هو ما يفشل أخيرًا بسبب الطبقة الأصلية المفقودة، بعد عدة ثوانٍ ومربع حوار.

القاعدة تتعلق بـ *الخدمات* لا بـ JavaPOS. فالمورّد الذي يشحن خدمة متعددة المنصات سيعمل هنا، وتوسيع القاعدة
تغيير في `supportsJavaPos(String)` وحدها — وهي على مستوى الحزمة ومختبرة مقابل سلاسل `os.name` حتى تُغطى
الإجابتان على أي جهاز يشغّل البناء.

### الترميزات

يربط `Symbologies` جميع أنواع بيانات المسح **78** من `SCAN_SDT_*` في JavaPOS بأسماء عرض، وبقيمة
`DataCarrierType` في النواة حيث تتوافق المفردتان. وJavaPOS هو الأدق بين الاثنين — فهو يفصل UPC-A عن
EAN-13، وData Matrix العادي عن GS1 DataMatrix، حيث يجمع AIM عائلة كاملة تحت حرف رمز واحد.

النوع الذي لا يوجد في الجدول يحصل مع ذلك على اسم صالح، يُعثر عليه بالانعكاس على `ScannerConst`، لأن
خدمات المورّدين تبلّغ فعلًا عن قيم خارج قائمة المواصفات. ويمر اختبار على `ScannerConst` ويفشل إن كان أي
نوع معلن بلا اسم — وهو ما يلتقط أيضًا الثوابت التي قد يضيفها JavaPOS مستقبلًا.

بعض ربطات الحوامل تُركت عمدًا `UNKNOWN` بدل التخمين: 2 of 5 المستقيم (يفصل AIM بين `]R`/`]S` حسب عدد
أشرطة البداية والنهاية، وهو ما لا يبلّغ عنه JavaPOS)، والرموز البريدية رباعية الحالات، وTLC-39.

## التوطين

تعيش التسميات في ملف خصائص واحد لكل لغة تحت `src/main/resources/i18n/ui_<CODE>.properties`، باستخدام
الرموز نفسها التي تستخدمها فهارس الأخطاء في النواة (`EN`، `FR`، `PCM`، …). الملفات الخمسة والثلاثون كلها
موجودة، وكلها تحمل مجموعة مفاتيح متطابقة. تُقرأ الملفات بترميز **UTF-8**، لا ISO-8859-1 الذي يفترضه
`Properties`، فتُخزن الترجمات بشكل مقروء بدلًا من تسلسلات الهروب `\uXXXX`.

**الرجوع يكون لكل مفتاح، لا لكل ملف** — وهذا ما يجعل اللغة المترجمة جزئيًا مفيدة منذ لحظة وصول أول مفتاح
فيها. الإنجليزية هي العقد: يجب أن يوجد كل مفتاح فيها.

| الطبقة | المفاتيح | التغطية |
|---|---|---|
| مفردات التقارير المشتركة | 31 | اللغات الخمس والثلاثون كلها |
| إطار سطح المكتب — القوائم والأزرار والمُنشئ والخيارات وسطر الحالة وتخطيط التقرير وحالة الماسح ونصوص مربعات الحوار | 114 | اللغات الخمس والثلاثون كلها |

ستة من المصطلحات المشتركة (`generated`، `status`، `dlRole`، `interpretations`، `message`، `level`) لا
يستخدمها تقرير هذا التطبيق.
أُبقيت عن قصد؛ وترويسة الملف تقول ذلك.

### الوسيط `--language`

يقرأ `GaiaDesktopApp.languageOverride()` الوسيط `--language=…` عبر `getParameters().getNamed()` الخاص بـ
JavaFX نفسه، ويحلّه باستخدام `Languages.fromArgument` — رمز فهرس، أو اسم enum، أو وسم BCP 47، دون تمييز
لحالة الأحرف — ويسلّمه إلى `MainView`.

**التجاوز يخص التشغيل، لا الملف.** يحتفظ `MainView` باللغة التي حمّلها في `savedLanguage` ويكتب *تلك*
اللغة عند الحفظ، إلى أن يشير `languageChosenInSession` إلى أن المستخدم اختار لغة بنفسه؛ عندها يُحفظ
اختياره كالمعتاد. هذا الفصل هو التصميم كله: يستطيع ملف شخصي لكشك أو اختصار لعرض تجريبي أن يفتح بالإسبانية
دون إعادة كتابة ما سيفتح به صاحب الجهاز غدًا، بينما يظل الاختيار الحقيقي في لوحة الخيارات ثابتًا.

القيمة التي لا تسمّي أي فهرس تُسجَّل مع الرموز المقبولة ثم تُتجاهل. فرفض بدء التشغيل بسبب خطأ إملائي في
اختصار سيكون الإخفاق الأسوأ، ولهذا السبب نفسه يعيد `Languages.fromArgument` القيمة `null` بدل رمي استثناء.

### إضافة لغة

لا حاجة إلى أي تغيير في الشيفرة.

1. حرّر `ui_<CODE>.properties` — لكل لغة ملف بالفعل.
2. ترجم القيم. اترك العناصر النائبة `{0}` / `{1}` في مكانها.
3. ابنِ. اختباران يفرضان العقد: أحدهما يفشل إن طلبت الشيفرة مفتاحًا لا تعرّفه الإنجليزية، والآخر إن
   انحرفت مجموعة مفاتيح أي فهرس عن الإنجليزية.

يفحص الاختبار الأول **الشيفرة المصدرية** بحثًا عن المفاتيح الحرفية بدل الانعكاس على الفئات، لأن المفاتيح
لا توجد إلا بوصفها سلاسل حرفية في مواضع الاستدعاء. ولهذا يجب أن تُبنى الرسالة الجديدة والمفتاح مكتوب
مباشرة — `strings.format("st.scannerError", …)` — لا أن يُبحث عنه عبر متغير، وإلا لم يستطع الاختبار رؤيته.

### ما يبقى دون ترجمة عن قصد

- أسماء الحقول المقتضبة المكتوبة بخط أحادي المسافة بجانب القيم الخام — `format` و`position` و`length` و
  `raw` و`part` في بطاقة العنصر، و`AI` و`sep` و`pos` و`len` في الشريط، والخلايا الأربع التي تحدد موضع
  الخطأ (`AI`، `position`، `level`، `stage`)، وقيمها أسماء enum غير مترجمة على أي حال؛
- أسماء أمثلة الإدخال، التي تسمّي بنى GS1، وأسماء الترميزات، وهي أسماء علم؛
- فقرة المعالجة الخاصة بـ `GE-C084` — نص معايير تكون ترجمته الناقصة أسوأ من الإنجليزية؛
- خط الدفاع الأخير في `ElementBuilder` للـ AI غير المعروف، الذي لا يمكن الوصول إليه من الواجهة: فالمحرر
  يتحقق بنفسه من الـ AI غير المعروفة ويبلّغ عنها من الفهرس؛
- أسطر السجل.

تبقى ثغرة واحدة: يوفّر `ScanSource.label()` القيم `manual` / `scanner` / `file` / `built` لصف السجل وترويسة
التقرير بالإنجليزية. وسدّها يحتاج إلى أكثر من مفتاح — فـ `HistoryCell` ليس لديه `UiStrings`، ومصنع خلايا
القائمة يُثبَّت مرة واحدة، فيجب تحديث الخلايا أيضًا عند تغيير اللغة.

## صيغ الحالة المخزنة

ملفان تحت `~/.gaia-desktop/`، منفصلان لأنهما يتغيران بإيقاعين مختلفين — فسجل التقاط تالف أو معدّل يدويًا
لا ينبغي أن يكلّف المستخدم إعداداته. تجاوز المجلد باستخدام `-Dgaia.desktop.home=…`، وهكذا تبقى
الاختبارات بعيدة عن المجلد المنزلي الحقيقي.

**`options.properties`** — يُكتب حين يتغير خيار، وعند الخروج.

| المفتاح | المعنى |
|---|---|
| `parse.mode`، `parse.language` | عمق خط المعالجة ولغة الرسائل |
| `date.endian`، `date.separator`، `date.month`، `date.year` | عرض التاريخ |
| `check.skipRequires`، `check.skipExcludes` | تخطّي الفحوص البنيوية |
| `ui.theme` | `LIGHT` أو `DARK` |
| `ui.optionsPane` | هل لوحة الخيارات مفتوحة؟ |
| `ui.scannerDevice` | آخر اسم منطقي لجهاز JavaPOS |
| `ui.mode` | `PARSE` أو `BUILD` أو `COMBINE` |
| `update.check` | هل يعمل فحص التحديثات اليومي (الافتراضي `true`) |
| `update.lastCheck` | وقت آخر تشغيل له، بصيغة ISO-8601؛ غيابه أو تعذر قراءته يعني أن الفحص مستحق |
| `update.skipVersion` | إصدار اختار له المستخدم *تخطي هذا الإصدار*؛ لا يُعرض مرة أخرى تلقائيًا |

الملف المفقود أو التالف ليس قاتلًا أبدًا: فكل قيمة ترجع إلى افتراضيها منفردة، فلا يكلّف السطر السيئ إلا
ذلك السطر. وعند التشغيل الأول، دون أي ملف، تُهيَّأ الخيارات من الإعدادات الإقليمية للجهاز بواسطة
`SystemDefaults` بدلًا من القيم الافتراضية المضمّنة في GAIA — فنمط التاريخ القصير للإعدادات المحلية يحدد
ترتيب المكونات، والفاصل، وما إذا كان الشهر والسنة مختصرين.

لا تمرّر null أبدًا إلى `Properties.setProperty`: فهو يرمي استثناءً، و`persistOptions()` يعمل من معالجات
أحداث الواجهة حيث يفلت الاستثناء إلى خيط FX. هذا عطل حقيقي حدث في هذا التطبيق من قبل.

**`captures.tsv`** — يُكتب حين يتغير السجل، وعند الخروج. الأحدث أولًا، بحد أقصى **500** مدخل.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

لا يُخزن إلا ما لا يمكن إعادة حسابه. `ParseResult` **لا** يُسلسَل — بل يُستنتج من جديد بتحليل الإدخال مرة
أخرى عند التحميل، فيعكس السجل المستعاد الخيارات السارية *الآن*. تحتوي المدخلات عادةً على FNC1 وأي شيء آخر
يصدره الماسح، ولذلك يُهرَّب حقل الإدخال (`\\`، `\t`، `\n`، `\r`، و`\xNN` لكل ما سواها تحت `0x20`)
ويُقرأ الملف ويُكتب بترميز ISO-8859-1، بايتًا ببايت.

الملفات التي كُتبت قبل تسجيل التاريخ تحمل وقت الساعة وحده؛ ولا تزال تُحمَّل، مؤرَّخة باليوم، لأن التاريخ
الحقيقي لم يُدوَّن قط.

## الاختبار

```bash
(cd gaia-desktop && mvn test)
```

198 اختبارًا، **خالية من مجموعة أدوات JavaFX** عن قصد، مما يجعلها سريعة وتعمل دون واجهة. تغطي عارض
التقارير، ومنطق الإنشاء والبحث عن AI، وتحويل `{GS}`، والقيم الافتراضية المستمدة من الإعدادات المحلية،
والمخزنين كليهما (بما في ذلك رحلة ذهاب وعودة تحمل `0x1D` وملفات تالفة عمدًا)، وجدول الترميزات، وقاعدة
منصة الماسح، وبديل الإصدار، والفهارس.

ثلاثة منها تستحق المعرفة لأنها تحمي عقودًا لا وظائف:

| الاختبار | يفشل حين |
|---|---|
| `CatalogueCoverageTest` | تطلب الشيفرة مفتاحًا لا يعرّفه `ui_EN.properties`، أو ينحرف أي من الملفات الخمسة والثلاثين عن مجموعة المفاتيح الإنجليزية |
| `SymbologiesTest` | يكون لأي ثابت `SCAN_SDT_*` يعلنه JavaPOS اسم عرض مفقود — بما في ذلك ما تضيفه ترقية JavaPOS |
| `ScannerServiceTest` | تتغير إجابة قاعدة المنصة بالنسبة إلى Windows أو إلى أي نظام آخر |

`UiStrings` متسامح عن قصد وقت التشغيل — فالمفتاح غير المعروف يُعرض كما هو بدلًا من رمي استثناء في منتصف
التخطيط — وهذا بالضبط سبب وجوب وجود اختبار الفهرس.

**غير مغطّى:** كل ما يحتاج إلى مجموعة أدوات حية — سلوك التركيز، ومفتاح تبديل الوضع، وتحرير الجداول،
وتبديل اللغة، والعطلان الموصوفان تحت [الخيوط](#الخيوط). تُحقق منها بتشغيل النافذة الحقيقية، لكن أي تراجع
فيها لن يُفشل البناء. وإضافة TestFX أو Monocle ستسد هذه الثغرة.

## استكشاف أخطاء البناء وإصلاحها

| العَرَض | السبب والحل |
|---|---|
| `package tools.pantheum.gaia does not exist` | النواة غير مثبتة. `(cd gaia && mvn install -DskipTests)` |
| *"JavaFX runtime components are missing"* | يجب أن تكون `Main-Class` في ملف jar هي `Launcher`، لا `GaiaDesktopApp` |
| *"Unsupported JavaFX configuration: classes were loaded from unnamed module"* عند بدء التشغيل | متوقع وغير ضار — JavaFX يلاحظ أنه على مسار الفئات. وهذا بالضبط سبب وجود `Launcher` |
| ملف jar لا يبدأ، `NoClassDefFoundError` | ملف jar الافتراضي لا يحمل إلا فئات هذه الوحدة؛ يجب أن يكون `dist/lib/` بجانبه. استخدم `-Pfat` للحصول على ملف واحد مكتفٍ بذاته |
| `Artifact has not been packaged yet … MDEP-187` في Eclipse | حلّ مساحة عمل m2e. انظر الملاحظة تحت [التحزيم](#التحزيم) |
| تظهر ملفات `… 2.properties` مكررة في البناء | المشروع في مجلد تزامنه iCloud، وأنتج التزامن نسخًا متعارضة في أثناء البناء. استخدم `mvn clean package` دائمًا؛ والأفضل استبعاد `target/` من التزامن |
| يُظهر عنصر قائمة مفتاحًا مثل `act.hri` | ذلك المفتاح مفقود من `ui_EN.properties`. كان ينبغي أن يلتقطه البناء — انظر [الاختبار](#الاختبار) |

## القيود المعروفة والعمل المتبقي

- **لا اختبارات واجهة بلا عرض.** انظر [الاختبار](#الاختبار).
- **مخرجات خاصة بالمنصة.** يرفق كلا التحزيمين مكتبات JavaFX الأصلية لمنصة واحدة؛ ابنِ واحدًا لكل هدف
  باستخدام `-Dfx.platform` (أي جهاز يمكنه بناؤها جميعًا). ولا يرفق أي منهما بيئة تشغيل Java — فذلك يحتاج
  إلى `jpackage`، الذي لا يبني إلا لنظام التشغيل الذي يعمل عليه.
- **إدخال الماسح على Windows فقط.** انظر [بوابة المنصة](#بوابة-المنصة).
- **`ScanSource.label()` غير مترجم.** انظر [ما يبقى دون ترجمة عن
  قصد](#ما-يبقى-دون-ترجمة-عن-قصد).
- **`UiState.mode` من نوع `String`** (`"PARSE"` / `"BUILD"`) بينما `Theme` بجانبه من نوع enum، فتظهر
  القيمة الحرفية في عدة مواضع. وتحويله إلى enum سيزيلها.
- **هدف Digital Link هو النطاق وبادئة المسار فقط.** يدعم `BuilderDigitalLinkConfig` أيضًا معاملات استعلام
  إضافية وجزءًا (fragment)؛ ولا يعرضها المحرر.
- **أزواج AI المتنافية (`GE-S006`) لا يُشار إليها في المحرر** كما يُشار إلى الـ AI غير المعروفة والمكررة —
  فالإنشاء يفشل ببساطة.
- **فهرس الأخطاء في النواة يضاعف علامات الاقتباس** (`value ''09506000134350''`)، وهو ما يظهر حرفيًا في
  حالات فشل الإنشاء وفي التقرير. يبدو أنه تهريب اقتباس من `MessageFormat` لا يُلغى؛ والإصلاح مكانه النواة.
