## ਮੋਡੀਊਲ ਇੱਕ ਨਜ਼ਰ ਵਿੱਚ

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

ਇਹ ਕੋਰ ਲਾਇਬ੍ਰੇਰੀ ਦਾ ਇੱਕ ਕਲਾਇੰਟ ਹੈ, ਇਸ ਤੋਂ ਵੱਧ ਕੁਝ ਨਹੀਂ। ਇਸ ਵਿੱਚ **GS1 ਦਾ ਕੋਈ ਗਿਆਨ ਨਹੀਂ ਹੈ**: ਹਰ AI ਪਰਿਭਾਸ਼ਾ,
ਪ੍ਰਮਾਣਿਕਤਾ ਨਿਯਮ, ਗਲਤੀ ਸੁਨੇਹਾ ਅਤੇ ਸਥਾਨਕ ਵੇਰਵਾ [`GaiaParser`](../../../../gaia/docs/GaiaParser.md) ਅਤੇ
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md) ਤੋਂ ਆਉਂਦਾ ਹੈ। ਖ਼ਾਸ ਕਰਕੇ, AI ਸੂਚੀ ਕਦੇ ਵੀ ਇਸ ਮੋਡੀਊਲ ਵਿੱਚ ਕਾਪੀ
ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ — ਬਿਲਡਰ ਦਾ ਪਿਕਰ ਕੋਰ ਦੀ ਆਪਣੀ ਰਜਿਸਟਰੀ ਪੜ੍ਹਦਾ ਹੈ, ਇਸ ਲਈ ਉਹ ਅਜਿਹਾ AI ਪੇਸ਼ ਨਹੀਂ ਕਰ ਸਕਦਾ ਜਿਸਨੂੰ ਬਿਲਡਰ
ਰੱਦ ਕਰ ਦੇਵੇ।

**ਦਾਖ਼ਲਾ ਬਿੰਦੂ:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX `Application`) ਅਤੇ
`tools.pantheum.gaia.desktop.Launcher` (ਪੈਕੇਜ ਕੀਤੇ jar ਦਾ `Main-Class`)।

ਮੋਡੀਊਲ ਇੱਕ ਪੱਤਾ (leaf) ਹੈ: ਇਸ ਉੱਤੇ ਕੁਝ ਵੀ ਨਿਰਭਰ ਨਹੀਂ, ਅਤੇ ਇਹ ਕਿਸੇ ਹੋਰ ਡਾਊਨਸਟ੍ਰੀਮ ਮੋਡੀਊਲ ਉੱਤੇ ਨਿਰਭਰ ਨਹੀਂ।

## ਬਿਲਡ ਅਤੇ ਚਲਾਉਣਾ

- ਚਲਾਉਣ ਲਈ **Java 21**, ਅਤੇ ਬਿਲਡ ਲਈ JDK 21 ਜਾਂ ਨਵਾਂ — ਮੋਡੀਊਲ `release=21` ਨਾਲ ਕੰਪਾਇਲ ਹੁੰਦਾ ਹੈ। JavaFX 21 ਇਸ ਨਾਲ
  ਮੇਲ ਖਾਂਦੀ LTS ਲੜੀ ਹੈ। ਕੋਰ jar ਅਜੇ ਵੀ Java 11 ਬਾਈਟਕੋਡ ਹੈ ਅਤੇ 21 ਉੱਤੇ ਬਿਨਾਂ ਬਦਲਾਅ ਦੇ ਚੱਲਦਾ ਹੈ।
- `PATH` ਉੱਤੇ **Maven**। ਇਸ ਰਿਪੋਜ਼ਟਰੀ ਵਿੱਚ ਕੋਈ wrapper ਨਹੀਂ ਹੈ।
- **ਪਹਿਲਾਂ ਕੋਰ ਇੰਸਟਾਲ ਕਰੋ।** ਇਹ ਮੋਡੀਊਲ `gaia:1.1.0` ਨੂੰ `~/.m2` ਤੋਂ ਲੈਂਦਾ ਹੈ; ਪੁਰਾਣਾ ਜਾਂ ਗੈਰ-ਮੌਜੂਦ ਕੋਰ jar ਹੀ
  ਆਮ ਤੌਰ ਉੱਤੇ `package tools.pantheum.gaia does not exist` ਦਾ ਕਾਰਨ ਹੁੰਦਾ ਹੈ।

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` ਇੱਕੋ-ਇੱਕ ਕਮਾਂਡ-ਲਾਈਨ ਆਰਗੂਮੈਂਟ ਹੈ, ਅਤੇ `-Dgaia.desktop.home=…` ਤੋਂ ਇਲਾਵਾ, ਜੋ ਪੂਰੀ ਪ੍ਰੋਫਾਈਲ ਨੂੰ ਕਿਤੇ ਹੋਰ
ਲੈ ਜਾਂਦਾ ਹੈ, ਸਟਾਰਟ-ਅੱਪ ਉੱਤੇ ਅਸਰ ਪਾਉਣ ਦਾ ਇੱਕੋ-ਇੱਕ ਤਰੀਕਾ ਹੈ।

`mvn javafx:run` ਵਿਕਾਸ ਦਾ ਰਾਹ ਹੈ: ਪਲੱਗਇਨ JavaFX ਨੂੰ **ਮੋਡੀਊਲ ਪਾਥ** ਉੱਤੇ ਰੱਖਦਾ ਹੈ, ਇਸ ਲਈ ਟੂਲਕਿੱਟ ਨਾਮ ਵਾਲੇ ਮੋਡੀਊਲ
ਵਜੋਂ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ ਅਤੇ `GaiaDesktopApp` ਸਿੱਧਾ ਲਾਂਚ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ। ਪੈਕੇਜ ਕੀਤਾ jar ਇਹ ਨਹੀਂ ਕਰ ਸਕਦਾ — ਉਸ ਵਿੱਚ ਸਭ
ਕੁਝ ਕਲਾਸ ਪਾਥ ਉੱਤੇ ਹੁੰਦਾ ਹੈ — ਇਸੇ ਲਈ ਉਸਦਾ `Main-Class` `Launcher` ਸ਼ਿਮ ਹੈ। ਉਸ ਬਣਤਰ ਵਿੱਚ `Main-Class` ਵਜੋਂ
`Application` ਦਾ ਸਬਕਲਾਸ *"JavaFX runtime components are missing"* ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ।

ਹਮੇਸ਼ਾਂ `clean` ਵਰਤੋ — ਪਲੇਟਫਾਰਮਾਂ ਦਾ ਇੱਕ ਸਮੂਹ ਬਿਲਡ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਇੱਕ ਵਾਰ, ਕਿਉਂਕਿ ਇਹ `target/dist/` ਨੂੰ ਉਹਨਾਂ ਸਭ
ਤੋਂ ਖਾਲੀ ਕਰ ਦਿੰਦਾ ਹੈ। ਕਾਰਨ ਲਈ [ਬਿਲਡ ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ ਦਾ ਹੱਲ](#ਬਿਲਡ-ਦੀਆਂ-ਸਮੱਸਿਆਵਾਂ-ਦਾ-ਹੱਲ) ਵੇਖੋ।

### ਪੈਕੇਜਿੰਗ

ਭੇਜਣ ਯੋਗ ਹਰ ਚੀਜ਼ `target/dist/gaia-desktop-<version>-<platform>/` ਹੇਠ ਇਕੱਠੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਹੋਰ ਕੁਝ ਨਹੀਂ, ਤਾਂ ਜੋ
ਉਸ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਇੱਕ ਸੈੱਟ ਵਜੋਂ zip ਜਾਂ ਕਾਪੀ ਕੀਤਾ ਜਾ ਸਕੇ, `target/` ਵਿੱਚ `classes/`, `maven-status/` ਅਤੇ ਬਿਲਡ ਦੀਆਂ
ਬਾਕੀ ਆਰਜ਼ੀ ਫਾਈਲਾਂ ਦੇ ਨਾਲੋਂ ਆਰਟੀਫੈਕਟ ਚੁਣੇ ਬਿਨਾਂ। `${dist.dir}` ਇਸਨੂੰ ਇੱਕ ਥਾਂ ਨਾਮ ਦਿੰਦਾ ਹੈ; ਆਰਟੀਫੈਕਟ ਲਿਖਣ ਵਾਲਾ ਹਰ
ਪਲੱਗਇਨ ਇਸੇ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ।

#### ਹਰ ਪਲੇਟਫਾਰਮ ਲਈ ਇੱਕ ਬਿਲਡ

JavaFX jar ਨੇਟਿਵ ਕੋਡ ਰੱਖਦੇ ਹਨ, ਇਸ ਲਈ ਹਰ ਵੰਡ ਇੱਕ ਪਲੇਟਫਾਰਮ ਲਈ ਹੁੰਦੀ ਹੈ, ਜਿਸਦਾ ਨਾਮ `fx.platform` ਪ੍ਰਾਪਰਟੀ OpenJFX
ਕਲਾਸੀਫਾਇਰ ਵਜੋਂ ਦਿੰਦੀ ਹੈ: `mac-aarch64`, `mac`, `win`, `linux` ਜਾਂ `linux-aarch64`। OS ਅਨੁਸਾਰ ਸਰਗਰਮ ਹੋਣ ਵਾਲੀਆਂ
ਪੰਜ `fx-*` ਪ੍ਰੋਫਾਈਲਾਂ ਇਸਨੂੰ ਬਿਲਡ ਕਰ ਰਹੀ ਮਸ਼ੀਨ ਦੇ ਆਪਣੇ ਪਲੇਟਫਾਰਮ ਉੱਤੇ ਸੈੱਟ ਕਰਦੀਆਂ ਹਨ, ਅਤੇ ਸਾਦੇ `mvn package` ਜਾਂ
`mvn javafx:run` ਨੂੰ ਬੱਸ ਇੰਨਾ ਹੀ ਚਾਹੀਦਾ ਹੈ; `-Dfx.platform=…` ਉਹਨਾਂ ਤੋਂ ਉੱਪਰ ਰਹਿ ਕੇ ਕਿਸੇ ਵੀ ਮਸ਼ੀਨ ਤੋਂ ਕੋਈ ਵੀ ਹੋਰ
ਪਲੇਟਫਾਰਮ ਬਿਲਡ ਕਰਦਾ ਹੈ — JavaFX jar ਸਿਰਫ਼ ਡਾਊਨਲੋਡ ਹਨ। `${dist.dir}` `target/dist/${fx.platform}` ਹੈ, ਇਸ ਲਈ ਇੱਕ
ਪਲੇਟਫਾਰਮ ਦਾ ਬਿਲਡ ਕਦੇ ਦੂਜੇ ਦੇ ਬਿਲਡ ਉੱਤੇ ਨਹੀਂ ਲਿਖਦਾ।

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

pom ਦੇ ਦੋ ਵੇਰਵੇ ਇਸਨੂੰ ਕੰਮ ਕਰਵਾਉਂਦੇ ਹਨ, ਅਤੇ ਦੋਵੇਂ ਹਟਾਉਣ ਯੋਗ ਲੱਗਦੇ ਹਨ:

- **ਹਰ JavaFX ਮੋਡੀਊਲ ਇੱਕ ਸਿੱਧੀ ਨਿਰਭਰਤਾ ਹੈ** — base, graphics, controls, media ਅਤੇ web — ਹਰ ਇੱਕ
  `<classifier>${fx.platform}</classifier>` ਅਤੇ ਇੱਕ `org.openjfx:*` ਬਾਹਰਕਰਨ ਨਾਲ। OpenJFX ਦੇ pom ਆਪਣੇ ਅਸਿੱਧੇ
  (transitive) jar *ਬਿਲਡ ਕਰ ਰਹੀ ਮਸ਼ੀਨ* ਦੇ OS ਅਨੁਸਾਰ ਚੁਣਦੇ ਹਨ, ਇਸ ਲਈ graphics ਜਾਂ base ਨੂੰ ਅਸਿੱਧੇ ਤੌਰ ਉੱਤੇ ਆਉਣ ਦੇਣ
  ਨਾਲ Windows ਬਿਲਡ ਵਿੱਚ Windows ਵਾਲਿਆਂ ਦੇ ਨਾਲ Mac ਦੇ ਨੇਟਿਵ ਵੀ ਆ ਜਾਂਦੇ ਹਨ।
- **ਪ੍ਰਾਪਰਟੀ `fx.platform` ਹੈ, `javafx.platform` ਨਹੀਂ।** ਬਾਹਰੋਂ ਸੈੱਟ ਕਰਨ ਉੱਤੇ OpenJFX ਦੀ ਆਪਣੀ ਪ੍ਰਾਪਰਟੀ ਨੂੰ ਉਸਦਾ
  ਪੇਰੈਂਟ pom ਖ਼ੁਦ ਉਸੇ ਦੇ ਰੂਪ ਵਿੱਚ ਮੁੜ ਪਰਿਭਾਸ਼ਿਤ ਕਰ ਦਿੰਦਾ ਹੈ; Maven ਉਸ pom ਨੂੰ ਅਵੈਧ ਮੰਨ ਕੇ ਰੱਦ ਕਰ ਦਿੰਦਾ ਹੈ ਅਤੇ ਚੁੱਪਚਾਪ
  ਪਲੇਟਫਾਰਮ jar ਛੱਡ ਦਿੰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਅਜਿਹਾ ਬਿਲਡ ਬਚਦਾ ਹੈ ਜਿਸ ਵਿੱਚ JavaFX ਹੈ ਹੀ ਨਹੀਂ।

ਦੋਵੇਂ ਬਣਤਰਾਂ ਇੱਕੋ ਪਾਥ ਲਿਖਦੀਆਂ ਹਨ, `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`, ਅਤੇ ਹਰ ਬਿਲਡ
ਵਿੱਚ ਉਹਨਾਂ ਵਿੱਚੋਂ ਠੀਕ ਇੱਕ ਚੱਲਦੀ ਹੈ। `${jar.phase}`, `assembly.skipAssembly` ਅਤੇ `mdep.skip` ਹੀ ਉਹਨਾਂ ਨੂੰ ਦੋਵਾਂ ਦੇ
ਇਸ ਉੱਤੇ ਦਾਅਵਾ ਕਰਨ ਤੋਂ ਰੋਕਦੇ ਹਨ।

| | ਡਿਫਾਲਟ | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — ਸਿਰਫ਼ ਇਸ ਮੋਡੀਊਲ ਦੀਆਂ ਕਲਾਸਾਂ ਅਤੇ ਸਰੋਤ | ~50 MB — ਨਿਰਭਰਤਾਵਾਂ ਇਸ ਵਿੱਚ ਖੋਲ੍ਹ ਕੇ ਰੱਖੀਆਂ |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 jar, ਮੈਨੀਫੈਸਟ `Class-Path` ਵਿੱਚ ਇੱਕ-ਇੱਕ ਕਰਕੇ ਨਾਮ ਦਿੱਤੇ | — |
| ਭੇਜੋ | jar **ਅਤੇ** ਉਸਦੇ ਨਾਲ `lib/` | ਇੱਕ ਫਾਈਲ |
| `dist/gaia-desktop-<version>-<platform>/` ਵਿੱਚ ਇਹ ਵੀ | `run.bat` (win) ਜਾਂ `run.sh` (ਬਾਕੀ) | ਉਹੀ |
| ਅਤੇ | `readme.html` ਅਤੇ `docs/` (ਹਰ ਪਲੇਟਫਾਰਮ) | ਉਹੀ |

ਹਰ ਵੰਡ ਵਿੱਚ ਗਾਈਡਾਂ ਵੀ ਹੁੰਦੀਆਂ ਹਨ: `docs/` ਆਪਣੀ ਬਣਤਰ ਸਮੇਤ ਕਾਪੀ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਤਾਂ ਜੋ ਗਾਈਡਾਂ ਅਤੇ ਅਨੁਵਾਦਾਂ ਵਿਚਕਾਰ ਲਿੰਕ
ਕੰਮ ਕਰਦੇ ਰਹਿਣ, ਅਨੁਵਾਦ ਟੂਲਿੰਗ (`check-i18n.py`, `i18n-manifest.json`, `i18n-plan.md`) ਨੂੰ ਛੱਡ ਕੇ; ਅਤੇ ਰੂਟ ਉੱਤੇ
`readme.html`, ਜੋ ਹਰ ਇੱਕ ਨਾਲ ਜੋੜਨ ਵਾਲਾ ਸੂਚਕਾਂਕ ਹੈ, `src/main/dist/readme.html` ਤੋਂ, ਜਿਸ ਵਿੱਚ `@VERSION@` ਨੂੰ pom
ਸੰਸਕਰਣ ਨਾਲ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ। ਦੋਵਾਂ ਨੂੰ `pick-launch-script` antrun ਪੜਾਅ ਲਿਖਦਾ ਹੈ, ਜੋ ਪਹਿਲਾਂ `docs/` ਮਿਟਾਉਂਦਾ ਹੈ
ਤਾਂ ਜੋ ਹਟਾਈ ਗਈ ਗਾਈਡ ਪਿੱਛੇ ਨਾ ਰਹਿ ਜਾਵੇ। readme ਦੇ ਲਿੰਕ ਹੱਥੀਂ ਲਿਖੇ ਗਏ ਹਨ — `docs/` ਹੇਠ ਕਿਸੇ ਗਾਈਡ ਦਾ ਨਾਮ ਬਦਲਣ ਜਾਂ
ਅਨੁਵਾਦ ਜੋੜਨ ਉੱਤੇ ਉੱਥੇ ਵੀ ਉਸਦੀ ਕਤਾਰ ਚਾਹੀਦੀ ਹੈ।

ਮੈਨੀਫੈਸਟ `Class-Path` ਅਤੇ `lib/` ਇੱਕੋ ਚੀਜ਼ ਦੇ ਦੋ ਅੱਧ ਹਨ: jar ਹਰ ਰਨਟਾਈਮ ਨਿਰਭਰਤਾ ਲਈ
`lib/<artifact>-<version>.jar` ਦਾ ਨਾਮ ਲੈਂਦਾ ਹੈ, ਅਤੇ `copy-dependencies` `lib/` ਨੂੰ ਠੀਕ ਇਹਨਾਂ ਨਾਵਾਂ ਨਾਲ ਭਰਦਾ ਹੈ। ਇਸੇ
ਨਾਲ `java -jar` ਕੰਮ ਕਰਦਾ ਹੈ।

#### macOS ਐਪ ਅਤੇ ਵੰਡ zip

ਇੱਕ antrun ਐਗਜ਼ੀਕਿਊਸ਼ਨ, `mac-app-and-zip`, `package` ਪੜਾਅ ਨੂੰ ਖ਼ਤਮ ਕਰਦਾ ਹੈ। ਇਸੇ ਕਾਰਨ antrun ਪਲੱਗਇਨ jar ਅਤੇ
assembly ਪਲੱਗਇਨਾਂ ਦੇ **ਬਾਅਦ** ਘੋਸ਼ਿਤ ਕੀਤਾ ਗਿਆ ਹੈ — Maven ਕਿਸੇ ਪੜਾਅ ਦੇ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਪਲੱਗਇਨ ਘੋਸ਼ਣਾ ਦੇ ਕ੍ਰਮ ਵਿੱਚ ਚਲਾਉਂਦਾ
ਹੈ — ਤਾਂ ਜੋ ਜਦੋਂ ਇਹ ਚੱਲੇ ਤਾਂ jar, ਕਿਸੇ ਵੀ ਪੈਕੇਜਿੰਗ ਵਿੱਚ, ਮੌਜੂਦ ਹੋਵੇ। (ਇਸਦਾ ਦੂਜਾ ਐਗਜ਼ੀਕਿਊਸ਼ਨ, `pick-launch-script`,
`prepare-package` ਵਿੱਚ ਹੈ ਅਤੇ ਪ੍ਰਭਾਵਿਤ ਨਹੀਂ ਹੁੰਦਾ।)

`mac` ਅਤੇ `mac-aarch64` ਲਈ ਇਹ ਪਹਿਲਾਂ ਵੰਡ ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ `GAIA Desktop.app` ਬਣਾਉਂਦਾ ਹੈ: `Info.plist` (ਜਿਸ ਵਿੱਚ
`@VERSION@` pom ਸੰਸਕਰਣ ਨਾਲ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ), ਲਾਂਚਰ `Contents/MacOS/gaia-desktop` (ਚੱਲਣਯੋਗ ਬਣਾਇਆ) ਅਤੇ
`gaia-desktop.icns`, ਸਭ `src/main/macos/` ਤੋਂ, ਫਿਰ `gaia-desktop.jar` ਅਤੇ `lib/` ਨੂੰ `Contents/Java` ਵਿੱਚ **ਲੈ
ਜਾਂਦਾ ਹੈ**, ਤਾਂ ਜੋ ਬੰਡਲ ਆਪਣੇ-ਆਪ ਵਿੱਚ ਪੂਰਾ ਰਹੇ। ਜਦੋਂ ਨਾਲ ਕੋਈ jar ਨਾ ਹੋਵੇ ਤਾਂ `run.sh` ਉੱਥੇ ਵੇਖਦਾ ਹੈ। ਲਾਂਚਰ ਸੰਸਕਰਣ
ਅਨੁਸਾਰ Java ਲੱਭਦਾ ਹੈ (`java_home -v 21+`, ਫਿਰ Homebrew ਦਾ openjdk — Finder ਤੋਂ ਲਾਂਚ ਕਰਨ ਉੱਤੇ `JAVA_HOME` ਜਾਂ `PATH`
ਨਹੀਂ ਦਿਸਦਾ), ਕੁਝ ਨਾ ਮਿਲਣ ਉੱਤੇ `osascript` ਰਾਹੀਂ ਡਾਇਲਾਗ ਵਿਖਾਉਂਦਾ ਹੈ, `~/.gaia-desktop` ਵਿੱਚ `cd` ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ
logback ਦਾ ਸਾਪੇਖ `logs/` ਲਿਖਣਯੋਗ ਹੋਵੇ, ਅਤੇ `-Xdock:name`/`-Xdock:icon` ਭੇਜਦਾ ਹੈ। macOS ਚੱਲ ਰਹੇ `java` ਨੂੰ ਬੰਡਲ
ਨਾਲ ਜੋੜਦਾ ਹੈ (ਉਸਦੀ bundle id ਅਤੇ Dock ਆਈਕਨ ਐਪ ਦੇ ਹੁੰਦੇ ਹਨ); ਮੀਨੂ ਬਾਰ ਵਿੱਚ GAIA Desktop ਦਿਸਦਾ ਹੈ।

ਫਿਰ, ਹਰ ਪਲੇਟਫਾਰਮ ਲਈ, ਇਹ Ant ਦੇ `<zip>` ਨਾਲ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਉਸੇ ਨਾਮ ਦੇ ਫੋਲਡਰ ਹੇਠ
`target/dist/gaia-desktop-<version>-<platform>.zip` ਵਿੱਚ zip ਕਰਦਾ ਹੈ: `run.sh` ਅਤੇ `Contents/MacOS/**` ਨੂੰ
`filemode="755"` ਨਾਲ ਵੱਖਰੇ ਫਾਈਲ ਸੈੱਟ ਵਜੋਂ, ਨਹੀਂ ਤਾਂ unzip ਹੋਣ ਉੱਤੇ ਉਹ ਚੱਲਣਯੋਗ ਨਹੀਂ ਰਹਿਣਗੀਆਂ। zip **ਨੱਥੀ ਨਹੀਂ
ਕੀਤਾ ਜਾਂਦਾ**: ਇਹ GitHub ਰਿਲੀਜ਼ਾਂ ਲਈ ਹੈ, ਅਤੇ ਚਾਰ ਪਲੇਟਫਾਰਮ ਚਾਰ ਬਿਲਡਾਂ ਤੋਂ ਆਉਂਦੇ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ Maven Central — ਹਰ
ਸੰਸਕਰਣ ਲਈ ਇੱਕ ਨਾ ਬਦਲਣਯੋਗ ਅੱਪਲੋਡ — ਕਦੇ ਇੱਕ ਰਿਲੀਜ਼ ਵਜੋਂ ਸਵੀਕਾਰ ਨਹੀਂ ਕਰ ਸਕਦਾ।

`project.build.outputTimestamp` ਬਿਲਡ ਦੇ ਸਮੇਂ ਉੱਤੇ ਸੈੱਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਨਹੀਂ ਤਾਂ maven-jar-plugin 3.5 ਅਤੇ
maven-assembly-plugin 3.8 ਦੇ ਆਰਕਾਈਵਰ ਹਰ ਐਂਟਰੀ ਦੀ ਤਾਰੀਖ਼ 1 ਫ਼ਰਵਰੀ 1980 ਰੱਖ ਦਿੰਦੇ ਹਨ।

ਐਪ ਆਈਕਨ `tools/icon/GaiaIcon.java` ਬਣਾਉਂਦਾ ਹੈ (ਇਹ ਬਿਲਡ ਦਾ ਹਿੱਸਾ ਨਹੀਂ; ਇਸਦੇ ਹੈਡਰ ਵਿੱਚ `sips`/`iconutil` ਦੇ ਪੜਾਅ
ਹਨ)। ਇਸਦੇ ਆਉਟਪੁੱਟ ਰਿਪੋਜ਼ਟਰੀ ਵਿੱਚ ਚੈੱਕ-ਇਨ ਹਨ: ਬੰਡਲ ਲਈ `src/main/macos/gaia-desktop.icns`, ਅਤੇ
`src/main/resources/icons/gaia-desktop-{16..256}.png`, ਜਿਨ੍ਹਾਂ ਨੂੰ `GaiaDesktopApp` ਵਿੰਡੋ ਆਈਕਨ ਵਜੋਂ ਸੈੱਟ ਕਰਦਾ ਹੈ
(Windows ਅਤੇ Linux; macOS ਵਿੰਡੋ ਆਈਕਨਾਂ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰਦਾ ਹੈ)।

#### ਲਾਂਚ ਸਕ੍ਰਿਪਟਾਂ

`run.sh` ਅਤੇ `run.bat` `src/main/scripts/` ਤੋਂ ਆਉਂਦੀਆਂ ਹਨ, ਅਤੇ ਬਿਨਾਂ ਫਿਲਟਰ ਕੀਤੇ `dist/gaia-desktop-<version>-<platform>/`
ਵਿੱਚ ਕਾਪੀ ਹੁੰਦੀਆਂ ਹਨ — `run.sh` `${...}` ਸ਼ੈੱਲ ਵਿਸਤਾਰਾਂ ਨਾਲ ਭਰੀ ਹੈ ਜਿਨ੍ਹਾਂ ਨੂੰ Maven ਫਿਲਟਰਿੰਗ ਮਨਮਰਜ਼ੀ ਨਾਲ ਬਦਲ ਸਕਦੀ
ਹੈ। ਫਿਰ ਇੱਕ antrun ਪੜਾਅ ਸਿਰਫ਼ ਉਹੀ ਰੱਖਦਾ ਹੈ ਜੋ ਪਲੇਟਫਾਰਮ ਚਲਾਉਂਦਾ ਹੈ — `win` ਲਈ `run.bat`, ਬਾਕੀ ਸਭ ਲਈ `run.sh` — ਅਤੇ
`run.sh` ਉੱਤੇ ਐਗਜ਼ੀਕਿਊਟ ਬਿੱਟ ਸੈੱਟ ਕਰਦਾ ਹੈ, ਕਿਉਂਕਿ `copy-resources` ਇਸਨੂੰ ਨਾਲ ਨਹੀਂ ਲੈ ਜਾਂਦਾ। ਇਹ ਪ੍ਰੋਫਾਈਲਾਂ ਦੀ ਬਜਾਏ
ਹੱਲ ਕੀਤੇ `${fx.platform}` ਤੋਂ ਫ਼ੈਸਲਾ ਕਰਦਾ ਹੈ, ਕਿਉਂਕਿ ਪ੍ਰੋਫਾਈਲ ਸਰਗਰਮੀ ਉਹ ਮੁੱਲ ਨਹੀਂ ਵੇਖ ਸਕਦੀ ਜੋ ਕਿਸੇ ਦੂਜੀ ਪ੍ਰੋਫਾਈਲ ਨੇ ਸੈੱਟ
ਕੀਤਾ ਹੋਵੇ: ਨਹੀਂ ਤਾਂ Windows ਉੱਤੇ ਬਣੇ Linux ਬਿਲਡ ਨੂੰ ਹੋਸਟ ਦੀ ਸਕ੍ਰਿਪਟ ਮਿਲ ਜਾਂਦੀ।

ਇਹ **ਮੈਨੀਫੈਸਟ ਉੱਤੇ ਨਿਰਭਰ ਨਹੀਂ ਕਰਦੀਆਂ**। ਹਰ ਇੱਕ ਕਲਾਸ ਪਾਥ ਖ਼ੁਦ ਬਣਾਉਂਦੀ ਹੈ, `gaia-desktop.jar` ਅਤੇ ਉਸ ਤੋਂ ਬਾਅਦ `lib/`
ਦਾ ਹਰ `.jar`, `lib/*` ਵਾਈਲਡਕਾਰਡ ਉੱਤੇ ਛੱਡਣ ਦੀ ਬਜਾਏ ਇੱਕ-ਇੱਕ ਕਰਕੇ ਨਾਮ ਦੇ ਕੇ, ਤਾਂ ਜੋ ਖ਼ਾਲੀ ਥਾਂ ਵਾਲਾ ਪਾਥ ਇੱਕੋ ਐਂਟਰੀ ਰਹੇ
ਅਤੇ ਜੋੜੇ ਗਏ ਦੀ ਗਿਣਤੀ ਅਸਲ ਹੋਵੇ। `-cp` ਨਾਲ ਲਾਂਚ ਕਰਨਾ ਹੀ ਕਾਰਨ ਹੈ ਕਿ ਇਹ `tools.pantheum.gaia.desktop.Launcher` ਨੂੰ
ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ ਨਾਮ ਦਿੰਦੀਆਂ ਹਨ: `-cp` ਮੈਨੀਫੈਸਟ ਦਾ `Main-Class` ਨਹੀਂ ਪੜ੍ਹਦਾ। ਫਿਰ ਵੀ ਇਹ ਉਸਦੇ `Class-Path` ਦੀ **ਪਾਲਣਾ
ਕਰਦਾ ਹੈ** — `-cp` ਉੱਤੇ ਮੌਜੂਦ jar ਆਪਣੇ ਮੈਨੀਫੈਸਟ ਵਿੱਚ ਨਾਮ ਦਿੱਤੇ jar ਨਾਲ ਲਿਆਉਂਦਾ ਹੈ, ਜਿਨ੍ਹਾਂ ਨੂੰ ਉਸ ਤੋਂ ਠੀਕ ਬਾਅਦ ਖੋਜਿਆ
ਜਾਂਦਾ ਹੈ — ਇਸ ਲਈ ਹਰ `lib/` jar ਲੋਡ ਹੁੰਦਾ ਹੈ ਭਾਵੇਂ ਸਕ੍ਰਿਪਟ ਉਸਨੂੰ ਸੂਚੀਬੱਧ ਕਰੇ ਜਾਂ ਨਾ, ਅਤੇ ਸਕ੍ਰਿਪਟ ਦੇ ਕਲਾਸ ਪਾਥ ਤੋਂ ਕਿਸੇ
ਨੂੰ ਛੱਡ ਦੇਣ ਨਾਲ ਉਹ JVM ਤੋਂ ਬਾਹਰ ਨਹੀਂ ਰਹਿੰਦਾ। ਸਕ੍ਰਿਪਟਾਂ ਫਿਰ ਵੀ ਸਭ ਨੂੰ ਸੂਚੀਬੱਧ ਕਰਦੀਆਂ ਹਨ, ਤਾਂ ਜੋ ਜਿਸ jar ਦਾ ਮੈਨੀਫੈਸਟ
ਪੁਰਾਣਾ, ਹੱਥੀਂ ਸੋਧਿਆ ਜਾਂ ਇੱਕ ਐਂਟਰੀ ਘੱਟ ਹੋਵੇ, ਉਹ ਵੀ ਸ਼ੁਰੂ ਹੋ ਜਾਵੇ। ਇੱਕੋ ਸਕ੍ਰਿਪਟ ਦੋਵਾਂ ਪੈਕੇਜਿੰਗਾਂ ਦੇ ਕੰਮ ਆਉਂਦੀ ਹੈ: `-Pfat`
jar ਕੋਲ ਜੋੜਨ ਲਈ ਕੋਈ `lib/` ਨਹੀਂ ਅਤੇ ਲੋੜ ਵੀ ਨਹੀਂ, ਇਸੇ ਲਈ ਖ਼ਾਲੀ `lib/` ਇੱਕ ਸੂਚਨਾ ਹੈ, ਗਲਤੀ ਨਹੀਂ।

#### Zebra ਨੇਟਿਵ ਲਾਇਬ੍ਰੇਰੀਆਂ

ਬਿਲਡ Zebra ਦਾ ਕੁਝ ਵੀ ਨਾਲ ਨਹੀਂ ਭੇਜਦਾ — ਨਾ DLL, ਨਾ ਸਰਵਿਸ jar। Windows ਉੱਤੇ ਇਹ ਮਸ਼ੀਨ ਉੱਤੇ ਇੰਸਟਾਲ ਕੀਤੇ Zebra ਦੇ
Scanner SDK ਤੋਂ ਆਉਂਦੇ ਹਨ: `run.bat` ਇਸਦੇ `Jpos*.jar` ਸਰਵਿਸ jar ਅਤੇ `bin\` ਨੂੰ ਕਲਾਸ ਪਾਥ ਵਿੱਚ ਅਤੇ `bin\` ਨੂੰ `PATH`
ਵਿੱਚ ਜੋੜਦਾ ਹੈ, ਜਿੱਥੇ `System.loadLibrary` `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` ਲੱਭਦਾ ਹੈ (`java.library.path`
ਦਾ ਡਿਫਾਲਟ `PATH` ਹੈ)। JavaPOS API ਅਤੇ ਇਸਦਾ ਕੌਂਫਿਗਰੇਸ਼ਨ ਲੋਡਰ ਹਮੇਸ਼ਾਂ `lib\javapos-*.jar` ਤੋਂ ਆਉਂਦੇ ਹਨ, SDK ਹੋਵੇ ਜਾਂ ਨਾ।

**`run.bat` ਕਦੇ ਵੀ SDK ਦਾ ਆਪਣਾ JavaPOS jar ਨਹੀਂ ਜੋੜਦਾ**, `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`। ਪਹਿਲਾਂ ਇਹ
ਅਜਿਹਾ ਕਰਦਾ ਸੀ, API ਦੀਆਂ ਦੋ ਕਾਪੀਆਂ ਤੋਂ ਬਚਣ ਲਈ `lib\javapos-*.jar` ਨੂੰ ਛੱਡ ਕੇ — ਪਰ ਮੈਨੀਫੈਸਟ `Class-Path` ਨੇ ਉਹਨਾਂ ਨੂੰ
ਫਿਰ ਵੀ ਲੋਡ ਕਰ ਦਿੱਤਾ (ਉੱਪਰ ਵੇਖੋ), ਇਸ ਲਈ JVM ਨੂੰ ਦੋਵੇਂ ਮਿਲ ਗਏ: `lib\` ਤੋਂ 4.x ਲੋਡਰ ਕਲਾਸਾਂ, ਅਤੇ ਉਹਨਾਂ ਦੇ ਨਾਲ
`javaPOS114.jar` ਦੇ `jpos/res/jpos.properties` ਅਤੇ `jcl.xsd`। ਪ੍ਰਾਪਰਟੀ ਫਾਈਲ [`JposConfig`](#ਸਕੈਨਰ-ਏਕੀਕਰਨ) ਨੂੰ
ਪਿੱਛੇ ਹਟਾ ਦਿੰਦੀ ਹੈ, ਅਤੇ ਉਹ `jcl.xsd` ਸਿਰਫ਼ 1.10 ਤੱਕ ਦੇ JavaPOS ਸੰਸਕਰਣ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ `jpos.xml` ਦੀ ਹਰ
ਐਂਟਰੀ (1.12–1.14) ਪ੍ਰਮਾਣਿਕਤਾ ਵਿੱਚ ਅਸਫਲ ਹੋਈ, ਰਜਿਸਟਰੀ ਖ਼ਾਲੀ ਰਹੀ, ਅਤੇ ਸਕੈਨਰ ਤੱਕ ਪਹੁੰਚਣ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ਹਰ ਕਨੈਕਟ ਗਲਤੀ
109 ਨਾਲ ਅਸਫਲ ਹੋਇਆ। ਇਸ ਲਈ ਉਸ jar ਦਾ ਕਲਾਸ ਪਾਥ ਉੱਤੇ ਹੋਣਾ ਹੀ ਕਾਫ਼ੀ ਹੈ, ਭਾਵੇਂ ਉਹ `lib\` ਦੇ jar ਦੇ ਪਿੱਛੇ ਹੀ ਕਿਉਂ ਨਾ ਹੋਵੇ।
Zebra ਦੇ ਸਰਵਿਸ jar `lib\` ਦੀ 1.14 API ਉੱਤੇ ਬਿਨਾਂ ਬਦਲਾਅ ਦੇ ਚੱਲਦੇ ਹਨ — open, claim ਅਤੇ ਸਕੈਨ ਨੂੰ ਇਸੇ ਤਰ੍ਹਾਂ ਇੱਕ ਅਸਲ
ਸਕੈਨਰ ਉੱਤੇ ਪਰਖਿਆ ਗਿਆ ਹੈ। `run.bat` ਦੇ ਨਾਲ ਹੱਥੀਂ ਰੱਖੇ DLL ਅਜੇ ਵੀ ਮੰਨੇ ਜਾਂਦੇ ਹਨ: ਤਦ ਸਕ੍ਰਿਪਟ
`-Djava.library.path=<dist>;%PATH%` ਸੈੱਟ ਕਰਦੀ ਹੈ, `PATH` ਨੂੰ ਅਖ਼ੀਰ ਵਿੱਚ ਜੋੜਦੇ ਹੋਏ ਕਿਉਂਕਿ ਇਹ ਪ੍ਰਾਪਰਟੀ ਡਿਫਾਲਟ ਖੋਜ ਪਾਥ
ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਬਦਲ ਦਿੰਦੀ ਹੈ।

`mvn javafx:run` ਇਹਨਾਂ ਵਿੱਚੋਂ ਕੁਝ ਨਹੀਂ ਕਰਦਾ, ਇਸ ਲਈ Windows ਉੱਤੇ ਵਿਕਾਸ ਰਨ ਤੋਂ ਸਕੈਨਰ claim ਕਰਨ ਲਈ SDK ਦੇ jar ਨੂੰ ਕਲਾਸ
ਪਾਥ ਉੱਤੇ ਅਤੇ ਇਸਦੇ `bin\` ਨੂੰ `PATH` ਉੱਤੇ ਕਿਸੇ ਹੋਰ ਤਰੀਕੇ ਨਾਲ ਰੱਖਣਾ ਪਵੇਗਾ; ਇਸ ਲਈ `dist/` ਤੋਂ ਚਲਾਓ।

ਕਲਾਸ ਪਾਥ ਤੋਂ ਇਲਾਵਾ ਇਹ ਉਹ ਵੀ ਸੰਭਾਲਦੀਆਂ ਹਨ ਜੋ `java -jar` ਨਹੀਂ ਕਰਦਾ: ਆਪਣੀ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਹੱਲ ਕਰਨਾ ਤਾਂ ਜੋ ਉਹ ਕਿਸੇ ਵੀ
ਕਾਰਜ ਡਾਇਰੈਕਟਰੀ ਤੋਂ ਕੰਮ ਕਰਨ, `PATH` ਦੀ ਬਜਾਏ `JAVA_HOME` ਨੂੰ ਤਰਜੀਹ ਦੇਣਾ, ਅਤੇ 11 ਤੋਂ ਪਹਿਲਾਂ ਦੇ JVM ਨੂੰ
`UnsupportedClassVersionError` ਦੀ ਬਜਾਏ ਉਪਾਅ ਦੱਸਣ ਵਾਲੇ ਵਾਕ ਨਾਲ ਰੱਦ ਕਰਨਾ। `GAIA_DESKTOP_OPTS` JVM ਵਿਕਲਪਾਂ ਨੂੰ ਅੱਗੇ
ਭੇਜਦਾ ਹੈ। `run.bat` `javaw.exe` ਨਹੀਂ, `java.exe` ਵਰਤਦਾ ਹੈ, ਤਾਂ ਜੋ ਕੰਸੋਲ ਖੁੱਲ੍ਹਾ ਰਹੇ — Windows ਹੀ ਇੱਕੋ-ਇੱਕ ਪਲੇਟਫਾਰਮ
ਹੈ ਜਿੱਥੇ ਸਕੈਨਰ ਚੱਲਦਾ ਹੈ, ਅਤੇ ਉਸਦੀ ਸਥਿਤੀ ਅਤੇ JavaPOS ਗਲਤੀਆਂ ਉੱਥੇ ਹੀ ਜਾਂਦੀਆਂ ਹਨ।

`run.bat` ਜੋ ਲੱਭਦਾ ਹੈ ਉਸ ਤੋਂ Java, JavaFX ਅਤੇ Zebra ਸਰਵਿਸਾਂ ਵੀ ਚੁਣਦਾ ਹੈ — ਬੰਡਲ ਕੀਤਾ `jdk*\`, ਮੋਡੀਊਲ ਪਾਥ ਉੱਤੇ
`javafx-sdk*\lib\`, `ZEBRA_HOME` ਉੱਤੇ Zebra ਦਾ Scanner SDK — SDK ਵਾਲਾ JavaFX ਵਰਤਦੇ ਸਮੇਂ `lib\` ਦੀਆਂ JavaFX ਕਾਪੀਆਂ ਨੂੰ
ਕਲਾਸ ਪਾਥ ਤੋਂ ਬਾਹਰ ਰੱਖਦਾ ਹੈ, ਅਤੇ JDK ਦਾ SAX ਪਾਰਸਰ, Windows ਪ੍ਰੌਕਸੀਆਂ ਅਤੇ ਟਰੱਸਟ ਸਟੋਰ, ਅਤੇ Java 17+ ਉੱਤੇ
`--enable-native-access` ਭੇਜਦਾ ਹੈ। README ਦੇ [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows)
ਵਿੱਚ ਸਾਰਣੀ ਹੈ। ਫਾਈਲ ਦੇ CRLF ਲਾਈਨ-ਅੰਤ ਬਣਾਈ ਰੱਖੋ: ਸਿਰਫ਼ LF ਵਾਲੀ ਬੈਚ ਫਾਈਲ ਵਿੱਚ `cmd.exe` ਕਿਸੇ `call :label` ਨੂੰ ਖੁੰਝਾ
ਸਕਦਾ ਹੈ। `run.sh` ਵੀ `--enable-native-access=ALL-UNNAMED` ਭੇਜਦੀ ਹੈ — JavaFX ਆਪਣੇ ਨੇਟਿਵ `lib/` ਤੋਂ ਲੋਡ ਕਰਦਾ ਹੈ, ਅਤੇ
JavaFX ਦੇ ਕਲਾਸ ਪਾਥ ਉੱਤੇ ਹੋਣ ਉੱਤੇ `ALL-UNNAMED` ਹੀ ਉਹ ਮੋਡੀਊਲ ਹੈ ਜੋ ਇਸਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ — ਜਿਸਨੂੰ, `run.bat` ਵਾਂਗ, ਸਿਰਫ਼
ਤਦ ਛੱਡਿਆ ਜਾਂਦਾ ਹੈ ਜਦੋਂ Java ਸੰਸਕਰਣ ਪੜ੍ਹਿਆ ਨਾ ਜਾ ਸਕੇ।

ਦੋਵੇਂ ਬਣਤਰਾਂ **ਇੱਕ ਪਲੇਟਫਾਰਮ** ਦੇ, `${fx.platform}` ਦੇ, JavaFX ਨੇਟਿਵ ਰੱਖਦੀਆਂ ਹਨ, ਇਸ ਲਈ ਕੋਈ ਵੀ OS ਜਾਂ ਆਰਕੀਟੈਕਚਰ
ਦੇ ਪਾਰ ਲਿਜਾਣਯੋਗ ਨਹੀਂ। ਹਰ ਨਿਸ਼ਾਨੇ ਲਈ ਇੱਕ ਵਾਰ ਬਿਲਡ ਕਰੋ — [ਹਰ ਪਲੇਟਫਾਰਮ ਲਈ ਇੱਕ ਬਿਲਡ](#ਹਰ-ਪਲੇਟਫਾਰਮ-ਲਈ-ਇੱਕ-ਬਿਲਡ)
ਵੇਖੋ।

> **Eclipse।** `copy-dependencies` ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਵਿੱਚ ਇੱਕ `<?m2e ignore?>` ਹਦਾਇਤ ਹੈ। m2e ਖੁੱਲ੍ਹੇ ਵਰਕਸਪੇਸ ਪ੍ਰੋਜੈਕਟ ਨੂੰ jar
> ਦੀ ਬਜਾਏ ਉਸਦੇ `target/classes` ਫੋਲਡਰ ਵਿੱਚ ਹੱਲ ਕਰਦਾ ਹੈ, ਅਤੇ `copy-dependencies` ਪੈਕੇਜ ਨਾ ਕੀਤੇ ਆਰਟੀਫੈਕਟ ਨੂੰ ਕਾਪੀ ਕਰਨ
> ਤੋਂ ਇਨਕਾਰ ਕਰਦਾ ਹੈ (MDEP-187), ਜਿਸ ਨਾਲ ਜਦੋਂ ਵੀ `gaia` ਪ੍ਰੋਜੈਕਟ ਇਸਦੇ ਨਾਲ ਖੁੱਲ੍ਹਾ ਹੋਵੇ, ਆਟੋ-ਬਿਲਡ ਅਸਫਲ ਹੋ ਜਾਵੇਗਾ।
> ਨਤੀਜਾ ਇਹ ਹੈ ਕਿ ਸਿਰਫ਼ IDE ਵਾਲਾ ਬਿਲਡ `target/dist/gaia-desktop-<version>-<platform>/lib/` ਨਹੀਂ ਭਰਦਾ; jar ਨੂੰ ਖ਼ੁਦ
> ਵਰਤਣ ਤੋਂ ਪਹਿਲਾਂ `mvn package` ਚਲਾਓ।

### ਇਨਪੁੱਟ ਫਨਲ

ਹਰ ਇਨਪੁੱਟ — ਟਾਈਪ ਕੀਤਾ, ਪੇਸਟ ਕੀਤਾ, ਫਾਈਲ ਤੋਂ ਖੋਲ੍ਹਿਆ, ਸਕੈਨ ਕੀਤਾ ਜਾਂ ਬਣਾਇਆ — ਇੱਕੋ ਮੈਥਡ,
`MainView.capture(String, ScanSource, String)`, ਰਾਹੀਂ ਪਾਰਸਰ ਤੱਕ ਪਹੁੰਚਦਾ ਹੈ।

ਇਹੀ ਉਹ ਇੱਕੋ-ਇੱਕ ਡਿਜ਼ਾਈਨ ਫ਼ੈਸਲਾ ਹੈ ਜਿਸਦੇ ਦੁਆਲੇ ਐਪ ਬਣੀ ਹੈ। ਨਿਰਮਾਣ ਨੂੰ ਆਪਣੀ ਰਿਪੋਰਟ, ਆਪਣਾ ਇਤਿਹਾਸ ਜਾਂ ਆਪਣਾ ਨਿਰਯਾਤ ਰਾਹ
ਨਹੀਂ ਚਾਹੀਦਾ, ਕਿਉਂਕਿ ਫਨਲ ਤੋਂ ਬਾਅਦ ਬਣਾਈ ਸਟ੍ਰਿੰਗ ਸਕੈਨ ਕੀਤੀ ਸਟ੍ਰਿੰਗ ਤੋਂ ਵੱਖ ਨਹੀਂ ਪਛਾਣੀ ਜਾ ਸਕਦੀ। ਇਨਪੁੱਟ ਪੈਦਾ ਕਰਨ ਵਾਲੀ
ਕੋਈ ਵੀ ਨਵੀਂ ਚੀਜ਼ ਇਸਦੇ ਨਾਲੋਂ ਨਹੀਂ, ਇਸੇ ਵਿੱਚੋਂ ਲੰਘਣੀ ਚਾਹੀਦੀ ਹੈ।

ਕਰੈਸ਼ ਠੀਕ ਇਸੇ ਤੋਂ ਹੋਏ: ਪੌਪਅੱਪ ਦੇ ਆਪਣੇ `clearAndSelect` ਦੇ ਅੰਦਰ AI ਪਿਕਰ ਨੂੰ ਰੀਸੈੱਟ ਕਰਨਾ (`ListViewBehavior` ਤੋਂ
ਨਿਕਲਿਆ ਇੱਕ `IndexOutOfBoundsException`), ਅਤੇ ਭਾਸ਼ਾ ਕੌਂਬੋ ਵਾਲੇ ਪੈਨਲ ਨੂੰ ਉਸੇ ਕੌਂਬੋ ਦੇ ਆਪਣੇ ਹੈਂਡਲਰ ਦੇ ਅੰਦਰੋਂ ਮੁੜ ਬਣਾਉਣਾ।
ਦੋਵਾਂ ਨੂੰ ਹੁਣ `Platform.runLater` ਨਾਲ ਟਾਲਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ ਕਾਰਨ ਦੋਵਾਂ ਕਾਲ ਥਾਵਾਂ ਉੱਤੇ ਦਰਜ ਹਨ।

### ਮੁੜ-ਬਣਾਉਣਾ ਬਨਾਮ ਮੁੜ-ਲੇਬਲ ਕਰਨਾ

ਭਾਸ਼ਾ ਬਦਲਣ ਉੱਤੇ ਢਾਂਚਾ — ਮੀਨੂ, ਟੂਲਬਾਰ, ਚੋਣ ਪੈਨਲ — ਕੈਟਾਲਾਗ ਤੋਂ **ਮੁੜ ਬਣਾਇਆ** ਜਾਂਦਾ ਹੈ, ਜੋ ਸੁਰੱਖਿਅਤ ਹੈ ਕਿਉਂਕਿ ਉਹਨਾਂ
ਵਿੱਚੋਂ ਕਿਸੇ ਕੋਲ ਸਥਿਤੀ ਨਹੀਂ ਹੁੰਦੀ: `OptionsPane` `ParseOptions` ਦਾ ਦੋ-ਪਾਸੀ ਦ੍ਰਿਸ਼ ਹੈ, ਇਸ ਲਈ ਮੁੱਲ ਮਾਡਲ ਵਿੱਚ ਰਹਿੰਦੇ
ਹਨ ਅਤੇ ਨਵਾਂ ਪੈਨਲ ਉਹਨਾਂ ਨੂੰ ਤੁਰੰਤ ਮੁੜ ਚੁੱਕ ਲੈਂਦਾ ਹੈ।

**ਵਰਤੋਂਕਾਰ ਦਾ ਡੇਟਾ** ਰੱਖਣ ਵਾਲੇ ਕੰਟਰੋਲ ਫੀਲਡ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ ਉਹਨਾਂ ਦੀ ਥਾਂ ਉੱਤੇ ਹੀ ਮੁੜ ਲੇਬਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:
`BuilderPane.retext(UiStrings)` AI ਕਤਾਰਾਂ, Digital Link ਫੀਲਡਾਂ ਅਤੇ ਚੋਣ ਨੂੰ ਬਣਾਈ ਰੱਖਦਾ ਹੈ। ਇਸਨੂੰ ਮੁੜ ਬਣਾਉਣ ਨਾਲ ਚੱਲ
ਰਿਹਾ ਕੰਮ ਗੁਆਚ ਜਾਵੇਗਾ — ਜਿਵੇਂ ਕਦੇ ਹੋਇਆ ਵੀ ਸੀ।

## {GS} ਟੋਕਨ

JavaFX `TextField` `0x20` ਤੋਂ ਹੇਠਾਂ ਦੇ ਹਰ ਅੱਖਰ ਨੂੰ ਚੁੱਪਚਾਪ ਸੁੱਟ ਦਿੰਦਾ ਹੈ (`TextInputControl.filterInput`)। "ਅਜੀਬ
ਤਰੀਕੇ ਨਾਲ ਵਿਖਾਉਂਦਾ ਹੈ" ਨਹੀਂ — ਮਿਟਾ ਦਿੰਦਾ ਹੈ। ਟਾਈਪ ਕਰਨਾ, ਪੇਸਟ ਕਰਨਾ, `setText` ਅਤੇ `insertText` ਸਭ ਪ੍ਰਭਾਵਿਤ ਹਨ, ਇਸ ਲਈ
`setText("01…" + GS + "10LOT")` ਤੋਂ `"01…10LOT"` ਮਿਲਦਾ ਹੈ: ਇੱਕ ਐਲੀਮੈਂਟ ਸਟ੍ਰਿੰਗ ਜਿਸਦਾ ਅਰਥ ਚੁੱਪਚਾਪ ਬਦਲ ਗਿਆ ਹੈ,
ਕਿਉਂਕਿ ਬਦਲਵੀਂ ਲੰਬਾਈ ਵਾਲਾ AI ਹੁਣ ਆਪਣੇ ਬਾਅਦ ਵਾਲੇ ਹਿੱਸੇ ਨੂੰ ਨਿਗਲ ਜਾਂਦਾ ਹੈ।

`desktop.parse.GsToken` ਹੀ ਪੂਰਾ ਜਵਾਬ ਹੈ। ਵਿਭਾਜਕ UI ਵਿੱਚ ਸ਼ਾਬਦਿਕ ਟੈਕਸਟ `{GS}` ਵਜੋਂ ਚੱਲਦਾ ਹੈ ਅਤੇ ਪਾਰਸਰ ਤੱਕ ਜਾਂਦੇ ਹੋਏ
ਫਿਰ `0x1D` ਬਣ ਜਾਂਦਾ ਹੈ। ਇਹ ਟੋਕਨ ਇੱਥੇ ਈਜਾਦ ਨਹੀਂ ਕੀਤਾ ਗਿਆ — ਇਹ ਠੀਕ ਉਹੀ ਹੈ ਜਿਸ ਰੂਪ ਵਿੱਚ ਕੋਰ ਦਾ
`ASCIIRevealerUtils.printable` `0x1D` ਨੂੰ ਵਿਖਾਉਂਦਾ ਹੈ, ਇਸ ਲਈ ਰਿਪੋਰਟ ਤੋਂ ਕਾਪੀ ਕੀਤਾ ਮੁੱਲ ਸਿੱਧਾ ਇਨਪੁੱਟ ਬਾਰ ਵਿੱਚ ਵਾਪਸ
ਪੇਸਟ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ।

ਇਨਪੁੱਟ ਫੀਲਡ ਉੱਤੇ ਇੱਕ `TextFormatter` ਫਿਲਟਰ ਹਰ ਉਸ ਰਾਹ ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸ ਰਾਹੀਂ ਟੈਕਸਟ ਆ ਸਕਦਾ ਹੈ — ਟਾਈਪ ਕਰਨਾ, ⌘V, ਸੰਦਰਭ
ਮੀਨੂ, ਘਸੀਟ ਕੇ ਛੱਡਣਾ, `setText` — ਇਸੇ ਲਈ ਇਹ ਮੁੜ-ਲਿਖਣ ਹਰ ਹੈਂਡਲਰ ਵਿੱਚ ਨਹੀਂ, ਉੱਥੇ ਹੀ ਰਹਿੰਦਾ ਹੈ।

ਸਕੈਨਰ ਦਾ ਰਾਹ ਕਦੇ `GsToken` ਵਿੱਚੋਂ ਨਹੀਂ ਲੰਘਦਾ: ਸਕੈਨ ਪਾਰਸਰ ਤੱਕ ਬਾਈਟਾਂ ਵਜੋਂ ਪਹੁੰਚਦੇ ਹਨ।

## ਸਕੈਨਰ ਏਕੀਕਰਨ

`ScannerService` JavaPOS ਦੇ `Scanner` ਕੰਟਰੋਲ ਦਾ ਮਾਲਕ ਹੈ: open → claim → enable, ਹਰ ਸਕੈਨ ਤੋਂ ਬਾਅਦ ਡੇਟਾ ਇਵੈਂਟ ਨੂੰ ਮੁੜ
ਸਰਗਰਮ ਕਰਦੇ ਹੋਏ। ਤਾਰਕਿਕ ਡਿਵਾਈਸ ਨਾਮ `src/main/resources/jpos.xml` ਤੋਂ ਆਉਂਦੇ ਹਨ।

**ਹਰ ਡਿਵਾਈਸ ਕਾਲ ਇੱਕੋ ਥ੍ਰੈਡ, `gaia-scanner`, ਉੱਤੇ ਚੱਲਦੀ ਹੈ, ਜੋ ਸਰਵਿਸ ਜਿੰਨਾ ਚਿਰ ਹੀ ਜੀਉਂਦਾ ਰਹਿੰਦਾ ਹੈ** — ਕਦੇ FX ਥ੍ਰੈਡ
ਉੱਤੇ ਨਹੀਂ, ਅਤੇ ਕਦੇ ਅਜਿਹੇ ਥ੍ਰੈਡ ਉੱਤੇ ਨਹੀਂ ਜੋ ਕਾਲ ਤੋਂ ਬਾਅਦ ਖ਼ਤਮ ਹੋ ਜਾਵੇ। Zebra ਦੀ ਸਰਵਿਸ CoreScanner COM API ਰਾਹੀਂ JNI
ਨਾਲ ਸਕੈਨਰ ਤੱਕ ਪਹੁੰਚਦੀ ਹੈ, ਅਤੇ COM ਜੋ ਕੁਝ ਸੈੱਟ ਕਰਦਾ ਹੈ ਉਸਨੂੰ ਕਾਲ ਕਰਨ ਵਾਲੇ ਥ੍ਰੈਡ ਦੇ ਅਪਾਰਟਮੈਂਟ ਨਾਲ ਬੰਨ੍ਹ ਦਿੰਦਾ ਹੈ: ਕਿਸੇ
ਅਜਿਹੇ ਥ੍ਰੈਡ ਉੱਤੇ open ਕਰੋ ਜੋ ਬਾਅਦ ਵਿੱਚ ਖ਼ਤਮ ਹੋ ਜਾਵੇ, ਤਾਂ ਸਕੈਨਰ claim ਤਾਂ ਹੁੰਦਾ ਹੈ ਪਰ ਚੁੱਪ ਰਹਿੰਦਾ ਹੈ; ਕਿਸੇ ਹੋਰ ਥ੍ਰੈਡ
ਉੱਤੇ close ਕਰੋ, ਤਾਂ ਗਲਤ ਅਪਾਰਟਮੈਂਟ ਅਨਇਨੀਸ਼ੀਅਲਾਈਜ਼ ਹੁੰਦਾ ਹੈ। FX ਥ੍ਰੈਡ ਉੱਤੇ close ਕਰਨਾ ਸਭ ਤੋਂ ਮਾੜਾ ਮਾਮਲਾ ਹੈ, ਕਿਉਂਕਿ
JavaFX ਉੱਥੇ `OleInitialize` ਕਾਲ ਕਰਦਾ ਹੈ ਅਤੇ ਹਰ ਵਿੰਡੋ ਦਾ ਡ੍ਰੌਪ ਨਿਸ਼ਾਨਾ ਉਸੇ ਦੇ ਵਿਰੁੱਧ ਦਰਜ ਕਰਦਾ ਹੈ — ਉਸ ਉੱਤੇ ਇੱਕ
`CoUninitialize` ਪੂਰੀ ਐਪ ਵਿੱਚ ਘਸੀਟ ਕੇ ਛੱਡਣਾ ਖ਼ਤਮ ਕਰ ਦਿੰਦਾ ਹੈ। ਇਹ Windows ਉੱਤੇ JavaFX ਦੀ ਗੱਲ ਹੈ, ਕਿਸੇ ਇੱਕ JavaFX
ਸੰਸਕਰਣ ਦੀ ਨਹੀਂ। `connect()` ਅਤੇ `disconnect()` ਉਸ ਥ੍ਰੈਡ ਨੂੰ ਕੰਮ ਸੌਂਪ ਕੇ ਉਡੀਕ ਕਰਦੇ ਹਨ, ਇਸ ਲਈ `MainView` ਦੋਵਾਂ ਨੂੰ
ਇੱਕ ਥੋੜ੍ਹੀ ਉਮਰ ਵਾਲੇ ਪਿਛੋਕੜ ਥ੍ਰੈਡ ਤੋਂ ਕਾਲ ਕਰਦਾ ਹੈ; ਇਹ ਪੈਟਰਨ ਵਿਊਅਰ ਦੇ `JposScannerSession` ਦਾ ਹੈ, ਜਿੱਥੇ ਘਸੀਟ ਕੇ
ਛੱਡਣ ਦੀ ਅਸਫਲਤਾ ਪਹਿਲੀ ਵਾਰ ਮਿਲੀ ਸੀ।

ਦੋ ਨਿਯਮ ਗੜਬੜ ਕਰਨ ਵਾਲੇ ਡਿਵਾਈਸ ਨੂੰ ਕਨੈਕਸ਼ਨ ਜਾਮ ਕਰਨ ਤੋਂ ਰੋਕਦੇ ਹਨ। **ਬੰਦ ਕਰਨ ਦੀ ਕਿਰਿਆ ਕਦੇ ਜਲਦੀ ਨਹੀਂ ਰੁਕਦੀ:**
`closeQuietly` disable, release ਅਤੇ close ਨੂੰ ਵੱਖਰੇ ਪੜਾਵਾਂ ਵਿੱਚ ਕਰਦਾ ਹੈ, release ਸਿਰਫ਼ ਤਦ ਕਰਦਾ ਹੈ ਜਦੋਂ claim ਫੜਿਆ ਹੋਵੇ,
ਅਤੇ ਹਮੇਸ਼ਾਂ `close()` ਦੀ ਕੋਸ਼ਿਸ਼ ਕਰਦਾ ਹੈ — ਅਸਫਲ claim ਤੋਂ ਬਾਅਦ `release()` "not claimed" ਸੁੱਟਦਾ ਹੈ, ਅਤੇ ਜਦੋਂ ਪੜਾਅ ਇੱਕੋ
`try` ਸਾਂਝਾ ਕਰਦੇ ਸਨ ਤਾਂ ਇਸ ਨਾਲ close ਛੁੱਟ ਜਾਂਦਾ ਸੀ ਅਤੇ ਡਿਵਾਈਸ Zebra ਦੀ ਸਰਵਿਸ ਵਿੱਚ ਖੁੱਲ੍ਹਾ ਰਹਿ ਜਾਂਦਾ ਸੀ। **ਡੇਟਾ ਇਵੈਂਟ
ਨੂੰ `finally` ਵਿੱਚ ਮੁੜ ਸਰਗਰਮ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:** JavaPOS ਹਰ ਇਵੈਂਟ ਤੋਂ ਬਾਅਦ ਇਸਨੂੰ ਨਿਸ਼ਕਿਰਿਆ ਕਰ ਦਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਅਪਵਾਦ ਸੁੱਟਣ
ਵਾਲੇ ਰੀਡ ਜਾਂ ਹੈਂਡਲਰ ਨੂੰ ਵੀ ਮੁੜ ਸਰਗਰਮ ਕਰਨਾ ਹੀ ਪਵੇਗਾ, ਨਹੀਂ ਤਾਂ ਮੁੜ ਕਨੈਕਟ ਹੋਣ ਤੱਕ ਸਕੈਨਰ ਚੁੱਪ ਰਹੇਗਾ।
`ScannerLifecycleTest` ਦੋਵਾਂ ਨੂੰ ਇੱਕ ਸਕ੍ਰਿਪਟ ਕੀਤੇ `jpos.Scanner` ਦੇ ਵਿਰੁੱਧ ਚਲਾਉਂਦਾ ਹੈ।

**`JposConfig` ਪਹਿਲੇ open ਤੋਂ ਪਹਿਲਾਂ JavaPOS ਨੂੰ ਬੰਡਲ ਕੀਤੇ `jpos.xml` ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ।** Maven ਦੇ JavaPOS jar
(`javapos-config-loader` 4.x) ਅਤੇ ਕਲਾਸ ਪਾਥ ਉੱਤੇ ਕੋਈ `jpos/res/jpos.properties` ਨਾ ਹੋਣ ਉੱਤੇ, ਨਹੀਂ ਤਾਂ ਹਰ open
*"Service does not exist in loaded JCL registry"* (ਗਲਤੀ 109) ਨਾਲ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਤਿੰਨ ਵੱਖਰੇ ਕਾਰਨਾਂ ਕਰਕੇ: ਸਰਵਿਸ
ਮੈਨੇਜਰ `SimpleRegPopulator` ਉੱਤੇ ਮੁੜ ਜਾਂਦਾ ਹੈ, ਜੋ ਲੜੀਬੱਧ `jpos.cfg` ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਕਦੇ `jpos.xml` ਨਹੀਂ; XML ਲੋਡਰ
`jpos.xml` ਨੂੰ ਸਿਰਫ਼ ਕਾਰਜ ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ ਖੋਜਦਾ ਹੈ, jar ਦੇ ਅੰਦਰ ਨਹੀਂ; ਅਤੇ `lib/` ਵਿੱਚ Xerces 2.12.2 ਲੋਡਰ ਦੁਆਰਾ
ਸੈੱਟ ਕੀਤੀ JAXP `accessExternalDTD` ਪ੍ਰਾਪਰਟੀ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। `JposConfig` `jpos.config.regPopulatorClass`
(`JavaxRegPopulator`), `jpos.config.populatorFileURL` (jar ਦਾ ਆਪਣਾ `jar:file:…!/jpos.xml`) ਅਤੇ
`javax.xml.parsers.SAXParserFactory` (JDK ਦਾ) ਨੂੰ ਸਿਸਟਮ ਪ੍ਰਾਪਰਟੀਆਂ ਵਜੋਂ ਸੈੱਟ ਕਰਦਾ ਹੈ — ਕਦੇ ਪਹਿਲਾਂ ਤੋਂ ਸੈੱਟ ਕਿਸੇ
ਨੂੰ ਨਹੀਂ, ਇਸ ਲਈ `-Djpos.config.populatorFileURL=file:…` ਅਜੇ ਵੀ ਕੋਈ ਹੋਰ `jpos.xml` ਚੁਣ ਸਕਦਾ ਹੈ — ਅਤੇ ਜਦੋਂ ਕਲਾਸ
ਪਾਥ ਉੱਤੇ `jpos.properties` ਹੋਵੇ ਜਾਂ 4.x ਲੋਡਰ ਨਾ ਹੋਵੇ, ਤਾਂ ਕੁਝ ਵੀ ਸੈੱਟ ਨਹੀਂ ਕਰਦਾ। Zebra SDK ਦਾ `javaPOS114.jar` ਅਜਿਹਾ
ਹੀ ਮਾਮਲਾ ਹੈ ਅਤੇ ਰਜਿਸਟਰੀ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਤੋੜ ਦਿੰਦਾ ਹੈ, ਇਸੇ ਲਈ `run.bat` ਇਸਨੂੰ ਕਲਾਸ ਪਾਥ ਤੋਂ ਬਾਹਰ ਰੱਖਦਾ ਹੈ —
[Zebra ਨੇਟਿਵ ਲਾਇਬ੍ਰੇਰੀਆਂ](#zebra-ਨੇਟਿਵ-ਲਾਇਬ੍ਰੇਰੀਆਂ) ਵੇਖੋ। `JposConfigTest` ਸ਼ੁਰੂ ਤੋਂ ਅਖ਼ੀਰ ਤੱਕ ਜਾਂਚਦਾ ਹੈ ਕਿ ਰਜਿਸਟਰੀ ਵਿੱਚ
ਫਿਰ ਫਾਈਲ ਦੇ ਸਕੈਨਰ ਹੁੰਦੇ ਹਨ।

**ਡਿਵਾਈਸ ਪਿਕਰ ਉਸੇ ਰਜਿਸਟਰੀ ਤੋਂ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ**, ਕੋਡ ਵਿੱਚ ਸੂਚੀ ਵਜੋਂ ਨਹੀਂ ਰੱਖਿਆ ਜਾਂਦਾ:
`ScannerService.logicalNames()` `gaia-scanner` ਥ੍ਰੈਡ ਉੱਤੇ ਲੋਡ ਕੀਤੀਆਂ ਐਂਟਰੀਆਂ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਰੱਖਦਾ ਹੈ ਜਿਨ੍ਹਾਂ ਦੀ
ਡਿਵਾਈਸ ਸ਼੍ਰੇਣੀ `Scanner` ਹੈ — `jpos.xml` ਦੀਆਂ ਦੋ ਤੱਕੜੀ ਐਂਟਰੀਆਂ ਬਾਹਰ ਰਹਿੰਦੀਆਂ ਹਨ — `pickerOrder` ਕ੍ਰਮ ਵਿੱਚ: ਫਾਈਲ
ਵਿੱਚ ਪਰਿਭਾਸ਼ਿਤ ਹੋਵੇ ਤਾਂ `ZebraAllScanners` ਪਹਿਲਾਂ, ਬਾਕੀ ਵਰਣਮਾਲਾ ਕ੍ਰਮ ਵਿੱਚ (ਰਜਿਸਟਰੀ ਫਾਈਲ ਦਾ ਕ੍ਰਮ ਨਹੀਂ ਰੱਖਦੀ)। ਜਿਸ
ਫਾਈਲ ਵਿੱਚ ਇਹ ਨਹੀਂ, ਉਸਨੂੰ ਇਹ ਦਿੱਤਾ ਨਹੀਂ ਜਾਂਦਾ; ਕੁਝ ਵੀ ਲੋਡ ਨਾ ਹੋਣ ਉੱਤੇ ਸਿਰਫ਼ ਡਿਫਾਲਟ ਪੇਸ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ ਪਿਕਰ ਕਦੇ
ਖ਼ਾਲੀ ਨਹੀਂ ਹੁੰਦਾ। `MainView` ਡਿਫਾਲਟ ਨੂੰ ਤੁਰੰਤ ਵਿਖਾਉਂਦਾ ਹੈ ਅਤੇ ਸੰਭਾਲੀ ਚੋਣ ਨੂੰ ਬਣਾਈ ਰੱਖਦੇ ਹੋਏ ਇੱਕ ਪਿਛੋਕੜ ਥ੍ਰੈਡ ਤੋਂ ਸੂਚੀ
ਭਰਦਾ ਹੈ। ਇਸ ਲਈ `jpos.xml` ਵਿੱਚ ਜੋੜਿਆ ਸਕੈਨਰ — ਜਾਂ `-Djpos.config.populatorFileURL` ਨਾਲ ਨਾਮ ਦਿੱਤੀ ਪੂਰੀ ਫਾਈਲ — ਬਿਨਾਂ
ਕਿਸੇ ਕੋਡ ਬਦਲਾਅ ਦੇ ਪਿਕਰ ਵਿੱਚ ਦਿਸਦਾ ਹੈ, ਅਤੇ `JposConfigTest` ਪਿਕਰ ਨੂੰ ਬੰਡਲ ਕੀਤੀ ਫਾਈਲ ਦੇ ਸੁਤੰਤਰ ਪਾਠ ਨਾਲ ਮਿਲਾ ਕੇ ਜਾਂਚਦਾ
ਹੈ। ਉਹਨਾਂ ਐਂਟਰੀਆਂ ਵਿੱਚ ਨਾਮ ਦਿੱਤੀਆਂ ਸਰਵਿਸਾਂ Zebra ਦੀਆਂ ਕਲਾਸਾਂ ਹਨ (`com.zebra.jpos.service.scanner.*Factory`), ਜਿਨ੍ਹਾਂ
ਨੂੰ ਅਜੇ ਵੀ ਕਲਾਸ ਪਾਥ ਉੱਤੇ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ — `run.bat` ਰਾਹੀਂ Scanner SDK ਤੋਂ, ਜਾਂ `lib\` ਵਿੱਚ ਪਾਏ Zebra ਦੇ ਸਰਵਿਸ jar
ਤੋਂ।

ਸਕੈਨ ਡੇਟਾ ਨੂੰ **ISO-8859-1** ਵਜੋਂ ਡੀਕੋਡ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਤਾਂ ਜੋ ਹਰ ਬਾਈਟ 1:1 ਮੈਪ ਹੋਵੇ ਅਤੇ AIM Code ID ਅਗੇਤਰ ਅਤੇ ਹਰ
`0x1D` ਦੋਵੇਂ ਬਚੇ ਰਹਿਣ; ਰਿਪੋਰਟਾਂ UTF-8 ਵਿੱਚ ਲਿਖੀਆਂ ਜਾਂਦੀਆਂ ਹਨ।

ਸਰਵਿਸ ਵਿੱਚ ਕੁਝ ਵੀ ਵਰਤੋਂਕਾਰ ਲਈ ਟੈਕਸਟ ਨਹੀਂ ਰਚਦਾ। ਇਵੈਂਟ `ScannerListener.Event` ਸਥਿਰਾਂਕਾਂ ਅਤੇ ਬਦਲਣ ਵਾਲੇ ਮੁੱਲਾਂ ਵਜੋਂ
ਬਾਹਰ ਜਾਂਦੇ ਹਨ, ਅਤੇ `MainView` ਕੈਟਾਲਾਗ ਤੋਂ ਸ਼ਬਦ ਦਿੰਦਾ ਹੈ — ਨਹੀਂ ਤਾਂ 35 ਤਰੀਕਿਆਂ ਨਾਲ ਅਨੁਵਾਦਿਤ ਐਪਲੀਕੇਸ਼ਨ ਵਿੱਚ ਸਥਿਤੀ ਲਾਈਨ
ਅੰਗਰੇਜ਼ੀ ਵਿੱਚ ਹੁੰਦੀ। ਲੌਗ ਲਾਈਨਾਂ ਅਪਵਾਦ ਹਨ ਅਤੇ ਅੰਗਰੇਜ਼ੀ ਵਿੱਚ ਰਹਿੰਦੀਆਂ ਹਨ।

### ਪਲੇਟਫਾਰਮ ਗੇਟ

`ScannerService.isSupportedPlatform()` ਇੱਕ `os.name` ਜਾਂਚ ਹੈ, ਅਤੇ `MainView` ਕੋਈ ਵੀ ਸਕੈਨਰ ਕੰਟਰੋਲ ਬਣਾਉਣ ਤੋਂ ਪਹਿਲਾਂ
ਉਸ ਤੋਂ ਪੁੱਛਦਾ ਹੈ: macOS ਅਤੇ Linux ਉੱਤੇ ਨਾ ਟੌਗਲ ਹੈ, ਨਾ ਡਿਵਾਈਸ ਪਿਕਰ, ਨਾ ਸਕੈਨਰ ਮੀਨੂ (ਅਤੇ ਇਸ ਲਈ ਨਾ <kbd>⌘K</kbd>), ਨਾ
ਸਥਿਤੀ ਲੇਬਲ। ਇਹ ਲੁਕਾਏ ਨਹੀਂ ਗਏ — ਇਹ ਕਦੇ ਬਣਾਏ ਹੀ ਨਹੀਂ ਜਾਂਦੇ।

Zebra ਆਪਣੀਆਂ JavaPOS ਸਰਵਿਸਾਂ ਸਿਰਫ਼ Windows ਲਈ ਭੇਜਦਾ ਹੈ, ਅਤੇ ਹੋਰ ਕਿਤੇ ਕੁਝ ਵੀ ਜਲਦੀ ਅਸਫਲ ਨਹੀਂ ਹੁੰਦਾ: jar ਹੱਲ ਹੋ ਜਾਂਦੇ
ਹਨ ਅਤੇ ਕੰਟਰੋਲ ਬਣ ਜਾਂਦਾ ਹੈ, ਅਤੇ ਅਖ਼ੀਰ ਵਿੱਚ `open()` ਹੀ ਗੈਰ-ਮੌਜੂਦ ਨੇਟਿਵ ਪਰਤ ਕਾਰਨ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਕਈ ਸਕਿੰਟਾਂ ਅਤੇ ਇੱਕ
ਡਾਇਲਾਗ ਤੋਂ ਬਾਅਦ।

ਇਹ ਨਿਯਮ *ਸਰਵਿਸਾਂ* ਬਾਰੇ ਹੈ, JavaPOS ਬਾਰੇ ਨਹੀਂ। ਕਰਾਸ-ਪਲੇਟਫਾਰਮ ਸਰਵਿਸ ਭੇਜਣ ਵਾਲਾ ਵਿਕਰੇਤਾ ਇੱਥੇ ਕੰਮ ਕਰੇਗਾ, ਅਤੇ ਨਿਯਮ ਨੂੰ
ਵਿਆਪਕ ਕਰਨਾ ਸਿਰਫ਼ `supportsJavaPos(String)` ਵਿੱਚ ਬਦਲਾਅ ਹੈ — ਜੋ package-private ਹੈ ਅਤੇ `os.name` ਸਟ੍ਰਿੰਗਾਂ ਦੇ ਵਿਰੁੱਧ
ਟੈਸਟ ਕੀਤਾ ਗਿਆ ਹੈ ਤਾਂ ਜੋ ਬਿਲਡ ਚਲਾਉਣ ਵਾਲੀ ਕਿਸੇ ਵੀ ਮਸ਼ੀਨ ਉੱਤੇ ਦੋਵੇਂ ਜਵਾਬ ਕਵਰ ਹੋਣ।

### ਸਿੰਬੋਲੋਜੀਆਂ

`Symbologies` ਸਾਰੀਆਂ **78** JavaPOS `SCAN_SDT_*` ਸਕੈਨ-ਡੇਟਾ ਕਿਸਮਾਂ ਨੂੰ ਡਿਸਪਲੇ ਨਾਵਾਂ ਨਾਲ, ਅਤੇ ਜਿੱਥੇ ਦੋਵੇਂ ਸ਼ਬਦਾਵਲੀਆਂ
ਮੇਲ ਖਾਂਦੀਆਂ ਹਨ ਉੱਥੇ ਕੋਰ ਦੇ `DataCarrierType` ਨਾਲ ਮੈਪ ਕਰਦਾ ਹੈ। ਦੋਵਾਂ ਵਿੱਚੋਂ JavaPOS ਵਧੇਰੇ ਬਾਰੀਕ ਹੈ — ਇਹ UPC-A ਨੂੰ
EAN-13 ਤੋਂ, ਅਤੇ ਸਾਦੇ Data Matrix ਨੂੰ GS1 DataMatrix ਤੋਂ ਵੱਖ ਕਰਦਾ ਹੈ, ਜਿੱਥੇ AIM ਪੂਰੇ ਪਰਿਵਾਰ ਨੂੰ ਇੱਕ ਕੋਡ ਅੱਖਰ ਹੇਠ
ਸਮੂਹਿਤ ਕਰਦਾ ਹੈ।

ਸਾਰਣੀ ਤੋਂ ਬਾਹਰ ਦੀ ਕਿਸਮ ਨੂੰ ਵੀ ਵਰਤੋਂ ਯੋਗ ਨਾਮ ਮਿਲਦਾ ਹੈ, ਜੋ `ScannerConst` ਉੱਤੇ ਰਿਫਲੈਕਸ਼ਨ ਰਾਹੀਂ ਲੱਭਿਆ ਜਾਂਦਾ ਹੈ, ਕਿਉਂਕਿ
ਵਿਕਰੇਤਾ ਸਰਵਿਸਾਂ ਸੱਚਮੁੱਚ ਵਿਸ਼ੇਸ਼ਤਾ ਸੂਚੀ ਤੋਂ ਬਾਹਰ ਦੇ ਮੁੱਲ ਰਿਪੋਰਟ ਕਰਦੀਆਂ ਹਨ। ਇੱਕ ਟੈਸਟ `ScannerConst` ਉੱਤੇ ਚੱਲਦਾ ਹੈ ਅਤੇ
ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਜੇ ਕਿਸੇ ਘੋਸ਼ਿਤ ਕਿਸਮ ਦਾ ਨਾਮ ਨਾ ਹੋਵੇ — ਜੋ ਭਵਿੱਖ ਦੇ JavaPOS ਦੁਆਰਾ ਜੋੜੇ ਸਥਿਰਾਂਕਾਂ ਨੂੰ ਵੀ ਫੜਦਾ ਹੈ।

ਕੁਝ ਕੈਰੀਅਰ ਮੈਪਿੰਗਾਂ ਅੰਦਾਜ਼ਾ ਲਾਉਣ ਦੀ ਬਜਾਏ ਜਾਣਬੁੱਝ ਕੇ `UNKNOWN` ਛੱਡੀਆਂ ਗਈਆਂ ਹਨ: straight 2 of 5 (AIM `]R`/`]S` ਨੂੰ
start/stop ਬਾਰਾਂ ਦੀ ਗਿਣਤੀ ਨਾਲ ਵੱਖ ਕਰਦਾ ਹੈ, ਜਿਸਨੂੰ JavaPOS ਰਿਪੋਰਟ ਨਹੀਂ ਕਰਦਾ), ਚਾਰ-ਅਵਸਥਾ ਵਾਲੇ ਡਾਕ ਕੋਡ, ਅਤੇ TLC-39।

## ਸਥਾਨੀਕਰਨ

ਲੇਬਲ ਹਰ ਭਾਸ਼ਾ ਲਈ ਇੱਕ ਪ੍ਰਾਪਰਟੀਜ਼ ਫਾਈਲ ਵਿੱਚ `src/main/resources/i18n/ui_<CODE>.properties` ਹੇਠ ਰਹਿੰਦੇ ਹਨ, ਕੋਰ ਦੇ
ਗਲਤੀ ਕੈਟਾਲਾਗਾਂ ਵਾਲੇ ਹੀ ਕੋਡ ਵਰਤਦੇ ਹੋਏ (`EN`, `FR`, `PCM`, …)। ਸਾਰੀਆਂ 35 ਮੌਜੂਦ ਹਨ ਅਤੇ ਸਾਰੀਆਂ 35 ਵਿੱਚ ਇੱਕੋ ਜਿਹਾ
ਕੁੰਜੀ-ਸਮੂਹ ਹੈ। ਫਾਈਲਾਂ **UTF-8** ਵਜੋਂ ਪੜ੍ਹੀਆਂ ਜਾਂਦੀਆਂ ਹਨ, ਨਾ ਕਿ ਉਸ ISO-8859-1 ਵਜੋਂ ਜੋ `Properties` ਮੰਨਦਾ ਹੈ, ਇਸ ਲਈ
ਅਨੁਵਾਦ `\uXXXX` ਐਸਕੇਪ ਦੀ ਬਜਾਏ ਪੜ੍ਹਨਯੋਗ ਰੂਪ ਵਿੱਚ ਸੰਭਾਲੇ ਜਾਂਦੇ ਹਨ।

**ਫਾਲਬੈਕ ਹਰ ਕੁੰਜੀ ਲਈ ਹੈ, ਹਰ ਫਾਈਲ ਲਈ ਨਹੀਂ** — ਇਹੀ ਉਹ ਚੀਜ਼ ਹੈ ਜੋ ਅੰਸ਼ਕ ਤੌਰ ਉੱਤੇ ਅਨੁਵਾਦਿਤ ਭਾਸ਼ਾ ਨੂੰ ਉਸਦੀ ਪਹਿਲੀ ਕੁੰਜੀ ਆਉਂਦੇ
ਹੀ ਲਾਭਦਾਇਕ ਬਣਾ ਦਿੰਦੀ ਹੈ। ਅੰਗਰੇਜ਼ੀ ਇਕਰਾਰਨਾਮਾ ਹੈ: ਹਰ ਕੁੰਜੀ ਉੱਥੇ ਮੌਜੂਦ ਹੋਣੀ ਚਾਹੀਦੀ ਹੈ।

| ਪਰਤ | ਕੁੰਜੀਆਂ | ਕਵਰੇਜ |
|---|---|---|
| ਸਾਂਝੀ ਰਿਪੋਰਟ ਸ਼ਬਦਾਵਲੀ | 31 | ਸਾਰੀਆਂ 35 ਭਾਸ਼ਾਵਾਂ |
| ਡੈਸਕਟੌਪ ਢਾਂਚਾ — ਮੀਨੂ, ਬਟਨ, ਬਿਲਡਰ, ਚੋਣਾਂ, ਸਥਿਤੀ ਲਾਈਨ, ਰਿਪੋਰਟ ਲੇਆਉਟ, ਸਕੈਨਰ ਸਥਿਤੀ, ਡਾਇਲਾਗ ਟੈਕਸਟ | 114 | ਸਾਰੀਆਂ 35 ਭਾਸ਼ਾਵਾਂ |

ਸਾਂਝੇ ਸ਼ਬਦਾਂ ਵਿੱਚੋਂ ਛੇ (`generated`, `status`, `dlRole`, `interpretations`, `message`, `level`) ਇਸ ਐਪ ਦੀ ਰਿਪੋਰਟ
ਵਿੱਚ ਵਰਤੇ ਨਹੀਂ ਜਾਂਦੇ।
ਉਹਨਾਂ ਨੂੰ ਜਾਣਬੁੱਝ ਕੇ ਰੱਖਿਆ ਗਿਆ ਹੈ; ਫਾਈਲ ਹੈਡਰ ਇਹ ਦੱਸਦਾ ਹੈ।

### `--language` ਆਰਗੂਮੈਂਟ

`GaiaDesktopApp.languageOverride()` JavaFX ਦੇ ਆਪਣੇ `getParameters().getNamed()` ਰਾਹੀਂ `--language=…` ਪੜ੍ਹਦਾ ਹੈ, ਉਸਨੂੰ
`Languages.fromArgument` ਨਾਲ ਹੱਲ ਕਰਦਾ ਹੈ — ਕੈਟਾਲਾਗ ਕੋਡ, enum ਨਾਮ, ਜਾਂ BCP 47 ਟੈਗ, ਵੱਡੇ-ਛੋਟੇ ਅੱਖਰਾਂ ਤੋਂ ਨਿਰਪੱਖ — ਅਤੇ
`MainView` ਨੂੰ ਸੌਂਪ ਦਿੰਦਾ ਹੈ।

**ਇਹ ਓਵਰਰਾਈਡ ਰਨ ਲਈ ਹੈ, ਫਾਈਲ ਲਈ ਨਹੀਂ।** `MainView` ਜੋ ਭਾਸ਼ਾ ਲੋਡ ਕਰਦਾ ਹੈ ਉਸਨੂੰ `savedLanguage` ਵਿੱਚ ਰੱਖਦਾ ਹੈ ਅਤੇ *ਉਹੀ*
ਵਾਪਸ ਲਿਖਦਾ ਹੈ, ਜਦੋਂ ਤੱਕ `languageChosenInSession` ਇਹ ਨਾ ਦੱਸੇ ਕਿ ਵਰਤੋਂਕਾਰ ਨੇ ਖ਼ੁਦ ਕੋਈ ਭਾਸ਼ਾ ਚੁਣੀ ਹੈ; ਤਦ ਉਹਨਾਂ ਦੀ ਚੋਣ
ਆਮ ਵਾਂਗ ਸੰਭਾਲੀ ਜਾਂਦੀ ਹੈ। ਇਹੀ ਵੰਡ ਪੂਰਾ ਡਿਜ਼ਾਈਨ ਹੈ: ਕਿਓਸਕ ਪ੍ਰੋਫਾਈਲ ਜਾਂ ਡੈਮੋ ਸ਼ਾਰਟਕੱਟ ਮਸ਼ੀਨ ਦੇ ਮਾਲਕ ਦੀ ਕੱਲ੍ਹ ਖੁੱਲ੍ਹਣ ਵਾਲੀ
ਭਾਸ਼ਾ ਬਦਲੇ ਬਿਨਾਂ ਸਪੈਨਿਸ਼ ਵਿੱਚ ਖੁੱਲ੍ਹ ਸਕਦਾ ਹੈ, ਜਦਕਿ ਚੋਣ ਪੈਨਲ ਵਿੱਚ ਕੀਤੀ ਅਸਲ ਚੋਣ ਫਿਰ ਵੀ ਬਣੀ ਰਹਿੰਦੀ ਹੈ।

ਕਿਸੇ ਵੀ ਕੈਟਾਲਾਗ ਦਾ ਨਾਮ ਨਾ ਲੈਣ ਵਾਲਾ ਮੁੱਲ ਸਵੀਕਾਰ ਕੀਤੇ ਕੋਡਾਂ ਸਮੇਤ ਲੌਗ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਅਣਡਿੱਠਾ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।
ਸ਼ਾਰਟਕੱਟ ਵਿੱਚ ਇੱਕ ਟਾਈਪੋ ਕਾਰਨ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਇਨਕਾਰ ਕਰਨਾ ਵਧੇਰੇ ਮਾੜੀ ਅਸਫਲਤਾ ਹੁੰਦੀ, ਅਤੇ ਇਸੇ ਕਾਰਨ `Languages.fromArgument`
ਅਪਵਾਦ ਸੁੱਟਣ ਦੀ ਬਜਾਏ `null` ਵਾਪਸ ਕਰਦਾ ਹੈ।

### ਭਾਸ਼ਾ ਜੋੜਨਾ

ਕਿਸੇ ਕੋਡ ਬਦਲਾਅ ਦੀ ਲੋੜ ਨਹੀਂ।

1. `ui_<CODE>.properties` ਸੋਧੋ — ਹਰ ਭਾਸ਼ਾ ਦੀ ਫਾਈਲ ਪਹਿਲਾਂ ਤੋਂ ਹੈ।
2. ਮੁੱਲਾਂ ਦਾ ਅਨੁਵਾਦ ਕਰੋ। `{0}` / `{1}` ਪਲੇਸਹੋਲਡਰ ਆਪਣੀ ਥਾਂ ਛੱਡ ਦਿਓ।
3. ਬਿਲਡ ਕਰੋ। ਦੋ ਟੈਸਟ ਇਕਰਾਰਨਾਮਾ ਲਾਗੂ ਕਰਦੇ ਹਨ: ਇੱਕ ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਜੇ ਕੋਡ ਅਜਿਹੀ ਕੁੰਜੀ ਮੰਗੇ ਜਿਸਨੂੰ ਅੰਗਰੇਜ਼ੀ ਪਰਿਭਾਸ਼ਿਤ ਨਹੀਂ
   ਕਰਦੀ, ਦੂਜਾ ਜੇ ਕਿਸੇ ਕੈਟਾਲਾਗ ਦਾ ਕੁੰਜੀ-ਸਮੂਹ ਅੰਗਰੇਜ਼ੀ ਤੋਂ ਭਟਕ ਜਾਵੇ।

ਪਹਿਲਾ ਟੈਸਟ ਕਲਾਸਾਂ ਉੱਤੇ ਰਿਫਲੈਕਸ਼ਨ ਕਰਨ ਦੀ ਬਜਾਏ **ਸਰੋਤ ਕੋਡ** ਵਿੱਚ ਕੁੰਜੀ ਲਿਟਰਲ ਖੋਜਦਾ ਹੈ, ਕਿਉਂਕਿ ਕੁੰਜੀਆਂ ਸਿਰਫ਼ ਕਾਲ ਥਾਵਾਂ
ਉੱਤੇ ਸਟ੍ਰਿੰਗ ਲਿਟਰਲ ਵਜੋਂ ਮੌਜੂਦ ਹਨ। ਇਸੇ ਲਈ ਨਵਾਂ ਸੁਨੇਹਾ ਕੁੰਜੀ ਨੂੰ ਸਿੱਧਾ ਲਿਖ ਕੇ ਬਣਾਇਆ ਜਾਣਾ ਚਾਹੀਦਾ ਹੈ —
`strings.format("st.scannerError", …)` — ਕਿਸੇ ਵੇਰੀਏਬਲ ਰਾਹੀਂ ਖੋਜ ਕੇ ਨਹੀਂ, ਨਹੀਂ ਤਾਂ ਟੈਸਟ ਉਸਨੂੰ ਵੇਖ ਨਹੀਂ ਸਕੇਗਾ।

### ਜਾਣਬੁੱਝ ਕੇ ਅਨੁਵਾਦ ਨਾ ਕੀਤੀਆਂ ਚੀਜ਼ਾਂ

- ਕੱਚੇ ਮੁੱਲਾਂ ਦੇ ਨਾਲ ਮੋਨੋਸਪੇਸ ਵਿੱਚ ਵਿਖਾਏ ਜਾਣ ਵਾਲੇ ਛੋਟੇ ਫੀਲਡ ਨਾਮ — ਐਲੀਮੈਂਟ ਕਾਰਡ ਦੇ `format`, `position`, `length`,
  `raw` ਅਤੇ `part`, ਟੇਪ ਦੇ `AI`, `sep`, `pos` ਅਤੇ `len`, ਅਤੇ ਗਲਤੀ ਦੀ ਥਾਂ ਦੱਸਣ ਵਾਲੇ ਚਾਰ ਸੈੱਲ (`AI`, `position`,
  `level`, `stage`), ਜਿਨ੍ਹਾਂ ਦੇ ਮੁੱਲ ਉਂਝ ਵੀ ਅਨੁਵਾਦ ਨਾ ਕੀਤੇ enum ਨਾਮ ਹਨ;
- ਨਮੂਨਾ-ਇਨਪੁੱਟ ਦੇ ਨਾਮ, ਜੋ GS1 ਬਣਤਰਾਂ ਦੇ ਨਾਮ ਹਨ, ਅਤੇ ਸਿੰਬੋਲੋਜੀ ਨਾਮ, ਜੋ ਖ਼ਾਸ ਨਾਂਵ ਹਨ;
- `GE-C084` ਦਾ ਉਪਚਾਰ ਪੈਰਾ — ਮਿਆਰੀ ਗੱਦ, ਜਿੱਥੇ ਅੱਧਾ-ਅਧੂਰਾ ਅਨੁਵਾਦ ਅੰਗਰੇਜ਼ੀ ਨਾਲੋਂ ਮਾੜਾ ਹੈ;
- `ElementBuilder` ਦਾ ਅਣਜਾਣ-AI ਬੈਕਸਟੌਪ, ਜੋ UI ਤੋਂ ਪਹੁੰਚਯੋਗ ਨਹੀਂ: ਐਡੀਟਰ ਅਣਜਾਣ AI ਨੂੰ ਖ਼ੁਦ ਜਾਂਚਦਾ ਹੈ ਅਤੇ ਕੈਟਾਲਾਗ
  ਤੋਂ ਉਹਨਾਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ;
- ਲੌਗ ਲਾਈਨਾਂ।

ਇੱਕ ਘਾਟ ਬਾਕੀ ਹੈ: `ScanSource.label()` ਇਤਿਹਾਸ ਕਤਾਰ ਅਤੇ ਰਿਪੋਰਟ ਮਾਸਟਹੈੱਡ ਨੂੰ `manual` / `scanner` / `file` / `built`
ਅੰਗਰੇਜ਼ੀ ਵਿੱਚ ਦਿੰਦਾ ਹੈ। ਇਸਨੂੰ ਦੂਰ ਕਰਨ ਲਈ ਇੱਕ ਕੁੰਜੀ ਤੋਂ ਵੱਧ ਚਾਹੀਦਾ ਹੈ — `HistoryCell` ਕੋਲ `UiStrings` ਨਹੀਂ ਹੈ, ਅਤੇ ਸੂਚੀ
ਦੀ ਸੈੱਲ ਫੈਕਟਰੀ ਇੱਕ ਵਾਰ ਇੰਸਟਾਲ ਹੁੰਦੀ ਹੈ, ਇਸ ਲਈ ਭਾਸ਼ਾ ਬਦਲਣ ਉੱਤੇ ਸੈੱਲਾਂ ਨੂੰ ਵੀ ਤਾਜ਼ਾ ਕਰਨਾ ਪਵੇਗਾ।

## ਸਟੋਰ ਕੀਤੀ ਸਥਿਤੀ ਦੇ ਫਾਰਮੈਟ

`~/.gaia-desktop/` ਹੇਠ ਦੋ ਫਾਈਲਾਂ, ਵੱਖ ਰੱਖੀਆਂ ਗਈਆਂ ਕਿਉਂਕਿ ਉਹ ਵੱਖਰੀ ਰਫ਼ਤਾਰ ਨਾਲ ਬਦਲਦੀਆਂ ਹਨ — ਖ਼ਰਾਬ ਜਾਂ ਹੱਥੀਂ ਸੋਧੇ ਕੈਪਚਰ
ਲੌਗ ਦੀ ਕੀਮਤ ਵਰਤੋਂਕਾਰ ਨੂੰ ਆਪਣੀਆਂ ਸੈਟਿੰਗਾਂ ਨਾਲ ਨਹੀਂ ਚੁਕਾਉਣੀ ਚਾਹੀਦੀ। ਡਾਇਰੈਕਟਰੀ ਨੂੰ `-Dgaia.desktop.home=…` ਨਾਲ ਬਦਲੋ, ਜਿਸ
ਨਾਲ ਟੈਸਟ ਅਸਲ ਹੋਮ ਡਾਇਰੈਕਟਰੀ ਤੋਂ ਦੂਰ ਰਹਿੰਦੇ ਹਨ।

**`options.properties`** — ਕੋਈ ਚੋਣ ਬਦਲਣ ਉੱਤੇ, ਅਤੇ ਬਾਹਰ ਨਿਕਲਦੇ ਸਮੇਂ ਲਿਖੀ ਜਾਂਦੀ ਹੈ।

| ਕੁੰਜੀ | ਅਰਥ |
|---|---|
| `parse.mode`, `parse.language` | ਪਾਈਪਲਾਈਨ ਦੀ ਡੂੰਘਾਈ ਅਤੇ ਸੁਨੇਹੇ ਦੀ ਭਾਸ਼ਾ |
| `date.endian`, `date.separator`, `date.month`, `date.year` | ਤਾਰੀਖ਼ ਦਾ ਪ੍ਰਦਰਸ਼ਨ |
| `check.skipRequires`, `check.skipExcludes` | ਢਾਂਚਾਗਤ ਜਾਂਚ ਤੋਂ ਛੋਟ |
| `ui.theme` | `LIGHT` ਜਾਂ `DARK` |
| `ui.optionsPane` | ਚੋਣ ਪੈਨਲ ਖੁੱਲ੍ਹਾ ਹੈ? |
| `ui.scannerDevice` | ਆਖ਼ਰੀ JavaPOS ਤਾਰਕਿਕ ਨਾਮ |
| `ui.mode` | `PARSE`, `BUILD` ਜਾਂ `COMBINE` |
| `update.check` | ਰੋਜ਼ਾਨਾ ਅੱਪਡੇਟ ਜਾਂਚ ਚੱਲਦੀ ਹੈ ਜਾਂ ਨਹੀਂ (ਡਿਫਾਲਟ `true`) |
| `update.lastCheck` | ਇਹ ਆਖ਼ਰੀ ਵਾਰ ਕਦੋਂ ਚੱਲੀ, ISO-8601; ਗੈਰ-ਮੌਜੂਦ ਜਾਂ ਨਾ-ਪੜ੍ਹਨਯੋਗ ਹੋਣ ਦਾ ਅਰਥ ਹੈ ਕਿ ਜਾਂਚ ਬਾਕੀ ਹੈ |
| `update.skipVersion` | ਉਹ ਰਿਲੀਜ਼ ਜਿਸ ਲਈ ਵਰਤੋਂਕਾਰ ਨੇ *ਇਹ ਸੰਸਕਰਣ ਛੱਡੋ* ਚੁਣਿਆ; ਆਪਣੇ-ਆਪ ਮੁੜ ਪੇਸ਼ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ |

ਗੈਰ-ਮੌਜੂਦ ਜਾਂ ਨੁਕਸਾਨੀ ਫਾਈਲ ਕਦੇ ਘਾਤਕ ਨਹੀਂ ਹੁੰਦੀ: ਹਰ ਮੁੱਲ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ ਫਾਲਬੈਕ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਇੱਕ ਖ਼ਰਾਬ ਲਾਈਨ ਦੀ ਕੀਮਤ
ਸਿਰਫ਼ ਉਹੀ ਲਾਈਨ ਹੈ। ਪਹਿਲੀ ਵਾਰ ਲਾਂਚ ਕਰਨ ਉੱਤੇ, ਬਿਨਾਂ ਕਿਸੇ ਫਾਈਲ ਦੇ, ਚੋਣਾਂ GAIA ਦੇ ਅੰਦਰੂਨੀ ਡਿਫਾਲਟਾਂ ਦੀ ਬਜਾਏ
`SystemDefaults` ਦੁਆਰਾ ਮਸ਼ੀਨ ਦੀਆਂ ਖੇਤਰੀ ਸੈਟਿੰਗਾਂ ਤੋਂ ਭਰੀਆਂ ਜਾਂਦੀਆਂ ਹਨ — ਲੋਕੇਲ ਦਾ ਛੋਟਾ ਤਾਰੀਖ਼ ਪੈਟਰਨ ਹਿੱਸਿਆਂ ਦਾ ਕ੍ਰਮ,
ਵਿਭਾਜਕ, ਅਤੇ ਮਹੀਨਾ ਤੇ ਸਾਲ ਸੰਖੇਪ ਹਨ ਜਾਂ ਨਹੀਂ, ਇਹ ਦਿੰਦਾ ਹੈ।

`Properties.setProperty` ਨੂੰ ਕਦੇ null ਨਾ ਦਿਓ: ਇਹ ਅਪਵਾਦ ਸੁੱਟਦਾ ਹੈ, ਅਤੇ `persistOptions()` UI ਇਵੈਂਟ ਹੈਂਡਲਰਾਂ ਤੋਂ ਚੱਲਦਾ
ਹੈ ਜਿੱਥੇ ਅਪਵਾਦ FX ਥ੍ਰੈਡ ਉੱਤੇ ਨਿਕਲ ਜਾਂਦਾ ਹੈ। ਇਹ ਇੱਕ ਅਸਲ ਕਰੈਸ਼ ਹੈ ਜੋ ਇਸ ਐਪ ਵਿੱਚ ਪਹਿਲਾਂ ਹੋ ਚੁੱਕਾ ਹੈ।

**`captures.tsv`** — ਇਤਿਹਾਸ ਬਦਲਣ ਉੱਤੇ, ਅਤੇ ਬਾਹਰ ਨਿਕਲਦੇ ਸਮੇਂ ਲਿਖੀ ਜਾਂਦੀ ਹੈ। ਸਭ ਤੋਂ ਨਵਾਂ ਪਹਿਲਾਂ, ਵੱਧ ਤੋਂ ਵੱਧ **500**
ਐਂਟਰੀਆਂ।

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

ਸਿਰਫ਼ ਉਹੀ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ ਜਿਸਦੀ ਮੁੜ ਗਣਨਾ ਨਹੀਂ ਹੋ ਸਕਦੀ। `ParseResult` ਲੜੀਬੱਧ **ਨਹੀਂ** ਕੀਤਾ ਜਾਂਦਾ — ਲੋਡ ਹੋਣ ਉੱਤੇ
ਇਨਪੁੱਟ ਨੂੰ ਮੁੜ ਪਾਰਸ ਕਰਕੇ ਇਸਨੂੰ ਦੁਬਾਰਾ ਪ੍ਰਾਪਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ ਬਹਾਲ ਕੀਤਾ ਇਤਿਹਾਸ *ਹੁਣ* ਲਾਗੂ ਚੋਣਾਂ ਨੂੰ ਦਰਸਾਉਂਦਾ ਹੈ।
ਇਨਪੁੱਟ ਵਿੱਚ ਆਮ ਤੌਰ ਉੱਤੇ FNC1 ਅਤੇ ਸਕੈਨਰ ਦੁਆਰਾ ਕੱਢਿਆ ਕੁਝ ਵੀ ਹੋਰ ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ ਇਨਪੁੱਟ ਫੀਲਡ ਐਸਕੇਪ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`\\`,
`\t`, `\n`, `\r`, ਅਤੇ `0x20` ਤੋਂ ਹੇਠਾਂ ਬਾਕੀ ਹਰ ਚੀਜ਼ ਲਈ `\xNN`) ਅਤੇ ਫਾਈਲ ISO-8859-1 ਵਜੋਂ, ਬਾਈਟ-ਦਰ-ਬਾਈਟ, ਪੜ੍ਹੀ
ਅਤੇ ਲਿਖੀ ਜਾਂਦੀ ਹੈ।

ਤਾਰੀਖ਼ ਦਰਜ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਲਿਖੀਆਂ ਫਾਈਲਾਂ ਵਿੱਚ ਸਿਰਫ਼ ਘੜੀ ਦਾ ਸਮਾਂ ਹੁੰਦਾ ਹੈ; ਉਹ ਫਿਰ ਵੀ ਲੋਡ ਹੁੰਦੀਆਂ ਹਨ, ਅੱਜ ਦੀ ਤਾਰੀਖ਼ ਨਾਲ,
ਕਿਉਂਕਿ ਅਸਲ ਤਾਰੀਖ਼ ਕਦੇ ਲਿਖੀ ਹੀ ਨਹੀਂ ਗਈ ਸੀ।

## ਜਾਣੀਆਂ ਸੀਮਾਵਾਂ ਅਤੇ ਬਾਕੀ ਕੰਮ

- **ਕੋਈ ਹੈੱਡਲੈੱਸ UI ਟੈਸਟ ਨਹੀਂ।** [ਟੈਸਟਿੰਗ](#ਟੈਸਟਿੰਗ) ਵੇਖੋ।
- **ਪਲੇਟਫਾਰਮ-ਵਿਸ਼ੇਸ਼ ਆਰਟੀਫੈਕਟ।** ਦੋਵੇਂ ਪੈਕੇਜਿੰਗਾਂ ਇੱਕ ਪਲੇਟਫਾਰਮ ਦੇ JavaFX ਨੇਟਿਵ ਬੰਡਲ ਕਰਦੀਆਂ ਹਨ; ਹਰ ਨਿਸ਼ਾਨੇ ਲਈ
