## এক নজরে মডিউল

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

এটি কোর লাইব্রেরির একটি ক্লায়েন্ট, এর বেশি কিছু নয়। এর ভেতরে **কোনো GS1 জ্ঞান নেই**: প্রতিটি AI সংজ্ঞা,
যাচাইয়ের নিয়ম, ত্রুটি বার্তা ও স্থানীয়কৃত বিবরণ আসে [`GaiaParser`](../../../../gaia/docs/GaiaParser.md) ও
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md) থেকে। বিশেষ করে, AI তালিকা কখনো এই মডিউলে কপি করা হয়
না — বিল্ডারের পিকার কোরের নিজস্ব রেজিস্ট্রি পড়ে, তাই বিল্ডার প্রত্যাখ্যান করবে এমন কোনো AI সে দেখাতে পারে
না।

**প্রবেশ বিন্দু:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX `Application`) এবং
`tools.pantheum.gaia.desktop.Launcher` (প্যাকেজ করা jar-এর `Main-Class`)।

মডিউলটি একটি পাতা (leaf): কিছুই এর ওপর নির্ভর করে না, আর এটিও অন্য কোনো ডাউনস্ট্রিম মডিউলের ওপর নির্ভর করে
না। যে দুটি ক্লাস দিয়ে এর শুরু, সেগুলো নির্ভরতা হিসেবে নেওয়ার বদলে `gaia-demo` থেকে **কপি** করা হয়েছিল —
`Symbologies` এখনো হাতে সেখানকার যমজের সঙ্গে মিলিয়ে রাখা হয়, এবং দুটিতেই সে কথা জানানো একটি নোট আছে।

## বিল্ড ও চালানো

- চালাতে **Java 21**, আর বিল্ড করতে JDK 21 বা নতুনতর — মডিউলটি `release=21` দিয়ে কম্পাইল হয়। JavaFX 21
  এর সঙ্গে মেলানো LTS ধারা। কোর jar এখনো Java 11 বাইটকোড, এবং 21-এ কোনো পরিবর্তন ছাড়াই চলে।
- `PATH`-এ **Maven**। এই রিপোজিটরিতে কোনো wrapper নেই।
- **আগে কোর ইনস্টল করুন।** এই মডিউল `gaia:1.1.0` নেয় `~/.m2` থেকে; পুরোনো বা অনুপস্থিত কোর jar-ই সাধারণত
  `package tools.pantheum.gaia does not exist`-এর কারণ।

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` একমাত্র কমান্ড-লাইন আর্গুমেন্ট, এবং পুরো প্রোফাইলকে অন্য কোথাও সরিয়ে দেওয়া
`-Dgaia.desktop.home=…` বাদে স্টার্ট-আপকে প্রভাবিত করার একমাত্র উপায়।

`mvn javafx:run` হলো ডেভেলপমেন্টের পথ: প্লাগিন JavaFX-কে **মডিউল পাথে** রাখে, ফলে টুলকিট একটি নামযুক্ত মডিউল
হিসেবে শুরু হয় এবং `GaiaDesktopApp` সরাসরি চালু করা যায়। প্যাকেজ করা jar তা পারে না — সেখানে সবকিছু ক্লাস
পাথে থাকে — এ কারণেই তার `Main-Class` হলো `Launcher` শিম। সেই বিন্যাসে `Main-Class` হিসেবে `Application`-এর
একটি সাবক্লাস *"JavaFX runtime components are missing"* দিয়ে ব্যর্থ হয়।

সবসময় `clean` ব্যবহার করুন — একগুচ্ছ প্ল্যাটফর্ম বিল্ড করার আগে একবার, কারণ এটি `target/dist/` থেকে সবগুলো
খালি করে দেয়। কারণ জানতে দেখুন [বিল্ডের সমস্যা সমাধান](#বিল্ডের-সমস্যা-সমাধান)।

### প্যাকেজিং

পাঠানোর মতো সবকিছু `target/dist/gaia-desktop-<version>-<platform>/`-এর নিচে জড়ো করা হয় এবং অন্য কিছু নয়, যাতে
ডিরেক্টরিটিকে একটি সেট হিসেবে zip বা কপি করা যায়, `target/`-এর ভেতরে `classes/`, `maven-status/` ও বিল্ডের বাকি
অস্থায়ী ফাইলের পাশ থেকে আর্টিফ্যাক্ট বাছাই না করেই। `${dist.dir}` একবারই এর নাম দেয়; আর্টিফ্যাক্ট লেখে এমন
প্রতিটি প্লাগিন এর দিকেই নির্দেশ করে।

#### প্রতি প্ল্যাটফর্মে একটি বিল্ড

JavaFX jar নেটিভ কোড বহন করে, তাই প্রতিটি বিতরণ একটি প্ল্যাটফর্মের জন্য, যার নাম দেয় `fx.platform` প্রপার্টি
একটি OpenJFX ক্লাসিফায়ার হিসেবে: `mac-aarch64`, `mac`, `win`, `linux` বা `linux-aarch64`। OS অনুযায়ী সক্রিয়
হওয়া পাঁচটি `fx-*` প্রোফাইল একে বিল্ড করা মেশিনের নিজস্ব প্ল্যাটফর্মে সেট করে, আর সাধারণ `mvn package` বা
`mvn javafx:run`-এর এটুকুই দরকার; `-Dfx.platform=…` সেগুলোকে ছাপিয়ে যে-কোনো মেশিন থেকে অন্য যে-কোনো প্ল্যাটফর্ম
বিল্ড করে — JavaFX jar কেবল ডাউনলোড মাত্র। `${dist.dir}` হলো `target/dist/${fx.platform}`, তাই এক
প্ল্যাটফর্মের বিল্ড কখনো অন্যটির বিল্ডের ওপর লেখে না।

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

pom-এর দুটি খুঁটিনাটি এটি সম্ভব করে, এবং দুটিই মুছে ফেলার মতো দেখায়:

- **প্রতিটি JavaFX মডিউল একটি সরাসরি নির্ভরতা** — base, graphics, controls, media ও web — প্রতিটিতে
  `<classifier>${fx.platform}</classifier>` এবং একটি `org.openjfx:*` বর্জন। OpenJFX-এর pom তাদের ট্রানজিটিভ jar
  বাছে *বিল্ড করা মেশিনের* OS দেখে, তাই graphics বা base-কে ট্রানজিটিভভাবে আসতে দিলে Windows বিল্ডে Windows-এর
  নেটিভের পাশে Mac-এর নেটিভও ঢুকে পড়ে।
- **প্রপার্টিটি `fx.platform`, `javafx.platform` নয়।** বাইরে থেকে সেট করলে OpenJFX-এর নিজস্ব প্রপার্টিকে তার
  প্যারেন্ট pom নিজেরই সাপেক্ষে নতুন করে সংজ্ঞায়িত করে; Maven সেই pom-কে অবৈধ বলে প্রত্যাখ্যান করে এবং
  নিঃশব্দে প্ল্যাটফর্ম jar বাদ দেয়, ফলে এমন একটি বিল্ড থাকে যাতে JavaFX-ই নেই।

দুটি বিন্যাসই একই পাথ লেখে, `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`, এবং প্রতি বিল্ডে ঠিক
একটি চলে। `${jar.phase}`, `assembly.skipAssembly` ও `mdep.skip`-ই দুটিকে একসঙ্গে এর দাবি করা থেকে বিরত রাখে।

| | ডিফল্ট | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — কেবল এই মডিউলের ক্লাস ও রিসোর্স | ~50 MB — নির্ভরতাগুলো ভেতরে খুলে রাখা |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17টি jar, ম্যানিফেস্ট `Class-Path`-এ একে একে নাম দেওয়া | — |
| পাঠানো হয় | jar **এবং** তার পাশে `lib/` | একটি ফাইল |
| `dist/gaia-desktop-<version>-<platform>/`-এ আরও | `run.bat` (win) বা `run.sh` (অন্যগুলো) | একই |
| এবং | `readme.html` ও `docs/` (প্রতিটি প্ল্যাটফর্ম) | একই |

প্রতিটি বিতরণে নির্দেশিকাগুলোও থাকে: `docs/` তার বিন্যাস বজায় রেখে কপি করা হয়, যাতে নির্দেশিকা ও অনুবাদের
মধ্যকার লিংক কাজ করে, অনুবাদের টুলিং (`check-i18n.py`, `i18n-manifest.json`, `i18n-plan.md`) বাদে; আর রুটে
`readme.html`, যা প্রতিটির সঙ্গে লিংক করা একটি সূচি, আসে `src/main/dist/readme.html` থেকে, যেখানে `@VERSION@`
pom সংস্করণ দিয়ে বদলানো হয়। দুটিই লেখে `pick-launch-script` antrun ধাপ, যা আগে `docs/` মুছে দেয় যাতে সরানো
নির্দেশিকা রয়ে না যায়। readme-এর লিংক হাতে লেখা — `docs/`-এর নিচে কোনো নির্দেশিকার নাম বদলালে বা অনুবাদ
যোগ করলে সেখানেও তার সারি লাগবে।

ম্যানিফেস্ট `Class-Path` আর `lib/` একই জিনিসের দুই অর্ধেক: jar প্রতিটি রানটাইম নির্ভরতার জন্য
`lib/<artifact>-<version>.jar` নাম দেয়, এবং `copy-dependencies` ঠিক সেই নামগুলো দিয়েই `lib/` ভরে। এটাই
`java -jar`-কে কাজ করায়।

#### macOS অ্যাপ ও বিতরণের zip

একটি antrun এক্সিকিউশন, `mac-app-and-zip`, `package` পর্যায় শেষ করে। সেই কারণেই antrun প্লাগিন jar ও assembly
প্লাগিনের **পরে** ঘোষণা করা হয়েছে — Maven একটি পর্যায়ের এক্সিকিউশনগুলো প্লাগিন ঘোষণার ক্রমে চালায় — ফলে এটি
চলার সময় jar, যে-কোনো প্যাকেজিংয়ে, ইতিমধ্যে থাকে। (এর অন্য এক্সিকিউশন, `pick-launch-script`, আছে
`prepare-package`-এ এবং প্রভাবিত হয় না।)

`mac` ও `mac-aarch64`-এর জন্য এটি প্রথমে বিতরণ ডিরেক্টরিতে `GAIA Desktop.app` বানায়: `Info.plist` (যেখানে
`@VERSION@` pom সংস্করণ দিয়ে বদলানো), লঞ্চার `Contents/MacOS/gaia-desktop` (এক্সিকিউটেবল করা) ও
`gaia-desktop.icns`, সবই `src/main/macos/` থেকে, তারপর `gaia-desktop.jar` ও `lib/`-কে `Contents/Java`-তে **সরিয়ে**
দেয়, যাতে বান্ডলটি নিজে নিজে চলে। পাশে কোনো jar না থাকলে `run.sh` সেখানে খোঁজে। লঞ্চার সংস্করণ দেখে Java খোঁজে
(`java_home -v 21+`, তারপর Homebrew-এর openjdk — Finder থেকে চালালে `JAVA_HOME` বা `PATH` দেখা যায় না), কিছু না
পেলে `osascript` দিয়ে একটি ডায়ালগ দেখায়, `~/.gaia-desktop`-এ `cd` করে যাতে logback-এর আপেক্ষিক `logs/` লেখার
যোগ্য হয়, এবং `-Xdock:name`/`-Xdock:icon` পাঠায়। macOS চলমান `java`-কে বান্ডলের সঙ্গে যুক্ত করে (এর bundle id ও
Dock আইকন অ্যাপেরই হয়); মেনু বারে GAIA Desktop দেখায়।

তারপর, প্রতিটি প্ল্যাটফর্মের জন্য, এটি Ant-এর `<zip>` দিয়ে ডিরেক্টরিটিকে একই নামের একটি ফোল্ডারের নিচে
`target/dist/gaia-desktop-<version>-<platform>.zip`-এ zip করে: `run.sh` ও `Contents/MacOS/**`-কে
`filemode="755"` সহ আলাদা একটি ফাইল সেট হিসেবে, নইলে unzip করার পর সেগুলো চালানো যেত না। zip **সংযুক্ত করা হয়
না**: এটি GitHub রিলিজের জন্য, আর চারটি প্ল্যাটফর্ম আসে চারটি বিল্ড থেকে, যা Maven Central — প্রতি সংস্করণে একটি
অপরিবর্তনীয় আপলোড — কখনো একটি রিলিজ হিসেবে নিতে পারত না।

`project.build.outputTimestamp` বিল্ডের সময়ে সেট করা হয়। নইলে maven-jar-plugin 3.5 ও maven-assembly-plugin
3.8-এর আর্কাইভাররা প্রতিটি এন্ট্রির তারিখ দেয় 1 ফেব্রুয়ারি 1980।

অ্যাপ আইকন আঁকে `tools/icon/GaiaIcon.java` (বিল্ডের অংশ নয়; এর হেডারে `sips`/`iconutil` ধাপগুলো আছে)। এর আউটপুট
রিপোজিটরিতে চেক-ইন করা: বান্ডলের জন্য `src/main/macos/gaia-desktop.icns`, এবং
`src/main/resources/icons/gaia-desktop-{16..256}.png`, যেগুলো `GaiaDesktopApp` উইন্ডো আইকন হিসেবে সেট করে
(Windows ও Linux; macOS উইন্ডো আইকন উপেক্ষা করে)।

#### লঞ্চ স্ক্রিপ্ট

`run.sh` ও `run.bat` আসে `src/main/scripts/` থেকে, ফিল্টার ছাড়াই `dist/gaia-desktop-<version>-<platform>/`-এ কপি
হয় — `run.sh` এমন `${...}` শেল এক্সপ্যানশনে ভরা যা Maven ফিল্টারিং ইচ্ছেমতো বদলে লিখতে পারে। তারপর একটি antrun
ধাপ কেবল সেটিই রাখে যা প্ল্যাটফর্মটি চালায় — `win`-এর জন্য `run.bat`, বাকি সবার জন্য `run.sh` — এবং `run.sh`-এ
এক্সিকিউট বিট সেট করে, কারণ `copy-resources` তা বহন করে না। এটি প্রোফাইলের মাধ্যমে নয়, সমাধান করা
`${fx.platform}` দেখে সিদ্ধান্ত নেয়, কারণ প্রোফাইল সক্রিয়করণ অন্য প্রোফাইলের সেট করা মান দেখতে পায় না: নইলে
Windows-এ বানানো Linux বিল্ড হোস্টের স্ক্রিপ্ট পেয়ে যেত।

এগুলো **ম্যানিফেস্টের ওপর নির্ভর করে না**। প্রতিটি নিজেই ক্লাস পাথ তৈরি করে, `gaia-desktop.jar` এবং তারপর
`lib/`-এর প্রতিটি `.jar`, `lib/*` ওয়াইল্ডকার্ডের হাতে না ছেড়ে একে একে নাম দিয়ে, যাতে স্পেসসহ পাথ একটি এন্ট্রিই
থাকে এবং যা যোগ হলো তার গণনা বাস্তব হয়। `-cp` দিয়ে চালু করাই কারণ যে এগুলো
`tools.pantheum.gaia.desktop.Launcher` স্পষ্টভাবে উল্লেখ করে: `-cp` ম্যানিফেস্টের `Main-Class` পড়ে না। তবে এটি
এখনো এর `Class-Path` **মেনে চলে** — `-cp`-এ থাকা একটি jar তার ম্যানিফেস্টে নাম দেওয়া jar-গুলোও নিয়ে আসে, যেগুলো
ঠিক তার পরেই খোঁজা হয় — তাই স্ক্রিপ্ট তালিকাভুক্ত করুক বা না করুক প্রতিটি `lib/` jar লোড হয়, এবং স্ক্রিপ্টের
ক্লাস পাথ থেকে একটি বাদ দিলেও তা JVM-এর বাইরে থাকে না। তবু স্ক্রিপ্টগুলো সবই তালিকাভুক্ত করে, যাতে যে jar-এর
ম্যানিফেস্ট পুরোনো, হাতে সম্পাদিত বা একটি এন্ট্রি কম, সেটিও চালু হয়। একই স্ক্রিপ্ট দুই প্যাকেজিংয়েরই কাজ করে:
`-Pfat` jar-এর যোগ করার মতো কোনো `lib/` নেই এবং দরকারও নেই, এ কারণেই খালি `lib/` একটি নোট, ত্রুটি নয়।

#### Zebra নেটিভ লাইব্রেরি

বিল্ড Zebra-র কিছুই পাঠায় না — কোনো DLL নয়, কোনো সার্ভিস jar নয়। Windows-এ সেগুলো আসে মেশিনে ইনস্টল করা
Zebra-র Scanner SDK থেকে: `run.bat` এর `Jpos*.jar` সার্ভিস jar ও `bin\`-কে ক্লাস পাথে এবং `bin\`-কে `PATH`-এ
যোগ করে, যেখানে `System.loadLibrary` `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` খুঁজে পায়
(`java.library.path`-এর ডিফল্ট হলো `PATH`)। JavaPOS API ও এর কনফিগারেশন লোডার সবসময় আসে
`lib\javapos-*.jar` থেকে, SDK থাকুক বা না থাকুক।

**`run.bat` কখনো SDK-র নিজস্ব JavaPOS jar যোগ করে না**, `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`। একসময়
করত, API-র দুটি কপি এড়াতে `lib\javapos-*.jar` বাদ দিয়ে — কিন্তু ম্যানিফেস্ট `Class-Path` সেগুলো তবুও লোড করেছিল
(ওপরে দেখুন), ফলে JVM দুটোই পেয়েছিল: `lib\` থেকে 4.x লোডার ক্লাস, পাশে `javaPOS114.jar`-এর
`jpos/res/jpos.properties` ও `jcl.xsd`। প্রপার্টি ফাইলটি [`JposConfig`](#স্ক্যানার-সংযুক্তি)-কে সরে দাঁড়াতে
বাধ্য করে, আর সেই `jcl.xsd` কেবল 1.10 পর্যন্ত JavaPOS সংস্করণ গ্রহণ করে, তাই `jpos.xml`-এর প্রতিটি এন্ট্রি
(1.12–1.14) যাচাইয়ে ব্যর্থ হয়েছিল, রেজিস্ট্রি খালি থেকেছিল, এবং স্ক্যানারে পৌঁছানোর আগেই প্রতিটি সংযোগ ত্রুটি
109 দিয়ে ব্যর্থ হয়েছিল। এর জন্য সেই jar-টি ক্লাস পাথে থাকাই যথেষ্ট, এমনকি `lib\`-এর jar-গুলোর পেছনে থাকলেও।
Zebra-র সার্ভিস jar `lib\`-এর 1.14 API-তে কোনো পরিবর্তন ছাড়াই চলে — open, claim ও স্ক্যান এভাবেই একটি আসল
স্ক্যানারে যাচাই করা হয়েছে। `run.bat`-এর পাশে হাতে রাখা DLL এখনো মানা হয়: তখন স্ক্রিপ্ট
`-Djava.library.path=<dist>;%PATH%` সেট করে, `PATH` জুড়ে দিয়ে, কারণ এই প্রপার্টি ডিফল্ট সার্চ পাথকে পুরোপুরি
প্রতিস্থাপন করে।

`mvn javafx:run` এর কিছুই করে না, তাই Windows-এ ডেভেলপমেন্ট রান থেকে স্ক্যানার claim করতে হলে SDK-র jar-কে
ক্লাস পাথে এবং এর `bin\`-কে `PATH`-এ অন্য উপায়ে রাখতে হবে; সে জন্য `dist/` থেকে চালান।

ক্লাস পাথের বাইরেও এগুলো সেই কাজগুলো করে যা `java -jar` করে না: নিজের ডিরেক্টরি নির্ধারণ করা যাতে যে-কোনো কাজের
ডিরেক্টরি থেকে চলে, `PATH`-এর চেয়ে `JAVA_HOME`-কে অগ্রাধিকার দেওয়া, এবং 11-এর আগের JVM-কে
`UnsupportedClassVersionError`-এর বদলে প্রতিকার জানানো একটি বাক্য দিয়ে প্রত্যাখ্যান করা। `GAIA_DESKTOP_OPTS`
JVM বিকল্পগুলো পৌঁছে দেয়। `run.bat` `javaw.exe` নয়, `java.exe` ব্যবহার করে, যাতে কনসোল খোলা থাকে — Windows-ই
একমাত্র প্ল্যাটফর্ম যেখানে স্ক্যানার চলে, আর এর অবস্থা ও JavaPOS ত্রুটি সেখানেই যায়।

`run.bat` যা খুঁজে পায় তা থেকে Java, JavaFX ও Zebra সার্ভিসও বাছে — বান্ডল করা `jdk*\`, মডিউল পাথে
`javafx-sdk*\lib\`, `ZEBRA_HOME`-এ Zebra-র Scanner SDK — SDK-র JavaFX ব্যবহার করলে `lib\`-এর JavaFX কপিগুলো ক্লাস
পাথের বাইরে রাখে, এবং JDK-র SAX পার্সার, Windows প্রক্সি ও ট্রাস্ট স্টোর, আর Java 17+-এ `--enable-native-access`
পাঠায়। README-এর [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows)-এ সারণিটি আছে।
ফাইলের CRLF লাইন-শেষ বজায় রাখুন: কেবল LF-যুক্ত ব্যাচ ফাইলে `cmd.exe` কোনো `call :label` হারিয়ে ফেলতে পারে।
`run.sh`-ও `--enable-native-access=ALL-UNNAMED` পাঠায় — JavaFX নিজের নেটিভ `lib/` থেকে লোড করে, আর JavaFX ক্লাস
পাথে থাকলে `ALL-UNNAMED`-ই সেই মডিউল যা একে আওতায় আনে — `run.bat`-এর মতোই, কেবল Java সংস্করণ পড়া না গেলে বাদ
দেওয়া হয়।

দুটি বিন্যাসই **একটি প্ল্যাটফর্মের**, `${fx.platform}`-এর, JavaFX নেটিভ বহন করে, তাই কোনোটিই OS বা আর্কিটেকচার
পেরিয়ে বহনযোগ্য নয়। প্রতিটি লক্ষ্যের জন্য একবার বিল্ড করুন — দেখুন [প্রতি প্ল্যাটফর্মে একটি
বিল্ড](#প্রতি-প্ল্যাটফর্মে-একটি-বিল্ড)।

> **Eclipse।** `copy-dependencies` এক্সিকিউশনে একটি `<?m2e ignore?>` নির্দেশ আছে। m2e খোলা ওয়ার্কস্পেস প্রজেক্টকে
> jar-এর বদলে তার `target/classes` ফোল্ডারে নির্ধারণ করে, আর `copy-dependencies` প্যাকেজ না করা আর্টিফ্যাক্ট কপি
> করতে অস্বীকার করে (MDEP-187), যার ফলে `gaia` প্রজেক্ট এর পাশে খোলা থাকলেই অটো-বিল্ড ব্যর্থ হতো। পরিণতি হলো,
> কেবল IDE-তে করা বিল্ড `target/dist/gaia-desktop-<version>-<platform>/lib/` পূরণ করে না; jar নিজে ব্যবহারের আগে
> `mvn package` চালান।

### ইনপুট ফানেল

প্রতিটি ইনপুট — টাইপ করা, পেস্ট করা, ফাইল থেকে খোলা, স্ক্যান করা বা নির্মিত — একটি মেথড,
`MainView.capture(String, ScanSource, String)`, দিয়ে পার্সারে পৌঁছায়।

এটাই সেই একমাত্র ডিজাইন সিদ্ধান্ত যার চারপাশে অ্যাপটি গড়া। নির্মাণের নিজস্ব রিপোর্ট, নিজস্ব ইতিহাস বা নিজস্ব
এক্সপোর্ট পথ লাগে না, কারণ ফানেল পেরোনোর পর নির্মিত স্ট্রিং স্ক্যান করা স্ট্রিং থেকে আলাদা করা যায় না। ইনপুট
তৈরি করে এমন নতুন যে-কোনো কিছু এর পাশ দিয়ে নয়, এর ভেতর দিয়েই যাওয়া উচিত।

| `gaia-scanner` | স্ক্যানারে প্রতিটি কল — open, claim, enable, disable, release, close। `ScannerService`-এর মালিকানাধীন একটি দীর্ঘজীবী থ্রেড; দেখুন [স্ক্যানার সংযুক্তি](#স্ক্যানার-সংযুক্তি) |
| JavaPOS ইভেন্ট থ্রেড | `ScannerService` কলব্যাক। `MainView.FxScannerListener` প্রতিটিকে `Platform.runLater` দিয়ে পার করে দেয় |
| পটভূমি | স্ক্যানারের `connect()` / `disconnect()`-এর অপেক্ষা (claim-এ 5 সেকেন্ড পর্যন্ত লাগতে পারে), স্টার্ট-আপে সংরক্ষিত ইতিহাস ফিরিয়ে আনা — যা পার্সারকে গরম করার কাজও করে — এবং আপডেট পরীক্ষা (`gaia-update-check`, একটি GitHub অনুরোধ, ফলাফল `Platform.runLater` দিয়ে ফেরত পাঠানো) |

**কোনো নিয়ন্ত্রণের নিজস্ব নির্বাচন ইভেন্টের ভেতর থেকে তার নির্বাচন কখনো বদলাবেন না, বা নিয়ন্ত্রণটি ধ্বংস করবেন
না।** এই অ্যাপের তিনটি আলাদা ক্র্যাশ ঠিক এ থেকেই এসেছিল: পপআপের নিজস্ব `clearAndSelect`-এর ভেতরে AI পিকার রিসেট
করা (`ListViewBehavior` থেকে একটি `IndexOutOfBoundsException`), এবং ভাষা কম্বোর মালিক প্যানেলটিকে সেই কম্বোর
নিজস্ব হ্যান্ডলারের ভেতর থেকে পুনর্নির্মাণ করা। দুটিই এখন `Platform.runLater` দিয়ে পিছিয়ে দেওয়া হয়, এবং কারণগুলো
দুটি কল স্থানেই লেখা আছে।

### পুনর্নির্মাণ বনাম পুনঃলেবেলিং

ভাষা বদলালে কাঠামো — মেনু, টুলবার, বিকল্প প্যানেল — ক্যাটালগ থেকে **পুনর্নির্মিত** হয়, যা নিরাপদ কারণ এদের
কারোরই অবস্থা নেই: `OptionsPane` হলো `ParseOptions`-এর দ্বিমুখী দৃশ্য, তাই মানগুলো মডেলে থাকে এবং নতুন প্যানেল
সেগুলো সরাসরি তুলে নেয়।

**ব্যবহারকারীর ডেটা** রাখে এমন নিয়ন্ত্রণগুলো ফিল্ড, এবং সেগুলোকে বরং জায়গাতেই পুনরায় লেবেল করা হয়:
`BuilderPane.retext(UiStrings)` AI সারি, Digital Link ফিল্ড ও নির্বাচন অক্ষুণ্ণ রাখে। একে পুনর্নির্মাণ করলে চলমান
কাজ হারিয়ে যেত — যেমন একসময় হয়েছিলও।

## {GS} টোকেন

JavaFX `TextField` `0x20`-এর নিচের প্রতিটি অক্ষর নিঃশব্দে ফেলে দেয় (`TextInputControl.filterInput`)। "অদ্ভুতভাবে
দেখায়" নয় — মুছে ফেলে। টাইপ করা, পেস্ট করা, `setText` ও `insertText` সবই প্রভাবিত, তাই
`setText("01…" + GS + "10LOT")` থেকে পাওয়া যায় `"01…10LOT"`: একটি এলিমেন্ট স্ট্রিং যার অর্থ নিঃশব্দে বদলে গেছে,
কারণ পরিবর্তনশীল দৈর্ঘ্যের AI এখন তার পরের অংশ গিলে ফেলে।

`desktop.parse.GsToken`-ই পুরো উত্তর। বিভাজকটি UI-তে আক্ষরিক টেক্সট `{GS}` হিসেবে চলে এবং পার্সারে যাওয়ার পথে
আবার `0x1D` হয়ে যায়। টোকেনটি এখানে উদ্ভাবিত নয় — কোরের `ASCIIRevealerUtils.printable` ঠিক এভাবেই `0x1D` দেখায়,
তাই রিপোর্ট থেকে কপি করা মান সরাসরি ইনপুট বারে ফিরিয়ে পেস্ট করা যায়।

ইনপুট ফিল্ডে একটি `TextFormatter` ফিল্টার টেক্সট আসার প্রতিটি পথ ধরে — টাইপ করা, ⌘V, কনটেক্সট মেনু, টেনে এনে
ছাড়া, `setText` — এ কারণেই পুনর্লিখন প্রতিটি হ্যান্ডলারে নয়, সেখানেই থাকে।

স্ক্যানারের পথ কখনো `GsToken` দিয়ে যায় না: স্ক্যান পার্সারে পৌঁছায় বাইট হিসেবে।

## স্ক্যানার সংযুক্তি

`ScannerService` JavaPOS-এর `Scanner` নিয়ন্ত্রণের মালিক: open → claim → enable, প্রতিটি স্ক্যানের পর ডেটা ইভেন্ট
আবার সক্রিয় করে। লজিক্যাল ডিভাইসের নাম আসে `src/main/resources/jpos.xml` থেকে।

**প্রতিটি ডিভাইস কল চলে একটি থ্রেডে, `gaia-scanner`-এ, যা সার্ভিসের আয়ু পর্যন্ত বাঁচে** — কখনো FX থ্রেডে নয়, এবং
কখনো এমন থ্রেডে নয় যা কলের পর শেষ হয়ে যায়। Zebra-র সার্ভিস CoreScanner COM API-র মাধ্যমে JNI দিয়ে স্ক্যানারে
পৌঁছায়, আর COM যা সেট আপ করে তা কলকারী থ্রেডের অ্যাপার্টমেন্টে বেঁধে দেয়: এমন থ্রেডে open করুন যা পরে শেষ হয়ে
যায়, তাহলে স্ক্যানার claim হয় কিন্তু চুপ থাকে; অন্য থ্রেডে close করুন, তাহলে ভুল অ্যাপার্টমেন্ট আনইনিশিয়ালাইজ
হয়। FX থ্রেডে close করা সবচেয়ে খারাপ ঘটনা, কারণ JavaFX সেখানে `OleInitialize` কল করে এবং প্রতিটি উইন্ডোর ড্রপ
টার্গেট তার সাপেক্ষে নিবন্ধন করে — সেখানে একটি `CoUninitialize` পুরো অ্যাপে টেনে এনে ছাড়া নষ্ট করে দেয়। এটি
Windows-এ JavaFX-এর ব্যাপার, কোনো নির্দিষ্ট JavaFX সংস্করণের নয়। `connect()` ও `disconnect()` সেই থ্রেডে কাজ
জমা দিয়ে অপেক্ষা করে, তাই `MainView` দুটিকেই একটি স্বল্পজীবী পটভূমি থ্রেড থেকে কল করে; এই প্যাটার্নটি ভিউয়ারের
`JposScannerSession`-এর, যেখানে টেনে এনে ছাড়ার ব্যর্থতা প্রথম ধরা পড়েছিল।

দুটি নিয়ম বেয়াড়া ডিভাইসকে সংযোগ আটকে দেওয়া থেকে রক্ষা করে। **বন্ধ করার প্রক্রিয়া কখনো আগেভাগে থামে না:**
`closeQuietly` disable, release ও close আলাদা ধাপে করে, কেবল claim ধরা থাকলে release করে, এবং সবসময় `close()`
চেষ্টা করে — ব্যর্থ claim-এর পর `release()` "not claimed" ছোড়ে, আর ধাপগুলো যখন একটি `try` ভাগ করত, তখন এতে close
বাদ পড়ত এবং ডিভাইস Zebra-র সার্ভিসে খোলা থেকে যেত। **ডেটা ইভেন্ট আবার সক্রিয় করা হয় একটি `finally`-তে:**
JavaPOS প্রতিটি ইভেন্টের পর এটি নিষ্ক্রিয় করে, তাই ব্যতিক্রম ছোড়া রিড বা হ্যান্ডলারকেও আবার সক্রিয় করতেই হবে,
নইলে পুনঃসংযোগ পর্যন্ত স্ক্যানার চুপ থাকে। `ScannerLifecycleTest` দুটিকেই একটি স্ক্রিপ্ট করা `jpos.Scanner`-এর
বিরুদ্ধে চালায়।

**`JposConfig` প্রথম open-এর আগে JavaPOS-কে বান্ডল করা `jpos.xml`-এর দিকে নির্দেশ করে।** Maven-এর JavaPOS jar
(`javapos-config-loader` 4.x) এবং ক্লাস পাথে কোনো `jpos/res/jpos.properties` না থাকলে, অন্যথায় প্রতিটি open
*"Service does not exist in loaded JCL registry"* (ত্রুটি 109) দিয়ে ব্যর্থ হয়, তিনটি আলাদা কারণে: সার্ভিস
ম্যানেজার `SimpleRegPopulator`-এ ফিরে যায়, যা একটি সিরিয়ালাইজ করা `jpos.cfg` পড়ে এবং কখনো `jpos.xml` নয়; XML
লোডার `jpos.xml` খোঁজে কেবল কাজের ডিরেক্টরিতে, jar-এর ভেতরে নয়; এবং `lib/`-এর Xerces 2.12.2 লোডারের সেট করা
JAXP `accessExternalDTD` প্রপার্টি প্রত্যাখ্যান করে। `JposConfig` `jpos.config.regPopulatorClass`
(`JavaxRegPopulator`), `jpos.config.populatorFileURL` (jar-এর নিজস্ব `jar:file:…!/jpos.xml`) ও
`javax.xml.parsers.SAXParserFactory` (JDK-র) সিস্টেম প্রপার্টি হিসেবে সেট করে — আগে থেকে সেট করা কোনোটি কখনো
নয়, তাই `-Djpos.config.populatorFileURL=file:…` এখনো অন্য একটি `jpos.xml` বাছতে পারে — এবং ক্লাস পাথে
`jpos.properties` থাকলে বা 4.x লোডার না থাকলে কিছুই সেট করে না। Zebra SDK-র `javaPOS114.jar` এমনই একটি ঘটনা
এবং রেজিস্ট্রিকে পুরোপুরি ভেঙে দেয়, এ কারণেই `run.bat` একে ক্লাস পাথের বাইরে রাখে — দেখুন [Zebra নেটিভ
লাইব্রেরি](#zebra-নেটিভ-লাইব্রেরি)। `JposConfigTest` শুরু থেকে শেষ পর্যন্ত পরীক্ষা করে যে রেজিস্ট্রিতে তারপর ফাইলের
স্ক্যানারগুলো থাকে।

**ডিভাইস পিকার সেই রেজিস্ট্রি থেকে তৈরি হয়**, কোডে তালিকা হিসেবে রাখা হয় না: `ScannerService.logicalNames()`
`gaia-scanner` থ্রেডে লোড হওয়া এন্ট্রি পড়ে এবং সেগুলো রাখে যাদের ডিভাইস শ্রেণি `Scanner` — `jpos.xml`-এর দুটি
ওজন-যন্ত্রের এন্ট্রি বাইরে থাকে — `pickerOrder` ক্রমে: ফাইলে সংজ্ঞায়িত থাকলে `ZebraAllScanners` প্রথমে, বাকিগুলো
বর্ণানুক্রমে (রেজিস্ট্রি ফাইলের ক্রম রাখে না)। যে ফাইলে এটি নেই তাকে এটি দেওয়া হয় না; কিছুই লোড না হলে কেবল
ডিফল্টটি দেখানো হয়, তাই পিকার কখনো খালি থাকে না। `MainView` ডিফল্টটি সঙ্গে সঙ্গে দেখায় এবং সংরক্ষিত পছন্দ বজায়
রেখে একটি পটভূমি থ্রেড থেকে তালিকা ভরে। তাই `jpos.xml`-এ যোগ করা স্ক্যানার — অথবা `-Djpos.config.populatorFileURL`
দিয়ে নাম দেওয়া পুরো একটি ফাইল — কোনো কোড পরিবর্তন ছাড়াই পিকারে দেখা দেয়, এবং `JposConfigTest` পিকারকে বান্ডল
করা ফাইলের একটি স্বাধীন পাঠের সঙ্গে মিলিয়ে দেখে। সেই এন্ট্রিগুলো যে সার্ভিসের নাম দেয় সেগুলো Zebra-র ক্লাস
(`com.zebra.jpos.service.scanner.*Factory`), যেগুলোকে এখনো ক্লাস পাথে থাকতে হবে — `run.bat`-এর মাধ্যমে Scanner SDK
থেকে, অথবা `lib\`-এ রাখা Zebra-র সার্ভিস jar থেকে।

স্ক্যান ডেটা **ISO-8859-1** হিসেবে ডিকোড করা হয় যাতে প্রতিটি বাইট 1:1 ম্যাপ হয় এবং AIM Code ID উপসর্গ ও প্রতিটি
`0x1D` দুটোই অক্ষত থাকে; রিপোর্ট লেখা হয় UTF-8-এ।

সার্ভিসের কিছুই ব্যবহারকারীর জন্য টেক্সট রচনা করে না। ইভেন্টগুলো বের হয় `ScannerListener.Event` ধ্রুবক আর
পরিবর্তনশীল মান হিসেবে, এবং `MainView` ক্যাটালগ থেকে শব্দ জোগায় — নইলে 35 রকমে অনূদিত একটি অ্যাপ্লিকেশনে
অবস্থা লাইন ইংরেজিতে থাকত। লগ লাইন ব্যতিক্রম এবং ইংরেজিতেই থাকে।

`ScannerService.isSupportedPlatform()` একটি `os.name` পরীক্ষা, এবং `MainView` কোনো স্ক্যানার নিয়ন্ত্রণ বানানোর আগে
তাকে জিজ্ঞেস করে: macOS ও Linux-এ কোনো টগল নেই, কোনো ডিভাইস পিকার নেই, কোনো স্ক্যানার মেনু নেই (এবং তাই কোনো
<kbd>⌘K</kbd> নেই), এবং কোনো অবস্থা লেবেল নেই। এগুলো লুকানো নয় — এগুলো কখনো তৈরিই হয় না।

Zebra তার JavaPOS সার্ভিস কেবল Windows-এর জন্য পাঠায়, এবং অন্য কোথাও কিছুই আগেভাগে ব্যর্থ হয় না: jar নির্ধারিত
হয় এবং নিয়ন্ত্রণ তৈরি হয়, আর শেষে অনুপস্থিত নেটিভ স্তরের কারণে `open()`-ই ব্যর্থ হয়, কয়েক সেকেন্ড ও একটি
ডায়ালগের পরে।

নিয়মটি *সার্ভিস* সম্পর্কে, JavaPOS সম্পর্কে নয়। ক্রস-প্ল্যাটফর্ম সার্ভিস পাঠানো কোনো বিক্রেতা এখানে কাজ করবে,
এবং নিয়মটি প্রসারিত করা কেবল `supportsJavaPos(String)`-এ একটি পরিবর্তন — যা package-private এবং `os.name`
স্ট্রিংয়ের বিরুদ্ধে পরীক্ষিত, যাতে যে মেশিনই বিল্ড চালাক, দুটি উত্তরই আওতায় থাকে।

### সিম্বোলজি

`Symbologies` JavaPOS-এর সব **78**টি `SCAN_SDT_*` স্ক্যান-ডেটা টাইপকে প্রদর্শন নামে, এবং যেখানে দুই শব্দভান্ডার
মেলে সেখানে কোরের `DataCarrierType`-এ ম্যাপ করে। দুটির মধ্যে JavaPOS সূক্ষ্মতর — এটি UPC-A-কে EAN-13 থেকে, এবং
সাধারণ Data Matrix-কে GS1 DataMatrix থেকে আলাদা করে, যেখানে AIM পুরো একটি পরিবারকে একটি কোড অক্ষরের নিচে রাখে।

সারণির বাইরের টাইপও একটি ব্যবহারযোগ্য নাম পায়, যা `ScannerConst`-এর ওপর রিফ্লেকশন দিয়ে খুঁজে পাওয়া যায়, কারণ
বিক্রেতার সার্ভিস সত্যিই স্পেসিফিকেশন তালিকার বাইরের মান রিপোর্ট করে। একটি পরীক্ষা `ScannerConst` ঘুরে দেখে এবং
কোনো ঘোষিত টাইপের নাম না থাকলে ব্যর্থ হয় — যা ভবিষ্যতের JavaPOS-এর যোগ করা ধ্রুবকও ধরে ফেলে।

কিছু ক্যারিয়ার ম্যাপিং অনুমান করার বদলে ইচ্ছাকৃতভাবে `UNKNOWN` রাখা হয়েছে: straight 2 of 5 (AIM `]R`/`]S`-কে
start/stop বারের সংখ্যা দিয়ে আলাদা করে, যা JavaPOS রিপোর্ট করে না), চার-অবস্থার ডাক কোড, এবং TLC-39।

## স্থানীয়করণ

লেবেলগুলো প্রতি ভাষায় একটি প্রপার্টিজ ফাইলে থাকে `src/main/resources/i18n/ui_<CODE>.properties`-এর নিচে, কোরের
ত্রুটি ক্যাটালগের মতো একই কোড ব্যবহার করে (`EN`, `FR`, `PCM`, …)। 35টিই আছে এবং 35টিতেই একই কী-সেট। ফাইলগুলো
পড়া হয় **UTF-8** হিসেবে, `Properties` যে ISO-8859-1 ধরে নেয় তা নয়, তাই অনুবাদ `\uXXXX` এস্কেপের বদলে পাঠযোগ্য
রূপে সংরক্ষিত থাকে।

**ফলব্যাক প্রতি কী-তে, প্রতি ফাইলে নয়** — এটাই আংশিক অনূদিত একটি ভাষাকে তার প্রথম কী আসার মুহূর্ত থেকে কাজের
করে তোলে। ইংরেজিই চুক্তি: প্রতিটি কী সেখানে থাকতে হবে।

| স্তর | কী | আওতা |
|---|---|---|
| ভাগ করা রিপোর্ট শব্দভান্ডার, `gaia-demo`-এর `GaiaHtmlReport` থেকে নেওয়া | 31 | সব 35টি ভাষা |
| ডেস্কটপ কাঠামো — মেনু, বোতাম, বিল্ডার, বিকল্প, অবস্থা লাইন, রিপোর্ট বিন্যাস, স্ক্যানার অবস্থা, ডায়ালগের মূল টেক্সট | 114 | সব 35টি ভাষা |

ভাগ করা শব্দগুলোর ছয়টি (`generated`, `status`, `dlRole`, `interpretations`, `message`, `level`) এই অ্যাপের রিপোর্টে
ব্যবহৃত হয় না। ভাগ করা অংশটি ডেমো শব্দভান্ডারের বিশ্বস্ত কপি হিসেবে রাখতে এগুলো রাখা হয়েছে; ফাইলের হেডারে সে কথা
বলা আছে।

### `--language` আর্গুমেন্ট

`GaiaDesktopApp.languageOverride()` JavaFX-এর নিজস্ব `getParameters().getNamed()` দিয়ে `--language=…` পড়ে,
`Languages.fromArgument` দিয়ে নির্ধারণ করে — ক্যাটালগ কোড, enum নাম বা BCP 47 ট্যাগ, বড়-ছোট হাতের অক্ষর নির্বিশেষে
— এবং `MainView`-এর হাতে দেয়।

**ওভাররাইড রানের জন্য, ফাইলের জন্য নয়।** `MainView` যে ভাষা লোড করেছিল তা `savedLanguage`-এ রাখে এবং *সেটিই* ফিরে
লেখে, যতক্ষণ না `languageChosenInSession` জানায় যে ব্যবহারকারী নিজে একটি ভাষা বেছেছেন; তখন তাঁদের পছন্দ
স্বাভাবিকভাবে সংরক্ষিত হয়। এই ভাগটাই পুরো নকশা: কিয়স্ক প্রোফাইল বা ডেমো শর্টকাট মেশিনের মালিক আগামীকাল যে ভাষায়
খুলবেন তা না বদলেই স্প্যানিশে খুলতে পারে, অথচ বিকল্প প্যানেলে করা আসল পছন্দ তবুও টিকে থাকে।

কোনো ক্যাটালগের নাম দেয় না এমন মান গ্রহণযোগ্য কোডগুলোসহ লগ করা হয় এবং উপেক্ষা করা হয়। শর্টকাটে একটি টাইপোর
জন্য শুরু হতে অস্বীকার করা হতো আরও খারাপ ব্যর্থতা, আর একই কারণে `Languages.fromArgument` ব্যতিক্রম ছোড়ার বদলে
`null` ফেরত দেয়।

### ভাষা যোগ করা

কোনো কোড পরিবর্তনের দরকার নেই।

1. `ui_<CODE>.properties` সম্পাদনা করুন — প্রতিটি ভাষার ফাইল আগে থেকেই আছে।
2. মানগুলো অনুবাদ করুন। `{0}` / `{1}` প্লেসহোল্ডার জায়গামতো রেখে দিন।
3. বিল্ড করুন। দুটি পরীক্ষা চুক্তিটি বলবৎ করে: একটি ব্যর্থ হয় যদি কোড এমন কী চায় যা ইংরেজি সংজ্ঞায়িত করে না,
   অন্যটি যদি কোনো ক্যাটালগের কী-সেট ইংরেজি থেকে সরে যায়।

প্রথম পরীক্ষাটি ক্লাসের ওপর রিফ্লেকশনের বদলে **সোর্স কোডে** কী লিটারেল খোঁজে, কারণ কী-গুলো কেবল কল স্থানে
স্ট্রিং লিটারেল হিসেবেই থাকে। এ কারণেই নতুন বার্তা কী সরাসরি লিখে তৈরি করতে হবে —
`strings.format("st.scannerError", …)` — কোনো ভেরিয়েবলের মাধ্যমে খুঁজে নয়, নইলে পরীক্ষা তা দেখতে পায় না।

### যা ইচ্ছাকৃতভাবে অনূদিত নয়

- কাঁচা মানের পাশে মনোস্পেসে দেখানো সংক্ষিপ্ত ফিল্ড নাম — এলিমেন্ট কার্ডের `format`, `position`, `length`, `raw`
  ও `part`, টেপের `AI`, `sep`, `pos` ও `len`, এবং ত্রুটির অবস্থান নির্দেশ করা চারটি ঘর (`AI`, `position`, `level`,
  `stage`), যাদের মান এমনিতেই অনূদিত নয় এমন enum নাম;
- নমুনা-ইনপুটের নাম, যেগুলো GS1 গঠনের নাম, এবং সিম্বোলজির নাম, যেগুলো নামবাচক বিশেষ্য;
- `GE-C084`-এর প্রতিকার অনুচ্ছেদ — মানদণ্ডের গদ্য, যেখানে আধাআধি অনুবাদ ইংরেজির চেয়েও খারাপ;
- `ElementBuilder`-এর অজানা-AI-এর শেষ রক্ষাকবচ, যা UI থেকে পৌঁছানো যায় না: এডিটর নিজেই অজানা AI পরীক্ষা করে
  এবং ক্যাটালগ থেকে সেগুলোর কথা জানায়;
- লগ লাইন।

একটি ফাঁক রয়ে গেছে: `ScanSource.label()` ইতিহাসের সারি ও রিপোর্টের শিরোনামে `manual` / `scanner` / `file` /
`built` ইংরেজিতে দেয়। এটি বন্ধ করতে একটি কী-র চেয়ে বেশি লাগে — `HistoryCell`-এর কোনো `UiStrings` নেই, এবং
তালিকার সেল ফ্যাক্টরি একবারই ইনস্টল হয়, তাই ভাষা বদলালে সেলগুলোও রিফ্রেশ করতে হবে।

## সংরক্ষিত অবস্থার ফরম্যাট

`~/.gaia-desktop/`-এর নিচে দুটি ফাইল, আলাদা রাখা কারণ এরা ভিন্ন তালে বদলায় — একটি দূষিত বা হাতে সম্পাদিত ক্যাপচার
লগের জন্য ব্যবহারকারীর সেটিংস হারানো উচিত নয়। ডিরেক্টরিটি `-Dgaia.desktop.home=…` দিয়ে বদলান, যা দিয়েই পরীক্ষাগুলো
আসল হোম ডিরেক্টরি থেকে দূরে থাকে।

**`options.properties`** — কোনো বিকল্প বদলালে, এবং প্রস্থানের সময় লেখা হয়।

| কী | অর্থ |
|---|---|
| `parse.mode`, `parse.language` | পাইপলাইনের গভীরতা ও বার্তার ভাষা |
| `date.endian`, `date.separator`, `date.month`, `date.year` | তারিখ প্রদর্শন |
| `check.skipRequires`, `check.skipExcludes` | কাঠামোগত পরীক্ষা থেকে ছাড় |
| `ui.theme` | `LIGHT` বা `DARK` |
| `ui.optionsPane` | বিকল্প প্যানেল খোলা? |
| `ui.scannerDevice` | শেষ JavaPOS লজিক্যাল নাম |
| `ui.mode` | `PARSE`, `BUILD` বা `COMBINE` |
| `update.check` | দৈনিক আপডেট পরীক্ষা চলে কি না (ডিফল্ট `true`) |
| `update.lastCheck` | এটি শেষ কখন চলেছিল, ISO-8601; অনুপস্থিত বা অপাঠ্য হলে পরীক্ষা বাকি |
| `update.skipVersion` | যে রিলিজের জন্য ব্যবহারকারী *এই সংস্করণটি এড়িয়ে যান* বেছেছেন; স্বয়ংক্রিয়ভাবে আর দেখানো হয় না |

অনুপস্থিত বা ক্ষতিগ্রস্ত ফাইল কখনো মারাত্মক নয়: প্রতিটি মান আলাদাভাবে ফলব্যাক করে, তাই একটি খারাপ লাইনের মূল্য
কেবল সেই লাইনটিই। প্রথমবার চালু করার সময়, কোনো ফাইলই না থাকলে, বিকল্পগুলো GAIA-র অন্তর্নির্মিত ডিফল্টের বদলে
`SystemDefaults` দিয়ে মেশিনের আঞ্চলিক সেটিংস থেকে পূরণ হয় — লোকেলের ছোট তারিখ প্যাটার্ন দেয় উপাদানের ক্রম,
বিভাজক, এবং মাস ও বছর সংক্ষিপ্ত কি না।

`Properties.setProperty`-কে কখনো null দেবেন না: এটি ব্যতিক্রম ছোড়ে, আর `persistOptions()` চলে UI ইভেন্ট হ্যান্ডলার
থেকে, যেখানে ব্যতিক্রম FX থ্রেডে বেরিয়ে যায়। এটি একটি আসল ক্র্যাশ যা এই অ্যাপে আগেই ঘটেছে।

**`captures.tsv`** — ইতিহাস বদলালে, এবং প্রস্থানের সময় লেখা হয়। নতুনতমটি আগে, সর্বোচ্চ **500**টি এন্ট্রি।

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

যা আবার গণনা করা যায় না কেবল তা-ই সংরক্ষিত হয়। `ParseResult` সিরিয়ালাইজ করা **হয় না** — লোডের সময় ইনপুট আবার
পার্স করে তা পুনরায় বের করা হয়, তাই পুনরুদ্ধার করা ইতিহাস *এখন* কার্যকর বিকল্পগুলো প্রতিফলিত করে। ইনপুটে নিয়মিত
FNC1 ও স্ক্যানার যা-ই বের করে তা থাকে, তাই ইনপুট ফিল্ড এস্কেপ করা হয় (`\\`, `\t`, `\n`, `\r`, এবং `0x20`-এর
নিচের বাকি সবকিছুর জন্য `\xNN`) এবং ফাইলটি ISO-8859-1 হিসেবে, বাইট ধরে ধরে, পড়া ও লেখা হয়।

তারিখ রেকর্ড শুরু হওয়ার আগে লেখা ফাইলে কেবল ঘড়ির সময় থাকে; সেগুলো তবুও লোড হয়, আজকের তারিখ দিয়ে, কারণ আসল
তারিখ কখনো লেখাই হয়নি।

## পরীক্ষা

```bash
(cd gaia-desktop && mvn test)
```

96টি পরীক্ষা, ইচ্ছাকৃতভাবে **JavaFX টুলকিট-মুক্ত**, যা এগুলোকে দ্রুত ও হেডলেস রাখে। এগুলো রিপোর্ট রেন্ডারার,
নির্মাণ যুক্তি ও AI খোঁজা, `{GS}` রূপান্তর, লোকেল থেকে পাওয়া ডিফল্ট, দুটি স্টোর (একটি `0x1D`-যুক্ত রাউন্ড ট্রিপ ও
ইচ্ছাকৃতভাবে ক্ষতিগ্রস্ত ফাইলসহ), সিম্বোলজি সারণি, স্ক্যানার প্ল্যাটফর্ম নিয়ম, সংস্করণ স্টাব, এবং ক্যাটালগগুলো
আওতায় আনে।

তিনটি জানার মতো, কারণ এগুলো ফাংশন নয়, চুক্তি রক্ষা করে:

| পরীক্ষা | কখন ব্যর্থ হয় |
|---|---|
| `CatalogueCoverageTest` | কোড এমন কী চায় যা `ui_EN.properties` সংজ্ঞায়িত করে না, বা 35টি ফাইলের যে-কোনোটি ইংরেজি কী-সেট থেকে সরে যায় |
| `SymbologiesTest` | JavaPOS ঘোষিত কোনো `SCAN_SDT_*` ধ্রুবকের প্রদর্শন নাম নেই — JavaPOS আপগ্রেডে যোগ হওয়া ধ্রুবকসহ |
| `ScannerServiceTest` | প্ল্যাটফর্ম নিয়ম Windows বা অন্য যে-কোনো কিছুর জন্য উত্তর বদলায় |

`UiStrings` রানটাইমে ইচ্ছাকৃতভাবে ক্ষমাশীল — একটি অজানা কী বিন্যাসের মাঝখানে ব্যতিক্রম ছোড়ার বদলে কী নিজেই হিসেবে
দেখায় — ঠিক এ কারণেই ক্যাটালগ পরীক্ষাটি থাকা জরুরি।

**আওতার বাইরে:** লাইভ টুলকিট লাগে এমন যে-কোনো কিছু — ফোকাস আচরণ, মোড টগল, সারণি সম্পাদনা, ভাষা বদল, এবং
[থ্রেডিং](#থ্রেডিং)-এ বর্ণিত দুটি ক্র্যাশ। এগুলো আসল উইন্ডো চালিয়ে যাচাই করা হয়েছিল, কিন্তু এগুলোতে রিগ্রেশন হলে
বিল্ড ব্যর্থ হবে না। TestFX বা Monocle যোগ করলে এই ফাঁক বন্ধ হবে।

## জানা সীমাবদ্ধতা ও বাকি কাজ

- **কোনো হেডলেস UI পরীক্ষা নেই।** দেখুন [পরীক্ষা](#পরীক্ষা)।
- **প্ল্যাটফর্ম-নির্দিষ্ট আর্টিফ্যাক্ট।** দুটি প্যাকেজিংই একটি প্ল্যাটফর্মের JavaFX নেটিভ বান্ডল করে; প্রতিটি
  লক্ষ্যের জন্য `-Dfx.platform` দিয়ে একটি বিল্ড করুন (যে-কোনো মেশিন সবগুলো বিল্ড করতে পারে)। কোনোটিই Java রানটাইম
  বান্ডল করে না — তার জন্য `jpackage` লাগে, যা কেবল সেই OS-এর জন্য বিল্ড করে যেখানে এটি চলে।
- **স্ক্যানার ইনপুট কেবল Windows-এ।** দেখুন [প্ল্যাটফর্ম গেট](#প্ল্যাটফর্ম-গেট)।
- **`ScanSource.label()` স্থানীয়কৃত নয়।** দেখুন [যা ইচ্ছাকৃতভাবে অনূদিত
  নয়](#যা-ইচ্ছাকৃতভাবে-অনূদিত-নয়)।
- **`UiState.mode` একটি `String`** (`"PARSE"` / `"BUILD"`), অথচ এর পাশের `Theme` একটি enum, তাই লিটারেলটি কয়েক
  জায়গায় আসে। একটি enum এগুলো দূর করবে।
- **Digital Link লক্ষ্য কেবল ডোমেইন ও পাথ উপসর্গ।** `BuilderDigitalLinkConfig` অতিরিক্ত কোয়েরি প্যারামিটার ও একটি
  ফ্র্যাগমেন্টও সমর্থন করে; এডিটর সেগুলো দেখায় না।
- **পারস্পরিক বর্জনশীল AI জোড়া (`GE-S006`) এডিটরে চিহ্নিত হয় না** যেভাবে অজানা ও ডুপ্লিকেট AI হয় — নির্মাণ সোজা
  ব্যর্থ হয়।
- **কোরের ত্রুটি ক্যাটালগ উদ্ধৃতিচিহ্ন দ্বিগুণ করে** (`value ''09506000134350''`), যা নির্মাণ ব্যর্থতায় ও রিপোর্টে
  হুবহু দেখা যায়। এটি `MessageFormat`-এর উদ্ধৃতি-এস্কেপিং বলে মনে হয় যা আন-এস্কেপ হচ্ছে না; সমাধান কোরে হওয়া
  উচিত।
