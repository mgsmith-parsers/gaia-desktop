## Модуль коротко

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

Клієнт основної бібліотеки, і нічого більше. У ньому **немає жодних знань про GS1**: кожне визначення AI,
правило перевірки, повідомлення про помилку й локалізований опис беруться з
[`GaiaParser`](../../../../gaia/docs/GaiaParser.md) і
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md). Зокрема, список AI ніколи не копіюється в цей модуль —
засіб вибору в конструкторі читає власний реєстр ядра, тож не може запропонувати AI, який конструктор
відхилив би.

**Точки входу:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (JavaFX-`Application`) і
`tools.pantheum.gaia.desktop.Launcher` (`Main-Class` запакованого jar).

Модуль — це лист: від нього ніщо не залежить, і сам він не залежить від жодного іншого подальшого модуля.

## Збирання та запуск

- **Java 21** для запуску і JDK 21 або новіший для збирання — модуль компілюється з `release=21`. JavaFX 21 —
  відповідна лінія LTS. Jar ядра й досі містить байт-код Java 11 і без змін працює на 21.
- **Maven** у `PATH`. Обгортки (wrapper) у цьому репозиторії немає.
- **Спочатку встановлене ядро.** Цей модуль розв'язує `gaia:1.1.0` з `~/.m2`; застарілий або відсутній jar
  ядра — звична причина помилки `package tools.pantheum.gaia does not exist`.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` — єдиний аргумент командного рядка і, крім `-Dgaia.desktop.home=…`, що переносить увесь
профіль деінде, єдиний спосіб вплинути на запуск.

`mvn javafx:run` — шлях розробки: плагін кладе JavaFX у **module path**, тож інструментарій стартує як
іменований модуль, а `GaiaDesktopApp` можна запускати напряму. Запакований jar так не може — усе лежить у
class path, — тому його `Main-Class` — прошарок `Launcher`. Підклас `Application` як `Main-Class` у такому
розкладі падає з *"JavaFX runtime components are missing"*.

Завжди використовуйте `clean` — один раз, перед збиранням набору платформ, бо він очищує `target/dist/` для
всіх. Чому — див. [Усунення проблем збирання](#усунення-проблем-збирання).

### Пакування

Усе, що постачається, збирається в `target/dist/gaia-desktop-<version>-<platform>/`, і нічого більше, тож
каталог можна запакувати в zip або скопіювати цілком, не вибираючи артефакти з `target/` поряд із
`classes/`, `maven-status/` та рештою робочих файлів збирання. `${dist.dir}` називає його один раз; кожен
плагін, що записує артефакт, вказує на нього.

#### Одне збирання на платформу

Jar-файли JavaFX містять нативний код, тож кожен дистрибутив призначено для однієї платформи, заданої
властивістю `fx.platform` як класифікатор OpenJFX: `mac-aarch64`, `mac`, `win`, `linux` або `linux-aarch64`.
П'ять профілів `fx-*`, що активуються за ОС, задають її рівною платформі машини, яка збирає, — цього досить
для простого `mvn package` чи `mvn javafx:run`; `-Dfx.platform=…` має пріоритет над ними, щоб зібрати будь-яку
іншу, з будь-якої машини — jar-файли JavaFX лише завантажуються. `${dist.dir}` дорівнює
`target/dist/${fx.platform}`, тож збирання однієї платформи ніколи не перезаписує іншу.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

Це працює завдяки двом деталям pom, і обидві здаються зайвими:

- **Кожен модуль JavaFX — пряма залежність** — base, graphics, controls, media і web, — кожен із
  `<classifier>${fx.platform}</classifier>` і виключенням `org.openjfx:*`. Pom-файли OpenJFX вибирають свої
  транзитивні jar-файли за ОС *машини, яка збирає*, тож якщо дозволити graphics чи base прийти транзитивно,
  нативні бібліотеки Mac опиняться в збиранні для Windows поряд із бібліотеками Windows.
- **Властивість називається `fx.platform`, а не `javafx.platform`.** Якщо задати її ззовні, власна
  властивість OpenJFX перевизначається батьківським pom через саму себе; Maven відкидає такий pom як
  некоректний і мовчки відкидає платформні jar-файли, лишаючи збирання взагалі без JavaFX.

Обидва розклади пишуть один і той самий шлях, `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`,
і за одне збирання виконується рівно один із них. `${jar.phase}`, `assembly.skipAssembly` і `mdep.skip` не
дають обом на нього претендувати.

| | Типовий | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | ~290 KB — лише класи й ресурси цього модуля | ~50 MB — залежності розпаковано всередину |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 jar-файлів, поіменно перелічених у `Class-Path` маніфесту | — |
| Постачати | jar **і** `lib/` поряд із ним | один файл |
| Також у `dist/gaia-desktop-<version>-<platform>/` | `run.bat` (win) або `run.sh` (решта) | те саме |
| І | `readme.html` і `docs/` (кожна платформа) | те саме |

Кожен дистрибутив містить і посібники: `docs/`, скопійований зі збереженням структури, щоб посилання між
посібниками й перекладами й далі працювали, без інструментів перекладу (`check-i18n.py`,
`i18n-manifest.json`); і `readme.html` у корені — покажчик із посиланнями на кожен із них, із
`src/main/dist/readme.html`, де `@VERSION@` замінено версією з pom. Обидва записує крок antrun
`pick-launch-script`, який спершу видаляє `docs/`, щоб вилучений посібник не залишався. Посилання в readme
написано вручну — перейменованому посібнику чи перекладу, доданому в `docs/`, потрібен і свій рядок там.

`Class-Path` маніфесту і `lib/` — дві половини одного цілого: jar називає `lib/<artifact>-<version>.jar` для
кожної залежності часу виконання, а `copy-dependencies` заповнює `lib/` саме цими іменами. Саме це змушує
`java -jar` працювати.

#### Застосунок macOS і zip-архів дистрибутива

Одне виконання antrun, `mac-app-and-zip`, завершує фазу `package`. Тому плагін antrun оголошено **після**
плагінів jar і assembly — Maven виконує виконання фази в порядку оголошення плагінів, — тож jar за будь-якого
пакування вже існує, коли воно запускається. (Інше його виконання, `pick-launch-script`, міститься в
`prepare-package` і не зачеплене.)

Для `mac` і `mac-aarch64` воно спочатку будує `GAIA Desktop.app` у каталозі дистрибутива: `Info.plist` (з
`@VERSION@`, заміненим версією з pom), скрипт запуску `Contents/MacOS/gaia-desktop` (зроблений виконуваним)
і `gaia-desktop.icns`, усе з `src/main/macos/`, а потім **переміщує** `gaia-desktop.jar` і `lib/` до
`Contents/Java`, щоб пакет був самодостатнім. `run.sh` шукає там, коли поруч із ним немає jar. Скрипт запуску
знаходить Java за версією (`java_home -v 21+`, потім openjdk із Homebrew — запуски з Finder не бачать ні
`JAVA_HOME`, ні `PATH`), показує діалог через `osascript`, якщо її немає, робить `cd` у `~/.gaia-desktop`,
щоб відносний каталог `logs/` у logback був доступний для запису, і передає `-Xdock:name`/`-Xdock:icon`.
macOS пов'язує запущений `java` з пакетом (його ідентифікатор пакета й значок у Dock — від застосунку); у
рядку меню показано GAIA Desktop.

Потім для кожної платформи воно пакує каталог у `target/dist/gaia-desktop-<version>-<platform>.zip` у теку з
тією самою назвою за допомогою `<zip>` з Ant: `run.sh` і `Contents/MacOS/**` йдуть окремим набором файлів із
`filemode="755"`, інакше після розпакування вони не запускалися б. Zip **не прикріплюється**: він для
релізів на GitHub, а чотири платформи виходять із чотирьох збирань, які Maven Central — одне незмінне
завантаження на версію — ніколи не зміг би прийняти як один реліз.

`project.build.outputTimestamp` задається часом збирання. Інакше архіватори в maven-jar-plugin 3.5 і
maven-assembly-plugin 3.8 датують кожен запис 1 лютого 1980 року.

Значок застосунку малює `tools/icon/GaiaIcon.java` (не входить до збирання; у його заголовку описано кроки
`sips`/`iconutil`). Його результати зберігаються в репозиторії: `src/main/macos/gaia-desktop.icns` для пакета
і `src/main/resources/icons/gaia-desktop-{16..256}.png`, які `GaiaDesktopApp` встановлює як значок вікна
(Windows і Linux; macOS значки вікон ігнорує).

#### Скрипти запуску

`run.sh` і `run.bat` беруться з `src/main/scripts/` і копіюються до `dist/gaia-desktop-<version>-<platform>/`
без фільтрації — `run.sh` повний підстановок оболонки `${...}`, які фільтрація Maven могла б вільно
переписати. Потім крок antrun залишає лише той, що його запускає платформа, — `run.bat` для `win`, `run.sh`
для всіх інших — і ставить біт виконання на `run.sh`, бо `copy-resources` його не зберігає. Він вирішує за
розв'язаним значенням `${fx.platform}`, а не через профілі, тому що активація профілю не бачить значення,
заданого іншим профілем: збирання для Linux, зроблене у Windows, інакше отримало б скрипт хоста.

Вони **не покладаються на маніфест**. Кожен сам будує class path: `gaia-desktop.jar`, а за ним кожен `.jar` з
`lib/`, перелічені по одному, а не через символ підстановки `lib/*`, щоб шлях із пробілами залишався одним
записом, а підрахунок доданого був справжнім. Запуск із `-cp` — причина, чому вони явно називають
`tools.pantheum.gaia.desktop.Launcher`: `-cp` не читає `Main-Class` з маніфесту. Проте його `Class-Path` він
**усе ж** враховує — jar у `-cp` приносить jar-файли, названі в його маніфесті, і їх шукають одразу після
нього, — тож кожен jar з `lib/` завантажується, перелічено його у скрипті чи ні, а вилучення одного з class
path скрипту не тримає його поза JVM. Скрипти все одно їх перелічують, щоб jar із застарілим, відредагованим
вручну чи неповним маніфестом усе ж запускався. Один
і той самий скрипт обслуговує обидва пакування: jar `-Pfat` не має `lib/` для додавання й не потребує його,
— тому й порожній `lib/` є зауваженням, а не помилкою.

#### Нативні бібліотеки Zebra

Збирання не постачає нічого від Zebra — ні DLL, ні jar-файлів служб. У Windows вони беруться зі Scanner SDK
від Zebra, встановленого на комп'ютері: `run.bat` додає його jar-файли служб `Jpos*.jar` і `bin\` до class
path, а `bin\` — до `PATH`, де `System.loadLibrary` знаходить `CSJPOSScanner.dll` / `CSJPOSScanner64.dll`
(`java.library.path` типово дорівнює `PATH`). API JavaPOS і його завантажувач конфігурації завжди беруться з
`lib\javapos-*.jar`, з SDK чи без нього.

**`run.bat` ніколи не додає власний jar JavaPOS з SDK**, `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`.
Колись він це робив, оминаючи `lib\javapos-*.jar`, щоб уникнути двох копій API, — але `Class-Path`
маніфесту однаково їх завантажував (див. вище), тож JVM отримувала обидві: класи завантажувача 4.x з `lib\`, а
поруч — `jpos/res/jpos.properties` і `jcl.xsd` з `javaPOS114.jar`. Файл властивостей змушує
[`JposConfig`](#інтеграція-сканера) відступити, а цей `jcl.xsd` приймає версії JavaPOS лише до 1.10, тож
кожен запис у `jpos.xml` (1.12–1.14) не проходив перевірку, реєстр лишався порожнім, і кожне під'єднання
завершувалося помилкою 109, навіть не дійшовши до сканера. Для цього досить узагалі мати цей jar у class path,
навіть позаду jar-файлів з `lib\`. Jar-файли служб Zebra без змін працюють на API 1.14 з `lib\` — відкриття,
захоплення й сканування так перевірено на справжньому сканері. Бібліотеки DLL, вручну покладені поруч із
`run.bat`, і далі враховуються: тоді скрипт задає `-Djava.library.path=<dist>;%PATH%`, дописуючи `PATH`, бо
ця властивість повністю замінює типовий шлях пошуку.

`mvn javafx:run` нічого з цього не робить, тож для захоплення сканера під час запуску з середовища розробки у
Windows треба іншими способами покласти jar-файли SDK у class path, а його `bin\` — у `PATH`; для цього
запускайте з `dist/`.

Окрім class path, вони покривають те, чого не робить `java -jar`: визначають власний каталог, щоб працювати
з будь-якого робочого каталогу, віддають перевагу `JAVA_HOME` перед `PATH` і відхиляють JVM, старішу за 11,
реченням, що називає спосіб виправлення, замість `UnsupportedClassVersionError`. `GAIA_DESKTOP_OPTS` передає
параметри JVM. `run.bat` використовує `java.exe`, а не `javaw.exe`, щоб консоль лишалася відкритою — Windows
є єдиною платформою, де працює сканер, і його стан та помилки JavaPOS виводяться туди.

`run.bat` також вибирає свої Java, JavaFX і служби Zebra за тим, що знайде, — вкладений `jdk*\`,
`javafx-sdk*\lib\` у module path, Scanner SDK від Zebra в `ZEBRA_HOME`, — виключаючи з class path копії
JavaFX з `lib\`, коли використовує копії з SDK, і передає SAX-парсер JDK, проксі та сховище сертифікатів
Windows, а також `--enable-native-access` на Java 17 і новіших. Таблиця — у розділі README
[What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows). Зберігайте у файлі закінчення
рядків CRLF: `cmd.exe` може пропустити `call :label` у пакетному файлі лише з LF. `run.sh` теж передає
`--enable-native-access=ALL-UNNAMED` — JavaFX завантажує власні нативні бібліотеки з `lib/`, а з JavaFX у
class path саме `ALL-UNNAMED` є модулем, який це покриває, — і пропускає його, як і `run.bat`, лише тоді, коли
версію Java прочитати не вдається.

Будь-який із розкладів містить нативні бібліотеки JavaFX **однієї платформи**, `${fx.platform}`, тож жоден
не переноситься між ОС чи архітектурами. Збирайте по одному разу на цільову платформу — див.
[Одне збирання на платформу](#одне-збирання-на-платформу).

> **Eclipse.** Виконання `copy-dependencies` містить інструкцію `<?m2e ignore?>`. m2e розв'язує відкритий
> проєкт робочої області в його теку `target/classes`, а не в jar, а `copy-dependencies` відмовляється
> копіювати незапакований артефакт (MDEP-187), через що автоматичне збирання падало б щоразу, коли проєкт
> `gaia` відкрито поруч із цим. Як наслідок, збирання лише в IDE не заповнює
> `target/dist/gaia-desktop-<version>-<platform>/lib/`; виконайте `mvn package`, перш ніж використовувати
> сам jar.

| `desktop.scanner` | `ScannerService` (JavaPOS), `ScannerListener`, `Symbologies` |
| `desktop.html` | `GaiaDesktopReport` — генератор звіту, без JavaFX і з модульними тестами без інструментарію |
| `desktop.i18n` | `UiStrings` — каталог підписів |
| `desktop.store` | `AppPaths`, `OptionsStore`, `CaptureStore` |

### Лійка захоплення

Будь-яке введення — набране, вставлене, відкрите з файлу, відскановане чи побудоване — потрапляє до
аналізатора через один метод, `MainView.capture(String, ScanSource, String)`.

Це єдине проєктне рішення, навколо якого побудовано застосунок. Побудованому рядку не потрібні ні власний
звіт, ні власна історія, ні власний шлях експорту, бо після лійки побудований рядок неможливо відрізнити від
відсканованого. Усе нове, що створює введення, має проходити через неї, а не в обхід.

### Потоки

| Потік | Виконує |
|---|---|
| Потік застосунку JavaFX | Увесь аналіз, малювання й інтерфейс. Коли таблиці AI прогріто, аналіз триває менше мілісекунди, тож робочий потік йому не потрібен |
| `gaia-scanner` | Кожен виклик сканера — відкриття, захоплення, увімкнення, вимкнення, звільнення, закриття. Один довговічний потік, що належить `ScannerService`; див. [Інтеграція сканера](#інтеграція-сканера) |
| Потік подій JavaPOS | Зворотні виклики `ScannerService`. `MainView.FxScannerListener` переносить кожен із них через `Platform.runLater` |
| Фоновий | Очікування `connect()` / `disconnect()` сканера (захоплення може тривати до 5 с), відновлення збереженої історії під час запуску — що водночас прогріває аналізатор — і перевірка оновлень (`gaia-update-check`, один запит до GitHub, результат повертається через `Platform.runLater`) |

**Ніколи не змінюйте вибір елемента керування і не знищуйте елемент керування зсередини його власної події
вибору.** Три окремі збої цього застосунку виникли саме так: скидання засобу вибору AI всередині власного
`clearAndSelect` спливного вікна (`IndexOutOfBoundsException` з `ListViewBehavior`) і перебудова панелі, якій
належить список вибору мови, з власного обробника цього списку. Обидва тепер відкладаються через
`Platform.runLater`, а причини записано в обох місцях виклику.

### Перебудувати чи переписати підписи

Зміна мови **перебудовує** обрамлення з каталогу — меню, панель інструментів, панель параметрів, — що
безпечно, бо ніщо з цього не зберігає стану: `OptionsPane` — двобічне подання `ParseOptions`, тож значення
живуть у моделі, і свіжа панель одразу їх підхоплює.

Елементи керування, що містять **дані користувача**, є полями й натомість отримують нові підписи на місці:
`BuilderPane.retext(UiStrings)` зберігає рядки AI, поля Digital Link і виділення. Перебудова відкинула б
незавершену роботу — що колись і сталося.

## Токен {GS}

`TextField` JavaFX мовчки відкидає кожен символ нижче `0x20` (`TextInputControl.filterInput`). Він не
«показує його дивно» — він його видаляє. Це стосується введення, вставлення, `setText` і `insertText`, тож
`setText("01…" + GS + "10LOT")` дає `"01…10LOT"`: рядок елементів, зміст якого непомітно змінився, бо AI
змінної довжини тепер поглинає те, що йшло за ним.

`desktop.parse.GsToken` — це вся відповідь. Роздільник проходить інтерфейсом як буквальний текст `{GS}` і на
шляху до аналізатора знову стає `0x1D`. Токен вигадано не тут — саме так `0x1D` відображає
`ASCIIRevealerUtils.printable` з ядра, тож значення, скопійоване зі звіту, вставляється назад у поле введення
без змін.

Фільтр `TextFormatter` на полі введення перехоплює будь-який шлях, яким може прийти текст, — набір, ⌘V,
контекстне меню, перетягування, `setText`, — тому перетворення живе там, а не в кожному обробнику.

Шлях сканера ніколи не проходить через `GsToken`: скани доходять до аналізатора у вигляді байтів.

## Інтеграція сканера

`ScannerService` володіє елементом керування `Scanner` з JavaPOS: відкриття → захоплення → увімкнення, з
повторним зведенням події даних після кожного скану. Логічні імена пристроїв беруться з
`src/main/resources/jpos.xml`.

**Кожен виклик пристрою виконується в одному потоці, `gaia-scanner`, що живе стільки ж, скільки служба**, —
ніколи в потоці FX і ніколи в потоці, який завершується після виклику. Служба Zebra звертається до сканера
через JNI поверх COM API CoreScanner, а COM прив'язує те, що налаштовує, до апартаменту потоку, який
викликає: відкрийте в потоці, що потім завершиться, — і сканер буде захоплено, але він замовкне; закрийте в
іншому потоці — і буде деініціалізовано не той апартамент. Закриття в потоці FX — найгірший випадок, бо
JavaFX викликає там `OleInitialize` і реєструє в ньому ціль перетягування кожного вікна — `CoUninitialize` у
ньому ламає перетягування в усьому застосунку. Це JavaFX у Windows, а не якась конкретна версія JavaFX.
`connect()` і `disconnect()` передають роботу в цей потік і чекають, тож `MainView` викликає обидва з
короткочасного фонового потоку.

Два правила не дають несправному пристрою заклинити з'єднання. **Розбирання ніколи не припиняється
передчасно:** `closeQuietly` вимикає, звільняє й закриває окремими кроками, звільняє лише за утримуваного
захоплення і завжди намагається виконати `close()` — після невдалого захоплення `release()` викидає «not
claimed», і коли кроки ділили один `try`, це пропускало закриття й лишало пристрій відкритим у службі Zebra.
**Подію даних повторно зводять у `finally`:** JavaPOS вимикає її після кожної події, тож читання чи обробник,
що викинув виняток, однаково має її звести, інакше сканер мовчатиме до перепідключення.
`ScannerLifecycleTest` перевіряє обидва правила на сценарному `jpos.Scanner`.

**`JposConfig` спрямовує JavaPOS на вкладений `jpos.xml`** перед першим відкриттям. З jar-файлами JavaPOS з
Maven (`javapos-config-loader` 4.x) і без `jpos/res/jpos.properties` у class path будь-яке відкриття інакше
завершується помилкою *"Service does not exist in loaded JCL registry"* (помилка 109) з трьох окремих причин:
диспетчер служб відкочується до `SimpleRegPopulator`, який читає серіалізований `jpos.cfg` і ніколи —
`jpos.xml`; завантажувач XML шукає `jpos.xml` лише в робочому каталозі, а не в jar; а Xerces 2.12.2 у `lib/`
відхиляє JAXP-властивість `accessExternalDTD`, яку задає завантажувач. `JposConfig` задає
`jpos.config.regPopulatorClass` (`JavaxRegPopulator`), `jpos.config.populatorFileURL` (власний
`jar:file:…!/jpos.xml` з jar) і `javax.xml.parsers.SAXParserFactory` (з JDK) як системні властивості —
ніколи вже задану, тож `-Djpos.config.populatorFileURL=file:…` і далі вибирає інший `jpos.xml`, — і не задає
нічого, якщо в class path є `jpos.properties` або немає завантажувача 4.x. `javaPOS114.jar` із Zebra SDK —
саме такий випадок і просто ламає реєстр, тому `run.bat` тримає його поза class path — див.
[Нативні бібліотеки Zebra](#нативні-бібліотеки-zebra). `JposConfigTest` наскрізно перевіряє, що реєстр тоді
містить сканери з файлу.

**Засіб вибору пристрою генерується з цього реєстру**, а не зберігається списком у коді:
`ScannerService.logicalNames()` читає завантажені записи в потоці `gaia-scanner` і залишає ті, категорія
пристрою яких — `Scanner` (два записи ваг у `jpos.xml` лишаються поза ним), у порядку `pickerOrder`: спершу
`ZebraAllScanners`, якщо файл його визначає, решта за абеткою (реєстр не зберігає порядку файлу). Файл без
нього його не отримує; якщо нічого не завантажено, пропонується лише типове значення, тож засіб вибору ніколи
не буває порожнім. `MainView` одразу показує типове значення й доповнює список із фонового потоку, зберігаючи
збережений вибір. Отже, сканер, доданий до `jpos.xml`, — або цілий файл, указаний через
`-Djpos.config.populatorFileURL`, — з'являється в засобі вибору без змін коду, а `JposConfigTest` звіряє засіб
вибору з незалежним читанням вкладеного файлу. Служби, названі в цих записах, — класи Zebra
(`com.zebra.jpos.service.scanner.*Factory`), які однаково мають бути в class path — зі Scanner SDK через
`run.bat` або як jar-файли служб Zebra, покладені в `lib\`.

Дані сканування декодуються як **ISO-8859-1**, щоб кожен байт відображався 1:1 і збереглися і префікс AIM
Code ID, і кожен `0x1D`; звіти записуються в UTF-8.

Ніщо в службі не складає текст для користувача. Події виходять як константи `ScannerListener.Event` разом зі
змінними значеннями, а `MainView` підставляє формулювання з каталогу — інакше рядок стану був би англійською
в застосунку, перекладеному 35 мовами. Виняток — рядки журналу, вони лишаються англійською.

### Платформне обмеження

`ScannerService.isSupportedPlatform()` — одна перевірка `os.name`, і `MainView` звертається до неї, перш ніж
будувати будь-який елемент керування сканером: у macOS і Linux немає ні перемикача, ні засобу вибору
пристрою, ні меню «Сканер» (а отже, і <kbd>⌘K</kbd>), ні підпису стану. Вони не приховані — вони ніколи не
створюються.

Zebra постачає свої служби JavaPOS лише для Windows, а в інших системах ніщо не падає рано: jar-файли
розв'язуються, елемент керування створюється, і лише `open()` зрештою падає через відсутній нативний шар —
кілька секунд і один діалог по тому.

Правило стосується *служб*, а не JavaPOS. Постачальник, який випустив би кросплатформну службу, працював би
тут, і розширення правила — це зміна лише в `supportsJavaPos(String)`, методі з видимістю в межах пакета, який
тестують на рядках `os.name`, тож обидві відповіді перевірено на будь-якій машині, де йде збирання.

### Символіки

`Symbologies` зіставляє всі **78** типів даних сканування JavaPOS `SCAN_SDT_*` з іменами для показу, а також
із `DataCarrierType` ядра там, де два словники збігаються. JavaPOS — детальніший із двох: він розрізняє UPC-A
і EAN-13, а також простий Data Matrix і GS1 DataMatrix, тоді як AIM об'єднує ціле сімейство під одним
символом коду.

Тип поза таблицею однаково отримує придатне ім'я, знайдене відображенням (reflection) по `ScannerConst`,
бо служби постачальників справді повідомляють значення поза списком специфікації. Тест обходить
`ScannerConst` і падає, якщо в якогось оголошеного типу немає імені, — це заодно ловить константи, які
додасть майбутня версія JavaPOS.

Деякі зіставлення носіїв навмисно залишено `UNKNOWN`, а не вгадано: простий 2 з 5 (AIM розрізняє `]R`/`]S`
за кількістю стартових/стопових штрихів, про які JavaPOS не повідомляє), поштові коди з чотирма станами і
TLC-39.

## Локалізація

Підписи зберігаються в одному файлі властивостей на мову в `src/main/resources/i18n/ui_<CODE>.properties`, з
тими самими кодами, що й каталоги помилок ядра (`EN`, `FR`, `PCM`, …). Існують усі 35, і всі 35 мають
однаковий набір ключів. Файли читаються як **UTF-8**, а не як ISO-8859-1, яку припускає `Properties`, щоб
переклади зберігалися в читабельному вигляді, а не як екрановані послідовності `\uXXXX`.

**Відкат виконується за ключем, а не за файлом** — завдяки цьому частково перекладена мова корисна з тієї
миті, як з'являється її перший ключ. Англійська — це контракт: кожен ключ мусить у ній існувати.

| Шар | Ключі | Охоплення |
|---|---|---|
| Спільна лексика звіту | 31 | усі 35 мов |
| Обрамлення застосунку — меню, кнопки, конструктор, параметри, рядок стану, макет звіту, стан сканера, тексти діалогів | 114 | усі 35 мов |

Шість спільних термінів (`generated`, `status`, `dlRole`, `interpretations`, `message`, `level`) звіт цього
застосунку не використовує.
Їх збережено навмисно; про це сказано в заголовку файлу.

### Аргумент `--language`

`GaiaDesktopApp.languageOverride()` читає `--language=…` через власний `getParameters().getNamed()` JavaFX,
розв'язує його за допомогою `Languages.fromArgument` — код каталогу, ім'я переліку або тег BCP 47, без
урахування регістру — і передає в `MainView`.

**Перевизначення діє на запуск, а не на файл.** `MainView` зберігає завантажену мову в `savedLanguage` і
записує назад *її*, доки `languageChosenInSession` не покаже, що користувач сам вибрав мову; тоді його вибір
зберігається як зазвичай. У цьому поділі й полягає весь задум: профіль кіоску чи демонстраційний ярлик може
відкритися іспанською, не переписуючи того, з чим завтра відкриється власник комп'ютера, а справжній вибір,
зроблений на панелі параметрів, і далі зберігається.

Значення, що не вказує на жоден каталог, записується в журнал разом із допустимими кодами й ігнорується.
Відмова запускатися через друкарську помилку в ярлику була б гіршим збоєм, і з тієї ж причини
`Languages.fromArgument` повертає `null`, а не викидає виняток.

### Додавання мови

Змін коду не потрібно.

1. Відредагуйте `ui_<CODE>.properties` — кожна мова вже має файл.
2. Перекладіть значення. Залиште на місці заповнювачі `{0}` / `{1}`.
3. Зберіть. Два тести стежать за контрактом: один падає, якщо код запитує ключ, якого немає в англійській,
   інший — якщо набір ключів якогось каталогу розходиться з англійським.

Перший тест шукає літерали ключів у **вихідному коді**, а не застосовує відображення до класів, бо ключі
існують лише як рядкові літерали в місцях виклику. Тому нове повідомлення треба будувати з ключем,
записаним просто у виклику, — `strings.format("st.scannerError", …)`, — а не шукати через змінну, інакше
тест його не побачить.

### Що навмисно не перекладається

- короткі назви полів моноширинним шрифтом поряд із необробленими значеннями — `format`, `position`,
  `length`, `raw` і `part` картки елемента, `AI`, `sep`, `pos` і `len` стрічки та чотири клітинки, що
  вказують місце помилки (`AI`, `position`, `level`, `stage`), значення яких так чи так — неперекладені
  імена переліків;
- назви прикладів введення, що позначають конструкції GS1, і назви символік, які є власними назвами;
- абзац із рекомендацією щодо виправлення для `GE-C084` — нормативний текст, де переклад наполовину гірший
  за англійську;
- захисна перевірка `ElementBuilder` на невідомі AI, недосяжна з інтерфейсу: редактор сам перевіряє невідомі
  AI і повідомляє про них із каталогу;
- рядки журналу.

Лишається одна прогалина: `ScanSource.label()` видає `manual` / `scanner` / `file` / `built` англійською в
рядок історії та в шапку звіту. Щоб її закрити, потрібно більше, ніж ключ: `HistoryCell` не має
`UiStrings`, а фабрику клітинок списку встановлюють один раз, тож під час зміни мови довелося б оновлювати й
клітинки.

## Формати збереженого стану

Два файли в `~/.gaia-desktop/`, що зберігаються окремо, бо змінюються в різному ритмі: пошкоджений чи
відредагований вручну журнал захоплень не повинен коштувати користувачеві його налаштувань. Каталог можна
перевизначити через `-Dgaia.desktop.home=…` — так тести тримаються поза справжнім домашнім каталогом.

**`options.properties`** — записується, коли змінюється параметр, і під час виходу.

| Ключ | Значення |
|---|---|
| `parse.mode`, `parse.language` | Глибина конвеєра й мова повідомлень |
| `date.endian`, `date.separator`, `date.month`, `date.year` | Відображення дат |
| `check.skipRequires`, `check.skipExcludes` | Винятки зі структурних перевірок |
| `ui.theme` | `LIGHT` або `DARK` |
| `ui.optionsPane` | Панель відкрито? |
| `ui.scannerDevice` | Останнє логічне ім'я JavaPOS |
| `ui.mode` | `PARSE`, `BUILD` або `COMBINE` |
| `update.check` | Чи виконується щоденна перевірка оновлень (типово `true`) |
| `update.lastCheck` | Коли вона виконувалася востаннє, ISO-8601; відсутність чи нечитабельне значення означає, що перевірка потрібна |
| `update.skipVersion` | Реліз, для якого користувач вибрав *Пропустити цю версію*; автоматично більше не пропонується |

Відсутній чи пошкоджений файл ніколи не фатальний: кожне значення відкочується окремо, тож один поганий рядок
коштує лише цього рядка. Під час першого запуску, коли файлу немає зовсім, параметри заповнює `SystemDefaults`
з регіональних налаштувань комп'ютера, а не з вбудованих типових значень GAIA: короткий шаблон дати для
мовного стандарту дає порядок складників, роздільник і те, чи скорочуються місяць і рік.

Ніколи не передавайте `Properties.setProperty` значення null: він викидає виняток, а `persistOptions()`
виконується з обробників подій інтерфейсу, де виняток іде в потік FX. Це справжній збій, який у цього
застосунку вже був.

**`captures.tsv`** — записується, коли змінюється історія, і під час виходу. Найновіші першими, не більше
**500** записів.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

Зберігається лише те, що неможливо обчислити заново. `ParseResult` **не** серіалізується — його відновлюють
повторним аналізом введення під час завантаження, тож відновлена історія відображає параметри, чинні
*зараз*. Введення зазвичай містить FNC1 і все, що ще видає сканер, тому поле введення екранується (`\\`,
`\t`, `\n`, `\r` і `\xNN` для всього іншого нижче `0x20`), а файл читається й записується як ISO-8859-1,
байт у байт.

Файли, записані до того, як почали зберігати дату, містять лише час; вони й далі завантажуються, із
сьогоднішньою датою, бо справжню дату так і не записали.

## Тестування

```bash
(cd gaia-desktop && mvn test)
```

198 тестів, навмисно **незалежних від інструментарію JavaFX**, що робить їх швидкими й такими, що не
потребують дисплея. Вони покривають генератор звіту, логіку побудови й пошук AI, перетворення `{GS}`, типові
значення, виведені з мовного стандарту, обидва сховища (включно з проходженням туди й назад із `0x1D` і
навмисно пошкодженими файлами), таблицю символік, платформне правило сканера, заглушку версії та каталоги.

Три варто знати, бо вони захищають контракти, а не функції:

| Тест | Падає, коли |
|---|---|
| `CatalogueCoverageTest` | Код запитує ключ, якого немає в `ui_EN.properties`, або будь-який із 35 файлів розходиться з англійським набором ключів |
| `SymbologiesTest` | Якась оголошена в JavaPOS константа `SCAN_SDT_*` не має імені для показу — включно з тією, яку додасть оновлення JavaPOS |
| `ScannerServiceTest` | Платформне правило змінює відповідь для Windows або для будь-чого іншого |

`UiStrings` навмисно поблажливий під час виконання — невідомий ключ показується як сам ключ, а не викидає
виняток посеред розкладки, — і саме тому тест каталогу мусить існувати.

**Не покрито:** усе, що потребує робочого інструментарію, — поведінку фокуса, перемикання режиму,
редагування таблиць, зміну мови й обидва збої, описані в розділі [Потоки](#потоки). Це перевірено керуванням
справжнім вікном, але регресія в них не провалила б збирання. Додавання TestFX або Monocle закрило б цю
прогалину.

## Усунення проблем збирання

| Симптом | Причина й рішення |
|---|---|
| `package tools.pantheum.gaia does not exist` | Ядро не встановлено. `(cd gaia && mvn install -DskipTests)` |
| *"JavaFX runtime components are missing"* | `Main-Class` jar-файлу має бути `Launcher`, а не `GaiaDesktopApp` |
| *"Unsupported JavaFX configuration: classes were loaded from unnamed module"* під час запуску | Очікувано й нешкідливо — JavaFX зазначає, що він у class path. Саме тому існує `Launcher` |
| Jar не запускається, `NoClassDefFoundError` | Типовий jar містить лише класи цього модуля; поряд має лежати `dist/lib/`. Використовуйте `-Pfat`, щоб отримати один самодостатній файл |
| `Artifact has not been packaged yet … MDEP-187` в Eclipse | Розв'язання робочої області в m2e. Див. примітку в розділі [Пакування](#пакування) |
| У збиранні з'являються дублікати файлів `… 2.properties` | Проєкт лежить у теці, що синхронізується з iCloud, і синхронізація посеред збирання створила конфліктні копії. Завжди `mvn clean package`; краще виключіть `target/` із синхронізації |
| Пункт меню показує ключ на кшталт `act.hri` | Цього ключа немає в `ui_EN.properties`. Збирання мало це виявити — див. [Тестування](#тестування) |

## Відомі обмеження та відкрита робота

- **Немає тестів інтерфейсу без дисплея.** Див. [Тестування](#тестування).
- **Платформно залежні артефакти.** Обидва пакування містять нативні бібліотеки JavaFX однієї платформи;
  збирайте по одному на цільову платформу з `-Dfx.platform` (будь-яка машина може зібрати всі). Жодне не
  містить середовища виконання Java — для цього потрібен `jpackage`, який збирає лише для тієї ОС, на якій
  працює.
- **Введення зі сканера лише у Windows.** Див. [Платформне обмеження](#платформне-обмеження).
- **`ScanSource.label()` не локалізовано.** Див. [Що навмисно не
  перекладається](#що-навмисно-не-перекладається).
- **`UiState.mode` — це `String`** (`"PARSE"` / `"BUILD"`), тоді як `Theme` поруч — перелік, тож літерал
  трапляється в кількох місцях. Перелік позбавив би від них.
- **Ціль Digital Link — лише домен і префікс шляху.** `BuilderDigitalLinkConfig` підтримує також додаткові
  параметри запиту й фрагмент; редактор їх не надає.
- **Взаємовиключні пари AI (`GE-S006`) не позначаються в редакторі** так, як невідомі й повторювані AI, —
  побудова просто завершується помилкою.
- **Каталог помилок ядра подвоює лапки** (`value ''09506000134350''`), що дослівно з'являється в помилках
  побудови й у звіті. Схоже на екранування лапок у `MessageFormat`, яке не знімається; виправлення стосується
  ядра.
