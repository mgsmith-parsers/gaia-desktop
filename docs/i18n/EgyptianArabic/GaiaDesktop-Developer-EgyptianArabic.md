## الموديول في لمحة

```
tools.pantheum:gaia-desktop:1.0.0   Java 21 · JavaFX 21
        └── depends on tools.pantheum:gaia:1.1.0
```

ده عميل للمكتبة الأساسية وبس. ما فيهوش **أي معرفة بـ GS1**: كل تعريف AI، وكل قاعدة تحقق، وكل رسالة غلط، وكل
وصف مترجم جاي من [`GaiaParser`](../../../../gaia/docs/GaiaParser.md) و
[`GaiaBuilder`](../../../../gaia/docs/GaiaBuilder.md). وبالذات قايمة الـ AI عمرها ما بتتنسخ جوّه الموديول ده — منتقي
المُنشئ بيقرا سجل النواة نفسه، فمش ممكن يعرض AI المُنشئ هيرفضه.

**نقط الدخول:** `tools.pantheum.gaia.desktop.GaiaDesktopApp` (الـ `Application` بتاع JavaFX) و
`tools.pantheum.gaia.desktop.Launcher` (الـ `Main-Class` بتاع الـ jar المتغلّف).

الموديول ده ورقة طرفية: مفيش حاجة معتمدة عليه، وهو مش معتمد على أي موديول تاني بعده.

## البناء والتشغيل

- **Java 21** للتشغيل، وJDK 21 أو أحدث للبناء — الموديول بيتعمله compile بـ `release=21`. وJavaFX 21 هو خط الـ LTS
  اللي يناسبه. الـ jar بتاع النواة لسه bytecode بتاع Java 11 وبيشتغل على 21 من غير أي تغيير.
- **Maven** على الـ `PATH`. مفيش wrapper في الريبو ده.
- **نزّل النواة الأول.** الموديول ده بيجيب `gaia:1.1.0` من `~/.m2`؛ وjar نواة قديم أو مش موجود هو السبب المعتاد
  لـ `package tools.pantheum.gaia does not exist`.

```bash
(cd gaia && mvn -q install -DskipTests)      # publish the core
(cd gaia-desktop && mvn javafx:run)          # run from source
(cd gaia-desktop && mvn clean package)       # target/dist/gaia-desktop-<version>-<platform>/ — jar (~290 KB), lib/, run.sh (run.bat on win)
(cd gaia-desktop && mvn clean -Pfat package) # one self-contained jar, ~50 MB
(cd gaia-desktop && mvn package -Dfx.platform=win)   # another platform; see Packaging
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar
java -jar gaia-desktop/target/dist/gaia-desktop-1.0.0-mac-aarch64/gaia-desktop.jar --language=FR
```

`--language` هو الوسيط الوحيد في سطر الأوامر، والطريقة الوحيدة اللي تأثر بيها على بداية التشغيل غير
`-Dgaia.desktop.home=…`، اللي بيودّي البروفايل كله مكان تاني.

`mvn javafx:run` هو طريق التطوير: الـ plugin بيحط JavaFX على **مسار الموديولات**، فمجموعة الأدوات بتبدأ كموديول ليه
اسم وتقدر تشغّل `GaiaDesktopApp` على طول. الـ jar المتغلّف ما يقدرش يعمل كده — كل حاجة فيه على مسار الكلاسات —
وعشان كده الـ `Main-Class` بتاعه هو الوسيط `Launcher`. لو حطيت كلاس فرعي من `Application` في `Main-Class` في
الترتيب ده هيقع برسالة *"JavaFX runtime components are missing"*.

استعمل `clean` دايمًا — مرة واحدة قبل ما تبني مجموعة منصات، عشان بيفضّي `target/dist/` منهم كلهم. بُص على
[حل مشاكل البناء](#حل-مشاكل-البناء) عشان تعرف ليه.

### التغليف

كل حاجة تتشحن بتتجمع تحت `target/dist/gaia-desktop-<version>-<platform>/` ومفيش حاجة غيرها، عشان تقدر تعمل zip للفولدر
أو تنسخه حتة واحدة من غير ما تنقّي المخرجات من `target/` جنب `classes/` و`maven-status/` وباقي الملفات المؤقتة بتاعة
البناء. `${dist.dir}` بيسمّيه مرة واحدة؛ وكل plugin بيكتب مخرَج بيشاور عليه.

#### بناء لكل منصة

ملفات الـ jar بتاعة JavaFX فيها كود أصلي، فكل توزيعة بتبقى لمنصة واحدة، والخاصية `fx.platform` هي اللي بتسمّيها كمصنِّف
OpenJFX: `mac-aarch64` أو `mac` أو `win` أو `linux` أو `linux-aarch64`. فيه خمس بروفايلات `fx-*` بتشتغل حسب نظام
التشغيل وبتظبطها على منصة الجهاز اللي بيبني، وده كل اللي `mvn package` أو `mvn javafx:run` العادي محتاجه؛ و
`-Dfx.platform=…` بيغلبهم عشان تبني أي منصة تانية من أي جهاز — ملفات jar بتاعة JavaFX مجرد تنزيلات. و
`${dist.dir}` هو `target/dist/${fx.platform}`، فبناء منصة عمره ما يكتب فوق بناء منصة تانية.

```bash
(cd gaia-desktop && mvn -q clean package)    # this machine's platform, with the tests
for p in win linux mac mac-aarch64; do (cd gaia-desktop && mvn -q package -DskipTests -Dfx.platform=$p); done
```

فيه تفصيلتين في الـ pom هما اللي مشغّلين الحكاية دي، والاتنين شكلهم ممكن يتشالوا:

- **كل موديول من موديولات JavaFX تبعية مباشرة** — base وgraphics وcontrols وmedia وweb — كل واحد بـ
  `<classifier>${fx.platform}</classifier>` واستبعاد `org.openjfx:*`. ملفات pom بتاعة OpenJFX بتختار ملفات jar
  المتعدية حسب نظام تشغيل *الجهاز اللي بيبني*، فلو سبت graphics أو base ييجوا بشكل متعدي، المكتبات الأصلية بتاعة Mac
  هتدخل في بناء Windows جنب بتوع Windows.
- **الخاصية اسمها `fx.platform` مش `javafx.platform`.** لو ظبطت خاصية OpenJFX نفسها من برّه، الـ pom الأب بتاعها
  بيعيد تعريفها بنفسها؛ فـ Maven بيرفض الـ pom ده على إنه مش صالح وبيشيل ملفات jar بتاعة المنصة من غير ما يقول، ويفضل
  بناء مافيهوش JavaFX خالص.

الترتيبين بيكتبوا نفس المسار، `target/dist/gaia-desktop-<version>-<platform>/gaia-desktop.jar`، وواحد بس منهم بيشتغل في
كل بناء. و`${jar.phase}` و`assembly.skipAssembly` و`mdep.skip` هما اللي بيمنعوا الاتنين يطالبوا بيه مع بعض.

| | الافتراضي | `-Pfat` |
|---|---|---|
| `gaia-desktop.jar` | حوالي 290 KB — كلاسات وموارد الموديول ده بس | حوالي 50 MB — التبعيات مفكوكة جوّاه |
| `dist/gaia-desktop-<version>-<platform>/lib/` | 17 ملف jar، متسمّيين واحد واحد في `Class-Path` بتاع المانيفست | — |
| اللي بيتشحن | الـ jar **و** `lib/` اللي جنبه | ملف واحد |
| وكمان في `dist/gaia-desktop-<version>-<platform>/` | `run.bat` (win) أو `run.sh` (الباقي) | نفس الحاجة |
| و | `readme.html` و`docs/` (كل المنصات) | نفس الحاجة |

كل توزيعة فيها الأدلة كمان: `docs/` بيتنسخ بترتيبه زي ما هو، عشان الروابط بين الأدلة والترجمات تفضل شغالة، من غير
أدوات الترجمة (`check-i18n.py` و`i18n-manifest.json`)؛ و`readme.html` في الجذر، وده فهرس بيربط بكل
واحد منهم، جاي من `src/main/dist/readme.html` و`@VERSION@` فيه بيتغير لإصدار الـ pom. الاتنين بيكتبهم خطوة antrun
اسمها `pick-launch-script`، وهي بتمسح `docs/` الأول عشان أي دليل اتشال ما يفضلش قاعد. روابط الـ readme مكتوبة بالإيد
— لو غيّرت اسم دليل أو ضفت ترجمة تحت `docs/` لازم تضيف السطر بتاعها هناك كمان.

`Class-Path` بتاع المانيفست و`lib/` نصّين لحاجة واحدة: الـ jar بيسمّي `lib/<artifact>-<version>.jar` لكل تبعية وقت
التشغيل، و`copy-dependencies` بيملا `lib/` بنفس الأسامي دي بالظبط. ده اللي بيخلّي `java -jar` يشتغل.

#### تطبيق macOS وملف zip للتوزيع

تنفيذ antrun واحد، `mac-app-and-zip`، هو اللي بيقفل مرحلة `package`. وعشان كده plugin الـ antrun متعرّف **بعد**
plugins الـ jar والـ assembly — Maven بيشغّل تنفيذات المرحلة الواحدة بترتيب تعريف الـ plugins — فالـ jar بيبقى موجود،
في أي تغليف من الاتنين، لما ده يشتغل. (التنفيذ التاني بتاعه، `pick-launch-script`، في `prepare-package` ومش بيتأثر.)

لـ `mac` و`mac-aarch64` بيبني الأول `GAIA Desktop.app` في فولدر التوزيع: `Info.plist` (و`@VERSION@` فيه بيتغير
لإصدار الـ pom)، والمشغّل `Contents/MacOS/gaia-desktop` (بعد ما يبقى قابل للتنفيذ)، و`gaia-desktop.icns`، كلهم من
`src/main/macos/`، وبعدين **بينقل** `gaia-desktop.jar` و`lib/` لـ `Contents/Java`، عشان الحزمة تقف لوحدها. و
`run.sh` بيدوّر هناك لما مايلاقيش jar جنبه. المشغّل بيدوّر على Java حسب الإصدار (`java_home -v 21+`، وبعدين openjdk
بتاع Homebrew — التشغيل من Finder ما بيشوفش `JAVA_HOME` ولا `PATH`)، ولو مالقاش حاجة بيطلّع dialog عن طريق
`osascript`، وبيعمل `cd` لـ `~/.gaia-desktop` عشان المسار النسبي `logs/` بتاع logback يبقى ينفع يتكتب فيه، وبيبعت
`-Xdock:name`/`-Xdock:icon`. macOS بيربط الـ `java` اللي شغال بالحزمة (الـ bundle id وأيقونة الـ Dock بتوع
التطبيق)؛ وشريط القوايم بيبان فيه GAIA Desktop.

وبعدين، لكل منصة، بيعمل zip للفولدر في `target/dist/gaia-desktop-<version>-<platform>.zip` تحت فولدر بنفس الاسم،
باستخدام `<zip>` بتاع Ant: `run.sh` و`Contents/MacOS/**` كمجموعة ملفات لوحدها بـ `filemode="755"`، وإلا مش هيشتغلوا
بعد فك الضغط. الـ zip **مش بيترفق**: ده لإصدارات GitHub، والأربع منصات جايين من أربع عمليات بناء، وMaven Central — رفعة
واحدة ثابتة لكل إصدار — عمره ما يقدر ياخدهم كإصدار واحد.

`project.build.outputTimestamp` بيتظبط على وقت البناء. وإلا أدوات الأرشفة في maven-jar-plugin 3.5 و
maven-assembly-plugin 3.8 بتحط تاريخ 1 فبراير 1980 على كل مدخل.

أيقونة التطبيق بيرسمها `tools/icon/GaiaIcon.java` (مش جزء من البناء؛ وفي الهيدر بتاعه خطوات `sips`/`iconutil`).
والمخرجات بتاعته متسجلة في الريبو: `src/main/macos/gaia-desktop.icns` للحزمة، و
`src/main/resources/icons/gaia-desktop-{16..256}.png` اللي `GaiaDesktopApp` بيحطها أيقونة للشباك (Windows وLinux؛
macOS بيتجاهل أيقونات الشبابيك).

#### سكربتات التشغيل

`run.sh` و`run.bat` جايين من `src/main/scripts/`، وبيتنسخوا لـ `dist/gaia-desktop-<version>-<platform>/` من غير فلترة —
`run.sh` مليان توسيعات shell من نوع `${...}` ممكن فلترة Maven تعيد كتابتها على مزاجها. بعد كده خطوة antrun بتسيب بس
السكربت اللي المنصة بتشغّله — `run.bat` لـ `win`، و`run.sh` لأي حاجة تانية — وبتحط بت التنفيذ على `run.sh`، عشان
`copy-resources` ما بينقلوش. وهي بتقرر من `${fx.platform}` بعد ما اتحدد مش من خلال البروفايلات، عشان تفعيل بروفايل
ما يقدرش يشوف قيمة بروفايل تاني ظبطها: وإلا بناء Linux معمول على Windows كان هياخد سكربت الجهاز المضيف.

السكربتات دي **مش معتمدة على المانيفست**. كل واحد بيبني مسار الكلاسات بنفسه: `gaia-desktop.jar` وبعده كل `.jar` في
`lib/`، متسمّيين واحد واحد بدل ما يتسابوا للنمط `lib/*`، عشان المسار اللي فيه مسافات يفضل مدخل واحد وعدد اللي اتضاف
يبقى حقيقي. التشغيل بـ `-cp` هو السبب إنهم بيكتبوا `tools.pantheum.gaia.desktop.Launcher` صريح: `-cp` ما بيقراش
`Main-Class` بتاع المانيفست. بس هو **لسه** بيمشي ورا `Class-Path` بتاعه — الـ jar اللي على `-cp` بيجيب معاه ملفات
jar اللي المانيفست بتاعه بيسمّيها، وبيتدوّر فيها على طول بعده — فكل jar في `lib/` بيتحمّل سواء السكربت كتبه أو لأ،
وشيله من مسار كلاسات السكربت مش هيبعده عن الـ JVM. ومع ذلك السكربتات بتكتبهم كلهم، عشان jar المانيفست بتاعه قديم أو
متعدّل بالإيد أو ناقصه مدخل يقدر يشتغل برضه. نفس السكربت بيخدم التغليفين: الـ jar بتاع `-Pfat` مالوش `lib/` يضيفه
ومش محتاجه، وده برضه السبب إن `lib/` الفاضي ملاحظة مش غلطة.

#### مكتبات Zebra الأصلية

البناء مش بيشحن أي حاجة بتاعة Zebra — لا DLL ولا jar خدمات. على Windows دول جايين من Scanner SDK بتاع Zebra المتنزّل
على الجهاز: `run.bat` بيضيف ملفات jar الخدمات `Jpos*.jar` و`bin\` لمسار الكلاسات و`bin\` لـ `PATH`، وهناك
`System.loadLibrary` بيلاقي `CSJPOSScanner.dll` / `CSJPOSScanner64.dll` (القيمة الافتراضية لـ `java.library.path`
هي `PATH`). واجهة JavaPOS ومحمّل الإعدادات بتاعها دايمًا جايين من `lib\javapos-*.jar`، سواء فيه SDK أو لأ.

**`run.bat` عمره ما بيضيف ملف jar الـ JavaPOS بتاع الـ SDK نفسه**، يعني `External\JavaPOS-1.14.0-Dist\javaPOS114.jar`.
زمان كان بيعمل كده، وكان بيشيل `lib\javapos-*.jar` عشان ما يبقاش فيه نسختين من الواجهة — بس `Class-Path` بتاع
المانيفست حمّلهم في كل الأحوال (بُص فوق)، فالـ JVM خد الاتنين: كلاسات المحمّل 4.x من `lib\`، وجنبها
`jpos/res/jpos.properties` و`jcl.xsd` بتوع `javaPOS114.jar`. ملف الخصائص بيخلّي [`JposConfig`](#ربط-الماسح) يتنحّى،
والـ `jcl.xsd` ده بيقبل إصدارات JavaPOS لحد 1.10 بس، فكل مدخل في `jpos.xml` (1.12–1.14) وقع في التحقق، والسجل فضل
فاضي، وكل اتصال وقع بغلطة 109 قبل ما يوصل للماسح أصلًا. مجرد وجود الـ jar ده على مسار الكلاسات كفاية عشان يحصل كده،
حتى لو ورا ملفات jar بتاعة `lib\`. ملفات jar الخدمات بتاعة Zebra بتشتغل من غير تغيير على واجهة 1.14 اللي في `lib\` —
الفتح والحجز والمسح اتجرّبوا على ماسح حقيقي بالطريقة دي. والـ DLL اللي بتتحط بالإيد جنب `run.bat` لسه بتتاخد في
الحسبان: السكربت ساعتها بيظبط `-Djava.library.path=<dist>;%PATH%`، وبيزوّد `PATH` في الآخر عشان الخاصية دي بتبدّل
مسار البحث الافتراضي خالص.

`mvn javafx:run` مش بيعمل أي حاجة من دي، فعشان تحجز الماسح من تشغيل تطوير على Windows محتاج تحط ملفات jar بتاعة الـ SDK
على مسار الكلاسات و`bin\` بتاعه على `PATH` بطريقة تانية؛ شغّل من `dist/` عشان كده.

وغير مسار الكلاسات، السكربتات بتعمل اللي `java -jar` مش بيعمله: بتحدد الفولدر بتاعها عشان تشتغل من أي فولدر شغل،
وبتفضّل `JAVA_HOME` على `PATH`، وبترفض أي JVM أقدم من 11 بجملة بتقول الحل بدل `UnsupportedClassVersionError`. و
`GAIA_DESKTOP_OPTS` بيعدّي خيارات الـ JVM. `run.bat` بيستعمل `java.exe` مش `javaw.exe`، عشان الكونسول يفضل مفتوح —
Windows هي المنصة الوحيدة اللي الماسح بيشتغل عليها، وحالته وغلطات JavaPOS بتروح هناك.

`run.bat` كمان بيختار Java وJavaFX وخدمات Zebra من اللي بيلاقيه — `jdk*\` جاي معاه، و`javafx-sdk*\lib\` على مسار
الموديولات، وScanner SDK بتاع Zebra في `ZEBRA_HOME` — وبيشيل نسخ JavaFX اللي في `lib\` من مسار الكلاسات لما يستعمل
نسخة الـ SDK، وبيبعت محلل SAX بتاع الـ JDK، والبروكسيات ومخزن الثقة بتوع Windows، و`--enable-native-access` على Java
17 وما بعدها. الجدول موجود في [What `run.bat` adds on Windows](../../../README.md#what-runbat-adds-on-windows) في
الـ README. خلّي نهايات السطور في الملف CRLF: `cmd.exe` ممكن يفوّت `call :label` في ملف batch بنهايات LF بس. و
`run.sh` كمان بيبعت `--enable-native-access=ALL-UNNAMED` — JavaFX بيحمّل المكتبات الأصلية بتاعته من `lib/`، ولما
JavaFX يبقى على مسار الكلاسات `ALL-UNNAMED` هو الموديول اللي بيغطيه — وبيتشال، زي في `run.bat`، بس لما إصدار Java ما
يتقريش.

الترتيبين شايلين مكتبات JavaFX الأصلية **لمنصة واحدة**، `${fx.platform}`، فولا واحد فيهم ينفع يتنقل بين أنظمة تشغيل
أو معماريات مختلفة. ابني مرة لكل هدف — بُص على [بناء لكل منصة](#بناء-لكل-منصة).

> **Eclipse.** تنفيذ `copy-dependencies` عليه تعليمة `<?m2e ignore?>`. m2e بيحوّل مشروع مساحة الشغل المفتوح لفولدر
> `target/classes` بتاعه بدل jar، و`copy-dependencies` بيرفض ينسخ مخرَج مش متغلّف (MDEP-187)، وده كان هيوقّع البناء
> التلقائي كل ما مشروع `gaia` يبقى مفتوح جنب المشروع ده. النتيجة إن البناء اللي جوّه الـ IDE بس مش بيملا
> `target/dist/gaia-desktop-<version>-<platform>/lib/`؛ شغّل `mvn package` قبل ما تستعمل الـ jar نفسه.

### قمع الإدخال

كل إدخال — مكتوب، أو ملصوق، أو مفتوح من ملف، أو ممسوح، أو متعمل بالمُنشئ — بيوصل للمحلل من دالة واحدة،
`MainView.capture(String, ScanSource, String)`.

ده قرار التصميم الوحيد اللي البرنامج كله مبني حواليه. الإنشاء مش محتاج تقرير لوحده، ولا سجل لوحده، ولا طريق تصدير
لوحده، عشان بعد القمع السلسلة المتعملة ما تتفرقش عن السلسلة الممسوحة. أي حاجة جديدة بتطلّع إدخال لازم تعدّي منه، مش
تلف حواليه.

### الخيوط

| الخيط | بيشغّل إيه |
|---|---|
| خيط تطبيق JavaFX | كل التحليل والرسم والواجهة. التحليل بياخد أقل من ملي ثانية بعد ما جداول الـ AI تسخن، فمش محتاج خيط شغّال |

| خيط أحداث JavaPOS | الـ callbacks بتاعة `ScannerService`. `MainView.FxScannerListener` بيعدّي كل واحد فيهم بـ `Platform.runLater` |

جت من كده بالظبط: إعادة ضبط منتقي الـ AI جوّه `clearAndSelect` بتاع الـ popup نفسه (`IndexOutOfBoundsException`
طالع من `ListViewBehavior`)، وإعادة بناء اللوحة اللي فيها قايمة اللغات من جوّه الـ handler بتاع القايمة نفسها. الاتنين
دلوقتي بيتأجلوا بـ `Platform.runLater`، والأسباب مكتوبة في مكانين النداء.

### إعادة البنا مقابل إعادة التسمية

تغيير اللغة **بيعيد بناء** إطار الواجهة من الكتالوج — القوايم وشريط الأدوات ولوحة الخيارات — وده آمن عشان ولا حاجة
فيهم شايلة حالة: `OptionsPane` عرض في الاتجاهين لـ `ParseOptions`، فالقيم عايشة في الموديل واللوحة الجديدة بتلقطها على
طول.

`BuilderPane.retext(UiStrings)` بيحتفظ بسطور الـ AI وحقول Digital Link والاختيار. لو اتعاد بناؤها الشغل اللي لسه
ما خلصش هيضيع — وده حصل فعلًا مرة.

## رمز {GS}

الـ `TextField` بتاع JavaFX بيرمي من غير ما يقول كل حرف أقل من `0x20` (`TextInputControl.filterInput`). مش "بيعرضه
بشكل غريب" — بيمسحه. الكتابة واللزق و`setText` و`insertText` كلهم بيتأثروا، فـ `setText("01…" + GS + "10LOT")`
بيطلّع `"01…10LOT"`: سلسلة عناصر معناها اتغير من غير ما حد ياخد باله، عشان الـ AI اللي طوله متغير بقى بيبلع اللي
بعده.

`desktop.parse.GsToken` هو الحل كله. الفاصل بيمشي في الواجهة كنص حرفي `{GS}` وبيرجع `0x1D` تاني وهو رايح للمحلل.
والرمز ده مش متخترع هنا — هو بالظبط الشكل اللي `ASCIIRevealerUtils.printable` بتاع النواة بيعرض بيه `0x1D`، فأي قيمة
تنسخها من تقرير تقدر تلزقها على طول في شريط الإدخال.

فلتر `TextFormatter` على حقل الإدخال بيمسك كل طريق النص ممكن ييجي منه — الكتابة، و⌘V، وقايمة السياق، والسحب والإفلات،
و`setText` — وعشان كده إعادة الكتابة قاعدة هناك مش في كل handler.

طريق الماسح عمره ما بيعدّي على `GsToken`: المسحات بتوصل للمحلل بايتات.

## ربط الماسح

`ScannerService` هو صاحب عنصر التحكم `Scanner` بتاع JavaPOS: فتح ← حجز ← تفعيل، وبيرجّع حدث البيانات بعد كل مسحة.
أسامي الأجهزة المنطقية جاية من `src/main/resources/jpos.xml`.

**كل نداء للجهاز بيشتغل على خيط واحد، `gaia-scanner`، عايش طول ما الخدمة عايشة** — عمره ما على خيط FX، وعمره ما على
خيط بيخلص بعد النداء. خدمة Zebra بتوصل للماسح بـ JNI عن طريق CoreScanner COM API، وCOM بيربط اللي بيجهّزه بشقة
(apartment) الخيط اللي ندهه: افتح على خيط هيخلص بعدين، والماسح هيتحجز بس هيفضل ساكت؛ واقفل على خيط تاني، والشقة الغلط
هي اللي هتتلغي تهيئتها. القفل على خيط FX أسوأ حالة، عشان JavaFX بيندَه `OleInitialize` هناك وبيسجّل هدف الإفلات لكل
شباك عليه — و`CoUninitialize` واحد عليه بيموّت السحب والإفلات في البرنامج كله. ده JavaFX على Windows، مش إصدار JavaFX
معيّن. `connect()` و`disconnect()` بيبعتوا الشغل للخيط ده وبيستنّوا، فـ `MainView` بيندههم الاتنين من خيط خلفي عمره
قصير.

فيه قاعدتين بيمنعوا جهاز بايظ من إنه يعلّق الاتصال. **الفك عمره ما بيقف بدري:** `closeQuietly` بيعطّل ويحرّر ويقفل
كخطوات منفصلة، وما بيحررش غير لو الحجز ماسك، ودايمًا بيحاول `close()` — بعد حجز فاشل `release()` بيرمي "not claimed"،
ولما الخطوات كانت شايلة `try` واحد ده كان بيفوّت القفل ويسيب الجهاز مفتوح في خدمة Zebra. **حدث البيانات بيرجع يتفعّل
جوّه `finally`:** JavaPOS بيعطّله بعد كل حدث، فلو القراية أو الـ handler رمى استثناء لازم برضه يرجع يتفعّل، وإلا الماسح
هيسكت لحد ما تعيد الاتصال. `ScannerLifecycleTest` بيجرّب القاعدتين على `jpos.Scanner` متبرمج مسبقًا.

**`JposConfig` بيوجّه JavaPOS لـ `jpos.xml` اللي جاي مع البرنامج** قبل أول فتح. مع ملفات jar بتاعة JavaPOS من Maven
(`javapos-config-loader` 4.x) ومن غير `jpos/res/jpos.properties` على مسار الكلاسات، كل فتح غير كده بيقع برسالة
*"Service does not exist in loaded JCL registry"* (غلطة 109)، لتلات أسباب مختلفة: مدير الخدمات بيرجع لـ
`SimpleRegPopulator`، اللي بيقرا `jpos.cfg` متسلسَل وعمره ما بيقرا `jpos.xml`؛ ومحمّل XML بيدوّر على `jpos.xml` في
فولدر الشغل بس، مش جوّه الـ jar؛ وXerces 2.12.2 اللي في `lib/` بيرفض خاصية JAXP اسمها `accessExternalDTD` المحمّل
بيظبطها. `JposConfig` بيظبط `jpos.config.regPopulatorClass` (`JavaxRegPopulator`) و`jpos.config.populatorFileURL`
(`jar:file:…!/jpos.xml` بتاع الـ jar نفسه) و`javax.xml.parsers.SAXParserFactory` (بتاع الـ JDK) كخصائص نظام — عمره
ما بيلمس حاجة متظبطة قبل كده، فـ `-Djpos.config.populatorFileURL=file:…` لسه يقدر يختار `jpos.xml` تاني — ومش بيظبط
أي حاجة لما يكون فيه `jpos.properties` على مسار الكلاسات أو المحمّل 4.x مش موجود. `javaPOS114.jar` بتاع Zebra SDK
حالة من دول، وبيبوّظ السجل خالص، وعشان كده `run.bat` بيبعده عن مسار الكلاسات — بُص على
[مكتبات Zebra الأصلية](#مكتبات-zebra-الأصلية). `JposConfigTest` بيتأكد من الأول للآخر إن السجل بعد كده فيه ماسحات
الملف.

**منتقي الأجهزة بيتعمل من السجل ده**، مش متخزن كقايمة في الكود: `ScannerService.logicalNames()` بيقرا المدخلات
المتحمّلة على خيط `gaia-scanner` وبيسيب اللي فئة جهازها `Scanner` — فمدخلين الميزان اللي في `jpos.xml` بيفضلوا برّه —
بترتيب `pickerOrder`: `ZebraAllScanners` الأول لو الملف معرّفه، والباقي بالترتيب الأبجدي (السجل ما بيحفظش ترتيب
الملف). الملف اللي مش معرّفه مش بيتضاف له؛ ولو ما اتحمّلش حاجة بيظهر الافتراضي لوحده، فالمنتقي عمره ما يبقى فاضي.
`MainView` بيعرض الافتراضي على طول وبيملا القايمة من خيط خلفي، وهو محافظ على الاختيار المتخزن. فأي ماسح تضيفه لـ
`jpos.xml` — أو ملف كامل تسمّيه بـ `-Djpos.config.populatorFileURL` — بيظهر في المنتقي من غير أي تغيير في الكود، و
`JposConfigTest` بيقارن المنتقي بقراية مستقلة للملف اللي جاي مع البرنامج. الخدمات اللي المدخلات دي بتسمّيها هي كلاسات
Zebra (`com.zebra.jpos.service.scanner.*Factory`)، ولازم برضه تبقى على مسار الكلاسات — من Scanner SDK عن طريق
`run.bat`، أو ملفات jar خدمات Zebra تتحط في `lib\`.

بيانات المسح بتتفك بـ **ISO-8859-1** عشان كل بايت يقابل حرف واحد بالظبط، فبادئة AIM Code ID وكل `0x1D` بيفضلوا
سليمين؛ والتقارير بتتكتب UTF-8.

ولا حاجة في الخدمة بتألف نص للمستخدم. الأحداث بتطلع كثوابت `ScannerListener.Event` ومعاها القيم اللي بتتغير، و
`MainView` هو اللي بيجيب الكلام من الكتالوج — وإلا سطر الحالة كان هيبقى إنجليزي في برنامج مترجم لـ 35 لغة. سطور
اللوج هي الاستثناء وبتفضل إنجليزي.

### بوابة المنصة

`ScannerService.isSupportedPlatform()` اختبار واحد لـ `os.name`، و`MainView` بيسأله قبل ما يبني أي عنصر تحكم للماسح:
على macOS وLinux مفيش مفتاح تبديل، ولا منتقي أجهزة، ولا قايمة الماسح (يعني ولا <kbd>⌘K</kbd>)، ولا تسمية حالة. دول
مش مستخبيين — دول عمرهم ما بيتعملوا أصلًا.

Zebra بتشحن خدمات JavaPOS بتاعتها لـ Windows بس، وفي أي مكان تاني مفيش حاجة بتقع بدري: ملفات jar بتتحل والعنصر
بيتعمل، وفي الآخر `open()` هو اللي بيقع عشان الطبقة الأصلية مش موجودة، بعد كام ثانية وdialog.

القاعدة دي عن *الخدمات*، مش عن JavaPOS. لو فيه مورّد بيشحن خدمة شغالة على كل المنصات هتشتغل هنا، وتوسيع القاعدة تغيير
في `supportsJavaPos(String)` لوحدها — ودي package-private ومتختبرة على سلاسل `os.name` عشان الإجابتين يتغطّوا على أي
جهاز بيشغّل البناء.

### الترميزات

`Symbologies` بيربط كل أنواع بيانات المسح الـ **78** من `SCAN_SDT_*` في JavaPOS بأسامي عرض، وبـ `DataCarrierType`
بتاع النواة لما المفردتين يتقابلوا. وJavaPOS هو الأدق فيهم — بيفرّق بين UPC-A وEAN-13، وبين Data Matrix العادي وGS1
DataMatrix، في حين إن AIM بيجمع عيلة كاملة تحت حرف كود واحد.

النوع اللي مش في الجدول برضه بياخد اسم ينفع يتستعمل، بيتلاقي بالـ reflection على `ScannerConst`، عشان خدمات المورّدين
فعلًا بتبلّغ عن قيم برّه قايمة المواصفات. فيه اختبار بيلف على `ScannerConst` وبيقع لو أي نوع متعرّف مالوش اسم — وده
برضه بيمسك الثوابت اللي JavaPOS ممكن يضيفها بعدين.

شوية ربطات حوامل متسابة `UNKNOWN` عن قصد بدل التخمين: 2 of 5 المستقيم (AIM بيفصل `]R`/`]S` حسب عدد بارات البداية
والنهاية، وده JavaPOS مش بيبلّغ عنه)، وأكواد البريد اللي ليها أربع حالات، وTLC-39.

## التوطين

التسميات عايشة في ملف خصائص واحد لكل لغة تحت `src/main/resources/i18n/ui_<CODE>.properties`، وبتستعمل نفس الأكواد
بتاعة كتالوجات الغلطات في النواة (`EN`، `FR`، `PCM`، …). الـ 35 ملف كلهم موجودين، وكلهم شايلين نفس مجموعة المفاتيح.
الملفات بتتقري **UTF-8**، مش ISO-8859-1 اللي `Properties` بيفترضه، فالترجمات متخزنة بشكل يتقري بدل escapes من نوع
`\uXXXX`.

**الرجوع بيبقى لكل مفتاح، مش لكل ملف** — وده اللي بيخلّي لغة مترجمة نص نص تنفع من أول ما أول مفتاح فيها يوصل.
الإنجليزي هو العقد: كل مفتاح لازم يبقى موجود فيه.

| الطبقة | المفاتيح | التغطية |
|---|---|---|
| مفردات التقارير المشتركة | 31 | الـ 35 لغة كلهم |
| إطار سطح المكتب — القوايم، والزراير، والمُنشئ، والخيارات، وسطر الحالة، وترتيب التقرير، وحالة الماسح، ونصوص الـ dialogs | 114 | الـ 35 لغة كلهم |

ستة من المصطلحات المشتركة (`generated`، `status`، `dlRole`، `interpretations`، `message`، `level`) مش مستعملين في
تقرير البرنامج ده.
متسابين عن قصد؛ وهيدر الملف بيقول كده.

### الوسيط `--language`

`GaiaDesktopApp.languageOverride()` بيقرا `--language=…` عن طريق `getParameters().getNamed()` بتاع JavaFX نفسه،
وبيحدده بـ `Languages.fromArgument` — كود كتالوج، أو اسم enum، أو وسم BCP 47، ومش فارقة الحروف كبيرة ولا صغيرة —
وبيسلّمه لـ `MainView`.

**التجاوز ده للتشغيل ده، مش للملف.** `MainView` بيحتفظ باللغة اللي حمّلها في `savedLanguage` وبيكتب *هي* تاني، لحد ما
`languageChosenInSession` يقول إن المستخدم اختار لغة بنفسه؛ ساعتها اختياره بيتحفظ عادي. الفصل ده هو التصميم كله:
بروفايل كشك أو اختصار ديمو يقدر يفتح بالإسباني من غير ما يغيّر اللغة اللي صاحب الجهاز هيفتح بيها بكرة، وفي نفس الوقت
الاختيار الحقيقي اللي اتعمل في لوحة الخيارات بيفضل ثابت.

أي قيمة مش بتسمّي كتالوج بتتسجل في اللوج مع الأكواد المقبولة وبتتجاهل. إن البرنامج يرفض يبدأ عشان غلطة إملائية في
اختصار كان هيبقى فشل أسوأ، وعشان نفس السبب `Languages.fromArgument` بيرجّع `null` بدل ما يرمي استثناء.

### إضافة لغة

مش محتاج أي تغيير في الكود.

1. عدّل `ui_<CODE>.properties` — كل لغة ليها ملف أصلًا.
2. ترجم القيم. سيب العلامات `{0}` / `{1}` في مكانها.
3. ابني. فيه اختبارين بيفرضوا العقد: واحد بيقع لو الكود طلب مفتاح الإنجليزي مش معرّفه، والتاني لو مجموعة مفاتيح أي
   كتالوج بعدت عن الإنجليزي.

الاختبار الأول بيدوّر في **الكود المصدري** على المفاتيح الحرفية بدل الـ reflection على الكلاسات، عشان المفاتيح موجودة
بس كسلاسل حرفية في أماكن النداء. وعشان كده أي رسالة جديدة لازم تتبني والمفتاح مكتوب على طول —
`strings.format("st.scannerError", …)` — مش تتدوّر عن طريق متغير، وإلا الاختبار مش هيشوفها.

### الحاجات اللي مش بنترجمها عن قصد

- أسامي الحقول القصيرة اللي بتظهر بخط ثابت العرض جنب القيم الخام — `format` و`position` و`length` و`raw` و`part`
  في كارت العنصر، و`AI` و`sep` و`pos` و`len` في الشريط، والخانات الأربعة اللي بتحدد مكان الغلطة (`AI`، `position`،
  `level`، `stage`)، وقيمهم أصلًا أسامي enum مش مترجمة؛
- أسامي أمثلة الإدخال، اللي بتسمّي تراكيب GS1، وأسامي الترميزات، ودي أسماء علم؛
- فقرة العلاج بتاعة `GE-C084` — كلام معايير الترجمة الناقصة فيه أوحش من الإنجليزي؛
- خط الدفاع الأخير في `ElementBuilder` للـ AI المجهول، اللي ما ينفعش توصله من الواجهة: المحرر بيتأكد بنفسه من الـ AI
  المجهول وبيبلّغ عنه من الكتالوج؛
- سطور اللوج.

فاضل فجوة واحدة: `ScanSource.label()` بيدّي `manual` / `scanner` / `file` / `built` لسطر السجل وراس التقرير
بالإنجليزي. قفلها محتاج أكتر من مفتاح — `HistoryCell` مالوش `UiStrings`، ومصنع الخلايا بتاع القايمة بيتركّب مرة واحدة،
فالخلايا لازم تتحدّث هي كمان لما اللغة تتغير.

## صيغ الحالة المتخزنة

ملفين تحت `~/.gaia-desktop/`، منفصلين عشان بيتغيروا بإيقاعات مختلفة — سجل التقاط بايظ أو متعدّل بالإيد ما ينفعش
يكلّف المستخدم إعداداته. غيّر الفولدر بـ `-Dgaia.desktop.home=…`، وبكده الاختبارات بتفضل بعيد عن الفولدر الرئيسي
الحقيقي.

**`options.properties`** — بيتكتب لما خيار يتغير، ولما تقفل.

| المفتاح | المعنى |
|---|---|
| `parse.mode`، `parse.language` | عمق خط المعالجة ولغة الرسايل |
| `date.endian`، `date.separator`، `date.month`، `date.year` | عرض التاريخ |
| `check.skipRequires`، `check.skipExcludes` | تخطّي الفحوص البنيوية |
| `ui.theme` | `LIGHT` أو `DARK` |
| `ui.optionsPane` | لوحة الخيارات مفتوحة؟ |
| `ui.scannerDevice` | آخر اسم منطقي لجهاز JavaPOS |
| `ui.mode` | `PARSE` أو `BUILD` أو `COMBINE` |
| `update.check` | فحص التحديثات اليومي شغال ولا لأ (الافتراضي `true`) |
| `update.lastCheck` | آخر مرة اشتغل إمتى، بصيغة ISO-8601؛ لو مش موجود أو ما يتقريش يبقى الفحص جه وقته |
| `update.skipVersion` | إصدار المستخدم اختار له *فوّت النسخة دي*؛ مش هيتعرض تاني لوحده |

الملف الناقص أو البايظ عمره ما بيقتل البرنامج: كل قيمة بترجع لافتراضيها لوحدها، فالسطر البايظ بيكلّف السطر ده بس ومفيش
حاجة تانية. أول مرة يشتغل فيها، ومفيش ملف خالص، الخيارات بتتملا من الإعدادات الإقليمية للجهاز عن طريق `SystemDefaults`
بدل القيم الافتراضية اللي جوّه GAIA — نمط التاريخ القصير بتاع اللغة المحلية بيدّي ترتيب الأجزاء، والفاصل، وإذا كان
الشهر والسنة مختصرين ولا لأ.

ما تدّيش null لـ `Properties.setProperty` أبدًا: بيرمي استثناء، و`persistOptions()` بيشتغل من handlers أحداث الواجهة
اللي الاستثناء بيهرب منها لخيط FX. دي وقعة حقيقية البرنامج ده شافها قبل كده.

**`captures.tsv`** — بيتكتب لما السجل يتغير، ولما تقفل. الأحدث الأول، وبحد أقصى **500** مدخل.

```
captured(ISO)              <TAB> source  <TAB> symbology   <TAB> input
2026-08-09T14:22:05.123    SCANNER       Data Matrix       0109506000134352\x1D10LOT-001
```

بيتخزن بس اللي ما ينفعش يتحسب تاني. `ParseResult` **مش** بيتسلسل — بيتطلّع تاني بإعادة تحليل الإدخال وقت التحميل، فالسجل
المترجّع بيعكس الخيارات الشغالة *دلوقتي*. الإدخالات عادةً فيها FNC1 وأي حاجة تانية الماسح بيطلّعها، فحقل الإدخال
بيتعمله escape (`\\`، `\t`، `\n`، `\r`، و`\xNN` لأي حاجة تانية تحت `0x20`) والملف بيتقري ويتكتب ISO-8859-1، بايت ببايت.

الملفات اللي اتكتبت قبل ما التاريخ يبتدي يتسجل فيها وقت الساعة بس؛ ولسه بتتحمّل، بتاريخ النهارده، عشان التاريخ الحقيقي
عمره ما اتكتب.

## الاختبارات

```bash
(cd gaia-desktop && mvn test)
```

198 اختبار، **من غير مجموعة أدوات JavaFX** عن قصد، وده بيخلّيهم سريعين وبيشتغلوا من غير شاشة. بيغطّوا بتاع رسم
التقارير، ومنطق الإنشاء والبحث عن الـ AI، وتحويل `{GS}`، والقيم الافتراضية اللي جاية من اللغة المحلية، والمخزنين
الاتنين (ومنهم رحلة رايح جاي فيها `0x1D` وملفات متبوّظة عن قصد)، وجدول الترميزات، وقاعدة منصة الماسح، وبديل الإصدار،
والكتالوجات.

تلاتة منهم يستاهلوا تعرفهم عشان بيحموا عقود مش وظايف:

| الاختبار | بيقع لما |
|---|---|
| `CatalogueCoverageTest` | الكود يطلب مفتاح `ui_EN.properties` مش معرّفه، أو أي ملف من الـ 35 يبعد عن مجموعة المفاتيح الإنجليزي |
| `SymbologiesTest` | أي ثابت `SCAN_SDT_*` معرّفه JavaPOS مالوش اسم عرض — ومنهم اللي ترقية JavaPOS تضيفه |
| `ScannerServiceTest` | قاعدة المنصة تغيّر إجابتها لـ Windows أو لأي حاجة تانية |

`UiStrings` متسامح عن قصد وقت التشغيل — المفتاح المجهول بيظهر زي ما هو بدل ما يرمي استثناء في نص الترتيب — وده بالظبط
السبب إن اختبار الكتالوج لازم يبقى موجود.

**مش متغطّي:** أي حاجة محتاجة مجموعة أدوات شغالة — سلوك التركيز، ومفتاح تبديل الوضع، وتعديل الجداول، وتبديل اللغة،
والوقعتين اللي متوصّفين تحت [الخيوط](#الخيوط). دول اتأكدنا منهم بتشغيل الشباك الحقيقي، بس لو حصل فيهم تراجع البناء مش
هيقع. إضافة TestFX أو Monocle هتقفل الفجوة دي.

## حل مشاكل البناء

| العَرَض | السبب والحل |
|---|---|
| `package tools.pantheum.gaia does not exist` | النواة مش متنزّلة. `(cd gaia && mvn install -DskipTests)` |
| *"JavaFX runtime components are missing"* | الـ `Main-Class` بتاع الـ jar لازم يبقى `Launcher`، مش `GaiaDesktopApp` |
| *"Unsupported JavaFX configuration: classes were loaded from unnamed module"* وقت البداية | متوقع ومش بيضر — JavaFX بيقول إنه على مسار الكلاسات. وده بالظبط سبب وجود `Launcher` |
| الـ jar مش راضي يشتغل، `NoClassDefFoundError` | الـ jar الافتراضي فيه كلاسات الموديول ده بس؛ `dist/lib/` لازم يبقى جنبه. استعمل `-Pfat` لملف واحد مكفّي نفسه |
| `Artifact has not been packaged yet … MDEP-187` في Eclipse | تحديد مساحة الشغل بتاع m2e. بُص على الملاحظة تحت [التغليف](#التغليف) |
| ملفات `… 2.properties` متكررة بتظهر في البناء | المشروع في فولدر iCloud بيعمله مزامنة، والمزامنة عملت نسخ متعارضة في نص البناء. استعمل `mvn clean package` دايمًا؛ والأحسن، شيل `target/` من المزامنة |
| عنصر في قايمة بيظهر مفتاح زي `act.hri` | المفتاح ده ناقص من `ui_EN.properties`. البناء كان المفروض يمسكه — بُص على [الاختبارات](#الاختبارات) |

## القيود المعروفة والشغل اللي فاضل

- **مفيش اختبارات واجهة من غير شاشة.** بُص على [الاختبارات](#الاختبارات).
- **مخرجات خاصة بكل منصة.** التغليفين بيشيلوا مكتبات JavaFX الأصلية لمنصة واحدة؛ ابني واحد لكل هدف بـ `-Dfx.platform`
  (أي جهاز يقدر يبنيهم كلهم). ولا واحد فيهم بيشيل بيئة تشغيل Java — دي محتاجة `jpackage`، وده بيبني بس لنظام التشغيل
  اللي شغال عليه.
- **إدخال الماسح على Windows بس.** بُص على [بوابة المنصة](#بوابة-المنصة).
- **`ScanSource.label()` مش مترجم.** بُص على [الحاجات اللي مش بنترجمها عن
  قصد](#الحاجات-اللي-مش-بنترجمها-عن-قصد).
- **`UiState.mode` نوعه `String`** (`"PARSE"` / `"BUILD"`) في حين إن `Theme` اللي جنبه enum، فالقيمة الحرفية بتظهر في
  كذا مكان. لو بقى enum هيشيلهم.
- **هدف Digital Link هو الدومين وبادئة المسار بس.** `BuilderDigitalLinkConfig` بيدعم كمان باراميترات استعلام زيادة
  وجزء (fragment)؛ والمحرر مش بيعرضهم.
- **أزواج الـ AI اللي ما ينفعش يجتمعوا (`GE-S006`) مش بيتعلّم عليها في المحرر** زي الـ AI المجهول والمتكرر — الإنشاء
  بيقع وخلاص.
- **كتالوج الغلطات بتاع النواة بيكرر علامات التنصيص** (`value ''09506000134350''`)، وده بيظهر زي ما هو في فشل الإنشاء
  وفي التقرير. شكله escape للتنصيص من `MessageFormat` ما بيتفكّش؛ والتصليح مكانه النواة.
